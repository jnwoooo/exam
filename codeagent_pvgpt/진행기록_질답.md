## 3. MCP 구조 설명(6번 답)

### 3-1. "MCP 버전"이라는 말에 들어 있는 두 가지
| 구분 | 무엇 | 이 프로젝트 |
|---|---|---|
| MCP **프로토콜** | Continue(클라이언트)와 서버가 주고받는 메시지 약속. `tools/list`(메뉴판)·`tools/call`(실행) 등. 전송 방식은 stdio(로컬 프로세스) 또는 **streamable-http**(원격) | streamable-http — Continue가 `http://localhost:8200/mcp`로 접속 |
| 파이썬 **SDK** | 그 약속을 구현해 둔 라이브러리 `mcp` | **2.x**. 1.x의 `FastMCP` 클래스가 2.x에서 `MCPServer`로 이름만 바뀜. `@mcp.tool()`로 함수를 도구로 등록하는 구조는 같음 |
버전은 **import 한 줄**에만 영향이 있다. 구조 설계는 버전과 무관하다. (별도 패키지 `fastmcp`(4.x)는 다른 프로젝트 — 쓰지 않음)

### 3-2. 전체 구조(로컬 개발 구성)
```
[IntelliJ + Continue]  ← 하네스: 에이전트 루프·파일 읽기/수정·diff 승인·대화 기록 (만들지 않음, 설정만)
   │ ① 채팅: apiBase=http://localhost:8200/v1   (개인 토큰)
   │ ② 도구: http://localhost:8200/mcp          (같은 개인 토큰)
   ▼
[코드에이전트 서버 :8200]  ← 우리가 만드는 "중간 서버" (Python·FastAPI, 로컬 실행)
   ├─ /v1/chat/completions  LLM 프록시: 토큰→사번 → 한도 확인(Redis) → gemma4로 전달(스트리밍 그대로)
   │                         → 응답의 usage(토큰 수) 기록(Postgres)
   ├─ /mcp                  MCP 도구: search_code · search_docs · request_fix
   │                         → 신원은 헤더에서만 → RAG 서비스 호출(사번만 넘김) / request_fix는 gemma4 호출
   └─ /admin                감시: 사용자별 토큰·요청 수·도구 호출·오류
        │                                 │
        ▼                                 ▼
[외부 LLM: gemma4-26b-32k]       [RAG 서비스 :8100]  (Python·FastAPI, 로컬 실행)
                                   ├─ /search  사번 → 허용 항목(권한 DB) → KoE5 질문 임베딩 → Qdrant(필터)
                                   └─ /index   추출·청킹·KoE5 임베딩·삽입
                                        ▲
                         [색인기 CLI]  INDEX_REPOS의 git 주소 → 로컬 clone/pull → git diff 증분 → /index

[docker]  Qdrant :6333 · Redis :6379 · PostgreSQL :5432(사용자·토큰·권한·사용량·감사)
```

### 3-3. "실질적인 코드에이전트"는 어디인가
- **에이전트 루프는 Continue가 돈다.** 다음에 무슨 도구를 쓸지는 Continue의 LLM(gemma4)이 정한다.
- 코드에이전트 서버는 그 루프의 **모든 LLM 호출이 지나가는 관문**(①)이자 **서버 쪽 도구 제공자**(②)다. 그래서 키 관리·사용량·한도·감사·RAG를 한곳에서 처리한다.
- 파일 읽기·수정·터미널은 **Continue 내장 도구**가 PC에서 한다. 서버는 PC 파일에 닿지 못한다(2판 md 3-2).

### 3-4. 프록시(①)에서 챙길 것
| 항목 | 내용 |
|---|---|
| 그대로 전달 | 요청 본문의 `messages`·`tools`·`tool_choice`를 바꾸지 않고 넘긴다 — tool calling이 깨지지 않게 |
| 스트리밍 | Continue는 `stream: true`로 부른다 → SSE를 한 줄씩 그대로 흘려보냄 |
| 토큰 수 | 스트리밍에서는 `stream_options.include_usage=true`를 서버가 넣어 마지막 조각의 usage를 받는다. gemma4 서버가 지원 안 하면 토크나이저 추정값으로 기록(**확인 필요**) |
| 한도 | Redis에 사용자별 분당 요청 수·일일 토큰 누적 → 넘으면 429 |
| 모델 이름 | `/v1/models`도 제공. Continue 설정의 `model`을 gemma4 이름으로 매핑 |
| 기록 원칙 | 코드 원문은 남기지 않음 — 사용자·시각·모델·토큰 수·지연·상태만 |

## 4. request_fix 가치 재설명(8번 답)
**"가치가 없다"가 아니라 "단순 버전은 손해"라는 뜻이다.**

단순 버전 = "코드 + 요청을 받아 gemma4에게 수정 코드를 써 달라고 하고 그대로 돌려줌".
| 문제 | 설명 |
|---|---|
| 같은 모델이 두 번 일함 | Continue의 LLM도 gemma4다. 이미 파일을 읽은 상태라 **직접 편집 도구를 부를 수 있다.** 같은 모델에게 같은 일을 한 번 더 시키는 셈 |
| 같은 코드가 4번 실림 | 읽기 결과 → request_fix 인자 → 제안 결과 → 편집 도구 인자. **32k 컨텍스트**에서 300줄 파일이면 이것만으로 상당 부분을 먹음 |
| 시간 | LLM 호출이 하나 더 → MCP 호출 시간 제한에 걸릴 수 있음 |
| 결과를 다시 옮겨 적어야 | 제안 코드는 파일을 바꾸지 않는다. Continue의 LLM이 그것을 편집 도구 인자로 **다시 출력**해야 함(옮기다 틀릴 수 있음) |

**가치 있는 버전 — Continue의 LLM이 혼자 못 하는 일을 한다(이걸로 구현)**
| 더하는 일 | 왜 Continue LLM은 못 하나 |
|---|---|
| 서버 RAG로 **관련 코드·사내 규칙 문서**를 찾아 붙여서 생성 | Continue LLM은 search를 따로 불러야 하고, 결과가 대화에 계속 남아 컨텍스트를 먹음. 도구 안에서 쓰고 버리면 대화에는 결과만 남음 |
| **문법 검사**(파이썬은 `ast.parse`, 그 밖은 괄호 균형 등) → 실패 시 오류를 붙여 재생성(최대 2회) | Continue LLM은 검증 없이 편집함 |
| 결과를 **전체 코드가 아니라 바뀐 부분(찾을 글 → 바꿀 글)**으로 반환 | 편집 도구(`single_find_and_replace`) 인자에 바로 옮길 수 있어 토큰·옮겨 적기 실수 감소 |
| 코드 상한 초과 시 "함수 부분만 보내라" 안내 | 컨텍스트 보호 |
가치는 **평가로 확인**한다: 같은 골든 작업을 request_fix 있음/없음(Continue에서 Excluded)으로 비교(2판 md 8장).

## 9. "LLM 앞의 FastAPI" 참고 구현 — `llm_server/`(2026-10-05)

### 9-1. 질문
> "OpenAI 호환 3가지 확인"을 코드로 이해 못 하겠다. LLM 앞에서 Continue가 쓸 수 있게 해 주는 FastAPI가 떠 있을 거라는 **예측 코드**를 패키지로 짜 달라.

### 9-2. 결정
| 항목 | 결정 | 이유 |
|---|---|---|
| 패키지 이름 | `llm_server/` | `fastapi`라고 지으면 진짜 FastAPI 라이브러리를 가려서 두 서버의 import가 깨진다 |
| 예측한 외부 구성 | FastAPI(:8000) → **Ollama**(gemma4) | 모델 이름의 `:latest` 태그가 Ollama 방식 |
| 도구 방식 | `native`(Ollama tools) / `prompt`(미지원 모델용: 도구 설명을 시스템 글로, `<tool_call>` 출력을 해석) | gemma 계열은 Ollama 템플릿에 따라 tools 미지원일 수 있음 |

### 9-3. 3가지 확인이 코드에서 어디인가
```
코드에이전트 서버 ──OpenAI 형식──▶ llm_server(:8000) ──Ollama 형식──▶ Ollama(gemma4)
```
| 확인 | 의미 | 코드 위치 |
|---|---|---|
| ① 경로·응답 모양 | `POST /v1/chat/completions`가 있고 응답이 `choices[0].message`(스트리밍이면 `choices[0].delta`) 모양 | `app.py`의 `@app.post("/v1/chat/completions")`, `convert.completion_response()`, `convert.chunk()` |
| ② tools·stream·tool_calls | 요청의 `tools`(도구 목록)를 모델에 전달하고, 모델이 도구를 부르면 응답에 `tool_calls`(id·이름·**JSON 문자열 인자**) + `finish_reason="tool_calls"`. 다음 요청에 오는 도구 결과(`role=tool`)도 모델 형식으로 바꿔 넘김 | `convert.to_ollama_messages()`(대화 기록 변환), `convert.openai_tool_calls()`, `app.py`의 `relay()`(스트리밍 중 `delta.tool_calls`에 `index`), 프롬프트 방식 `build_tool_prompt()`·`extract_tool_calls()` |
| ③ usage | 스트리밍 요청에 `stream_options.include_usage=true`면 마지막에 `choices: []` + `usage` 조각 | `convert.usage_from()`(Ollama `prompt_eval_count`·`eval_count` → `prompt_tokens`·`completion_tokens`), `relay()`의 `if include_usage` |

②가 안 되면 Continue Agent 모드가 동작하지 않는 이유: Continue는 응답의 `tool_calls`를 보고서야 `read_file`·MCP 도구를 실행한다. 글로만 답하면 "도구를 쓰라"는 신호가 없다.

### 9-4. 확인 도구와 결과
- `uv run python -m llm_server.check_compat --base-url {주소}/v1` → ①, ② 스트림, ② 도구, ② 도구+스트림, ③을 실제 호출해 OK/FAIL + 해결 방법 출력
- 테스트 4개 추가(합계 **13 passed**): 형식 변환, 네이티브 방식 전부 통과, 도구 미지원 모델 + native는 ② 실패 + 안내, 같은 모델 + prompt 방식은 전부 통과
- 실제 연결 시험: 코드에이전트(LLM_BASE_URL=`http://0.0.0.0:8000/v1`) → llm_server(:8000) → 가짜 Ollama 에서 Continue와 같은 요청(stream+tools) → `tool_calls`·실제 `usage` 확인

### 9-5. 외부 호스트 연결할 때 순서
1. `check_compat --base-url http://외부호스트:포트/v1`
2. 전부 OK → `.env`의 `LLM_BASE_URL`만 바꾸고 끝
3. ①이 FAIL(형식이 다름) → 외부 FastAPI의 요청·응답 예시를 받아서 `llm_server`처럼 감싸는 변환을 만든다
4. ②만 FAIL → 외부 쪽에 tools 지원을 넣거나, `llm_server`를 `LLM_SERVER_TOOL_MODE=prompt`로 앞에 둔다
5. ③만 FAIL → 그대로 사용 가능(토큰은 추정치로 기록)
