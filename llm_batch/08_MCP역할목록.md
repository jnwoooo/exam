## 0. 먼저 답

**서버 쪽은 목록대로 한 곳에 만들면 된다. py 쪽에 더 짤 코드는 없다.**

- 서버가 만들 것은 **OpenAI 호환 중계 주소 하나**다(`POST .../chat/completions`). py는 지금도 이 형식으로 부르므로, 주소만 서버의 것으로 바꾸면 py를 고치지 않고 붙는다. 주소는 PC의 환경변수 `VUPDATE_LLM_ENDPOINT`에 넣는다.
- 그 주소가 지켜야 할 약속이 3절의 10가지다. 약속을 지키는지는 `vupdate llmcheck`로 확인한다. 전부 "정상"이면 끝이다.
- **재호출**은 대부분 py의 일이다. 서버는 "연결이 끊겼을 때 다시 걸기"와 "바쁠 때 기다리게 하기"만 맡는다(6절).
- **ripgrep 같은 검색 요청은 서버에 둘 필요가 없다.** 소스는 로컬 PC에 있고 서버에는 없다. 검색은 py가 로컬에서 직접 한다(7절).

## 1. 왜 이렇게 나뉘는가

| 사실 | 따라 나오는 결론 |
|---|---|
| 소스 파일은 로컬 PC에 있다. 서버는 파일을 볼 수 없다 | 파일을 읽고, 찾고, 자르고, 고치는 일은 전부 py |
| sLLM 주소와 모델은 서버만 안다 | 모델을 부르는 일은 서버를 거친다 |
| 여러 PC가 같은 sLLM을 쓴다 | 누가 얼마나 쓰는지, 동시에 몇 건인지는 서버만 통제할 수 있다 |
| 응답이 맞는지는 원본 코드와 대조해야 안다 | 응답을 검사하고 다시 묻는 일은 py |
| 요청 1건의 한도가 24k다 | 한도 안에 들도록 자르는 일은 py(파일을 아는 쪽), 한도를 검사해 거절하는 일은 서버(실제 토큰 수를 아는 쪽) |

## 3. 서버가 지켜야 할 약속(필수 10가지)

한 주소(`POST <주소>/chat/completions`)에 전부 들어간다.

| 번호 | 약속 | 내용 | 지키지 않으면 |
|---|---|---|---|
| 1 | 주소와 모델을 서버가 갖는다 | py가 보낸 `model` 값은 무시하거나 서버의 모델로 바꿔도 된다. sLLM이 옮겨 가도 PC는 손대지 않는다 | 주소가 바뀔 때마다 PC를 고쳐야 한다 |
| 2 | 호출자를 확인하고 기록한다 | py는 요청 머리말에 `X-Vupdate-Caller`(PC 이름\계정, % 부호화)와 `X-Vupdate-Run`(패키지/실행 ID)을 싣는다. 인증이 필요하면 `Authorization: Bearer`도 보낼 수 있다 | 누가 얼마나 썼는지 모른다 |
| 3 | 본문을 건드리지 않는다 | py가 보낸 메시지를 자르거나 요약하거나 고치지 않는다. 한도를 넘으면 자르지 말고 거절한다(5번) | 잘린 코드로 만든 수정이 그대로 적용될 수 있다. 가장 위험하다 |
| 4 | 공통 프롬프트는 앞에 붙이고 상한을 정한다 | 붙일 수 있다. 다만 "최대 몇 토큰"인지 정해 알려 준다. py는 그만큼 비워 두고 보낸다(설정 `server_prompt_reserve_tokens`) | 정하지 않아도 py가 응답의 토큰 수로 알아내지만, 한도에 가까운 처음 한두 건은 거절될 수 있다 |
| 5 | 한도 초과는 모델을 부르기 전에 거절한다 | 상태 400. 본문에 한도와 실제 입력 토큰 수를 담는다(8절의 형식) | 알아보지 못하는 형식이면 py는 줄여서 다시 보내지 못하고 수동 검토로 보낸다 |
| 6 | 동시 수를 넘으면 기다리게 하거나 "잠시 후"로 답한다 | 서버가 줄을 세워도 되고, 상태 429(또는 503)와 `Retry-After`로 답해도 된다. py는 기다렸다 다시 보낸다(기본 5회) | 여러 PC가 몰리면 sLLM이 넘친다 |
| 7 | 모델 설정을 고정한다 | temperature 0, 추론(thinking) 모드는 끈다. py가 보낸 `max_tokens`(출력 상한)를 지킨다 | 같은 입력의 응답이 달라지고, 추론 토큰이 출력 상한을 먹어 응답이 잘린다 |
| 8 | 응답을 그대로 돌려준다 | 내용을 해석하거나 고치지 않는다. `usage.prompt_tokens`(실제 입력 토큰 수)와 `finish_reason`을 함께 준다 | 토큰 수가 없으면 추정 보정이 안 된다. `finish_reason`이 없으면 잘린 응답을 알아보지 못한다 |
| 9 | 전송 오류는 서버가 먼저 다시 건다 | sLLM과의 연결 실패, 일시 오류는 서버가 정한 횟수만큼 다시 시도한 뒤 오류로 답한다. 시간 제한도 서버가 둔다 | py도 2회 다시 보내므로 없어도 돌아간다 |
| 10 | 호출을 기록한다 | 호출자, 실행 ID, 시각, 입력·출력 토큰, 걸린 시간, 결과 상태. 본문(코드 조각)을 남길지는 정책으로 정한다 | 운영 통계가 없다 |

## 6. 재호출은 누가 하는가

| 상황 | 누가 | 동작 | py 쪽 |
|---|---|---|---|
| sLLM과 연결이 끊김, 일시 오류 | 서버 먼저, 그다음 py | 서버가 다시 걸고, 그래도 안 되면 오류로 답한다. py는 2회 더 보낸다. 한 번도 성공하지 못하고 3회 실패하면 sLLM 단계를 끝낸다 | 됨 |
| 서버가 바쁨(동시 수 초과) | 서버가 알리고 py가 기다림 | 429 또는 503. py는 `Retry-After`만큼(없으면 1, 2, 4초로 늘려 가며) 기다렸다 다시 보낸다 | 됨 |
| 토큰 한도 초과 | 서버가 거절하고 py가 줄임 | py는 같은 요청을 다시 보내지 않는다. 주변 줄을 줄이거나 나눠서 새 요청을 만든다. 작업당 2회까지 | 됨 |
| 응답이 출력 상한에서 잘림 | py | 수정 지점을 절반씩 나눠 다시 보낸다 | 됨 |
| 응답 형식이 틀림, 원문과 다름, 범위를 벗어남 | py | 틀린 이유를 붙여 다시 묻는다(2회). 그래도 틀리면 수동 검토 | 됨 |
| 응답이 "정의가 더 필요하다" | py | 로컬에서 그 정의를 찾아 붙여 다시 묻는다(2회) | 됨 |
| 응답이 대상 줄을 고치지 않음 | py | 일부만 빠졌으면 그 지점만 수동 검토로, 전부 빠졌으면 다시 묻는다 | 됨 |
| 요청 자체를 거절(권한 없음, 형식 오류) | py | 다시 보내지 않고 수동 검토로 보낸다 | 됨 |

서버가 맡는 재호출은 첫 줄 하나다. 나머지는 서버가 **알려 주기만** 하면 py가 한다.

## 7. ripgrep 같은 검색 요청

**서버에 만들 필요가 없다.**

- 검색 대상인 소스가 로컬 PC에 있다. 서버의 도구로는 볼 수 없다.
- 이 도구는 모델에게 "찾아봐"를 시키지 않는다. 어디를 볼지는 py가 정하고, 모델에는 볼 조각만 준다. 24k 한도에서 모델이 여러 번 검색하며 돌아다니게 하면 한도를 금방 쓴다.
- py 안에 검색이 들어 있다. 전체 파일을 규칙으로 훑고(S2), 모델이 "이 이름의 정의가 필요하다"고 하면 로컬에서 찾아 붙인다. ripgrep 실행 파일은 쓰지 않는다. 162만 자 파일도 1초 안에 처리했다.

검색 도구가 필요해지는 경우는 하나다. **사람이나 다른 에이전트가 대화하면서 패키지를 들여다보려 할 때**다. 그때는 서버가 아니라 로컬 PC에서 도는 도구여야 하고, 이 도구의 산출물(`manifest.csv`, `report.md`, `manual_review.md`)을 읽게 하는 것으로 대부분 충분하다. 이번 범위에는 넣지 않았다.

## 8. 한 곳에 만드는 모양

### 8.1 권장: OpenAI 호환 중계

py를 고치지 않고 붙는다.

| 경로 | 필수 | 요청 | 응답 |
|---|---|---|---|
| `POST <주소>/chat/completions` | 필수 | `model`, `messages`(system 1건과 user 1건), `temperature` 0, `max_tokens` | `choices[0].message.content`, `choices[0].finish_reason`, `usage.prompt_tokens`, `usage.completion_tokens` |
| `GET <주소>/models` | 선택 | 없음 | `data[].id`, `data[].max_model_len` |

py가 싣는 머리말: `Content-Type: application/json`, `X-Vupdate-Caller`, `X-Vupdate-Run`, (PC의 `config/server.json`에 `llm.api_key`가 있으면) `Authorization: Bearer <키>`. `<주소>`는 환경변수 `VUPDATE_LLM_ENDPOINT`에 넣는 값이고(예: `http://<서버>/v1`), py가 그 뒤에 `/chat/completions`와 `/models`를 붙인다.

오류로 답할 때의 형식:

| 상황 | 상태 코드 | 본문에 있어야 하는 것 | py의 동작 |
|---|---|---|---|
| 토큰 한도 초과 | 400 | 아래 둘 중 하나 | 한도와 토큰 수를 받아 줄여서 새로 보낸다 |
| 동시 수 초과, 과부하 | 429 또는 503 | 없어도 된다. `Retry-After` 머리말(초)을 주면 그만큼 기다린다 | 기다렸다 같은 요청을 다시 보낸다 |
| 권한 없음 | 401 또는 403 | 사유 | 다시 보내지 않고 수동 검토로 |
| 요청 형식 오류 | 400 또는 422 | 사유 | 다시 보내지 않고 수동 검토로 |
| sLLM 장애, 시간 초과 | 500, 502, 504 | 사유 | 2회 다시 보낸다 |

한도 초과는 본문의 문구로 알아본다. `context length`, `maximum model length`, `token limit`, `over_limit` 같은 말이 있으면 한도 초과로 보고, 한도와 입력 토큰 수가 적혀 있으면 읽어 쓴다. 아래 두 형식은 시험으로 확인했다. 어느 쪽이든 된다.

```
(가) vLLM 이 내는 문구 그대로
This model's maximum context length is 24000 tokens. However, you requested 27100 tokens
(24100 in the messages, 3000 in the completion). Please reduce the length of the messages or completion.

(나) 값으로
{"error": {"code": "over_limit", "limit": 24000, "input_tokens": 24100}}
```

sLLM을 vLLM으로 띄웠다면 sLLM이 내는 오류를 그대로 넘기면 된다(문구는 vLLM의 판에 따라 조금씩 다르다. 실제 문구를 알아보는지는 `vupdate llmcheck`의 "한도 초과 거절" 항목이 확인한다). 서버가 공통 프롬프트를 붙이더라도 sLLM은 붙인 뒤의 크기로 검사하므로 서버가 따로 셀 필요가 없다. 숫자가 없는 문구여도 py는 한도 초과로 알아보고 줄이지만, 얼마나 줄일지 모르므로 다시 계획하는 횟수가 늘 수 있다.

### 8.2 다른 방법: MCP 도구 호출

MCP의 도구 하나(`vupdate_llm`)로 만들고 py가 MCP 규약으로 부르게 할 수도 있다. 그러려면 py에 MCP 호출 코드를 더해야 한다(지금은 없다). 서버가 해 주는 일은 8.1과 같으므로, 같은 서버에 HTTP 경로 하나를 여는 8.1이 일이 적다. 호출자 관리를 MCP의 인증으로 하고 싶다면 이쪽이 맞다.

## 9. 만든 뒤 확인

```
$env:VUPDATE_LLM_ENDPOINT = "http://<서버>/v1"      (PowerShell. 명령 프롬프트에서는 set VUPDATE_LLM_ENDPOINT=http://<서버>/v1)
vupdate llmcheck
```

| llmcheck의 항목 | 확인하는 약속 |
|---|---|
| 기본 호출 | 1, 2 |
| 모델 목록, 모델 목록의 토큰 한도 | 11 |
| 토큰 수 반환, 추정과의 차이 | 8, 4(고정분이 공통 프롬프트의 크기다) |
| 출력 형식, 추론 블록, 출력 길이 | 7 |
| 같은 입력에 같은 응답 | 7 |
| 한도 초과 거절 | 5, 3(넘는 요청을 받아들이면 본문을 자르고 있을 수 있다) |
| 동시 요청 | 6 |

전부 "정상"이면 서버 쪽 일은 끝이다. "주의"가 있으면 설명에 적힌 영향을 보고 받아들일지 정한다. 결과 파일의 "설정에 반영할 것"을 PC의 `config/server.json`에 적는다.

## 10. 정해야 할 것

| 번호 | 정할 것 | 어디에 쓰이나 |
|---|---|---|
| 1 | 호출자를 무엇으로 식별할지(머리말의 이름을 믿을지, 키를 나눠 줄지) | 약속 2 |
| 2 | 동시 수의 상한. 전체 몇 건, PC 하나에 몇 건 | 약속 6, PC의 `llm.max_parallel` |

| 4 | 24k 한도를 어디서 거는지(sLLM 자체인지, 중계 서버인지) | 약속 5의 오류 형식 |
| 5 | 기록에 코드 조각을 남길지 | 약속 10 |
| 6 | 중계를 HTTP 경로로 열지, MCP 도구로 할지 | 8절 |
