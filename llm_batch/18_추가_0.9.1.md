## 1. OS·DB의 원본/대상 옵션

컴파일러를 `--from-vs`, `--to-vs`로 주듯이 OS와 DB도 원본과 대상을 준다. **모두 선택이다.** 값은 제품 이름과 판을 글로 적는다.

```
vupdate run --package D:\src\PKG_A --from-vs 2008 --to-vs 2022 ^
    --from-os "Windows 7" --to-os "Windows 11" --from-db "Oracle 11g" --to-db "Oracle 19c"
```

| 옵션 | 지금 하는 일 |
|---|---|
| `--from-os`, `--to-os` | 모든 sLLM 요청(분석, 수정)의 `[환경]`과 보고서에 `OS: Windows 7 -> Windows 11`로 들어간다. `--to-os`를 주면 낮은 `WINVER`, `_WIN32_WINNT`를 그 OS의 값으로 올린다(Windows 10·11 → `0x0A00`, 8.1 → `0x0603`, 7 → `0x0601`). 주지 않으면 `0x0601`이다 |
| `--from-db`, `--to-db` | `[환경]`과 보고서에 `DB: Oracle 11g -> Oracle 19c`로 들어간다 |
| 둘 다 | 규칙의 발동 조건으로 쓸 수 있다: `"when": {"db": "oracle"}`(값에 그 낱말이 있을 때), `{"os_changed": true}`(원본과 대상이 다를 때) |

**지금 없는 것**: OS나 DB의 판 차이에 따라 코드를 바꾸는 내장 규칙. 옵션과 조건의 자리만 만들었다. 제품이 정해지면 규칙을 더한다(`config/rules.json`으로도 더할 수 있다). 규칙으로 만들 수 있는 것으로 확인한 후보:

| 구분 | 후보 | 근거 |
|---|---|---|
| DB(SQL Server) | 연결 문자열과 헤더의 구 공급자(`SQLNCLI`, `SQLOLEDB`, `sqlncli.h`)를 `MSOLEDBSQL`로 | SQL Server 2022에서 SQL Server Native Client가 빠졌다(Microsoft 문서) |
| DB(MySQL) | `my_bool` 타입을 `bool`(또는 `int`)로 | MySQL 8.0에서 `my_bool`이 없어졌다(MySQL C API 문서) |
| OS | DCOM 클라이언트(OPC DA 등)의 인증 수준이 `RPC_C_AUTHN_LEVEL_PKT_INTEGRITY`보다 낮은 호출 탐지 | Windows의 DCOM 보안 강화(KB5004442). 2023년 3월부터 끌 수 없다 |

## 2. HMI는 원본/대상 옵션이 되는가

HMI는 제품마다 사정이 달라 한 가지 답이 없다.

| 종류 | 판 올림에 따른 코드 수정을 규칙으로 만들 수 있는가 |
|---|---|
| Qt로 만든 화면(Qt 4 → 5 → 6) | **가능.** 공식 포팅 안내와 판별 API 변경 목록이 공개돼 있고, 없어진 API가 명시돼 있다(예: `QTextStream::setCodec()` → `setEncoding()`). `--from-hmi "Qt 5.15" --to-hmi "Qt 6.5"` 같은 옵션에 규칙을 붙일 수 있다 |
| MFC 화면 | Visual Studio 판에 묶여 있다. 이미 `--from-vs`, `--to-vs`의 규칙이 다룬다 |
| ActiveX(OCX), OPC DA | 판 올림보다 플랫폼(32 → 64비트)과 OS 보안 변경의 문제다. x64 규칙과 위의 DCOM 후보가 다룬다 |
| 상용 HMI·SCADA 제품 | **화면과 스크립트는 대상이 아니다**(C++가 아니고 제조사의 변환 도구가 올린다). 개발 키트를 쓰는 C/C++ 프로그램은 대상이지만 그 판 올림은 대부분 컴파일러 올림이어서 `--from-vs`, `--to-vs`가 이미 다룬다. 제조사 자료로 확인한 내용과 도구로 돌려 본 결과는 `20_상용HMI_검토.md`에 있다 |

그래서 `--from-hmi`, `--to-hmi`는 넣지 않았다. 쓰는 HMI가 Qt 계열이면 넣을 가치가 있다.

## 3. 실행 옵션 전체(`vupdate run`)

| 묶음 | 옵션 | 뜻 |
|---|---|---|
| 대상 | `--package 폴더` | 대상 패키지. 원본은 읽기만 한다 |
| | `--out 폴더` | 실행 폴더를 만들 위치(기본 `./runs`) |
| | `--only 패턴`, `--exclude 패턴` | 처리할 파일 범위, 뺄 범위 |
| 환경값 | `--from-vs`, `--to-vs` | 원본과 대상의 Visual Studio 연도(필수) |
| | `--cpp-standard`, `--from-cpp-standard` | 대상과 원본의 C++ 언어 표준 |
| | `--platform` | keep, x86, x64 |
| | `--conformance` | 준수 모드(off, on) |
| | `--charset` | keep, mbcs, unicode |
| | `--deprecated` | 사용 중단 경고(suppress: 설정으로 끔, fix: 이름 치환) |
| | `--from-os`, `--to-os`, `--from-db`, `--to-db` | OS와 DB의 원본/대상(선택) |
| 요청 | `--ask "글"` | 요청문. 여러 번 줄 수 있다 |
| | `--ask-file 파일` | 요청문 파일(파일 전체가 요청 하나) |
| | `--request 파일` | 요청 파일(배열 → 구조체의 이름과 필드, 공통 요청) |
| 규칙 | `--rules 파일` | 추가 규칙 파일(기본 `config/rules.json`) |
| | `--disable-rule 규칙ID` | 규칙 끄기 |
| | `--exceptions 파일` | 예외 파일(끌 규칙, 제외할 파일과 줄, 고유 매크로) |
| sLLM | `--llm-endpoint 주소` | sLLM 주소. 없으면 환경변수 `VUPDATE_LLM_ENDPOINT`, 그다음 서버 설정 |
| | `--server-config 파일` | 서버 설정(기본 `config/server.json`) |
| | `--max-parallel N` | 동시 요청 수 |
| | `--max-calls N` | 이번 실행의 호출 수 상한. 다 쓰면 대기로 두고 종료 코드 4 |
| | `--compat-llm` | 환경 호환성 항목도 sLLM에 보냄(기본 꺼짐) |
| | `--no-llm` | sLLM을 쓰지 않음 |
| 실행 제어 | `--dry-run` | 탐지까지만(S0~S2) |
| | `--until 단계` | 그 단계까지만(예: `S5`) |
| | `--resume 실행폴더` | 이어서 실행 |
| 컴파일 검사 | `--no-compile` | 컴파일 검사를 하지 않음 |
| | `--compile-parallel N` | 컴파일 검사 동시 수 |
| | `--vs-path`, `--sdk-path` | Visual Studio, Windows SDK 폴더 직접 지정(환경변수 `VUPDATE_VS_PATH`, `VUPDATE_SDK_PATH`) |
| 공통 | `--console-encoding` | 콘솔 출력 인코딩(`run` 앞에 쓴다) |

다른 명령: `preflight`(환경 점검), `status --run 폴더`(진행 상태), `rules`(규칙 목록, `--test`, `--coverage`), `selftest`(자체 시험), `llmcheck`(서버 점검).

종료 코드: 0 완료 / 1 완료(수동 검토 있음) / 2 단계 실패 / 3 입력 오류 / 4 대기 남음.

## 4. 전체 흐름

그림은 `19_전체_흐름도.md`(`19_전체_흐름도.svg`)에 있다. 아래는 같은 흐름을 글로 자세히 적은 것이다.

```
사용자: vupdate run --package ... --from-vs ... --to-vs ... [--ask "..."] [--request ...]
 │
 ├ S0 준비        환경 점검, 원본을 실행 폴더에 복사(이후 원본은 건드리지 않는다)
 ├ S1 인벤토리    파일 분류, 인코딩, 함수 경계, 큰 초기화 목록, include
 ├ S2 탐지        규칙 65개로 문제 지점을 찾는다 → 이슈
 ├ S3 설정흡수    코드 변경 없이 옵션·매크로로 해결할 항목(_CRT_SECURE_NO_WARNINGS 등)
 ├ S4 규칙적용    기계적 변경(이름 치환 등) → 수정 레코드
 │
 ├ S5 영향분석    ┌ [sLLM] 요청문 원문 → 의도별 JSON              (요청문당 1회, 다시 묻기 1회까지)
 │                ├ 이름이 코드에 있는지 확인, 낱말로 후보 고르기
 │                ├ [sLLM] 후보가 8개를 넘으면 번호로 추리기        (필요할 때만)
 │                ├ 의도마다 대상 줄 찾기 → sLLM 대상 이슈          (find 의도는 목록 파일만)
 │                ├ 배열 → 구조체: 사용처 전수 분류, 선언과 상수 인덱스는 수정 레코드, 나머지는 sLLM 대상
 │                ├ --compat-llm 이면 흡수 항목의 사용 줄도 sLLM 대상
 │                └ out/ask_plan.json
 │
 ├ S6 sLLM수정    ┌ 환경 호환성 규칙의 sLLM 대상: --compat-llm 이 꺼져 있으면 수동 검토로
 │                ├ 대상이 0건이면 이유를 적고 끝
 │                ├ 대상 줄을 조각으로(앞뒤 25줄, 작업당 8곳·150줄, 큰 데이터 생략, 선언·감싼 구문은 참고)
 │                ├ 토큰 추정으로 한도 확인, 넘으면 나눠서 차례로
 │                ├ [sLLM] 조각 + 의도의 요청문 → 수정 블록 / NO_CHANGE   (동시 1~8)
 │                ├ 수용 검사(형식, 위치, 괄호, 선언 변화, sizeof(포인터), 새 이름)
 │                │    불합격 → 사유를 붙여 다시 요청(2회까지) → 그래도 안 되면 수동 검토
 │                ├ 통과 → 수정 레코드
 │                └ 호출 예산을 다 썼거나 서버가 계속 바쁨 → 남은 작업은 대기(종료 코드 4, --resume)
 │
 ├ S7 병합        배열 요청에서 sLLM 에 맡긴 곳이 실패했으면 그 요청을 전부 되돌림
 │                중복 선언 검사 → 수정 레코드를 사본에 적용 → 큰 초기화 목록이 그대로인지 확인
 ├ S8 검증        괄호 짝, include, 규칙 재검사, (가능하면) 컴파일 검사 → 불합격이면 되돌림
 │                배열 요청의 잔여 재탐지
 └ S9 산출        out/changed/(바뀐 파일), diff, report.md, manual_review.md, project_settings.md, build_guide.md
```
