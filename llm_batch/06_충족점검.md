## 0. 판정 기준

| 판정 | 뜻 |
|---|---|
| 충족 | 코드에 구현돼 있고, 리눅스의 합성 예제로 동작을 확인했다 |
| 부분 | 일부만 구현했거나 다른 방식으로 대체했다 |
| 미충족 | 구현하지 않았다 |
| 해당 없음 | 구조가 바뀌어 대상이 없어졌다 |

**"충족"도 실제 환경에서 확인했다는 뜻이 아니다.** Windows, 실제 sLLM, 실제 패키지에서는 한 번도 돌리지 못했다. 판정은 코드를 직접 검색해 확인한 결과다.

### 0.1 v2에서 바뀐 것(코드 0.3.0)

v1의 7절에서 제안한 1~3번을 코드에 넣었다.

| v1의 제안 | 0.3.0에서 한 일 | 판정이 바뀐 항목 |
|---|---|---|
| 1. 한도 초과 대응과 추정 보정 | 거절된 요청을 그대로 다시 보내지 않고 더 작게 다시 계획한다. 서버가 알려 준 실제 토큰 수로 추정식을 보정한다. 잘린 응답과 과부하 응답에도 대응한다 | G6(부분 → 충족). D1은 부분 그대로이나 내용이 바뀜 |
| 2. 실행 옵션 정리 | 환경값, 처리 범위, 단계 건너뛰기, 호출자를 실행 옵션으로. 주소와 Visual Studio 경로는 환경변수로. 컴파일 검사 병렬 | 판정 변화 없음(F4, H5의 근거 갱신) |
| 3. 규칙의 버전 구간 조건 | 규칙마다 "문제가 생긴 VS 연도"를 두고, 원본 < 그 연도 ≤ 대상일 때만 켠다 | B5(미충족 → 충족), B10(부분 → 충족) |

**v1에서 틀리게 적은 것을 바로잡는다.** v1은 F4와 H1에서 "컴파일 검사를 병렬로 실행"한다고 적었다. 실제 0.2.0의 컴파일 검사는 한 파일씩 순서대로 돌았고, 설정값 `compile_parallel`은 어디에서도 쓰이지 않았다. 0.3.0에서 실제로 병렬로 바꿨다.

### 0.2 v3에서 바뀐 것(코드 0.4.0)

v2의 7절에서 권한 1~3번을 코드에 넣었고, 4번(빌드 오류 로그)은 분류까지만 넣었다.

| v2의 제안 | 0.4.0에서 한 일 | 판정이 바뀐 항목 |
|---|---|---|
| 1. 서버 점검 명령 | `vupdate llmcheck`. 토큰 수 반환, 한도 초과 거절, 출력 형식, 추론 블록, 같은 입력에 같은 응답, 동시 요청을 점검하고 설정에 반영할 값을 알려 준다 | 판정 변화 없음(6.5의 확인 방법이 생김) |
| 2. 환경값 축과 공통 요청 | OS, SDK, DB, HMI 도구와 그 밖의 이름을 from → to로 받아 프롬프트, 보고서, 규칙 조건에 쓴다. 요청 파일의 `common`을 모든 조각에 붙인다 | B1(부분 → 충족). B2는 부분 그대로이나 내용이 바뀜 |
| 3. 규칙 확충과 커버리지 표 | 규칙 17개 → 38개. 알려진 변경 67항목의 처리 방식 표 | C15(미충족 → 부분), G8(미충족 → 충족) |
| 4. 빌드 오류 로그 반입 | `vupdate buildlog`. 로그의 오류를 단계와 코드로 나누고 대응을 안내한다. 이슈로 넣어 다시 처리하지는 않는다 | F8(미충족 → 부분), F9(미충족 → 부분) |

제안에 없던 것도 하나 넣었다. sLLM이 한 조각의 여러 지점 중 일부만 고친 응답을 보내면, 0.3.0까지는 조각 전체를 "수정됨"으로 쳤다. 고치지 않은 지점이 보고서에서 빠지는 결함이다. 0.4.0은 수정 블록이 덮지 않은 지점을 수동 검토로 보낸다.

**v2의 판정 두 개를 바로잡는다.**

- **A7(충족 → 부분).** 프로젝트 설정은 `.vcproj`에서만 읽는다. `.vcxproj`는 읽지 않는다. 원본이 VS2010 이상인 조합에서는 프로젝트 점검과 컴파일 검사의 프로젝트 옵션이 비어 있다. 버전 조합이 고정이 아니라는 조건에서 "충족"은 넘치는 판정이었다.
- **C11(미충족 → 부분).** v2는 "특정 규칙만 끄는 방법은 코드 수정뿐"이라고 적었다. 틀렸다. `config/rules.json`에 같은 ID로 규칙을 다시 적으면 내장 규칙을 대신하므로, 코드 수정 없이 끄거나 탐지 전용으로 바꿀 수 있다(이번에 실행해 확인했다. `07_오류대응.md` 3.6). 줄 단위 예외는 여전히 없다.

잘 된 쪽은 파일 처리의 뼈대다(전수 검사, 인코딩 보존, 규칙 수정, sLLM 조각 수정, 병합, 산출물). 0.4.0에서 처음 요청의 "환경값과 요청사항을 파라미터로 넣는 범용 프롬프트"가 자리를 갖췄다. 비어 있는 쪽은 세 군데다.
- **실제 환경에서의 확인.** 모든 판정이 리눅스의 합성 예제와 모의 서버 기준이다. Windows, 실제 sLLM, 실제 패키지, 실제 빌드 로그에서는 한 번도 돌리지 못했다. 0.4.0에서 넣은 규칙 21개와 오류 코드별 대응표도 같다. 지금은 코드를 더 만드는 것보다 이 확인이 먼저다(7절).
- **파일 간 영향 분석과 변경 계약**(E 전체). 구조체 선언이나 IPC 메시지 변경은 수동이다.
- **빌드 오류의 되먹임.** 빌드 환경의 오류를 분류하고 안내하는 데까지 왔다. 그 오류를 다시 넣어 자동으로 고치는 고리는 아직 없다.

## 2. 미해결 사항

처음 요청하신 내용에 영향이 큰 순서다. v2의 1번(환경값 축), 5번의 확인 방법(서버 응답 형식), 6번(규칙 수와 커버리지), 8번의 절반(빌드 오류 로그)은 0.4.0에서 다뤄 내용을 바꿨다.

| 순위 | 미해결 사항 | 관련 항목 | 영향 |
|---|---|---|---|
| 1 | 실제 환경에서 한 번도 돌리지 못했다 | 전체 | Windows(Visual Studio 탐지, `cl /Zs`, .ps1, exe), 실제 sLLM(형식 준수율, 토큰 수, 한도 초과 문구), 실제 패키지(새 규칙의 오탐), 실제 빌드 로그(대응표의 맞고 틀림)가 모두 미확인이다. 확인하는 명령은 다 있다(`selftest`, `preflight`, `--dry-run`, `llmcheck`, `buildlog`) |
| 2 | 영향범위 분석과 변경 계약이 없다 | E1~E6 | 배열 → 구조체에서 구조체 정의와 선언부 교체, 헤더 변경의 사용처 전파가 수동이다 |
| 3 | IPC 메시지 구조체 요청을 처리하지 못한다 | B2, C13, E5 | 수동 검토 목록에 올리기만 한다 |
| 4 | 빌드 오류를 다시 넣어 고치지 못한다 | F8 | `buildlog`는 분류와 안내까지다. 규칙에 없는 오류는 사람이 고치거나 규칙을 더해 다시 돌려야 한다(`07_오류대응.md` 3.5) |
| 5 | `.vcxproj`의 설정을 읽지 않는다 | A7, F7 | 원본이 VS2010 이상이면 프로젝트 점검이 비고, 컴파일 검사에 프로젝트의 include 경로와 전처리기 정의가 들어가지 않는다 |
| 6 | DB, HMI 도구에 따른 규칙이 없다 | B1, C1 | 받는 자리와 규칙 조건(`axis`)은 생겼다. 무엇을 고쳐야 하는지는 쓰는 제품(예: Pro*C 여부, HMI 도구 이름)을 알아야 정할 수 있다. 지금은 프롬프트의 [환경]에 들어가 sLLM이 참고하는 데 그친다 |
| 7 | 서버 쪽이 아직 없다 | I2, 05의 10절 | 서버에 만들 것은 `08_MCP역할목록.md`로 정리했다. OpenAI 호환 중계 주소를 열면 py는 고칠 것이 없다. MCP 도구 호출로만 연다면 py의 M06을 고쳐야 한다 |
| 8 | 커버리지 표가 MS 문서의 전 항목이 아니다 | C15 | 67항목은 추린 것이다. 그중 18항목은 정적으로 잡지 않고 빌드 오류가 났을 때 대응표로 안내한다. 7항목은 다루지 않는다 |
| 9 | 줄 단위 예외와 고유 매크로 목록이 없다 | C11, J4 | 파일 단위는 `--exclude`, 규칙 단위는 `rules.json`에서 같은 ID로 덮어쓰기. 특정 줄만 빼는 방법은 없다 |
| 10 | 서로 의존하는 수정을 구분하지 않는다 | 05의 6.1 | 30줄 넘게 떨어진 지점은 항상 별개로 동시에 간다 |
| 11 | 원본 쪽 언어 표준을 모른다 | B5 | 원본이 이미 C++17로 빌드되던 코드여도 대상이 C++17이면 C++17 규칙이 켜진다 |
| 12 | 파일이 5,200줄이다 | 04의 1절 | 스스로 정한 기준(전체 3,500줄, 구획 500줄)을 넘었다. 동작에는 문제가 없지만 AI로 고칠 때 구획 하나가 커서 다루기 어렵다. 자체 시험과 부가 명령을 떼면 약 1,000줄이 준다 |
| 13 | 그 밖의 작은 항목 | C12, D11, D12, D13, F12 | 규칙 승격 집계, 조각 재출력 전환, 참고 컨텍스트 축약, 추론 모드 설정, 치환 동등성 검사 |

## 5. 실행 옵션

v1에서 "값을 정하는 주체와 값이 놓인 자리가 맞지 않는다"고 적은 것을 0.3.0에서 정리했다.

### 5.1 실행할 때마다 사람이 정하는 값: 실행 옵션

| 옵션 | 뜻 | 상태 |
|---|---|---|
| `--package`, `--from-vs`, `--to-vs`, `--cpp-standard`, `--request`, `--profile` | 대상과 환경 | 있음 |
| `--platform`, `--conformance`, `--charset`, `--deprecated` | 나머지 환경값. 프로필보다 우선 | 0.3.0 |
| `--axis` | 컴파일러 말고 다른 환경값(os, sdk, db, hmi, 그 밖의 이름). `이름=값` 또는 `"이름=원본->대상"`. 프로필보다 우선 | 0.4.0 |
| `--only`, `--exclude` | 처리할 파일 범위. 큰 패키지를 일부만 돌리거나 서드파티 폴더를 뺄 때 | 0.3.0 |
| `--no-llm` | sLLM 단계를 건너뛰고 규칙 수정만 | 0.3.0 |
| `--no-chunk` | 분할 순차를 끄고 한도를 넘는 구간은 수동 검토로 | 0.3.0 |
| `--no-compile` | 컴파일 검사 생략 | 있음 |
| `--max-parallel` | sLLM 동시 요청 수. 서버 설정의 허용 동시 수 이하로만 적용 | 뜻을 바꿈(0.3.0) |
| `--caller` | 호출자 표시. 기본은 PC 이름과 계정. 요청 머리말과 보고서에 실린다 | 0.3.0 |
| `--dry-run`, `--until`, `--resume`, `--out` | 실행 제어 | 있음 |

이어서 실행할 때(`--resume`)는 처음 실행의 옵션을 그대로 쓴다. 처리 범위와 호출자는 중간에 바꿀 수 없다.

### 5.2 PC마다 다른 값: 환경변수와 실행 옵션

| 값 | 주는 방법 | 상태 |
|---|---|---|
| sLLM(또는 중계 서버) 주소 | `--llm-endpoint` > 환경변수 `VUPDATE_LLM_ENDPOINT` > 서버 설정 파일 | 0.3.0 |
| Visual Studio 설치 폴더 | `--vs-path` > 환경변수 `VUPDATE_VS_PATH` > 자동 탐지 | 0.3.0. Windows 미확인 |
| 컴파일 검사 동시 수 | `--compile-parallel`. 0이면 CPU 수에 맞춤(기본) | 0.3.0 |
| 컴파일 검사 타임아웃 | 서버 설정 파일의 `limits.compile_timeout_sec` | 있음 |

주소를 환경변수로 둔 것은 exe나 .ps1에 주소를 적어 배포하지 않기 위해서다. 주소가 바뀌면 PC의 환경변수만 바꾸면 된다. 다만 PC마다 바꿔야 하는 것은 그대로이므로, 근본 해결은 MCP 서버 경유(`05_기능정의.md` 3절)다.

### 5.3 서버가 정하는 값: 옵션으로 두지 않는다

| 값 | 지금 받는 방법 | 남은 일 |
|---|---|---|
| 토큰 한도 | 서버가 모델 목록으로 알려 주면 그 값, 한도 초과로 거절하면서 알려 주면 그 값. 둘 다 없으면 설정 파일의 값 | MCP의 `llm_info`로 받기 |
| 서버 프롬프트가 차지하는 토큰 | 설정 파일의 `llm.server_prompt_reserve_tokens`(예약량). 실제 값은 응답의 토큰 수로 배운다 | 서버가 예약량을 알려 주기 |
| 허용 동시 수 | 설정 파일의 `llm.max_parallel`. `--max-parallel`은 그 이하로만 | 서버가 호출자별 허용값을 알려 주기 |
| 모델 이름, 공용 프롬프트의 판 | 설정 파일. 서버 목록에 없는 이름이면 경고 | 응답에 담아 주기 |

### 5.4 패키지마다 다른 값: 프로필·요청 파일

| 값 | 상태 |
|---|---|
| 환경값(컴파일러 쪽), 요청사항 | 있음 |
| DB, HMI 도구, OS, SDK 축 | 있음(0.4.0). 프로필의 `from`, `to`에 이름을 붙여 적는다. 이 축에 따른 내장 규칙은 OS → WINVER 값 하나뿐 |
| 공통 요청 | 있음(0.4.0). 요청 파일의 `common` |
| 규칙 예외 | 파일 단위는 `--exclude`, 규칙 단위는 `rules.json`의 같은 ID 덮어쓰기. 줄 단위는 없음(C11) |
| 프로젝트 고유 매크로 목록 | 없음(J4) |

## 6. 토큰 한도의 처리

질문: 추정치가 애매한데, 서버에서 프롬프트가 늘어나면 어떻게 되는가. 매번 실패하고 다시 보내는가.

답: 매번 실패하고 다시 보내는 방식이 아니다. 0.3.0은 먼저 묻고, 실제 값으로 맞춰 가고, 넘으면 서버가 알려 준 수치로 줄인다.

### 6.1 0.3.0의 동작

| 단계 | 동작 | 상태 |
|---|---|---|
| 1. 시작할 때 묻는다 | 서버의 모델 목록에서 한도를 받는다. 설정값보다 작으면 서버 값을 쓴다 | 구현. 서버가 이 주소를 제공할 때만 |
| 2. 서버 몫을 비워 둔다 | 설정의 `server_prompt_reserve_tokens`만큼을 처음부터 빼고 조각 크기를 정한다 | 구현. 값은 사람이 적는다 |
| 3. 첫 요청으로 확인한다 | 가장 큰 조각 1건을 먼저 보내 실제 토큰 수를 확인한 뒤 나머지를 보낸다 | 구현 |
| 4. 실제 값으로 보정한다 | 응답에 담긴 실제 입력 토큰 수로 "실제 = 비율 × 추정 + 고정분"을 맞춘다. 비율은 토크나이저 차이, 고정분은 서버가 덧붙이는 프롬프트다 | 구현. 서버가 토큰 수를 돌려줄 때만 |
| 5. 보내기 직전에 다시 본다 | 보정값이 바뀌었거나 정의 보강으로 조각이 커졌으면 보내기 전에 줄인다 | 구현 |
| 6. 거절되면 수치를 받아 줄인다 | 한도 초과로 거절되면 서버가 알려 준 한도와 토큰 수를 반영해 더 작게 다시 계획한다. 같은 요청은 다시 보내지 않는다 | 구현 |
| 7. 잘린 응답도 줄인다 | 응답이 출력 상한에서 잘리면 수정 지점을 절반씩 나눠 다시 보낸다 | 구현 |
| 8. 횟수를 제한한다 | 작업 하나에 다시 계획은 2회까지. 그래도 안 되면 수동 검토로 보낸다 | 구현 |
| 9. 판이 바뀌면 다시 묻는다 | 응답의 공용 프롬프트 판 번호가 바뀌면 한도를 다시 묻는다 | 미착수. 판 번호를 받는 접점이 없다. 대신 4번의 보정이 응답마다 따라간다 |

"더 작게 다시 계획"의 방법은 두 가지다. 주변 줄을 줄이고(25줄 → 12줄 → 5줄 → 0줄), 그래도 넘으면 문장 경계에서 나눠 순서대로 보낸다. 분할 순차 도중에 걸리면 끝난 앞 조각은 그대로 두고 남은 부분만 다시 나눈다.

그 밖의 오류는 이렇게 다룬다.

| 서버 응답 | 동작 |
|---|---|
| 과부하(429, 503) | 그 요청만 기다렸다 다시 보낸다(기본 5회, 서버가 대기 시간을 알려 주면 그 값) |
| 요청 자체의 거절(400 중 한도와 무관한 것, 401, 403) | 다시 보내지 않고 수동 검토로 보낸다 |
| 연결 실패, 시간 초과, 그 밖의 오류 | 다시 보낸다(기본 2회). 한 번도 성공하지 못한 채 3회 실패하면 sLLM 단계를 끝내고 나머지를 수동 검토로 보낸다 |

### 6.2 핵심은 예약량이다

서버가 공통 프롬프트를 덧붙이는 구성이면, 그 프롬프트의 상한(예: 2,000토큰)을 정해 `server_prompt_reserve_tokens`에 적어 둔다. 프롬프트가 그 안에서 늘어나는 동안은 py 쪽에서 바꿀 것이 없고 거절도 생기지 않는다. 적어 두지 않아도 4번과 6번으로 따라가지만, 처음 한두 건은 거절된다.

### 6.3 확인 결과(리눅스, 모의 서버)

| 상황 | 결과 |
|---|---|
| 서버가 2,000토큰을 덧붙이는데 py는 모름(조각 6개) | 거절 1회. 그 요청은 다시 보내지 않고 주변 줄을 줄여 보냄. 응답 7건으로 고정분을 2,000토큰으로 정확히 알아냄. 12곳 모두 수정 |
| 같은 상황에서 예약량 2,000을 적어 둠 | 거절 0회 |
| 서버의 실제 한도(5,000)가 설정(7,000)보다 작고, 서버가 토큰을 1.2배로 세고 400토큰을 덧붙임 | 거절 1회. 서버 한도를 받아 적용하고 26곳 모두 수정 |
| 서버가 수치도 토큰 수도 알려 주지 않음 | 거절 1회. 같은 요청을 반복하지 않고 줄여서 보냄. 6건 모두 수정. 보정 표본은 0개로 기록됨 |
| 서버가 모델 목록으로 한도(5,000)를 알려 줌 | 보내기 전에 적용. 거절 0회 |
| 분할 순차의 둘째 조각에서 거절 | 끝난 첫 조각은 두고 남은 부분을 5조각으로 다시 나눔. 40곳이 한 번씩만 수정됨 |
| 응답이 출력 상한에서 잘림(수정 지점 12개) | 6개씩 두 조각으로 나눠 다시 보냄. 12곳 모두 수정 |
| 과부하 응답 2회 뒤 정상 | 기다렸다 다시 보내 성공 |
| 한도와 무관한 요청 거절(400) | 작업마다 한 번만 보내고 수동 검토로 |

### 6.4 서버에 필요한 것

- 응답에 실제 입력 토큰 수를 담는다(OpenAI 호환 규격의 `usage.prompt_tokens`). 없으면 4번이 동작하지 않는다.
- 한도 초과는 모델을 부르기 전에 검사하고, 한도와 실제 토큰 수를 담아 거절한다. py가 지금 알아보는 것은 vLLM의 문구(`maximum context length is N tokens ... (M in the messages, ...)`)와 `05_기능정의.md`의 `over_limit` 코드다.
- py가 보낸 본문을 한도에 맞추려고 잘라 내지 않는다.
- 공통 프롬프트를 덧붙인다면 그 상한(예약량)을 정해 알려 준다.

### 6.5 실제 서버에서 확인할 것

0.3.0의 대응은 모의 서버로만 확인했다. 실제 서버에서 아래가 다르면 동작이 달라진다. **0.4.0의 `vupdate llmcheck`가 아래 항목을 한 번에 확인하고, 설정에 반영할 값(예약량 등)을 알려 준다.** 서버가 지켜야 할 것은 `08_MCP역할목록.md` 3절에 약속으로 정리했다.

| 확인할 것 | 다르면 생기는 일 | 고칠 곳 |
|---|---|---|
| 응답에 토큰 수가 오는가 | 안 오면 보정이 안 된다. 보고서 6절에 "표본 0개"로 나온다. 추정치와 10% 여유로만 판단한다 | 서버 쪽 |
| 한도 초과를 어떤 문구로 거절하는가 | 알아보지 못하면 "요청 거절"로 보고 수동 검토로 보낸다. 반복해서 보내지는 않는다 | M06의 `classify_llm_error` |
| 24k 한도를 어디서 거는가(모델 서버인가, 앞단인가) | 앞단이 걸면 거절 문구와 수치 형식이 다를 수 있다 | 위와 같음 |
| 모델 목록이 한도를 알려 주는가 | 안 알려 주면 설정값으로 시작하고, 틀리면 첫 거절에서 배운다 | 없음 |

## 7. 다음 판 제안

0.4.0까지 오면서 py만으로 만들 수 있는 큰 덩어리는 거의 다 만들었다. 남은 것은 대부분 **실제 환경의 결과를 봐야 방향이 정해지는 것**이다.

### 7.1 먼저 할 일: 개발이 아니라 확인

아래 네 가지는 명령이 이미 있다. 결과 파일을 주시면 그에 맞춰 고친다.

| 순서 | 할 일 | 주실 것 | 그 결과로 고치는 곳 |
|---|---|---|---|
| 1 | Windows PC에서 exe 빌드, `vupdate selftest`, `vupdate preflight --package <패키지>` | 화면 출력, `preflight.md`, `logs/run.log` | M07(Visual Studio 탐지, `cl` 호출), .ps1 |
| 2 | 실제 패키지를 `vupdate run ... --dry-run` | `report.md`(4절의 규칙별 건수), `manual_review.md` 앞부분 | 규칙의 오탐과 미탐, 괄호 짝 분석 |
| 3 | 서버에 중계 주소를 만들고 `vupdate llmcheck` | `llm_check.md` | `classify_llm_error`(한도 초과 문구), 프롬프트(형식 준수), 설정값 |
| 4 | 패키지 하나를 끝까지 돌려 빌드 환경에서 빌드, `vupdate buildlog` | `build_errors.md` | `ERROR_GUIDE`(대응표), 새 규칙, 되먹임을 만들지의 판단 |

### 7.4 권장

- **7.1의 1, 2번을 가장 먼저 한다.** exe 빌드와 `selftest`, `--dry-run`은 서버 없이 된다. Windows 쪽의 큰 문제와 새 규칙의 오탐은 여기서 드러난다.
- 다음 판(0.5.0)은 **7.1의 결과에 맞춘 보정 + 7.2의 1, 2번**을 권한다. 결과가 아직 없으면 7.2의 1~4번만 먼저 해도 된다. 모두 작고, 밖의 결정에 걸리지 않는다.
- 7.2의 5번(빌드 오류 되먹임)은 실제 빌드 로그가 한 번 나온 뒤에 만드는 것이 낫다. 어떤 오류가 얼마나 남는지에 따라 만드는 모양이 달라진다. 규칙 한두 개로 없어지는 오류가 대부분이면 되먹임보다 규칙 추가가 싸다.
