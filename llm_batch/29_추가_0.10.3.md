새 옵션은 없다. 요청 파일의 `buffer_fields`에 `llm` 키가 하나 늘었다.

## 2. 3단계(`--compat-llm 3`): 남은 것을 모두 sLLM에

| 단계 | 뜻 | 0.10.3에서 하는 일 |
|---|---|---|
| 1 | 기계적 변경만 | 그대로 |
| 2 | 보수적 판단 | 그대로(선언을 읽어 조건이 맞는 줄만 규칙이 바꾼다) |
| 3 | sLLM의 판단 | 1, 2단계 뒤에 **남은 것을 모두** 보낸다 |

3단계에 더한 규칙은 둘이다.

| 규칙 | 대상 |
|---|---|
| `R-T3-CRT-SECURE-REST` | 보안 CRT 경고(C4996)에 걸린 호출 가운데 2단계가 바꾸지 않은 것. 이름만 바꾼 `_itoa`, `_ltoa`, `_ultoa`, `_strlwr`, `_strupr`도 들어간다 |
| `R-T3-WINSOCK-REST` | `inet_addr`, `inet_ntoa`. `<ws2tcpip.h>`를 이미 include한 파일만(조각 단위의 수정으로는 include를 더할 수 없다) |

설정 처리는 그대로 한다. sLLM이 고치지 않은 줄도 경고는 프로젝트 설정으로 꺼진다.

### 2.1 받는 수정과 받지 않는 수정

sLLM이 보안 함수로 바꾼 수정은 **도구가 확인할 수 있는 꼴 하나만** 받는다.

- 함수가 `strcpy_s`, `strcat_s`, `sprintf_s`, `vsprintf_s`, `gets_s`, `_itoa_s`, `_ltoa_s`, `_ultoa_s`, `_i64toa_s`, `_ui64toa_s`, `_strlwr_s`, `_strupr_s` 가운데 하나다.
- 쓰는 대상이 이름 하나이고, 그 선언이 배열이다(지역 배열, 클래스의 멤버 배열, 파일 범위의 배열).
- 크기 인자가 `sizeof(대상)` 또는 `_countof(대상)`이다.

받지 않는 것과 까닭은 다음과 같다. 문서 21의 결함이 모두 여기에 걸린다.

| 받지 않는 수정 | 까닭 |
|---|---|
| `strncpy_s`, `strncat_s` | 끝의 0과 채움이 달라진다(고정 길이 필드의 다음 자리에 0을 쓰거나 잘린다) |
| 대상이 구조체의 필드나 버퍼의 중간 위치 | 끝의 0이 들어갈 자리가 없을 수 있다 |
| 대상이 포인터나 함수 인자인데 `sizeof`를 씀 | 포인터의 크기다 |
| `fopen_s`, `localtime_s` 등 표 밖의 함수 | 동작이나 문장의 구조가 달라진다 |
| 없는 이름(`_strncat_s`) | 0.9.2부터 있던 검사 |

검사는 수정 블록마다 한다. 걸린 블록만 빼고 같은 응답의 다른 블록은 받는다. 빠진 블록이 고치려던 줄은 사유와 함께 미수정으로 남는다. 응답의 블록이 모두 걸리면 사유를 붙여 한 번 다시 묻는다.

sLLM이 그대로 두겠다고 답한 줄은 수동 검토 목록에 올리지 않는다(설정으로 경고가 꺼지므로). 건수는 집계의 "sLLM이 고칠 필요가 없다고 본 곳"에 나온다. `--no-llm`이거나 주소가 없으면 이 줄들은 보내지 않고 목록에도 올리지 않는다.

### 2.2 알아 둘 것

- 호출이 는다. 보안 CRT 경고 줄이 있는 함수마다 작업이 생긴다. `--max-calls`와 함께 쓴다.
- 받은 수정은 버퍼가 모자랄 때의 동작이 달라진다(옛 함수는 넘쳐 썼고 보안 함수는 프로그램을 끝낸다). 2단계와 같다. 모두 검토 대상이다.

## 3. 요청문의 구조 변환: 규칙이 못 정한 자리는 sLLM에

"배열·버퍼를 구조체로" 의도의 처리 순서다.

1. 구조 분석이 탐지한 전문 버퍼와 지역 병렬 배열을 대상으로 한다. 요청문의 이름이 그 가운데 하나를 가리키면 그것으로 좁힌다.
2. 위치와 길이를 확정한 접근은 규칙으로 바꾼다(0.10.0과 같다).
3. **위치나 길이를 확정하지 못한 접근은 함수 단위로 sLLM에 수정을 요청한다.**
4. 구조 분석의 대상도 표 변환의 대상도 없으면, 요청문의 이름이 쓰인 줄을 일반 수정 요청으로 sLLM에 보낸다.

3번의 물음에 넣는 것:

- 요청문(의도의 지시)과, 요청문에 있던 조건(`constraint`로 나뉜 문장)
- 기존 구조체의 필드 표. 예: `MES_BODY(크기 21): szTc[0..5) szLot[5..15) szQty[15..21)`
- 고치는 꼴: 그 구조체를 겹쳐 보는 포인터나 구조체 변수가 이미 있으면 그 필드를 쓴다. 없으면 고치지 않는다(요청에 `cast: add`가 있을 때만 캐스팅 꼴을 허용)
- 그대로 둘 것: 버퍼의 선언, 전문 길이, 송수신 호출, 커서를 올리는 문장

필드 표를 줄 구조체는 요청의 `struct`, 함수에 이름이 나온 구조체, 함수에 나온 필드 이름을 둘 이상 가진 구조체 순서로 넷까지 고른다. 후보가 없으면 보내지 않고 사유를 남긴다.

보내지 않는 것도 있다.

| 남은 자리 | 처리 |
|---|---|
| 대응은 확인했으나 겹쳐 보는 포인터가 없음 | 보내지 않는다(캐스팅을 더할지는 요청의 `cast`로 정한다) |
| 반복 안의 상대 위치, 필드의 경계와 다름, 맞는 구조체가 없음 | 보내지 않는다(도구가 맞지 않음을 확인한 것이다) |
| 막힌 병렬 배열 묶음 | 보내지 않는다. 선언과 모든 사용처를 함께 바꿔야 해서 일부만 바뀌면 컴파일되지 않는다 |
| 표로 쓰이는 실제 배열(문자열의 배열, 레코드 번호로 쓰는 배열)을 이름으로 가리킨 요청 | 다른 대상으로 넓히지 않고 사유를 남긴다 |

끄려면 요청 파일의 `buffer_fields`에 `"llm": "off"`를 주거나 `--no-llm`을 준다. `--compat-llm`과는 별개다.

sLLM의 수정은 위치를 도구가 확인하지 못한 자리에 들어간다. 모두 검토 대상이고 `out/ask_trace.md`에 작업 목록과 비고가 남는다. sLLM이 그대로 둔 자리는 규칙이 남긴 사유(위치 모름 등)와 함께 미수정으로 남는다.

## 4. 요청 연결(27의 1번)

- 요청문의 이름이 배열 선언과 같아도, 그 배열이 글자 버퍼(`char 이름[길이]`)이거나 인덱스로 쓰이지 않으면 구조 분석으로 넘어간다. 그 이름은 계획에 참고로만 적는다.
- 글자 버퍼는 숫자 인덱스가 있어도 글자 필드의 구조체로 쪼개지 않는다(`TC[5] = 0;`).
- 표로 쓰이는 배열을 가리킨 요청만 예전처럼 넓히지 않는다.

## 5. 구조 분석(27의 2번, 3번)

| 꼴 | 0.10.1 | 0.10.3 |
|---|---|---|
| `sizeof(m_stInsp.szLot)` — 클래스 멤버 | 필드 이름의 크기가 패키지에서 하나일 때만 | 메서드가 속한 클래스의 정의에서 멤버의 타입을 찾는다 |
| 파일 범위의 구조체 변수 | 위와 같음 | 파일 범위 선언에서 타입을 찾는다 |
| `sizeof(arr[i].szLen)` — 구조체 배열의 요소 | 길이 모름 | 읽는다 |
| `memcpy_s`, `memmove_s`, `strncpy_s` | 읽지 않음 | 읽는다(`strncpy_s`는 끝에 0을 더 쓰므로 그대로 둔다) |
| `memset(배열, ' ', sizeof(배열))` | 묶음 전체를 막음 | 바꾼다(아래) |
| 묶음의 일부만 지우는 문장 | 묶음 전체를 막음 | 바꾼다(아래) |

값으로 채우는 문장은 두 가지로 바꾼다.

- 한 덩어리가 묶음의 모든 배열을 같은 값으로 채우면 `memset(stRec, 값, sizeof(stRec));` 하나로.
- 일부만 채우거나 값이 다르면 레코드마다 도는 반복문 하나로. 채워지는 바이트는 원본과 같다.

```cpp
for (int iRec = 0; iRec < (MAX_ITEM); iRec++)
{
    memset(stRec[iRec].szLot, ' ', sizeof(stRec[iRec].szLot));
    memset(&stRec[iRec].cFlag, ' ', sizeof(stRec[iRec].cFlag));
}
```

C 파일에서는 반복 변수를 블록의 처음에 선언하는 꼴로 쓴다. 채우는 값은 상수(글자, 16진수, 10진수)만 받는다.

아직 읽지 못하는 것: `sizeof(((T*)0)->m)`, `_countof(x)`, 포인터를 옮겨 가며 쓰는 커서, 위치 접근이 한 곳뿐인 버퍼, 배치를 확정하지 못한 구조체(char가 아닌 멤버가 있고 `pack(1)`이 아님). 이 자리는 3절에 따라 sLLM에 가거나 사유와 함께 남는다.

## 6. 컴파일 검사와 보고서(27의 6번, 7번)

- 프로젝트의 상대 include 경로는 스냅샷 기준의 폴더 뒤에 **원본 패키지 기준의 폴더**를 더한다. 패키지 폴더 밖의 공용 헤더(`..\..\Common\Inc`)와 스냅샷에 복사하지 않은 파일을 찾는다. 원본은 읽기만 한다.
- 원본에서의 소스 폴더도 끝에 더한다(`#include "../x.h"` 꼴).
- 보고서 2절은 실제 검사 결과로 쓴다. "변경 파일 N개: 컴파일 검사 통과 a개, 미수행 b개, …". "새 컴파일 오류가 없음을 확인했다"는 통과한 파일에만 쓴다. 통과한 파일이 없으면 "컴파일 검사로 확인한 변경 파일이 없다"로 쓴다.
- 컴파일 검사를 막은 헤더의 이름과 분류를 표로 적는다: 백업으로 뺀 파일 / 패키지 안에 있음(경로 미지정) / 빌드 때 만들어지는 파일로 보임 / 찾지 못함.
- 백업 제외: 되살린 헤더가 include하는 헤더도 되살린다.

바꾸지 않은 것: 미수행이 있어도 종료 코드는 그대로다(0 또는 1). 경로의 `$(SolutionDir)`는 프로젝트 폴더로 치고, 그 밖의 매크로가 든 경로와 속성 시트(`.props`)는 읽지 않는다.

## 7. 이름 변경과 경고 해소(27의 8번)

처리 단계별 집계에 한 줄이 붙는다. "POSIX 이름을 밑줄 이름으로 바꾼 n곳 가운데 m곳(_itoa, _ltoa, _ultoa, _strlwr, _strupr)은 이름의 경고만 없어지고 보안 CRT 경고(C4996)는 남는다." 3단계에서는 이 줄들이 sLLM에 가고, 지역 배열이면 `_itoa_s(값, 배열, sizeof(배열), 진법)`으로 바뀐 수정을 받는다.

## 8. 확인한 것

- `tests/test_v103.py` 22개 항목. 변환 전후의 출력 비교(g++)가 들어 있다.
- 옛 설계를 전제로 한 시험 항목 11개를 새 설계에 맞게 고쳤다(3단계에서 보안 CRT 줄을 보내지 않는다는 항목 등). 문서 21의 결함과 같은 수정을 모의 모델이 내는 시험은 "보내지 않는다"에서 "보내지만 받지 않는다"로 바꿨고, 결과 파일이 달라지지 않는 것은 그대로 확인한다.
- 전체: selftest 50, 규칙 시험 33, 시험 파일 13종 모두 통과.
- 모의 서버와 모의 컴파일러로만 확인했다. 실제 모델이 어떤 수정을 내는지, 받지 않는 수정이 얼마나 되는지는 실제 실행의 `out/ask_trace.md`와 처리 단계별 집계로 봐야 한다.
