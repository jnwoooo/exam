## 1. 목적

레거시 C++ 프로젝트를 대상 환경(예: VS2008 → VS2022)에 맞게 수정하는 작업을, 규칙 기반 처리와 로컬 sLLM을 결합한 파이프라인으로 자동화한다. 빌드가 불가능한 개발환경에서 정적분석으로 빌드 실패 위험을 최대한 줄이고(보장 범위는 F11), 변경 파일, diff, 보고서를 산출한다.

## 2. 변경 이력

- **v1**: 범위, 파라미터화, 규칙 선처리, sLLM 처리, 영향범위, 정적 검증, 산출물을 정의.
- **v2**: LLM 비의존 규칙 처리, 24k 한도의 대형 함수·상수 배열 처리, 수정 블록 출력, 병렬 처리(H절), MCP·검색 도구·PowerShell(I절)을 추가.
- **v3**: 아래 내용을 추가·보강. 본문에 `[v3 신규]`, `[v3 변경]`으로 표시(v2 표시는 제거).
  - 버전 체계의 명시 규칙과 대응표 (B1, B9, B10, 부록 A)
  - 프로젝트 파일 처리 (A7)
  - 규칙 커버리지와 타입 의존 수정의 취급 (C15, C16)
  - 빌드 불가 상황의 검증 대처방안과 보장 범위의 정의 (F5~F12)
  - 분석 도구 계층 (J절)
  - 빌드 환경용 절차서와 커버리지 보고 (G7, G8)

## 3. 전제와 제약

| ID | 내용 |
|---|---|
| P1 | sLLM은 gemma4-31b. 모델 컨텍스트는 262k이나, 요청 1건의 송수신(입력+출력) 합계 한도는 24k 토큰이다. |
| P2 | 개발환경에서 컴파일·빌드가 불가하다. 검증은 정적분석으로만 수행한다. |
| P3 | 대상은 로컬 패키지이며 전 과정을 로컬에서 수행한다. |
| P4 | 실행 환경은 Windows이고 명령 호출은 PowerShell을 경유한다. |
| P5 | 140만~180만 자 규모의 상수 배열을 포함한 함수가 존재한다. 기능 함수의 최대 크기는 미확인이다. |
| P6 | 버전 조합(2008 → 2022)은 고정이 아니며, 프로젝트마다 환경값과 요청사항이 달라진다. |
| P7 | sLLM 연결은 MCP 서버에서 엔드포인트를 구성하는 방식을 상정한다. |
| P8 | `[v3 신규]` 빌드가 불가능한 원인과, 개발환경에서 쓸 수 있는 분석 도구·헤더의 범위는 미확인이다. 이에 따라 도달 가능한 검증 수준이 달라진다. |

## 4. 요구사항

### A. 범위와 원칙

- **A1** 목적은 버전 업데이트 대응(deprecated·제거 API, 컴파일러/OS/DB/HMI 도구 변경에 따른 필수 수정)이다. 리팩터링과 스타일 변경은 범위 밖이며 최소 변경을 원칙으로 한다.
- **A2** 로컬 패키지의 전체 파일을 전수 검사한다. 파일별 처리 상태(변경없음/설정흡수/규칙/sLLM/수동검토/제외)를 매니페스트로 남겨 누락이 없음을 보인다.
- **A3** .cpp/.h 외에 .sln/.vcproj, .rc, .idl, .def, 빌드 스크립트, DB 프리컴파일 소스도 대상에 포함한다.
- **A4** 원본은 읽기 전용이다. 인코딩(CP949/UTF-8/UTF-16, BOM 유무)과 개행(CRLF)을 보존한다.
- **A5** 모든 처리는 로컬에서 수행하고 코드를 외부로 내보내지 않는다.
- **A6** 처리 우선순위는 ①빌드 설정으로 흡수 ②규칙 기반 수정 ③sLLM 수정 ④수동 검토 순이다. 앞 단계에서 해결되는 건은 뒤 단계로 넘기지 않는다.
- **A7** `[v3 신규]` 프로젝트 파일에서 빌드 설정(포함 경로, 전처리기 정의, 소스 목록, 문자셋, 런타임 라이브러리, 링크 라이브러리)을 추출해 분석과 보고에 쓴다. 프로젝트 파일 자체의 변환(.vcproj → .vcxproj)은 Visual Studio가 있는 환경에서 수행하는 것을 원칙으로 하고, 변환 후 적용할 설정 변경 목록을 산출한다.

### B. 환경값·요청사항 파라미터화

- **B1** `[v3 변경]` [환경값]은 from → to 쌍으로 정의한다. 컴파일러 관련 값은 서로 다른 축으로 분리한다.
  - VS 제품 버전(연도)
  - 툴셋(v90, v143 등)
  - C++ 언어 표준(C++14/17/20)
  - 준수 모드(`/permissive-` 사용 여부)
  - 플랫폼(x86/x64), OS 버전, 대상 OS, Windows SDK 버전
  - CRT 링크 방식(`/MT`, `/MD`), 문자셋(MBCS/Unicode)
  - DB: 종류, 버전, 접속 방식
  - HMI 개발도구: 제품, 버전, SDK
  - 서드파티 라이브러리
- **B2** [요청사항]은 공통(전 프로젝트)과 프로젝트별 기능변경으로 구분한다. 기능변경은 구조화된 명세로 입력한다.
  - 배열 → 구조체: 인덱스 → 필드명/타입 매핑표
  - IPC 메시지: 변경 전/후 구조체 정의, 패킹·정렬 규칙
- **B3** 환경값과 요청사항은 설정 파일(YAML/JSON)로 관리하고, 필수/선택 항목과 기본값을 스키마로 검증한다.
- **B4** 프롬프트는 범용 템플릿에 파라미터를 삽입하는 구조다. 구성은 고정 규칙, 환경값, 요청사항, 작업유형별 지시, 컨텍스트, 대상 코드, 출력 형식이다.
- **B5** 규칙 카탈로그는 "어느 버전에서 deprecated/제거됐는지"를 기준으로 관리해, 임의의 from → to 조합에 해당하는 규칙만 선택되게 한다.
- **B6** 24k 한도 때문에 규칙과 요청사항 전체를 매번 넣지 않고, 해당 코드 조각에 관련된 항목만 선별 삽입한다.
- **B7** 사용한 템플릿과 파라미터의 버전을 보고서에 기록한다.
- **B8** `[v3 변경]` 처리 방침을 파라미터로 둔다.
  - deprecated 경고: 코드 수정 / 경고 억제 매크로 중 선택
  - 설정 흡수(호환 옵션, 억제 매크로)의 허용 범위
- **B9** `[v3 신규]` 버전 체계를 다음 규칙으로 명시한다.
  - VS 제품 연도만 입력해도 되며, 툴셋은 부록 A의 대응표로 자동 파생한다.
  - 명시하지 않은 축에는 기본값을 적용한다. 언어 표준은 C++14, 준수 모드는 끔, 플랫폼·문자셋·CRT 링크 방식은 기존 프로젝트 설정 유지다.
  - 제품 버전, 툴셋, 언어 표준은 숫자 체계가 서로 다르므로 입력 형식을 축별로 검증한다. "9", "13"처럼 어느 축인지 알 수 없는 값은 거부한다.
  - 실제 적용된 값 전체를 보고서 첫머리에 기록한다.
- **B10** `[v3 신규]` 각 규칙은 발동 조건(어느 축의 어떤 변화에서 켜지는지)을 속성으로 가진다. 환경값 조합에 해당하는 규칙만 선택한다. 예: `auto_ptr` 규칙은 언어 표준 C++17 이상, 포인터 캐스팅 규칙은 플랫폼 x64에서만 켜진다.

### C. 규칙 기반 처리 (LLM 비의존)

- **C1** 규칙마다 ID, 탐지 패턴, 치환 내용, 안전 등급(자동적용/검토필요/탐지만)을 가진 카탈로그를 구축한다.
- **C2** 먼저 탐지 전용으로 전체를 스캔해, 규칙으로 해결되는 비율과 sLLM이 맡을 물량을 산정한다.
- **C3** 주석과 문자열을 마스킹한 뒤 정규식을 적용하고, 매크로나 여러 줄 구문은 구문 분석 도구를 병행한다.
- **C4** 규칙은 멱등이어야 한다(재실행해도 결과가 같음).
- **C5** 정규식 처리 후보 예: `"…"MACRO` 리터럴 접합 공백, `#define snprintf _snprintf` 제거, POSIX 함수명(`itoa` → `_itoa`), `std::tr1::`, x64 전환 시 `SetWindowLong` → `SetWindowLongPtr`.
- **C6** 보안 CRT 경고는 B8의 방침에 따라 함수 치환 또는 억제 매크로로 처리한다.
- **C7** 기계적으로 결정할 수 있는 수정은 sLLM을 호출하지 않고 처리한다. sLLM 호출은 규칙으로 결정할 수 없는 건에 한정한다.
- **C8** 규칙을 4단계로 구분한다.
  - T0 설정 흡수: 코드 변경 없이 컴파일 옵션·전역 매크로로 해결
  - T1 문맥 무관 치환: 정규식으로 안전하게 치환
  - T2 구문 인식 치환: 토큰/구문 구조를 확인한 뒤 치환
  - T3 탐지만: 탐지 후 sLLM 또는 수동 검토로 전달
- **C9** 각 규칙은 전/후 테스트 케이스를 가지며, 적용 없이 탐지 건수와 대상만 출력하는 dry-run을 지원한다.
- **C10** 규칙 적용 결과는 sLLM 수정과 같은 "수정 레코드" 형식(파일, 범위, 변경 전/후, 근거 ID)으로 기록한다.
- **C11** 프로젝트별 예외(파일/줄/규칙 단위 제외)를 지정할 수 있다.
- **C12** sLLM 수정 결과 중 반복되는 패턴을 집계해 규칙 후보로 보고한다.
- **C13** 기능변경 요청(배열 → 구조체, IPC 구조체)도 매핑표로 결정할 수 있는 부분(상수 인덱스 접근, 필드명 변경)은 규칙으로 처리한다.
- **C14** T3 규칙은 sLLM에 전달할 수정 지침(이슈 설명, 수정 방법)을 함께 가진다.
- **C15** `[v3 신규]` 규칙 카탈로그는 MS 공식 변경 이력 문서의 항목에 대응시켜 관리한다. 대응한 항목 수와 대응하지 못한 항목 목록(규칙 커버리지)을 산출한다.
- **C16** `[v3 신규]` 타입 정보가 있어야 옳게 고칠 수 있는 수정(예: `auto_ptr`의 소유권 이전, 좁히기 변환에 따른 타입 변경)은 T2로 자동 적용하지 않는다. 컴파일러 기반 도구를 쓸 수 있는 환경에서만 자동 적용하고, 그 외에는 T3로 처리한다.

### D. sLLM 처리 (24k 한도 대응)

- **D1** 토큰 예산을 항목별(고정 지시, 파라미터, 컨텍스트, 코드, 출력, 여유)로 관리한다. 토큰 수는 실제 모델 토크나이저로 측정하고, 한도를 넘는 요청은 전송 전에 차단한다.
- **D2** 출력은 파일 전체가 아닌 수정 블록 단위로 받는다. 최종 파일은 프로그램이 수정 블록을 원본에 적용해 생성한다.
- **D3** 탐지된 수정 지점 주변, 함수 시그니처, 사용 변수 선언, 관련 타입 정의만 전달한다(지점 슬라이스).
- **D4** 함수 전체에 걸친 변경이 한도를 넘으면 문장/블록 경계에서 분할한다. 각 조각에 시그니처, 지역변수 타입표, 앞 조각의 변경 내역(변경 원장)을 붙여 순차 처리하고, 재조립 후 괄호와 전처리기 균형을 검증한다.
- **D5** temperature 0, 지시 범위 밖 수정 금지, 재시도 횟수 제한, 초과 시 수동 검토 큐로 이관한다.
- **D6** 모든 호출의 프롬프트와 응답을 보존하고, 중단 후 재개할 수 있어야 한다.
- **D7** 대용량 상수 데이터(초기화 목록, 문자열 테이블)는 sLLM에 전송하지 않는다. 자리표시자로 치환해 전달하고, 처리 후 원문을 바이트 단위로 복원해 해시로 검증한다. 데이터 자체의 점검은 규칙으로만 수행한다.
- **D8** 함수 크기와 변경 성격에 따라 처리 경로(단일 호출/지점 슬라이스/분할 순차/수동 검토)를 자동 결정한다. 임계값은 설정값으로 두고 파일럿 측정으로 보정한다.
- **D9** 수정 블록은 다음 조건을 모두 통과해야 수용한다. 하나라도 실패하면 기각하고 재시도한다.
  - 형식 파싱 성공
  - 원문과 유일하게 일치
  - 허용 범위 안의 수정
  - 자리표시자 미훼손
  - 적용 후 구문 검사 통과
- **D10** sLLM 응답은 수정/변경 없음/컨텍스트 부족(필요 심볼 명시) 세 유형을 허용한다. 컨텍스트 부족이면 프로그램이 해당 정의를 보강해 재요청하며, 횟수를 제한한다.
- **D11** 대부분의 줄이 바뀌는 구간은 조각 단위 재출력으로 전환할 수 있어야 한다. 어떤 경우에도 파일 전체 재출력은 사용하지 않는다.
- **D12** 참고용 컨텍스트는 주석 제거와 축약으로 토큰을 줄이고, 편집 대상 구간은 원문 그대로 전달한다.
- **D13** 모델의 추론(thinking) 모드는 추론 토큰이 24k 한도에 포함되므로, 작업 유형별 사용 여부와 상한을 설정값으로 둔다.
- **D14** sLLM 입출력은 UTF-8로 하고, 적용 시 원본 인코딩으로 되돌린다. 수정문에 원본 인코딩으로 표현할 수 없는 문자가 있으면 기각한다.

### E. 컨텍스트 영향범위

- **E1** 정의/참조, 호출 관계, include 관계, 타입 사용처를 담은 심볼 인덱스를 구축한다.
- **E2** 변경을 ①함수 내 ②파일·클래스 ③파일 간(헤더 시그니처, 구조체, IPC 메시지, 전역 배열)으로 분류한다.
- **E3** ③은 변경 계약(새 구조체 정의, 시그니처)을 먼저 확정하고, 모든 사용처 프롬프트에 고정 사실로 주입한다. 처리 순서는 타입/헤더 → 정의 → 호출부다.
- **E4** 변경 후 사용처를 전수 대조해 계약과 불일치하는 잔여 참조가 0건인지 확인한다.
- **E5** IPC 구조체는 sizeof, 패킹, 32/64비트 타입 크기, memcpy나 오프셋 기반 접근, 상대 프로세스와의 호환을 별도로 점검한다.
- **E6** `[v3 신규]` 컴파일러 없이 수행한 영향범위 분석은 텍스트 기준의 근사임을 결과에 표기한다. 매크로, 별칭, 포인터를 거친 접근은 자동 판정에서 제외하고 수동 검토 대상으로 분리한다.

### F. 정적 검증

- **F1** `[v3 변경]` 검증 수준을 단계로 정의한다.
  - L0 구문 무결성: 괄호와 전처리기 균형, 파싱 오류가 원본보다 늘지 않음
  - L1 심볼 일관성(근사): 선언과 정의의 이름·인자 개수 일치, include 대상 존재. 타입 일치는 대상이 아니다
  - L2 규칙 재스캔 시 잔여 탐지 0건
  - L3 파일 단위 컴파일 검사(링크 제외). 컴파일러 프런트엔드와 헤더를 쓸 수 있을 때만 수행
- **F2** 정적분석만으로는 빌드 성공을 보증할 수 없으며 링크 오류는 검출하지 못한다. 미검증 항목은 "실제 빌드 시 확인 목록"으로 보고서에 출력한다.
- **F3** 구 버전 툴셋으로 빌드된 서드파티 바이너리(.lib/.dll)를 목록화해 재빌드, 호환 버전 입수, DLL 경계 분리 중 어느 대상인지 식별한다.
- **F4** 수정 건별 수용 검사(D9)와 파일 단위 검증(L0~L3)을 구분하며, 파일 단위 검증은 병렬로 수행할 수 있어야 한다.
- **F5** `[v3 신규]` 빌드가 불가능한 원인을 구분하고(컴파일러 부재 / 의존성 부재로 전체 빌드만 불가 / 외부 환경에서는 가능), 그에 맞는 검증 경로를 선택한다.
- **F6** `[v3 신규]` 원본과 수정본에 같은 검사를 수행해, 수정으로 새로 생긴 문제만 보고한다(차등 검증).
- **F7** `[v3 신규]` 컴파일러 프런트엔드를 쓸 수 있으면 파일 단위 컴파일 검사를 수행한다. 파일별 옵션은 A7에서 추출한 설정으로 구성한다.
- **F8** `[v3 신규]` 외부 빌드의 오류 로그(파일, 줄, 오류 코드)를 입력으로 받아, 오류 지점을 탐지 결과에 편입하고 재처리할 수 있어야 한다.
- **F9** `[v3 신규]` 문제를 드러나는 단계(컴파일/링크/실행)로 분류한다. 링크·실행 단계 항목은 정적 검출 대상에서 제외하고 점검 목록으로 산출한다.
- **F10** `[v3 신규]` 보고서에 파일별 도달 검증 수준(L0~L3)과 미검증 사유를 기록한다.
- **F11** `[v3 신규]` "빌드 가능성 보장"의 범위를 환경별로 정의한다.
  - 컴파일러가 없는 환경: 문서화된 변경 패턴의 처리와, 수정으로 새 구문 오류가 생기지 않음까지
  - 파일 단위 컴파일 검사가 가능한 환경: 컴파일 검사 통과까지
  - 링크 성공과 실행 동작은 어느 경우에도 보장 범위 밖
- **F12** `[v3 신규]` 기계적 치환은 수정 전후의 토큰열을 비교해 의도한 토큰만 바뀌었는지 확인한다.

### G. 산출물

- **G1** 변경 파일은 원본과 분리된 출력 경로에 같은 디렉터리 구조로 생성한다.
- **G2** 파일별 diff와 전체 요약을 생성한다.
- **G3** 보고서에는 적용한 환경값과 요청사항, 통계, 변경 건별 사유(규칙 ID, 요청 ID)와 처리 방식과 검증 결과, 수동 검토 목록, 잔여 리스크, 실제 빌드 시 확인 목록을 담는다.
- **G4** 버전 대응 변경과 기능변경 요청을 diff와 보고서에서 구분해 표기한다.
- **G5** diff는 sLLM 출력을 쓰지 않고, 원본과 결과 파일을 도구로 비교해 생성한다.
- **G6** 보고서에 처리 경로별 건수(설정 흡수/규칙/sLLM/수동), sLLM 호출 수와 토큰 사용량, 기각·재시도 건수를 포함한다.
- **G7** `[v3 신규]` 실제 빌드 환경에서 수행할 절차서를 산출한다. 프로젝트 변환 방법, 적용할 설정값, 확인 목록, 오류 로그 회수 방법을 담는다.
- **G8** `[v3 신규]` 규칙 커버리지(C15)를 보고서에 포함한다.

### H. 병렬 처리

- **H1** 작업을 독립 단위(파일 단위 규칙 적용, 슬라이스 단위 sLLM 호출, 파일 단위 검증)로 분해해 병렬 실행한다.
- **H2** 모든 작업은 변경되지 않는 스냅샷을 읽고, 결과는 수정 레코드로만 기록한다. 파일 쓰기는 병합 단계가 단독으로 수행한다.
- **H3** 의존 순서를 보장한다. 변경 계약 확정이 사용처 처리보다 먼저다. 같은 함수의 분할 조각은 순차로, 함수 간·파일 간은 병렬로 처리한다.
- **H4** 같은 파일에서 수정 범위가 겹치는 작업은 사전에 하나로 묶는다. 병합 시 충돌하면 재실행하거나 수동 검토로 보낸다.
- **H5** 동시 요청 수는 설정값으로 둔다. 서빙 엔진의 동시 처리 방식과 24k 한도의 관계를 확인한 뒤 정한다.
- **H6** 작업 ID는 입력(파일 해시, 범위, 이슈 ID, 템플릿·파라미터 버전)으로 결정한다. 이를 이용해 결과 캐시, 중단 후 재개, 재실행 시 동일 결과를 보장한다.
- **H7** 타임아웃과 재시도를 두고, 한 작업의 실패가 전체를 멈추지 않게 격리한다.
- **H8** 병렬 여부와 관계없이 최종 결과가 같아야 한다(병합 순서 고정).
- **H9** 프롬프트는 고정부를 앞에, 가변부를 뒤에 배치해 서빙 엔진의 프리픽스 캐시를 활용한다.

### I. MCP·도구·실행환경

- **I1** sLLM 호출은 하나의 연결 모듈로 일원화한다. 엔드포인트 주소, 모델명, 토큰 한도, 출력 상한, 동시 수, 타임아웃은 설정값이다.
- **I2** MCP 서버는 파이프라인 단계(인벤토리, 탐지 스캔, 규칙 적용, 작업 계획, sLLM 수정, 검증, 보고서)를 도구로 노출한다.
- **I3** 전수 처리의 대상 선정과 순서는 프로그램이 결정한다. sLLM이 스스로 탐색 범위를 정하는 방식에 의존하지 않는다.
- **I4** 코드 검색 기능(ripgrep 기반)을 제공한다. 용도는 규칙 탐지 스캔, 참조 조회, 수정 후 잔여 탐지 재스캔, 최소 컨텍스트 추출이다.
- **I5** 모든 도구 응답에 크기 상한(건수, 줄 길이, 토큰)을 둔다. 초과분은 총건수와 페이지 방식으로 제공한다. 대량 결과는 파일로 저장하고 응답에는 요약과 경로만 담는다.
- **I6** 검색 도구의 기본 제외 동작(ignore 파일, 숨김 파일, 바이너리 판정)을 해제하거나, 제외된 파일을 매니페스트에 기록해 전수 검사를 보장한다.
- **I7** CP949/UTF-8/UTF-16이 혼재해도 탐지 누락이 없도록 파일별 인코딩을 판별한 뒤 검색한다.
- **I8** 초장문 줄(상수 배열)이 검색 결과나 파일 읽기 응답에 통째로 들어가지 않도록 줄 길이를 제한한다.
- **I9** PowerShell 경유 시 인코딩 변환과 인용부호 문제 없이 실행되어야 한다. 소스 파일 입출력은 바이트를 보존한다.
- **I10** 도구는 오프라인으로 반입·설치할 수 있어야 한다.
- **I11** ripgrep이 없을 때는 대체 검색 경로로 기능이 동작해야 한다(성능 저하는 허용).
- **I12** sLLM이 도구를 직접 호출하게 할 경우(선택 사항), 도구 수와 정의 크기를 최소화하고 호출 횟수 상한을 두며 읽기 전용 도구만 제공한다.

### J. 분석 도구 `[v3 신규]`

- **J1** 분석 도구를 계층으로 구성한다. 텍스트 검색(ripgrep), 어휘 분석(주석·문자열·전처리기 구분, 괄호 깊이), 구문 분석(함수·문장·초기화 목록의 범위), 심볼 색인, 컴파일러 프런트엔드 순이다.
- **J2** 텍스트 검색과 어휘 분석만으로도 전 단계가 동작해야 한다(정확도 저하는 허용). 상위 계층 도구는 있으면 자동으로 활용한다.
- **J3** 구문 분석이 실패한 파일(매크로, `#if` 분기 등)은 어휘 분석 기반의 대체 경로로 처리하고, 실패 파일 목록을 보고서에 남긴다.
- **J4** 프로젝트 고유 매크로 목록(문법을 바꾸는 매크로)을 파라미터로 받아 분석 전에 처리한다.
- **J5** 컴파일러 기반 도구의 진단은 출처를 구분해 표기한다. 대상 컴파일러(MSVC)의 진단과 그 외 컴파일러(clang)의 진단은 일치하지 않을 수 있다.
- **J6** 사용한 도구의 버전과 옵션을 보고서에 기록한다.

## 5. 확인 필요 사항

앞의 세 가지가 설계 전체를 좌우한다. 점검 절차는 `03_확인사항.md`에 있다.

1. 빌드가 불가능한 이유: 컴파일러(VS2022)가 없는 것인지, 의존성(서드파티 lib, DB·HMI SDK)이 없어 전체 빌드만 안 되는 것인지.
2. 외부에 빌드 가능한 환경이 있는지, 그 오류 로그를 받아 올 수 있는지.
3. VS2022·Windows SDK 헤더를 개발환경에 둘 수 있는지, 설치 가능한 분석 도구(ripgrep, tree-sitter, ctags, cppcheck, clang, Python/.NET)가 무엇인지.
4. 24k 한도를 서버 설정에서 상향할 수 있는지, 서빙 엔진 종류와 동시 요청 처리 방식, 별도의 출력 토큰 상한이 있는지.
5. MCP 호스트(클라이언트)가 무엇인지. sLLM이 도구 호출의 주체인지, 별도 호스트가 sLLM을 도구로 부르는지.
6. "정적빌드"가 정적 링크(/MT, .lib) 제약을 포함하는지.
7. 대상 환경값: 언어 표준(C++14 유지 여부), 준수 모드, x86 → x64 전환, 문자셋 변경 여부.
8. 설정 흡수(경고 억제 매크로, 호환 옵션)의 허용 범위.
9. PowerShell 버전(5.1/7)과 스크립트 실행 정책.
10. 기능 함수의 크기 분포(줄 수, 토큰 수). 인벤토리 단계에서 측정한다.
11. 모델의 추론(thinking) 모드 현재 설정.
12. 보고서 최종 형식, DB와 HMI 도구의 종류.

- 내부 제품 버전은 12.0(2013) 다음이 14.0(2015)이다. 13은 없다.
- 2015 이후의 툴셋(v140~v143)은 서로 이진 호환이다. 2008(v90)로 만든 바이너리와는 호환되지 않는다.
- 언어 표준 선택 옵션(`/std`)이 생긴 뒤로는 C++14가 기본값이자 최저값이다. C++03이나 C++11 모드는 고를 수 없다.
- 2008 코드는 언어 표준 선택이 없던 시절의 코드이므로, 2022로 가면 최소 C++14 규칙으로 컴파일된다.
