# 추가 0.9.0: 요청문을 sLLM이 의도별로 나누는 단순 흐름

| 항목 | 내용 |
|---|---|
| 읽는 순서 | 17 / 17 |
| 작성일 | 2026-11-25 |
| 대상 코드 | `vupdate.py` 0.9.0 (약 8,000줄) |
| 우선순위 | 00~16과 다르면 이 문서가 맞다. 00~16에 적힌 기능 가운데 6절의 "뺀 것"은 0.8.0까지의 설명이다 |

**확인 범위(먼저 읽을 것).** 이 판의 모든 확인은 Linux, 합성 예제, 모의 sLLM으로 했다. Windows, 실제 sLLM(gemma4), 실제 패키지에서는 한 번도 돌리지 못했다. 특히 **요청문의 의미 분석은 모델이 하는 일**이어서, 실제 모델이 의도를 쓸 만하게 나누는지는 이 판으로 처음 확인하게 된다.

---

## 1. 무엇이 바뀌었나

0.8.0은 요청 종류마다 입구와 형식이 따로 있었고(`--ask "대상: 요청문"`, `[if]`, `--say`, 요청 파일의 정책 키), 형식이 맞지 않으면 sLLM을 한 번도 부르지 않고 조용히 끝났다. 0.9.0은 입구를 `--ask` 하나로 줄이고 판단을 sLLM에 먼저 맡긴다.

```
--ask "하려는 일을 글로"
   │ ① 의미 분석 (sLLM 1회)      요청 원문 → JSON(의도별 묶음)
   │ ② 검증과 대상 찾기 (도구)    이름이 코드에 있는지 확인, 의도마다 파일·줄을 찾음
   │ ③ 수정 요청 (sLLM N회)       "그 의도의 요청문 + 코드 조각" → 수정 블록
   │ ④ 후처리 (도구)              수용 검사, 병합, 검증, 보고
```

- 요청 하나에 여러 가지 일이 섞여 있어도 된다. JSON이 의도별로 묶여 오고, 수정 요청도 의도별 요청문을 달고 나간다.
- 환경 호환성 변경은 요청문이 아니라 `--from-vs`, `--to-vs`의 차이로 규칙이 수행한다. sLLM까지 부를지는 `--compat-llm`으로 정한다(기본 꺼짐).
- 수정 요청을 한 건도 보내지 않으면 **이유를 로그와 보고서 첫머리에 적는다.**

## 2. 쓰는 법

```
vupdate run --package D:\src\PKG_A --from-vs 2008 --to-vs 2022 ^
    --ask "WriteLog 호출에 줄 번호 인자를 추가하고 g_data 배열을 구조체로 바꾼다. 주석은 바꾸지 않는다"
```

| 옵션 | 뜻 |
|---|---|
| `--ask "글"` | 요청문. 정해진 형식이 없다. 여러 번 주면 각각 따로 분석한다 |
| `--ask-file 파일` | 파일 전체가 요청 하나다(`#`으로 시작하는 줄은 뺀다). 한 건에 4,000자까지 |
| `--compat-llm` | 환경 호환성 항목도 sLLM에 보낸다(4절) |
| `--until S5` | 대상 판정까지만. `out/ask_plan.json`으로 어떻게 이해했는지 먼저 본다 |
| `--only`, `--max-calls`, `--resume` | 범위와 호출 수 조절, 이어서 실행(0.8.0과 같다). `--max-calls`는 분석 호출도 센다. 이어서 실행할 때 분석은 다시 묻지 않는다 |
| `--request 파일` | 배열 이름과 필드 이름을 정확히 줄 때(3.4) |

**요청문을 적는 요령**
- 함수나 변수의 이름을 적으면 정확하게 찾는다. 도구가 원문의 영문 이름 가운데 코드에 실제로 있는 것을 분석 요청에 함께 알려 준다.
- 이름을 모르면 무엇을 하는 함수인지 적는다("로그를 남기는 함수"). 모델이 이름에 들어갈 영어 낱말을 내고, 도구가 그 낱말이 든 호출 이름을 찾는다.
- 범위를 좁히려면 글로 적는다("if 문 안에서", "Src/Net 폴더에서").

**결과를 보는 곳**

| 파일 | 내용 |
|---|---|
| `out/ask_plan.json` | 요청별로 나뉜 의도, 모델이 낸 이름 가운데 버린 것, 찾은 대상과 줄 수, 못 찾은 이유 |
| `logs/llm/ask_ASK-1_analyze_1.txt` | 분석 요청과 응답의 원문 |
| `logs/llm/task0001_a1_prompt.txt` | 수정 요청의 원문(의도의 요청문이 `[수정 지침]`에 있다) |
| `out/found_ASK-1-1.md` | 찾기 의도의 결과 목록 |
| `out/report.md` | 호출이 없었으면 첫머리에 이유. 5절 "변경 계약"에 의도별 결과 |

## 3. 흐름 상세

### 3.1 분석 요청과 JSON 양식

보내는 것: 환경(VS 판), 요청 원문, 원문의 이름 가운데 코드에 있는 것(종류와 횟수). **코드는 보내지 않는다.**

받는 것(이 꼴의 JSON 하나):

```json
{"intents": [
  {"type": "modify", "instruction": "WriteLog 호출에 줄 번호 인자를 추가한다",
   "names": ["WriteLog"], "words": [], "construct": "call", "files": []},
  {"type": "find", "instruction": "if 문 안에서 로그를 남기는 함수 호출을 찾는다",
   "names": [], "words": ["log", "trace"], "construct": "if", "files": []},
  {"type": "constraint", "instruction": "주석은 바꾸지 않는다",
   "names": [], "words": [], "construct": "any", "files": []}
]}
```

| 키 | 값 | 도구가 하는 일 |
|---|---|---|
| `type` | `modify`, `find`, `array_to_struct`, `compat`, `constraint` | 3.3의 갈래. 모르는 값은 `modify`로 본다 |
| `instruction` | 그 의도만 떼어 낸 요청문 | 수정 요청의 지침이 된다 |
| `names` | 코드에서 찾을 정확한 이름 | **코드에 없는 이름은 버린다**(`ask_plan.json`의 `names_dropped`) |
| `words` | 이름에 들어갈 영어 낱말(3글자 이상, 8개까지) | 낱말 단위로 맞는 호출 이름을 후보로 고른다(`log`로 `Dialog`를 잡지 않는다) |
| `construct` | `any`, `call`, `if`, `for`, `while`, `loop`, `switch`, `string`, `comment` | 대상을 그 구문 안으로 한정한다 |
| `files` | 경로 패턴 | 맞는 파일이 하나도 없으면 무시한다 |

- 답이 형식에 맞지 않으면 이유를 붙여 한 번 다시 묻는다. 또 어긋나면 그 요청은 "분석하지 못함"으로 수동 검토에 남는다.
- 낱말로 고른 후보가 8개를 넘을 때만 후보 확인 호출을 한 번 더 한다(150개씩). 번호 목록을 보내 `{"keep": [1, 4]}`를 받는다. 넘지 않으면 전부 대상으로 하고, 무관한 줄은 수정 단계에서 모델이 `NO_CHANGE`로 걸러 낸다.

### 3.2 대상 찾기(도구)

| 받은 것 | 대상 줄 |
|---|---|
| 이름(또는 낱말로 고른 이름) | 그 이름이 쓰인 줄. `construct`가 있으면 그 구문 안의 것만. `call`이면 이름 뒤에 `(`가 오는 것만 |
| 이름 없이 `if`·`for`·`while`·`loop`·`switch`만 | 그 구문의 머리 줄 전부(양이 많다. `--only`, `--max-calls`와 함께 쓴다) |
| 이름도 낱말도 구문도 없음 | 찾지 않는다. "대상을 찾지 못함"으로 보고한다(전체 훑기는 하지 않는다) |

### 3.3 의도의 종류별 처리

| 종류 | 처리 |
|---|---|
| `modify` | 대상 줄을 조각으로 잘라 의도의 요청문과 함께 sLLM에 보낸다. 작업 하나에 8곳·150줄까지 |
| `find` | 고치지 않고 `out/found_<의도>.md`에 목록만 낸다. 수정 요청을 보내지 않는다 |
| `constraint` | 모든 수정 요청의 `[공통 요청]`에 붙인다 |
| `array_to_struct` | 3.4 |
| `compat` | 대상을 만들지 않는다. 규칙과 `--compat-llm`이 맡는다는 안내를 남긴다(4절) |

### 3.4 배열 → 구조체

큰 배열의 선언은 모델이 고칠 수 없다(데이터는 생략해서 보내고, 생략 표식이 있는 줄의 수정은 기각된다). 그래서 이 의도만은 도구가 선언을 바꾼다.

- **요청문으로**: 문장에 배열 이름이 있으면 된다("g_data 배열을 구조체로 바꾼다"). 필드 이름은 그 배열의 인덱스로 쓰인 상수의 이름에서 만든다(`IDX_TEMP` → `temp`, `COL_MIN` → `min`). 상수 없이 숫자만 쓰였으면 `f0`, `f1`…이다.
- **요청 파일로**: 필드 이름을 정확히 정하려면 `--request` 파일에 적는다. 요청문에 "명시한 배열"처럼 이름 없이 적었을 때도 요청 파일의 배열 요청은 그대로 처리된다.

```json
{"features": [{"id": "REQ-1", "type": "array_to_struct", "target": "LIMIT_TBL", "struct_name": "LIMIT_ROW_T",
               "mapping": {"COL_ID": "id", "COL_MIN": "min", "COL_MAX": "max"}}]}
```

처리는 한 가지다(0.8.0의 정책 키는 뺐다).
1. 이름이 나온 곳을 전부 분류한다(`out/request_<id>_sites.md`).
2. 선언, 상수 인덱스, 메모리 함수의 인자 등 기계적으로 되는 곳은 규칙으로 바꾼다.
3. 변수 인덱스, 통째로 쓰는 곳은 sLLM에 보낸다. 지침에 대응표와 바꾸는 꼴(`((int*)&g_data)[i]`)을 넣는다.
4. **맡긴 곳이 하나라도 실패하면 그 요청의 수정을 전부 되돌린다**(반쯤 바뀐 결과는 컴파일되지 않는다). `--no-llm`이면 3이 안 되므로 적용하지 않고 사용처 목록만 낸다.

### 3.5 수정 요청과 후처리

- 수정 요청의 형식은 0.8.0과 같다(`[수정 지침]`, `[수정 대상 줄]`, `[참고]`, `[코드 조각]` → 수정 블록 또는 `NO_CHANGE`).
- 수용 검사(형식, 위치, 선언 변화, `sizeof(포인터)`, 새 이름 메모, 중복 선언)와 병합·검증도 0.8.0과 같다.
- 모델이 고치지 않은 줄의 처리가 달라졌다.

| 대상 | 모델이 `NO_CHANGE`로 답함 | 고치려다 수용 검사에서 끝내 실패 |
|---|---|---|
| 요청문의 의도로 찾은 줄 | 건너뜀(수동 검토로 올리지 않음) | 수동 검토 |
| `--compat-llm`의 흡수 항목 | 건너뜀 | 건너뜀(빌드에 지장이 없다) |
| 규칙의 sLLM 대상, 배열 요청의 사용처 | 수동 검토 | 수동 검토(배열 요청은 전부 되돌림) |

## 4. 환경 호환성 항목의 sLLM 호출 (`--compat-llm`)

> 0.9.3에서 이 옵션은 값 1, 2, 3을 받는다(1: 기계적 변경만, 2: 1 + 보안 CRT의 기계적 변환, 3: 2 + 남은 것을 sLLM에). 아래의 "켬"은 지금의 3단계에 해당하고, 보안 CRT와 Winsock 줄은 더 이상 sLLM에 보내지 않는다. 지금의 동작은 `22_추가_0.9.3.md`가 맞다.

| | 기본(꺼짐) | `--compat-llm` |
|---|---|---|
| 규칙의 기계적 변경(이름 치환 등), 설정 흡수 | 한다 | 한다 |
| 규칙이 "sLLM 대상"으로 분류한 것(`gets` 등) | **보내지 않고 수동 검토로 둔다** | 보낸다 |
| 설정으로 흡수하던 보안 CRT 함수(`sprintf`, `strcpy`, `_itoa` …), Winsock 함수의 사용 줄 | 코드를 그대로 둔다 | 보내서 수정을 시도한다 |

- 0.8.0까지는 규칙의 sLLM 대상을 기본으로 보냈다. **0.9.0은 기본이 "보내지 않음"이다.** 예전처럼 하려면 `--compat-llm`을 준다.
- 켜면 호출이 크게 늘 수 있다(`sprintf` 류는 수가 많다). `--only`, `--max-calls`와 함께 쓴다.
- 보안 CRT 함수로 바꾸면 **실행 동작이 달라진다**(버퍼가 모자라면 프로그램을 끝낸다). 고친 곳은 모두 검토 대상이고 보고서에 따로 집계된다.
- 대상 버퍼가 포인터여서 크기를 알 수 없는 곳은 모델이 고치지 않거나, `sizeof(포인터)`를 쓰면 수용 검사가 기각한다. 그런 곳은 그대로 둔다. `sizeof(구조체->멤버)` 꼴은 검사하지 못한다(멤버가 포인터여도 통과한다).

## 5. 호출이 없을 때

수정 요청을 한 건도 보내지 않으면 로그(`[S6.sLLM수정][_explain_no_calls]`)와 보고서 첫머리에 이유를 적는다. 예:

```
sLLM 에 수정 요청을 한 건도 보내지 않습니다. 이유:
  - 환경 호환성 규칙의 sLLM 대상 100건은 --compat-llm 이 꺼져 있어 보내지 않음(수동 검토 목록에 있음)
  - 요청 ASK-1-1: 환경 호환성 변경은 요청문으로 처리하지 않음(규칙이 수행. sLLM 시도는 --compat-llm)
  - 요청문 가운데 분석하지 못했거나 대상을 찾지 못한 것 1건(out/ask_plan.json 과 manual_review.md 에 이유가 있음)
```

0.8.0 시험에서 넣었던 문장("환경 호환성 변경과 명시한 배열->구조체 개선 수행한다")은 이제 이렇게 처리된다: 분석 호출 1회 → 의도 2개(환경 호환성, 배열) → 환경 호환성은 안내만, 배열은 이름이 없으므로 요청 파일의 배열 요청이 있으면 그것으로 처리하고 없으면 "배열 이름을 받지 못함"으로 보고.

## 6. 뺀 것과 남긴 것

**뺀 것**(0.8.0에 있다. git 브랜치 `add-vupdate-v0.8.0`)

| 뺀 것 | 대신 |
|---|---|
| `--say`, `--say-file`, 요청 파일의 `sentences`, `request_resolved.json` | `--ask`와 `ask_plan.json` |
| 요청문의 문법: `대상: 요청문`, `[if]`·`[find]` 꼬리표, `/정규식/:`, `@파일`, `*:` | 글로 적으면 모델이 나눈다 |
| 배열 요청의 정책 키(`variable_index`, `bare_use`, `on_unresolved`)와 0.7.1의 옛 키 | 한 가지 처리(3.4). 요청 파일에 남아 있으면 알림만 내고 읽지 않는다 |
| 구조체 변경 요청(`struct_change`) | 없음 |
| `--build-log`, `buildlog` 명령 | 없음 |
| MCP 경유 호출(`transport: mcp`), 중계 서버 참고 구현, 관련 예제 설정 | OpenAI 호환 호출 하나 |
| `--axis`, `--profile`, 환경값 축에 따른 확인 목록 | 환경값은 `--from-vs` 등 실행 옵션으로만 |
| `--caller`, `--no-chunk`, `shared_cache_file` | 호출자 표시는 PC 이름\계정으로 자동. 분할은 `limits.chunk_enabled` |

**남긴 것**: 규칙 65개와 설정 흡수, 구조 분석, 배열·표 변환(사용처 전수 분류, 원자성, 잔여 재탐지), 참고 영역과 작업 나누기, `--max-calls`·대기·`--resume`(종료 코드 4), 수용 검사, 컴파일 검사 옵션, `preflight`·`status`·`rules`·`selftest`·`llmcheck`.

## 7. 설정 키(`config/server.json`의 `limits`)

| 키 | 기본 | 뜻 |
|---|---|---|
| `ask_check_over` | 8 | 낱말로 고른 후보가 이 수를 넘으면 sLLM에 번호로 추리게 한다. 0이면 묻지 않고 전부 대상으로 한다 |

| `new_name_check`, `decl_change_check`, `size_arg_check`, `known_names` | mark, true, true, [] | 0.8.0과 같다 |

**서버 쪽**: 분석 호출도 수정 호출과 같은 주소(`/chat/completions`), 같은 메시지 구조로 간다. 서버에서 형식을 나눌 필요가 없다. 다만 분석 호출은 시스템 메시지가 다르므로, 서버가 자체 시스템 프롬프트를 고정으로 덧씌운다면 `llm.use_system_role`을 `false`로 둔다(시스템 글을 사용자 메시지 앞에 붙여 보낸다).

## 8. 시험하는 방법

```
python vupdate.py selftest                         50항목
python vupdate.py rules --test                     규칙 시험 예 30건
python tests\test_v090.py . %TEMP%\v090            0.9.0 시험 48항목(g++ 가 없으면 1항목은 건너뛴다)
```

실제 패키지에서는 이 순서를 권한다.

1. `--only`로 좁히고 `--until S5 --ask "..."`: `out/ask_plan.json`에서 의도가 맞게 나뉘었는지, 대상 줄 수가 납득되는지 본다. 틀리면 `logs/llm/ask_*.txt`의 응답 원문을 본다.
2. `--max-calls 20`으로 수정까지: `logs/run.log`의 "수용", "수정 블록 기각"과 보고서 7절의 "확인할 점"을 본다.
3. `--resume`으로 이어서 보낸다.
4. 환경 호환성 항목은 따로 `--compat-llm --only ... --max-calls ...`로 시험한다.

**실제 모델에서 볼 것**(알려 주면 고칠 곳)

| 증상 | 고칠 곳 |
|---|---|
| JSON이 아니거나 설명이 섞임 | `ANALYZE_SYSTEM`, `ANALYZE_USER`의 문구. 추론 블록이 길면 `llm.extra_body`로 끈다 |
| 의도를 잘못 나눔, `names`에 새 이름을 넣음, 지어냄 | `ANALYZE_USER`의 설명과 예. 지어낸 이름은 도구가 버리므로 틀린 수정으로 이어지지는 않는다 |
| `words`가 너무 넓어 후보가 많음 | `ask_check_over`를 낮추거나 요청문에 이름을 적는다 |
| 옳은 수정이 기각됨 | 기각 사유를 보고 `limits`의 검사 키를 끈다 |

## 10. 알려진 제약과 다음에 붙일 분기

- 이름을 못 받은 의도는 찾지 않는다. "전체를 훑어 모델이 판단" 방식은 넣지 않았다(호출 수가 코드 크기에 비례한다).
- `construct: call`은 이름 뒤에 `(`가 오는 줄을 다 잡는다. 함수의 선언과 정의 줄도 들어가고, 모델이 `NO_CHANGE`로 걸러 내야 한다.
- 한 작업의 응답에 기각되는 수정 블록이 하나라도 있으면 그 작업 전체를 사유와 함께 다시 묻는다(부분 수용은 하지 않는다).
- 요청문으로 온 배열 의도의 필드 이름은 자동으로 만든 것이다. 구조체 이름은 `<배열이름>_T`(2차원은 `_ROW_T`)다.
- 저장소 규칙의 "줄 단위 한국어 주석"은 적용하지 않았다(구획·함수의 목적 주석과 주요 줄의 주석만 있다).
- 의도의 종류를 늘리려면 `_ASK_TYPES`와 `_analyze_asks`의 갈래, `ANALYZE_USER`의 설명에 한 줄씩 더한다. 0.8.0에서 뺀 기능(구조체 변경 등)을 의도로 되살릴 때도 같은 자리다.
