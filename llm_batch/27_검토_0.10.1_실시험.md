|---|---|
| 읽는 순서 | 27 |
| 작성일 | 2026-11-26 |
| 대상 코드 | `vupdate.py` 0.10.1 (**이 문서로 코드를 바꾸지 않았다**) |

## 0. 결론

8가지 가운데 **의도대로 동작한 것은 5번 하나**다. 그것도 기대하신 동작과는 다르다. 나머지는 도구의 결함이거나, 알고 있던 한계가 실제 코드에서 그대로 드러난 것이다.

| # | 전달받은 문제 | 판정 | 재현 |
|---|---|---|---|
| 1 | 요청 연결 오류(일반 낱말 TC) | **결함** | 됨 |
| 2 | 멤버 타입·sizeof 연결 실패 | 설계 한계(범위가 좁았음) | 됨 |
| 3 | 공백 초기화 미지원 | 알고 있던 한계 | 됨 |
| 4 | 미처리 내역 집계 부족 | **결함**(1번에 딸린 것) | 됨 |
| 5 | 남은 경고를 sLLM에 보내지 않음 | 설계대로(0.9.3). 기대와 다름 | 됨 |
| 6 | 컴파일 검사 미완료 | 미수행 표시는 설계대로. **원인 쪽에 결함 2개** | 됨 |
| 7 | 보고서의 검증 범위 과장 | **결함** | 됨 |

재현하다 새로 찾은 것이 3개 있다.

- 일반 낱말이 숫자 인덱스를 쓰는 지역 배열과 맞으면, 요청과 무관한 그 배열을 구조체로 바꾸는 작업이 만들어진다(1번).
- 프로젝트의 include 경로가 패키지 폴더 밖을 가리키면 컴파일 검사가 그 헤더를 찾지 못한다(6번).
- 변경 파일을 하나도 컴파일 검사하지 못했는데 종료 코드가 0이다(7번).

## 1. 요청 연결 오류 — 결함

**재현.** 요청문 "MES 전문 Data 배열을 TC 별 구조체로 개선해 줘", 의도 분석 결과의 이름은 `MES, Data, TC`. 코드에는 `char TC[6];` 지역 배열이 있다.

| 꼴 | 결과 |
|---|---|
| `TC`에 숫자 인덱스가 없음(전달받은 경우) | 수동 검토 3건(이름 실패)뿐. 수정 0건. 구조 분석으로 넘어가지 않음 |
| `TC[5] = 0;` 이 있음 | `char TC[6]`을 `struct TC_T`로 바꾸는 작업이 만들어지고 나머지 사용처가 sLLM에 넘어감. 모의 모델이 거절해 기각됨 |

**원인.** 두 군데다.

- `_analyze_asks`(6858번째 줄)가 "배열 선언은 있는데 필드로 삼지 못한 이름이 있으면 구조 분석 전체로 넓히지 않는다"로 돼 있다. 0.10.0에서 "실제 배열 이름을 준 요청을 엉뚱하게 넓히지 않게" 넣은 조건인데, 일반 낱말이 우연히 배열 이름과 같을 때를 가르지 못한다.
- 요청문의 낱말을 배열에 연결할 때 이름만 본다. 옛 변환기는 큰 상수 표를 위한 것인데 6바이트 지역 문자열 버퍼도 대상으로 삼는다. 0.10.0의 보호(문자열 배열을 글자 필드로 쪼개지 않음)는 2차원에만 걸려 있다.

**개선 방향.**

1. 실패한 이름이 대체 경로를 막지 않게 한다. 요청문의 이름이 전부 변환 대상으로 풀릴 때만 그 대상으로 좁히고, 하나라도 풀리지 않으면 구조 분석 전체를 돌린다.
2. 1차원 글자 배열(문자열 버퍼)은 옛 변환기의 대상에서 뺀다. 지역 배열은 요청 파일에 이름을 직접 적었을 때만 대상으로 삼는다.
3. 풀리지 않은 이름은 "참고" 한 줄로만 남기고, 수동 검토 목록은 실제 대상(4번)으로 채운다.

## 2. 멤버 타입과 sizeof 연결 — 설계 한계

**재현.** 꼴을 하나씩 나눠 돌린 결과다.

| 꼴 | 0.10.1의 결과 |
|---|---|
| `sizeof(m_stInsp.szLot)` — 같은 필드 이름이 두 구조체에 다른 크기로 있음 | 길이 모름. 뒤따르는 커서도 모름이 되어 그 뒤 전부 위치 모름 |
| `sizeof(m_arHdr[1].szLen)` — 구조체 배열 | 길이 모름 |
| `sizeof(((HDR*)0)->szLen)`, `_countof(x)`, `sizeof(x)/sizeof(x[0])` | 길이 모름 |
| 접근이 `memcpy_s`, `strncpy_s`뿐인 함수 | **미탐지**(결과 문서에 나오지 않음) |
| 위치를 준 접근이 1곳뿐인 버퍼 | **미탐지** |
| 포인터를 옮겨 가며 쓰는 꼴(`q = pBuf; q += 4;`) | **미탐지**(문서에 적어 둔 한계) |
| 멤버 포인터 버퍼, 전역 버퍼, `LPBYTE` 인자, 길이를 변수에 받아 쓰는 꼴 | 확정(필드 이름의 크기가 패키지에서 하나일 때) |

**원인.** `_SxFn.sizeof`(4445번째 줄)는 변수의 타입을 **지역 변수와 인자의 선언에서만** 찾는다. 클래스 멤버 변수(`m_stInsp`)는 클래스 정의에 선언이 있어도 따라가지 않고, "그 필드 이름의 크기가 패키지 전체에서 하나뿐일 때"만 푼다. 전문 구조체가 여러 개면 `szLot`, `szDate` 같은 이름이 겹치기 쉬워 대부분 모름이 된다. 커서 방식은 길이 하나를 모르면 그 뒤 위치를 전부 모르게 되므로 피해가 커진다.

미탐지는 버퍼로 인정하는 문턱(4922번째 줄: 위치 접근 2곳 이상, 그 가운데 읽을 줄 아는 함수가 있어야 함)과 함수 목록(`_SX_CALLS`, 4032번째 줄)에 `_s` 계열이 없는 데서 온다.

**개선 방향.**

1. 클래스 멤버 표를 만든다(클래스 → 멤버 변수 → 타입). 메서드 `CMesProc::ParseInsp`의 `m_stInsp`는 `CMesProc`의 정의에서 타입을 찾는다. 전역 변수, 안쪽 구조체, 구조체 배열의 요소도 같은 길로 따라간다.
2. 변수의 타입을 따라가 필드 크기를 읽을 때 배치가 확정된 구조체만 쓰는 조건을 뗀다. `sizeof(필드)`는 정렬에 좌우되지 않는다. 위치를 정할 때의 조건은 그대로 둔다.
3. `sizeof(((T*)0)->m)`, `sizeof(T::m)`, `_countof(x)`, `sizeof(x)/sizeof(x[0])`를 읽는다.
4. `memcpy_s`, `memmove_s`, `strncpy_s`, `strcpy_s`, `strcat_s`, `sprintf_s`, `_snprintf`, `_snprintf_s`를 접근으로 읽는다.
5. 미탐지를 숨기지 않는다. 문턱에 못 미친 버퍼와 읽지 못한 꼴도 결과 문서에 "후보(분석하지 않음: 사유)"로 적는다.
6. 포인터 커서는 지역 `char*` 하나가 버퍼에서 시작해 상수만큼 늘어나는 꼴에 한해 정수 커서와 같은 규칙으로 읽는다. 안전장치는 정수 커서와 같게 둔다.

## 3. 병렬 배열의 공백 초기화 — 알고 있던 한계

**재현.** `memset(szLot, ' ', sizeof(szLot));` 5문장이 있는 묶음(문자열 배열 4개, 글자 배열 1개, 정수 배열 1개)은 탐지되지만 "이름을 통째로 사용" 5건으로 묶음 전체가 변환되지 않는다.

**원인.** 0으로 지우는 문장만 처리한다(5015번째 줄의 분류에 0 지우기만 있음). 0.10.0 문서에 적어 둔 한계다.

**개선 방향.** 채우는 값이 상수인 `memset(배열, 값, sizeof(배열))`을 받아들인다.

- 묶음의 모든 배열을 같은 값으로 채우면 `memset(stRec, 값, sizeof(stRec));` 하나로 바꾼다.
- 일부만 채우거나 값이 다르면(이번처럼 정수 배열이 섞인 경우) 레코드마다 도는 반복문 하나로 바꾼다. `memset(stRec[i].szLot, ' ', sizeof(stRec[i].szLot));`, 글자 하나짜리는 `stRec[i].cFlag = ' ';`. 채워지는 바이트는 원본과 같다.
- 길이를 `MAX_ITEM * 11`처럼 직접 쓴 꼴은 계산한 값이 배열 크기와 같을 때만 받아들인다.
- 0 지우기와 같은 조건(같은 블록, 사이에 묶음을 쓰는 문장 없음)을 지킨다. 전후 출력 비교 시험을 붙인다.

## 4. 미처리 내역 집계 — 결함

**재현.** 1번의 경우 `struct_scan.md`는 만들어지지만 모든 대상이 "(요청 대상이 아님)"으로 적히고, 보고서에 "구조 분석" 집계 절이 없으며, 수동 검토는 이름 실패 3건뿐이다. 실제 버퍼와 묶음을 시도했는지, 왜 남았는지 대조할 수 없다.

**개선 방향.**

1. 배열·구조체 의도의 요청이 있으면 연결 성패와 무관하게 집계표를 낸다.
2. 대상 원장을 하나 둔다(`out/struct_ledger.csv`). 대상(버퍼의 접근 한 곳, 묶음 하나)마다 한 줄이고 열은 파일, 줄, 함수, 대상, 탐지, 요청 연결, 시도, 결과, 사유다.
3. 상태를 넷으로 가른다. 바꿈 / 시도했으나 남김(사유) / 시도하지 않음(요청 연결 실패) / 분석하지 못함(사유).
4. 수동 검토 목록에는 함수·버퍼(묶음)별로 위치와 함께 넣는다. 지금은 요청이 연결됐을 때만 들어간다.

## 5. 남은 사용 중단 경고를 sLLM에 보내지 않음 — 설계대로, 기대와 다름

**재현.** `--compat-llm 3`에서 모델 호출은 의도 분석 1회뿐이다. 보안 CRT 경고에 걸린 4줄은 대상이 포인터 인자라 2단계 조건에 맞지 않았고 sLLM에도 가지 않았다.

**판정.** 0.9.3에서 정한 대로다. 3단계는 T3-llm 규칙 5개만 sLLM에 보낸다. 조건에 맞지 않는 보안 CRT 줄은 설정(`_CRT_SECURE_NO_WARNINGS`)으로 경고를 끄고 코드는 두는 것이 설계다. 0.9.1 실제 시험에서 이 줄들을 sLLM에 맡겼을 때 없는 `_s` 이름, 포인터에 `sizeof`를 쓰는 결함이 나왔기 때문이다(문서 21).

다만 "3이면 남은 경고를 전부 보낸다"로 읽히는 것은 표시의 문제다. 보고서 첫머리의 "보내지 않은 이유"에 이 까닭이 없고 뒤쪽 절에만 있다.

**선택지.**

| 안 | 내용 | 얻는 것 | 위험 |
|---|---|---|---|
| A(권장) | sLLM에는 계속 보내지 않고 2단계의 기계적 변환을 넓힌다. 대상에 클래스 멤버 배열과 같은 파일의 전역 배열을 더하고, 함수에 `_itoa`류와 `_strlwr`·`_strupr`을 더한다 | 남는 줄이 줄어든다. 결과가 매번 같다 | 낮음. 크기를 선언에서 확인한 것만 바꾼다 |
| B | 4단계를 새로 둔다. 남은 줄을 sLLM에 보내되 **제안만** 받아 `out/suggestions.md`에 적고 코드에는 넣지 않는다 | 사람이 고칠 때의 초안 | 호출 수가 줄 수만큼 든다. 제안의 옳고 그름은 사람이 본다 |
| C | 4단계에서 sLLM의 수정을 코드에 넣는다 | 경고 줄이 가장 많이 줄어든다 | 높음. 대상이 포인터면 버퍼 크기를 도구가 확인할 길이 없어 문서 21의 결함이 다시 나올 수 있다 |

도구가 크기를 확인할 수 있는 줄은 sLLM 없이 바꿀 수 있고, 확인할 수 없는 줄은 sLLM이 바꿔도 검증할 수 없다. 그래서 A를 권한다. 어느 안이든 보고서 첫머리에 "남은 n줄은 설정으로 경고를 끄고 코드는 두었다"를 적는다.

`strncpy`, `fopen`, `localtime`은 A에서도 바꾸지 않는다. Microsoft 문서 기준으로 `strncpy_s`는 끝의 0이 들어갈 자리가 없으면 문자열을 비우고 잘못된 매개 변수 처리기를 부르며(옛 함수는 0 없이 채웠다) 남는 자리를 0으로 채우지도 않는다. `fopen_s`는 파일을 공유 상태로 열 수 없다. `localtime_s`는 결과를 받는 방식이 달라 문장을 다시 써야 한다.

## 6. 컴파일 검사 미완료 — 표시는 설계대로, 원인 쪽에 결함

**판정.** 원본이 치명적 오류로 멈추면 "통과"가 아니라 "미수행"으로 적고 검증 수준을 L2로 두는 것은 0.9.2의 설계다. 문제는 **헤더를 못 찾은 원인이 도구 쪽일 수 있다**는 점이다.

**재현으로 확인한 원인 후보.**

| 원인 | 확인 |
|---|---|
| 프로젝트의 include 경로가 패키지 폴더 밖을 가리킴(`..\..\Common\Inc`) | 컴파일 검사는 스냅샷 사본에서 돌고 상대 경로를 스냅샷 기준으로 푼다(3267번째 줄). 밖의 폴더는 스냅샷에 없어 헤더가 디스크에 있어도 C1083이 난다. **결함** |
| 경로에 매크로가 있음 | `$(ProjectDir)`, `$(SolutionDir)`, `$(InputDir)` 말고는 그 경로를 통째로 건너뛴다. `$(SolutionDir)`는 프로젝트 폴더로 친다. 속성 시트(`.props`)의 설정은 읽지 않는다(문서에 적어 둔 한계) |
| 백업 제외(0.10.1) | 되살린 백업 헤더가 include하는 같은 백업 폴더의 다른 헤더는 되살리지 않는다. **결함** |
| 빌드 때 만들어지는 헤더(`_i.h`, `.tlh`, `#import`) | 재현하지 않음. 문법 검사만 하므로 원래 없는 파일이다 |

실제로 어느 것이었는지는 `logs/compile/` 아래 파일의 C1083 줄에 적힌 헤더 이름으로 가릴 수 있다. 보고서에는 그 이름이 없다(아래 2).

**개선 방향.**

1. 스냅샷에서 풀리지 않는 include 경로는 원본 패키지의 위치 기준으로 다시 푼다(읽기만 하므로 원본을 건드리지 않는다). `--include-dir`(여러 번)과 환경 변수 `VUPDATE_INCLUDE`를 둔다. `$(SolutionDir)`는 실제 `.sln`의 위치로 풀고 속성 시트의 include 경로도 읽는다.
2. 막힌 파일마다 헤더 이름과 분류를 보고서에 적는다. 패키지 안에 있음(경로 미지정) / 백업으로 제외됨 / 패키지 밖(경로가 가리키는 곳) / 빌드 때 만들어지는 파일로 보임 / 어디에도 없음.
3. 같은 진단을 sLLM 호출 전(S1)에 한다. `preflight.md`에는 이미 "외부 후보" 헤더 목록이 있다. 거기에 "이대로면 컴파일 검사를 못 하는 파일 n개"를 붙인다.
4. 백업 헤더의 되살림을 더 되살릴 것이 없을 때까지 되풀이한다.

## 7. 보고서의 검증 범위 과장 — 결함

**재현.** 변경 파일 2개가 모두 L3 미수행인데 보고서 2절에 "파일 단위 컴파일 검사 가능. 변경 파일에서 새 컴파일 오류가 없음을 확인했다."가 나온다. 첫머리에는 "컴파일 검사를 하지 못한 변경 파일이 2개 있다"가 함께 있어 서로 어긋난다. 종료 코드는 0이었다.

**원인.** 2절의 문구가 환경 등급("나")에 묶인 고정 문장이다(9340번째 줄). 실제 검사 결과를 보지 않는다.

**개선 방향.**

1. 2절을 실제 결과에서 만든다. "변경 파일 N개: 컴파일 검사 통과 a, 미수행 b, 새 오류 c". "새 컴파일 오류가 없음을 확인했다"는 통과한 a개에만 쓴다. a가 0이면 "컴파일 검사로 확인한 파일이 없다. 보장 범위는 정적 검사까지다"로 쓴다.
2. 등급은 "할 수 있는 검사", 검증 수준은 "실제로 한 검사"로 나눠 적는다.
3. 미수행이 하나라도 있으면 종료 코드를 1(수동 확인 있음)로 한다. 자동화에서 0을 통과로 읽고 있다면 동작이 달라지는 변경이다.
4. 같은 문장이 `build_guide.md`와 콘솔 요약에 있는지 함께 본다. 코드에서 이 문장은 9340번째 줄 한 곳이다.

## 8. 이름 변경과 경고 해소의 구분 — 결함(집계)

**재현.** `itoa` → `_itoa` 2곳이 규칙 표에 "탐지 2, 수정 2"로 적힌다. 보안 CRT 경고 줄 수(4곳)에는 이 2곳이 들어 있지 않다.

**확인.** Microsoft 문서에 따르면 `_itoa`, `_ltoa`, `_ultoa`는 보안 문제로 그 자체가 C4996 대상이고 `_itoa_s`가 권장된다. `itoa`는 `_itoa`의 POSIX 별칭이다. 이름 변경은 "POSIX 이름" 경고만 없애고 "보안 CRT" 경고는 남긴다(learn.microsoft.com, itoa·_itoa 문서).

**원인.** 보안 CRT 탐지를 원본 글에서만 한다. 원본의 `itoa(`는 보안 CRT 패턴(`_itoa`)에 걸리지 않고, 바꾼 뒤의 `_itoa(`는 다시 세지 않는다. 이름을 바꾼 17개 가운데 바꾼 뒤에도 C4996이 남는 것은 `itoa`, `ltoa`, `ultoa`, `strlwr`, `strupr` 5개다. 나머지(`stricmp`, `strdup`, `getch` 등)는 이름 변경으로 경고가 없어진다.

**개선 방향.**

1. 경고를 종류별로 집계한다. 열은 발생 줄 / 코드 수정으로 해소 / 설정으로 억제(코드는 그대로) / 남음.
2. 위 5개는 "이름만 바꿈. 보안 CRT 경고는 남음"으로 따로 적고 보안 CRT 줄 수에 더한다.
3. 2단계에 `_itoa(v, buf, r)` → `_itoa_s(v, buf, sizeof(buf), r)`를 더한다(5번의 A안). 조건은 대상이 크기를 아는 배열이고 반환값을 쓰지 않는 문장일 때다. `_itoa_s`는 반환 타입이 다르고 버퍼가 모자라면 프로그램을 끝낸다.

## 11. 정정(같은 날 16:44의 의견 반영)

5번의 선택지 A / B / C는 **철회한다.** 단계의 뜻은 처음 정한 대로다.

| 단계 | 뜻 |
|---|---|
| 1 | 기계적 변경만 |
| 2 | 보수적 판단(선언을 읽어 조건이 맞을 때만 규칙이 바꾼다) |
| 3 | sLLM의 판단으로 수정 |

0.9.3의 구현은 3단계에서 sLLM에 보내는 것을 "고치지 않으면 컴파일되지 않는 규칙 5개"로 좁혔고, 남은 사용 중단 경고 줄은 어느 단계에서도 보내지 않게 했다. 이 좁힘은 구현하면서 넣은 것이고 단계의 뜻과 맞지 않는다. 5번의 판정을 "설계대로"에서 **"구현이 단계의 뜻보다 좁다"**로 고친다.

요청문(`--ask`)에서 sLLM 수정 호출이 없었던 것도 의도와 다르다. 원인은 둘이다.

- `--compat-llm`은 환경 호환성 규칙에만 걸리고 요청문과는 별개다. 요청문의 수정 호출은 의도의 종류로 정해진다. `modify`는 대상마다 sLLM에 수정을 요청하지만, `array_to_struct`는 0.10.0부터 규칙(구조 분석)만 돌고 **규칙이 못 바꾼 자리를 sLLM에 넘기지 않는다.**
- 여기에 1번 결함이 겹쳐 규칙도 돌지 않았다.

"기계적 수정은 규칙으로, sLLM은 규칙으로 못 정하는 것만"에서 뒷부분(못 정한 것은 sLLM이 한다)을 0.10.0이 빠뜨렸다.

**고친 방향.**

| 대상 | 방향 |
|---|---|
| 3단계(환경 호환성) | 1·2단계 뒤에 **남은 것을 모두** sLLM에 보낸다. 보안 CRT의 남은 줄, Winsock, 이름만 바꾼 5개가 들어간다. 받은 수정은 지금의 수용 검사(없는 `_s` 이름, 포인터에 `sizeof` 등)를 거치고, 기각과 실패는 미수정으로 건수와 비고에 남긴다 |
| 요청문의 구조 변환 | ① 규칙이 위치와 길이를 확정한 자리는 규칙으로 바꾼다 ② **남은 자리는 함수 단위로 sLLM에 수정을 요청한다.** 물음에는 지시문, 함수 본문, 후보 구조체의 정의와 필드 표(위치, 길이), 도구가 확정한 줄, 조건(버퍼·전문 길이·송수신 호출은 그대로)을 넣는다. 이름 연결이 실패해도 ②로 간다 |
| 받은 수정의 검사 | 기존 검사에 더해, 쓴 필드가 그 구조체에 있는지와 버퍼 선언·송수신 호출이 그대로인지를 본다. 송신 한도(약 20k 토큰)를 넘는 함수는 나누거나 미수정(비고: 한도 초과)으로 남긴다 |
| 기록 | 단계와 의도마다 대상 / 규칙 수정 / sLLM 수정 요청 / sLLM 수정 / 미수정과 비고를 로그와 보고서에 남긴다. 기록의 틀은 0.10.2에 넣었다(`28_추가_0.10.2.md`) |

3단계와 요청문의 sLLM 수정은 문서 21의 결함(공간 부족, 다음 필드에 NUL, 잘림)이 다시 나올 수 있는 영역이다. 그래서 이 수정들은 "sLLM 판단"으로 표시해 검토 목록에 넣는다.
