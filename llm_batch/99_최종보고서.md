## 1. 한눈에 보기

**레거시 C++ 패키지를 새 Visual Studio 환경에 맞게 고치는 일을 한 명령으로 수행하는 도구다.**

- 정해진 수정은 규칙이 한다. 규칙이 못 정하는 것만 sLLM에 묻는다.
- 원본은 건드리지 않는다. 결과는 실행 폴더에 바뀐 파일, diff, 보고서로 낸다.
- sLLM의 답은 검사를 통과한 것만 받는다. 받은 것도 사람의 검토 대상이다.
- 빌드로 확인하지 못하는 환경을 전제로 한다. 정적 검사가 기본이고, 보장 범위를 보고서에 적는다.

| 구분 | 내용 |
|---|---|
| 입력 | 패키지 폴더, 환경값(원본·대상 VS 등). 선택: 요청문(`--ask`), 요청 파일(`--request`) |
| 출력 | 바뀐 파일, diff, 보고서, 수동 검토 목록, 프로젝트 설정 안내 |
| sLLM | 로컬 gemma4. 요청 1건의 입력+출력 24,000토큰(입력 약 19,000, 출력 3,000) |
| 배포 | 표준 라이브러리만 쓰는 py 한 파일. PyInstaller로 exe를 만들어 폐쇄망에 반입 |
| 사람이 할 일 | 수동 검토 목록 확인, diff 검토, 대상 환경에서 빌드 |

## 2. 제약과 그에 따른 설계

**설계는 모두 아래 제약에서 나왔다.**

| 제약 | 설계 |
|---|---|
| sLLM 한도가 24k 토큰 | 함수 전체가 아니라 수정 지점 주변만 보낸다. 넘으면 나눠 보낸다 |
| sLLM은 코드 전체를 모른다 | 대상은 도구가 찾는다. 선언과 정의를 참고로 붙인다 |
| sLLM의 답은 틀릴 수 있다 | 형식과 내용을 검사해 통과한 수정만 받는다. 걸러지면 사유를 붙여 다시 묻는다 |
| 개발 PC에서 빌드할 수 없다 | 정적 검사로 확인한다. cl이 있으면 파일 단위 검사를 더한다 |
| 폐쇄망 | 외부 패키지를 쓰지 않는다. 설정과 로그는 파일로 둔다 |
| 환경이 패키지마다 다르다 | 환경값은 실행 옵션이다. 규칙은 환경값에 따라 켜진다 |
| 원본을 지켜야 한다 | 시작할 때 원본을 복사하고 그 사본만 읽는다 |
| 호출이 많고 오래 걸린다 | 단계마다 상태를 저장한다. 답을 캐시한다. 이어서 실행할 수 있다 |

## 3. 전체 흐름

**S0부터 S9까지 한 방향으로 흐른다. sLLM과 통신하는 단계는 S5와 S6뿐이다.**

```
입력: 패키지, 환경값, (요청문, 요청 파일)
  S0 준비 -> S1 인벤토리 -> S2 탐지 -> S3 설정흡수 -> S4 규칙적용
  -> S5 영향분석 -> S6 sLLM수정 -> S7 병합 -> S8 검증 -> S9 산출
출력: 실행 폴더의 out/ (바뀐 파일, diff, 보고서)
```

| 단계 | 하는 일 | sLLM |
|---|---|---|
| S0 준비 | 환경 점검, 원본 복사(스냅샷), 백업으로 보이는 파일 제외 | - |
| S1 인벤토리 | 파일 분류, 인코딩·줄끝, 함수 경계, include, 프로젝트 설정 수집 | - |
| S2 탐지 | 환경값에 맞는 규칙으로 전체 소스를 훑어 이슈를 만든다 | - |
| S3 설정흡수 | 코드 변경 없이 프로젝트 설정으로 풀 항목을 모은다 | - |
| S4 규칙적용 | 자동 치환이 되는 이슈를 수정 레코드로 만든다 | - |
| S5 영향분석 | 요청문 분석, 대상 찾기, 구조 분석(전문 버퍼, 병렬 배열) | 의미 분석, 후보 확인 |
| S6 sLLM수정 | 남은 이슈를 조각으로 잘라 보내고 답을 검사한다 | 수정 요청 |
| S7 병합 | 수정 레코드를 적용해 결과 파일을 만든다(파일을 쓰는 유일한 단계) | - |
| S8 검증 | 결과를 원본과 비교해 검사하고, 불합격이면 되돌린다 | - |
| S9 산출 | diff, 보고서, 목록을 낸다 | - |

- 수정은 S4~S6에서 "수정 레코드"로만 쌓인다. 파일은 S7에서 한 번에 쓴다.
- 단계 이름은 로그와 `--until`(그 단계까지만 실행)에 그대로 쓴다.

## 4. 수정은 누가 정하나

**규칙이 정할 수 있으면 규칙이 한다. 규칙이 못 정한 것은 sLLM에 넘긴다. 둘 다 못 하면 사람에게 남긴다.**

### 4.1 규칙의 단계(68개)

| 단계 | 뜻 | 수 | 예 |
|---|---|---|---|
| T0 | 설정으로 흡수(코드 무변경) | 30 | 보안 CRT 경고를 프로젝트 설정으로 끈다 |
| T1 | 자동 치환 | 4 | 문자열 리터럴과 매크로 사이에 공백 삽입 |
| T2 | 치환 + 검토 표시 | 7 | `make_pair`의 템플릿 인자 제거 |
| T3 | 탐지만. sLLM(7) 또는 수동(20) | 27 | x64의 `SetWindowLong`(sLLM), 인라인 어셈블리(수동) |

- 분류: C++ 표준 18, DB 15, CRT 13, HMI 12, Windows API 5, 64비트 3, 언어 준수성 2.
- 규칙은 "원본 VS < 문제가 생긴 VS ≤ 대상 VS"일 때만 켜진다. 플랫폼, 언어 표준 같은 조건도 본다.
- 켜진 규칙은 `vupdate rules --from-vs 2008 --to-vs 2022`로 본다.

### 4.2 환경 호환성의 처리 깊이(`--compat-llm`)

| 값 | 하는 일 |
|---|---|
| 1(기본) | 기계적 변경만. 규칙이 못 고친 것은 수동 검토로 |
| 2 | 1 + 선언을 읽어 조건이 맞을 때만 규칙이 바꾼다(지역 `char` 배열의 `strcpy` → `strcpy_s` 등) |
| 3 | 2 + 남은 것을 sLLM에 보낸다(없어진 함수, 남은 사용 중단 경고 줄) |

### 4.3 요청(사용자가 더 시키는 일)

| 방법 | 내용 | 정하는 쪽 |
|---|---|---|
| 요청문 `--ask`, `--ask-file` | 글로 적는다. sLLM이 의도로 나눈다(7절) | 종류에 따라 규칙 또는 sLLM |
| 요청 파일 `--request` | 구조 분석을 정형으로 시킨다(8절) | 규칙. 남은 자리는 sLLM |

## 5. 코드 추출: sLLM에 무엇을 보내나

**수정 지점 주변의 코드 조각과, 그 조각을 고치는 데 필요한 선언만 보낸다.**

| 순서 | 내용 | 기준값 |
|---|---|---|
| 1. 대상 모으기 | sLLM 대상인 열린 이슈(규칙 탐지분 + 요청분)를 파일별로 모은다 | - |
| 2. 묶기 | 가까운 지점은 한 작업으로 묶는다 | 30줄 안. 작업 하나에 8곳, 150줄까지 |
| 3. 조각 자르기 | 지점 앞뒤의 줄을 함께 자른다 | 앞뒤 25줄 |
| 4. 줄이기 | 긴 초기화 목록은 자리표시자로 바꾼다 | 2,000자 초과 |
| 5. 참고 붙이기 | 대상 줄에 쓰인 이름의 선언, 타입 정의, 감싼 구문의 머리 | 1,500자까지 |
| 6. 크기 확인 | 입력 추정 × 1.1 + 출력 3,000 ≤ 24,000 | 넘으면 7로 |
| 7. 나누기 | 문장 경계에서 나눠 앞 조각부터 차례로 보낸다 | 뒤 조각에 앞에서 바꾼 내용을 붙인다 |

- 조각의 기준 본문은 규칙 수정을 적용한 뒤의 것이다. 규칙과 sLLM이 같은 줄을 따로 고치지 않는다.
- 나눈 조각 가운데 하나라도 실패하면 그 구간의 수정을 모두 취소한다. 일부만 바뀌는 것을 막는다.
- 토큰 수는 글자 수로 추정한다. 첫 요청 1건으로 실제 값을 확인해 보정한다.
- 같은 이름의 정의가 여러 헤더에 있으면 그 파일이 include 하는 정의를 붙인다. 가리지 못하면 붙이지 않는다.

물음의 구성은 이렇다.

```
[환경]          원본·대상 VS, 표준, 플랫폼 등
[수정 지침]     규칙 또는 요청의 지침. 의도마다 한 줄
[공통 요청]     모든 수정에 적용할 조건(있을 때)
[수정 대상 줄]  조각 안의 줄 번호와 내용
[참고: 선언]    이름의 선언과 타입 정의
[코드 조각]     파일 경로, 원본 줄 범위, 코드
```

## 6. sLLM 호출과 답의 검사

**답은 세 가지 꼴만 받는다. 수정 블록은 검사를 통과해야 수정 레코드가 된다.**

| 답 | 처리 |
|---|---|
| 수정 블록(`SEARCH`/`REPLACE`) | 검사 후 수용 |
| `NO_CHANGE` | 고치지 않음. 수동 검토 또는 "고칠 필요 없음"으로 기록 |
| `NEED_CONTEXT: 이름` | 그 이름의 정의를 찾아 붙여 다시 묻는다(2회까지) |

수용 검사:
- 형식이 맞는가. `SEARCH`가 조각에 한 번만 나오는가.
- 대상 줄을 건드리는가. 자리표시자를 건드리지 않는가.
- 괄호 짝과 인코딩이 유지되는가. 블록끼리 겹치지 않는가.
- 선언을 없애거나 다시 선언하지 않는가. `sizeof(포인터)`를 새로 쓰지 않는가.
- 보안 CRT 변환은 대상이 배열이고 크기가 `sizeof(대상)`일 때만 받는다.

호출의 운영:

| 항목 | 내용 |
|---|---|
| 차수 | 1차는 가장 큰 작업 1건(토큰 확인). 2차는 나머지. 그 뒤는 재요청 |
| 재요청 | 걸러진 사유를 붙여 다시 묻는다. 2회까지. 그 뒤는 수동 검토 |
| 병렬 | 서버 설정의 동시 수 이하(`llm.max_parallel`, `--max-parallel`) |
| 캐시 | 같은 물음은 다시 보내지 않는다. 받은 답은 바로 저장한다 |
| 예산 | `--max-calls`. 다 쓰면 남은 작업을 대기로 두고 종료 코드 4 |
| 한도 초과 | 같은 요청을 다시 보내지 않고 더 작게 다시 계획한다(2회까지) |
| 기록 | 물음과 답의 원문이 `logs/llm/`에 작업별로 남는다 |

## 7. 요청문 처리(`--ask`)

**sLLM이 요청문을 의도로 나누고, 도구가 의도마다 대상을 찾아 처리한다.**

```
요청문 -> (S5) 의미 분석 1회 -> 의도 목록(12개까지)
       -> 의도마다 대상 찾기 -> 규칙 수정 또는 sLLM 대상 이슈 -> (S6) 수정 요청
```

| 종류 | 뜻 | 처리 |
|---|---|---|
| `modify` | 특정 대상을 찾아 고친다 | 이름이 쓰인 줄을 sLLM에 맡긴다 |
| `find` | 찾아서 목록만 낸다 | `out/found_의도.md` |
| `array_to_struct` | 배열·전문 버퍼를 구조체로 | 구조 분석(8절). 규칙이 먼저, 남은 자리는 sLLM |
| `compat` | 일반적인 호환성 수정 | 요청문으로 처리하지 않는다. 규칙과 `--compat-llm`이 한다 |
| `constraint` | 모든 수정에 적용할 조건 | 모든 수정 물음에 공통 요청으로 붙인다. 지켰는지 검사하지는 않는다 |

대상을 찾는 길:

| 길 | 내용 |
|---|---|
| 이름 | 요청문에 적힌 이름과 정확히 같은 것. 코드에 없으면 버린다. `--ask-match 2~4`로 넓힌다 |
| 낱말 | 이름을 모를 때. 함수 이름에 그 낱말이 든 것. 후보가 8개를 넘으면 sLLM이 번호로 고른다 |
| 구문 | 함수 호출, `if`, `for` 등으로 한정 |
| 구조 분석 | 코드에서 직접 탐지(이름 없이도 됨) |

- sLLM 호출은 의도 단위가 아니라 코드 조각 단위다. 한 조각에 여러 의도의 지침이 함께 실린다.
- 한 줄에 한 가지 일만 적고 함수 이름을 그대로 적으면 잘 나뉜다.
- 호환성 문장은 요청문에 넣지 않아도 결과가 같다.
- 먼저 `--until S5`로 돌려 `out/ask_trace.md`에서 의도와 대상 수를 확인한다.

## 8. 구조 분석

**전문 버퍼의 위치 접근을 기존 구조체의 필드 접근으로, 한 함수의 병렬 배열을 구조체의 배열로 바꾼다. 확정한 것만 규칙으로 바꾼다.**

요청 방법은 요청문의 `array_to_struct` 의도 또는 요청 파일의 `buffer_fields`, `record_group`이다. 결과와 사유는 `out/struct_scan.md`에 문장별로 남는다.

### 8.1 전문 버퍼 → 필드 접근

함수의 문장을 따라가며 버퍼 접근마다 (위치, 길이)를 계산하고, 기존 구조체의 필드와 같으면 바꾼다.

| 경우 | 조건 | 결과 |
|---|---|---|
| 기존 겹쳐 보기 포인터 | 버퍼를 구조체로 겹쳐 보는 포인터가 이미 있다 | `memcpy(pBuf + 37, s, 6)` → `memcpy(pBody->szQty, s, 6)` |
| 로컬 구조체 복사 | 읽기만 하고 구조체의 끝까지 읽는다 | 구조체 변수에 한 번 복사하고 필드로 읽는다 |
| 포인터 추가 | 요청에 `cast: add`를 줬다 | 겹쳐 보는 포인터를 새로 넣는다 |

- 버퍼, 전문 길이, 송수신 호출은 건드리지 않는다. 새 구조체를 만들지 않는다.
- 구조체의 배치는 채움(padding)이 없다고 확인될 때만 쓴다. 모든 멤버가 1바이트 타입이거나 `#pragma pack(1)` 안이어야 한다.
- 구조체 안에서 정의한 구조체는 필드로 풀어 본다. 공용체는 통째로 한 자리로 둔다.
- 같은 이름의 구조체가 여러 헤더에 있으면 파일마다 고른다. 순서는 같은 파일, include 하는 헤더, 같은 폴더, 가장 가까운 폴더다. 고르지 못하면 쓰지 않는다.
- 위치나 길이를 확정하지 못한 접근은 구조체의 필드 표를 붙여 sLLM에 맡긴다(요청 파일의 `llm: off`로 끈다).

### 8.2 병렬 배열 → 구조체의 배열

| 항목 | 내용 |
|---|---|
| 묶는 조건 | 같은 함수·같은 블록의 지역 배열, 첫 차원의 크기가 같음, 같은 번호 식으로 쓰임 |
| 바꾸는 것 | 선언을 지역 구조체와 그 배열 하나로. `이름[번호]` → `묶음[번호].이름` |
| 채우는 문장 | 모두 같은 값이면 한 문장으로, 아니면 레코드별 반복문으로. 값이 상수 매크로여도, 호출이 매크로여도 읽는다 |
| 바꾸지 않을 때 | 기계적으로 못 바꾸는 곳이 하나라도 있으면 그 묶음 전체를 두고 사유를 적는다 |

## 9. 병합과 검증, 보장 범위

**결과를 원본과 비교해 "새 문제를 만들지 않았는지"를 본다. 통과는 "컴파일된다"는 뜻이 아니다.**

| 수준 | 검사 | 조건 |
|---|---|---|
| L0 | 괄호 짝, `#if`/`#endif` 균형이 원본과 같은가 | 항상 |
| L1 | 새로 추가된 include를 찾을 수 있는가 | 항상 |
| L2 | 자동 치환 규칙을 다시 돌려 남은 것이 없는가 | 항상 |
| L3 | `cl /Zs`로 원본에 없던 오류가 생기지 않았는가 | 그 PC에 Visual Studio가 있을 때 |

- 불합격이면 그 파일에서 sLLM 수정만 빼고 다시 본다. 그래도 불합격이면 그 파일의 수정을 모두 뺀다.
- 원본이 헤더를 못 열어 컴파일이 멈추면 L3을 "미수행"으로 적는다. 통과로 치지 않는다.
- 병합은 원본의 인코딩, BOM, 줄끝을 그대로 따른다.
- 프로젝트 변환과 전체 빌드는 하지 않는다. 대상 환경에서 사람이 빌드해 확인해야 한다.

## 11. 실행 방법

**처음에는 설치 확인 세 가지를 하고, 본 실행은 작은 범위부터 넓힌다.**

```
vupdate selftest                                   설치 확인(샘플 + 모의 sLLM)
vupdate preflight --package D:\src\PKG_A           환경 점검
vupdate llmcheck                                   실제 sLLM 서버 점검

vupdate run --package D:\src\PKG_A --from-vs 2008 --to-vs 2022
vupdate run ... --compat-llm 3 --max-calls 200     남은 것을 sLLM에. 호출 200회까지
vupdate run ... --ask-file ask.txt --until S5      요청문의 의도와 대상 수만 먼저 본다
vupdate run --resume <실행 폴더>                    대기로 남은 작업을 잇는다
```

| 묶음 | 옵션 |
|---|---|
| 환경값 | `--from-vs`, `--to-vs`, `--platform`, `--cpp-standard`, `--charset`, `--conformance`, `--deprecated`, `--from-os`/`--to-os`, `--from-db`/`--to-db` |
| 요청 | `--ask`, `--ask-file`, `--ask-match`, `--request` |
| 범위 | `--only`, `--exclude`, `--backups`, `--exceptions`, `--disable-rule` |
| sLLM | `--compat-llm`, `--no-llm`, `--llm-endpoint`, `--max-parallel`, `--max-calls` |
| 진행 | `--until`, `--dry-run`, `--resume`, `--out` |
| 컴파일 검사 | `--no-compile`, `--vs-path`, `--sdk-path`, `--compile-parallel` |

- 서버 주소, 모델, 토큰 한도, 동시 수는 `config/server.json`에 둔다.
- PowerShell에서는 `Invoke-VersionUpdate.ps1`이 같은 옵션을 매개변수로 받는다.
- exe는 `tools/make_exe.bat`으로 만든다(PyInstaller가 있는 PC에서 한 번).
- 옵션별 예는 `vupdate examples` 또는 `23_옵션별_사용예시.md`에 있다.

## 12. 실행 폴더와 이어서 실행

**실행 하나가 폴더 하나다. 상태는 `state.db` 하나에 있다.**

| 경로 | 내용 |
|---|---|
| `snapshot/` | 원본의 사본. 이후 단계는 이것만 읽는다 |
| `work/` | 병합 중간 결과 |
| `out/` | 산출물(10절) |
| `logs/` | `run.log`, `llm/`(물음과 답) |
| `state.db` | SQLite. 파일, 함수, include, 이슈, 수정, 작업, 호출, 답 캐시, 검증 |
| `run.json` | 실행 옵션 |

- `--resume`은 끝난 단계를 건너뛰고 남은 작업부터 보낸다. 캐시에 있는 답은 다시 부르지 않는다.
- `vupdate status --run <실행 폴더>`로 진행 상태를 본다.

## 15. 한계와 남은 일

**"이름이나 구문으로 짚을 수 있는 줄을, 그 줄 주변 안에서 고치는 일"까지가 범위다.**

구조적 한계:
- sLLM은 조각 하나만 본다. 조각마다 따로 묻는다.
- 분석은 글자 수준이다. 타입과 자료의 흐름을 따라가지 않는다.
- 새 파일, 프로젝트 파일, 조각 밖의 include를 만들거나 고치지 않는다.
- 검증은 정적 검사와 파일 단위 컴파일까지다. 동작이 같은지는 확인하지 못한다.

요청의 범위(공개 코드에 흔한 요청 12개를 걸어 본 결과):

| 판정 | 수 | 예 |
|---|---|---|
| 됨 | 3 | 함수의 1:1 교체, 호출 뒤 검사 추가, 찾기 |
| 일부 | 6 | 사용 중단 함수 대체, 인자 추가, 타입 바꾸기, 대량 치환, 배열 → 구조체 |
| 안 됨 | 3 | 로직 공통화, 누수 수정, 64비트 포인터 잘림의 수정 |

하지 않는 것:
- 프로젝트 변환과 전체 빌드. `.rc`, `.idl`, `.def`의 규칙 탐지.
- 전문 버퍼를 구조체 변수로 통째로 바꾸기. 파일 범위 배열과 멤버 배열의 묶음.
- 빌드 오류 로그의 되먹임. 링크 오류와 프로젝트 설정 오류의 수정.

확인하지 못한 것:
- 실제 gemma4의 의미 분석과 수정의 품질.
- Windows의 cl을 쓰는 컴파일 검사 경로.
- 나눠 보내는 경로(분할 순차)의 실제 동작.

결정을 기다리는 일:

| 일 | 상태 |
|---|---|
| 넓혀 찾기(`--ask-match`)의 오탐 제외 | 실제 시험 뒤에 진행. 방안은 문서 33 |
| 요청 종류의 확장 | 검토만 함. 문서 34 |
| 의미 분석이 호환성과 구조체 요청을 한 의도로 뭉치는 문제 | 물음에 나누는 예를 넣는 방안. 미착수 |
| 컴파일 검사를 못 했을 때의 종료 코드 | 지금은 바꾸지 않음 |
| 줄 단위 한국어 주석 | 적용하지 않음. 함수와 구획 단위의 목적 주석만 있다 |
