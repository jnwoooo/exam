## 1. 처음 요구의 의도와 구현 상태

처음 요구는 두 가지였다. **환경값은 실행할 때 주는 파라미터**이고, **"배열을 구조체로 바꿔라" 같은 요청문은 사용자가 그때그때 적어 넣는 것**이다(파라미터든 파일을 줄 단위로 읽든 방법은 상관없다).

| 의도 | 구현 | 어느 판 |
|---|---|---|
| 환경값을 실행 파라미터로 | `--from-vs`, `--to-vs`, `--cpp-standard`, `--platform`, `--conformance`, `--charset`, `--deprecated`, `--axis 이름=값`. 자주 쓰는 조합은 프로필 파일(`--profile`)로 묶을 수 있다 | 원본·대상 버전은 0.1.0, 그 밖의 컴파일러 쪽 값은 0.3.0까지, OS·DB·HMI 축은 0.4.0 |
| 환경값이 프롬프트에 들어간다 | 모든 조각의 [환경]에 들어간다 | 0.1.0, 축은 0.4.0 |
| 요청문을 사용자가 적는다 | **0.6.0까지는 의도대로가 아니었다.** 아래 참고 | |
| ├ 공통 요청 | 요청 파일의 `common`. 문장은 자유지만, 다른 이유로 sLLM에 가는 조각에 따라붙기만 했다. 요청문이 처리 대상을 만들지는 못했다 | 0.4.0 |
| ├ 정형 요청 | `array_to_struct`, `struct_change`. 내가 정해 둔 두 유형을 JSON 형식에 맞춰 적어야 했다. 그 밖의 요청은 "처리 대상이 아닌 요청 유형"으로 수동 검토에 갔다 | 0.1.0, 0.5.0, 0.6.0 |
| └ **사용자 요청문** | **`--ask "대상: 요청문"`, `--ask-file`(한 줄에 하나), 요청 파일의 `asks`.** 유형 제한이 없다. 대상 이름이 쓰인 곳을 찾아 요청문을 그대로 지침으로 sLLM에 보낸다 | **0.7.0** |

0.6.0은 정형 요청의 완성도(배열 선언 교체)와 기본값(DB·HMI 규칙)을 넓힌 판이었다. 사용자가 요청문을 자유롭게 적는 길은 0.7.0에서 생겼다.

## 2. 쓰는 방법

```
vupdate run --package D:\src\PKG_A --from-vs 2008 --to-vs 2022 --platform x64 --axis "os=Windows 7->Windows 10" ^
    --ask "g_data: 배열 g_data 를 구조체 G_DATA 로 바꾼다. g_data[IDX_TEMP] 는 g_data.temp 로 쓴다" ^
    --ask "SendPacket: 둘째 인자와 셋째 인자의 순서가 바뀌었다. 호출하는 곳의 인자 순서를 바꾼다"

vupdate run --package D:\src\PKG_A --from-vs 2008 --to-vs 2022 --ask-file config\asks.txt
```

요청문 파일(`config/EXAMPLE_asks.txt`를 복사해 쓴다. UTF-8과 CP949 모두 읽는다):

```
# 한 줄에 요청 하나
g_data: 배열 g_data 를 구조체 G_DATA 로 바꾼다. g_data[IDX_TEMP] 는 g_data.temp, g_data[IDX_COUNT] 는 g_data.count 로 쓴다
@Src/Ipc/* MSG_HEADER: 필드 nLen 의 이름이 nLength 로 바뀌었다. 이 구조체의 멤버 접근만 고친다
SendPacket: 둘째 인자(길이)와 셋째 인자(버퍼)의 순서가 바뀌었다. 호출하는 곳의 인자 순서를 바꾼다
/LOG_(?:ERR|WARN)/: 첫 인자로 모듈 이름 문자열 "HMI" 를 추가한다
주석의 문구는 바꾸지 않는다
```

| 줄의 모양 | 뜻 |
|---|---|
| `대상: 요청문` | 대상 이름이 쓰인 줄을 패키지 전체에서 찾아 요청문대로 고치게 한다 |
| `대상1, 대상2: 요청문` | 대상이 여럿 |
| `/정규식/: 요청문` | 이름 대신 정규식으로 찾는다 |
| `@Src/Net/* 대상: 요청문` | 그 파일들에서만 |
| `*: 요청문` 또는 대상 없는 문장 | 공통 요청. sLLM에 보내는 모든 조각의 지침에 붙는다 |
| `#`으로 시작하는 줄, 빈 줄 | 건너뛴다 |

같은 내용을 요청 파일(JSON)의 `asks`에 적어도 된다(`config/requests/EXAMPLE.json`). 세 방법을 함께 쓰면 합쳐진다.

## 3. 동작

1. 요청마다 대상 이름(또는 정규식)이 쓰인 줄을 찾는다. 주석과 문자열 안은 보지 않는다.
2. 가까운 줄끼리 묶어 조각으로 만든다(다른 sLLM 작업과 같다. 24k 한도, 큰 함수 분할, 동시 호출이 그대로 적용된다).
3. 프롬프트의 [환경]에 환경값, [수정 지침]에 `사용자 요청: <요청문>. 대상은 <이름>이다 ...`, 끝에 공통 요청이 들어간다.
4. 응답의 수정 블록을 검사해 반영한다. 반영한 수정은 모두 검토 대상으로 표시한다.
5. `report.md`의 "변경 계약"에 요청문과 처리 건수가 나온다.

도구가 정하는 것은 **어디를 볼지**까지다. **어떻게 고칠지**는 요청문과 sLLM이 정한다.

## 4. 정형 요청과 요청문 가운데 무엇을 쓸까

| | 정형 요청(`array_to_struct`, `struct_change`) | 사용자 요청문(`--ask`) |
|---|---|---|
| 적는 방법 | JSON에 매핑표 | 문장 한 줄 |
| 고치는 주체 | 규칙(결과가 매번 같다) | sLLM(결과를 검토해야 한다) |
| 다루는 범위 | 정해 둔 두 유형 | 제한 없음 |
| 맞는 경우 | 사용처가 수백 곳이고 대응이 표로 정해지는 변경 | 유형이 정해져 있지 않은 변경, 몇십 곳 이하의 변경 |

같은 대상에 둘을 함께 쓰지 않는다. 정형 요청이 먼저 고치고 요청문은 그 결과를 본 sLLM이 다시 판단하므로, 같은 자리를 두 번 다루게 되어 수동 검토가 늘어난다.

## 5. 한계

- **확인은 흐름까지다.** 모의 sLLM은 정해진 한 가지 수정만 흉내 낸다. "요청문을 읽고, 대상을 찾고, 지침으로 보내고, 응답을 반영한다"는 흐름은 확인했지만, 실제 sLLM이 임의의 요청문을 얼마나 잘 따르는지는 확인하지 못했다. 처음에는 `--only`로 좁은 범위에서 `out\diff`를 본다.
- **한 조각 안에서만 본다.** sLLM은 조각(대상 줄의 앞뒤 25줄)만 본다. 선언과 사용처가 멀리 떨어진 변경은 요청문에 필요한 사실을 다 적어야 한다(예: 새 구조체의 필드 이름).
- **고칠 필요가 없다고 답한 곳은 수동 검토로 간다.** 대상 이름이 나오지만 요청과 관계없는 줄(예: 주석 처리된 선언, 다른 뜻으로 쓴 같은 이름)이 많으면 수동 검토가 늘어난다. 파일 범위(`@`)나 정규식으로 대상을 좁힌다.
- **요청 하나가 다루는 줄은 300곳까지다**(`limits.ask_max_sites`). 넘는 곳은 수동 검토로 간다. 흔한 이름을 대상으로 주면 sLLM 호출이 그만큼 늘어난다.
- 영문 낱말과 콜론으로 시작하는 공통 요청(예: `NOTE: ...`)은 대상으로 읽힌다. 공통 요청은 `*:`로 시작하면 확실하다.

## 7. 0.7.1: Windows SDK 경로 직접 지정

Visual Studio 경로(`--vs-path`)처럼 Windows SDK 경로도 직접 줄 수 있다. SDK를 설치하지 않고 폴더만 복사해 둔 PC, 여러 판 가운데 하나를 골라야 하는 PC에서 쓴다.

```
vupdate preflight --package D:\src\PKG_A --vs-path "C:\Program Files\Microsoft Visual Studio\2022\Professional" --sdk-path "C:\Program Files (x86)\Windows Kits\10"
vupdate run --package D:\src\PKG_A --from-vs 2008 --to-vs 2022 --sdk-path "C:\Program Files (x86)\Windows Kits\10\Include\10.0.19041.0"
```

환경변수로 주는 방법(PowerShell). 옵션을 함께 주면 옵션이 우선한다. 빈 값은 지정하지 않은 것과 같다.

```
$env:VUPDATE_VS_PATH  = "C:\Program Files\Microsoft Visual Studio\2022\Professional"
$env:VUPDATE_SDK_PATH = "C:\Program Files (x86)\Windows Kits\10"
vupdate preflight --package D:\src\PKG_A
```

| `--sdk-path`에 줄 수 있는 폴더 | 쓰는 판 |
|---|---|
| `...\Windows Kits\10` (키트 폴더) | `Include` 아래에서 가장 높은 판 |
| `...\Windows Kits\10\Include` | 위와 같다 |
| `...\Windows Kits\10\Include\10.0.19041.0` (판 폴더) | 그 판 |
| `...\Windows Kits\8.1` | 판 폴더가 없는 키트(`Include\um`, `shared`) |
| `...\Microsoft SDKs\Windows\v7.1A` | 구 SDK(`Include\windows.h`) |

**동작**
- 지정한 SDK의 헤더 폴더(`ucrt`, `shared`, `um`, `winrt`)를 컴파일 검사(`cl /Zs`)의 INCLUDE 맨 앞에 넣는다. Visual Studio가 고른 SDK보다 먼저 잡힌다.
- `preflight.md`의 "4.2 Windows SDK" 줄에 지정한 경로, 판, 헤더 폴더 수가 나온다. `logs/run.log`에는 `지정한 Windows SDK 경로를 씁니다`가 남는다.
- 헤더를 찾지 못하는 경로를 주면 경고하고 자동 탐지 결과를 쓴다.
- PowerShell 스크립트는 `-SdkPath`다.
- 환경변수 이름을 `VUPDATE_SKD_PATH`로 잘못 적어도 값을 받아 주고 경고한다. 바른 이름은 `VUPDATE_SDK_PATH`다.

**한계**
- 이 도구의 컴파일 검사는 문법 검사(`/Zs`)라서 헤더 경로만 쓴다. SDK의 라이브러리 경로(LIB)는 건드리지 않는다. 실제 빌드에 쓰는 SDK는 프로젝트 설정(`WindowsTargetPlatformVersion`)에서 따로 정한다.
- 경로 해석과 INCLUDE에 넣는 것까지는 가짜 SDK 폴더로 확인했다(`tests/test_v071.py` 17항목). 실제 컴파일러가 그 헤더로 검사하는 것은 Windows에서 확인해야 한다. `vupdate preflight`의 "4.4 컴파일러 동작 확인"이 정상인지 본다.
- `--vs-path`는 VS2017 이후의 폴더 구조(`VC\Tools\MSVC\...`)만 알아본다.
