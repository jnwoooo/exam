## 1. 결론

- **결함의 대부분은 모델의 답이 아니라 도구가 모델에 준 지침과 도구의 검사에서 나왔다.** 지침이 "보안 CRT 함수로 바꾼다. 배열이면 `sizeof`를 크기로 넣는다"고 시켰고, 모델은 대체로 시킨 대로 했다. 그 변환은 고정 길이 전문 필드에서는 어떻게 써도 원래 동작과 같아질 수 없다.
- **모델의 잘못이라고 볼 것은 두 가지다.** 없는 함수 이름(`_strncat_s`)을 쓴 것, 옛 복사 길이를 버퍼 크기로 넣고 `_TRUNCATE`를 고른 것.
- **코드 문제는 세 가지다.** 수용 검사가 이 수정들을 하나도 기각하지 못했다. 컴파일 검사가 헤더 오류로 막혔는데 통과로 기록했다. 동작이 달라지는 수정을 "고침, 수동 검토 0건"으로 보고했다.
- 이 변환은 빌드에 필요하지 않다. 도구가 이미 `_CRT_SECURE_NO_WARNINGS`를 설정으로 넣으므로 옛 함수 그대로 VS2022에서 컴파일된다. **당장은 `--compat-llm`을 빼고 돌리면 이 결함들이 생기지 않는다.** 같은 예제를 그렇게 돌려 모델 호출 0회, 수정 0건, 파일 변경 없음을 확인했다. 3.3의 요청문 경로였다면 요청문에서 호환성 문장도 뺀다. 규칙으로 하는 기계적 변경은 그대로 된다.

|---|---|---|---|
| 1 | 출력·복사 공간 부족(`sprintf_s`, `strncpy_s`의 ERANGE) | 프롬프트(지침) | 코드(수용 검사) |
| 2 | 전문 안에 NUL이 더 기록돼 다음 필드의 첫 바이트가 바뀜 | 프롬프트(지침) | 모델 |

## 2. 전달받은 결함 정리

| # | 결함 | 전달받은 내용 |
|---|---|---|
| 1 | 공간 부족 | `sprintf_s`와 `strncpy_s`에서 ERANGE를 재현했다 |
| 2 | 추가 NUL | 옛 고정 길이 복사는 지정한 바이트만 썼는데 바뀐 함수는 뒤에 NUL을 붙인다. posrip에서 응답 코드 뒤 길이 필드의 첫 바이트가 바뀌었다 |
| 3 | 잘림 | `.DAT`가 `.DA`로, `PA007`이 `PA00`으로 잘렸다. 옛 복사 길이를 `_TRUNCATE`를 쓰는 함수의 버퍼 용량으로 그대로 넣었다 |
| 4 | Debug 패딩 | Debug에서 전송되는 전문의 패딩 바이트가 달라졌다. Debug 보안 CRT의 버퍼 채움이 원인으로 보인다 |
| 5 | 없는 함수 | `strncat`를 `_strncat_s`로 바꿨다. 그런 선언은 CRT에도 패키지에도 없다. VS2022에서 C3861 |
| 6 | 필드를 문자열로 취급 | `char[1]` 필드에 `"1"`을 문자열로 쓰려면 2바이트, `%06d`를 `char[6]`에 쓰려면 7바이트가 필요하다. 배열의 실제 크기를 넣는 것과 그 배열이 문자열 저장 공간인지 확인하는 것을 구분하지 않았다 |
| 7 | 파일 공유 | `fopen_s`로 바꾼 곳에서, 추가 쓰기 모드일 때 되던 동시 읽기와 읽기 모드일 때 되던 동시 쓰기가 막혔다 |
| 8 | 검증 | 헤더 오류로 검사가 막혔는데 도구가 "새 진단이 늘지 않았다"며 통과로 처리했다 |

배열 → 구조체 요청에서 나온 결함은 목록에 없었다. 그쪽 결과는 보고서의 "변경 계약" 절에서 따로 확인해야 한다.

## 3. 원인: 도구가 모델에 보낸 것

### 3.1 지침의 원문

`--compat-llm`을 켜면 보안 CRT 경고 규칙(`R-T0-CRT-SECURE`)에 걸린 줄을 모두 "수정 대상 줄"로 찍어 보내고, 다음 지침을 붙인다.

> 이 함수를 보안 CRT 함수로 바꾼다(strcpy -> strcpy_s, sprintf -> sprintf_s, _itoa -> _itoa_s, fopen -> fopen_s 등). 버퍼 크기 인자가 필요하다. 대상 버퍼가 이 조각이나 [참고: 선언]에서 배열로 확인될 때만 _countof(이름)이나 sizeof(이름)을 크기로 넣는다. 포인터이거나 크기를 알 수 없으면 그 줄은 고치지 않는다. (뒤 생략)

이 지침에서 결함으로 이어진 점.

| 지침의 문제 | 이어진 결함 |
|---|---|
| "배열이면 `sizeof`를 크기로 넣는다"만 조건이다. 그 배열이 NUL로 끝나는 문자열을 담는 곳인지는 묻지 않는다 | 1, 6 |
| 대상 줄에 `strncpy`, `strncat`가 들어 있다. 길이를 정해 복사하는 옛 코드는 NUL을 붙이지 않는 동작에 기대는 경우가 많다 | 2, 3, 4 |
| `fopen -> fopen_s`를 예로 들어 바꾸라고 한다. 공유 방식이 달라진다는 말이 없다 | 7 |
| 함수 대응을 네 개만 예로 들고 "등"으로 끝낸다. `strncat`의 새 이름은 모델이 지어내야 한다. 예에 `_itoa_s`처럼 밑줄로 시작하는 이름이 섞여 있다 | 5 |
| 고치지 않아도 되는 조건이 "포인터이거나 크기를 모를 때"뿐이다. 대상 줄로 찍혀 오므로 모델은 고치는 쪽으로 기운다 | 전부 |

### 3.2 옛 함수와 보안 함수의 동작 차이(Microsoft 문서)

| 함수 | 옛 함수 | 보안 함수 | 관련 결함 |
|---|---|---|---|
| `strncpy` → `strncpy_s` | 원본이 길이 이상이면 NUL을 붙이지 않는다. 원본이 짧으면 남는 자리를 길이까지 NUL로 채운다 | 항상 NUL을 붙인다. 글자와 NUL이 들어갈 자리가 없으면 대상의 첫 바이트를 0으로 만들고 잘못된 매개변수 처리기를 부른다(계속 실행되면 ERANGE). 남는 자리를 채우지 않는다 | 1, 2 |
| `_TRUNCATE` | - | NUL 자리를 남기고 들어가는 만큼만 복사한다. 5바이트 버퍼면 4글자다 | 3 |
| Debug 라이브러리 | - | 이 함수들의 Debug 판은 먼저 버퍼를 0xFE로 채운다 | 4 |
| `sprintf` → `sprintf_s` | 크기를 보지 않는다 | 출력과 NUL이 크기를 넘으면 버퍼를 빈 문자열로 만들고 잘못된 매개변수 처리기를 부른다 | 1, 6 |
| `strncat` → `strncat_s` | - | 이름은 `strncat_s`다. 문서의 함수 목록에 `_strncat_s`는 없다 | 5 |
| `fopen` → `fopen_s` | - | 공유로 열 수 없다. 공유가 필요하면 `_fsopen`에 `_SH_DENYNO` 같은 공유 상수를 준다 | 7 |

`strncpy_s` 문서의 예제에는 NUL 종료를 원하지 않는 자리라서 `strncpy_s`를 쓸 수 없다는 주석이 있다. 고정 길이 필드에 쓰는 `strncpy`가 바로 그 경우다. 즉 **결함 1~4, 6은 모델이 인자를 잘못 골라서가 아니라, 그 줄에는 동작이 같은 `_s` 꼴이 없어서 생긴다.** 크기를 필드 크기로 주면 ERANGE(1), 필드보다 크게 주면 다음 필드에 NUL(2), `_TRUNCATE`를 쓰면 마지막 글자가 잘린다(3).

### 3.3 어느 경로였는지 확인하는 법

같은 수정이 나올 수 있는 경로가 둘이다. 실행 폴더의 `logs/llm/`에서 수정 요청 하나를 열어 [수정 지침]의 첫머리를 보면 알 수 있다.

- `[L-CRT-SECURE]`로 시작하면 `--compat-llm` 경로다. 3.1의 지침이 그대로 갔다.
- `[ASK-1-n]`으로 시작하면 요청문 경로다. 모델이 "환경 호환성 변경"을 일반 수정 의도로 나눈 경우이고, 이때는 3.1의 조건조차 없이 요청 문장만 갔다.

어느 쪽이든 아래의 원인 구분과 제안은 같다.

## 4. 도구에서 재현한 결과

전달받은 결함과 같은 꼴의 수정 8건을 모의 모델의 답으로 넣어 0.9.1을 돌렸다. "모델이 실제로 이렇게 답하는가"가 아니라 "이렇게 답했을 때 도구가 받아들이는가"를 본 것이다.

넣은 수정.

```c
strncpy_s(m->tc, 5, tc, _TRUNCATE);                 /* 잘림 */
strncpy_s(buf + 5, 3, rsp, 2);                      /* 다음 필드 첫 바이트에 NUL */
sprintf_s(m->flag, sizeof(m->flag), "%d", ok);      /* char[1] */
sprintf_s(m->seq, sizeof(m->seq), "%06d", seq);     /* char[6] 에 6자리 */
strncpy_s(m->file, sizeof(m->file), name, 12);      /* 12자 이름이면 ERANGE */
strcpy_s(path, sizeof(path), "D:\\MES\\");          /* 문제없는 수정 */
_strncat_s(path, sizeof(path), name, 12);           /* 없는 함수 */
fopen_s(&fp, path, "a");                            /* 공유 방식 변화 */
```

| 조건 | 결과 |
|---|---|
| A. 컴파일 검사 없음 | **8건 모두 수용, 검증 L2 통과, 종료 코드 0, 수동 검토 0건.** `_strncat_s`에만 "조각과 패키지에 없던 이름" 메모가 붙었다 |
| B. 컴파일 검사 있음, 소스에 열 수 없는 헤더가 있음 | **8건 모두 수용, "L3 통과: 오류 1건 -> 1건(새로 생긴 오류 없음)", 검증 수준 L3로 기록.** 전달받은 결함 8과 같다 |
| C. 컴파일 검사 있음, 헤더 문제 없음 | `_strncat_s`의 C3861로 불합격. 그 파일의 sLLM 수정 8건을 모두 취소했다. 문제없는 `strcpy_s` 수정도 함께 취소됐다 |

재현에 쓴 스크립트는 작업 폴더의 `repro_realdef.py`다(묶음에는 넣지 않았다).

## 5. 결함별 원인

### 5.1 프롬프트(지침) 문제

- **결함 1, 6**: 지침이 "배열이면 `sizeof`"만 조건으로 삼았다. `sprintf_s(m->seq, sizeof(m->seq), "%06d", seq)`는 지침을 글자 그대로 따른 답이다. 모델이 완벽했어도 같은 결과가 나온다.
- **결함 2, 4**: `strncpy`가 쓰인 줄을 대상으로 보낸 것 자체가 문제다. 3.2에 적은 대로 동작이 같은 `_s` 꼴이 없다. Debug의 0xFE 채움도 `_s` 함수의 고유한 동작이다.
  - 알아 둘 것: Release에서도 `strncpy_s`는 남는 자리를 NUL로 채우지 않는다. 버퍼를 미리 지우지 않는 코드라면 Release의 패딩도 달라질 수 있다. 전달받은 목록에는 Debug만 있었으므로 확인이 필요하다.
- **결함 7**: 지침이 `fopen -> fopen_s`를 예로 들었다. 모델은 시킨 대로 했다.

### 5.2 모델의 답 문제

- **결함 5**: `_strncat_s`는 없는 이름이다. 지침에 대응표가 없었던 것이 계기지만, 없는 이름을 만든 것은 모델이다.
- **결함 3**: `_TRUNCATE`는 지침에 없다. 모델이 고른 것이고, 옛 복사 길이를 버퍼 크기 자리에 넣었다. 다만 3.2대로 이 줄에는 맞는 답이 없었으므로, 맞는 답은 NO_CHANGE였다.

### 5.3 코드 문제

| 위치 | 문제 | 관련 결함 |
|---|---|---|
| 수용 검사 `size_arg_check` | 새로 쓴 `sizeof(이름)`의 이름이 포인터인지만 본다. `sizeof(m->seq)`처럼 멤버를 가리키면 검사하지 않는다. 숫자 상수나 `_TRUNCATE`로 준 크기, 형식 문자열의 출력 길이는 보지 않는다 | 1, 3, 6 |
| 수용 검사 `new_name_check` | 기본값이 `mark`여서 없던 이름을 메모만 하고 받아들인다 | 5 |
| 대상 선정 `_compat_sites` | 규칙에 걸린 줄을 가리지 않고 모두 보낸다. 구조체 멤버에 쓰는 줄, `버퍼 + 위치`에 쓰는 줄, `strncpy`, `fopen`을 걸러내지 않는다 | 1~4, 6, 7 |
| 검증 `_compile_run` | 수정 전과 후의 오류 목록을 비교해 늘지 않으면 통과로 본다. 치명적 오류(C1083 등)로 컴파일이 중단되면 두 목록이 똑같이 그 한 건이 되어 통과가 된다. 바뀐 줄은 컴파일러가 보지도 않았다 | 8, 5 |
| 검증 `s8_verify` | 파일에서 한 수정이 불합격이면 그 파일의 sLLM 수정을 모두 뺀다(재현 C에서 확인) | - |
| 보고 | 동작이 달라질 수 있는 수정을 "고침"으로 세고 종료 코드 0을 낸다. 보고서에 "모두 검토 대상"이라는 문장은 있지만 건수와 종료 코드에는 반영되지 않는다 | 전부 |

## 6. 제안 방향

수정은 하지 않았다. 방향을 정해 주면 진행한다.

### 6.1 먼저 정할 것: 보안 CRT 변환을 "환경 호환성"에 둘 것인가

`--compat-llm`(기본 꺼짐)을 켜면 두 묶음이 sLLM에 간다. 규칙이 직접 고치는 변경(이름 치환 등 10개 규칙)은 이 옵션과 무관하게 늘 규칙이 하고 sLLM에 가지 않는다.

| 묶음 | 무엇 | 끄면 | 켜면 |
|---|---|---|---|
| ㄱ. 규칙이 찾기만 하고 못 고치는 것 | 새 환경에서 컴파일 오류가 나는 5개 규칙: 없어진 `gets`, x64의 `SetWindowLong`, `stdint` 타입·`timespec`·`char16_t`의 자체 정의 | 수동 검토 목록에 올린다 | 그 줄을 sLLM에 보낸다 |
| ㄴ. 설정으로 이미 해결한 것 | 2개 규칙: 보안 CRT 경고(`_CRT_SECURE_NO_WARNINGS`), 사용 중단된 Winsock 함수(`_WINSOCK_DEPRECATED_NO_WARNINGS`) | 설정 안내만 낸다. 코드는 그대로다 | 설정은 그대로 넣고, 사용 줄을 sLLM에 보내 코드도 고치게 한다 |

전달받은 결함 1~7은 모두 ㄴ의 보안 CRT에서 나왔다. ㄱ은 고치지 않으면 빌드가 안 되는 것이고, ㄴ은 설정만으로 빌드가 되는데 코드까지 고쳐 보는 것이다. ㄴ은 빌드에 필요하지 않고 동작을 바꾼다. 제안은 **`--compat-llm`에서 ㄴ을 빼는 것**이다. 옵션과 ㄱ은 그대로 둔다.

| 안 | 내용 | 평가 |
|---|---|---|
| 가(권장) | `--compat-llm`은 ㄱ만 보낸다. ㄴ(보안 CRT, Winsock)은 끈 때와 같이 설정으로만 처리한다 | 전달받은 결함 1~7이 생기지 않는다. 판 올림의 목적(같은 동작으로 새 환경에서 빌드)에 맞다 |
| 나 | ㄴ을 별도 옵션으로 떼어 남기되, 도구가 정한 좁은 조건에서만 보낸다(6.2) | 원하는 사람만 쓴다. 조건을 통과하는 줄이 적을 것이다 |
| 다 | 지침 문구만 고친다 | 권하지 않는다. 작은 모델에게 "고정 길이 필드인지 판단하라"를 맡기는 것이어서 같은 결함이 줄 뿐 없어지지 않는다 |

Winsock 줄은 이번 결함 목록에 없었다. 다만 그 지침에 적혀 있듯이 새 함수는 인자와 반환값의 꼴이 달라 보안 CRT와 같은 성격이다. 그래서 같은 묶음으로 다룬다.

### 6.2 "나"를 택할 때의 조건(모델이 아니라 도구가 판정)

- 보내지 않는 줄: `strncpy`, `strncat`, `fopen`, 대상이 구조체 멤버(`a->b`, `a.b`)인 줄, 대상이 `버퍼 + 위치`나 `&버퍼[위치]`인 줄, 반환값을 쓰는 줄
- 보내는 줄: 대상이 같은 함수에서 선언된 지역 `char` 배열이고 호출이 `strcpy`, `strcat`, `sprintf`인 줄
- `sprintf`는 형식 문자열에서 계산되는 최소 출력 길이 + 1이 배열 크기를 넘으면 보내지 않는다(`%06d`는 6)
- 새 함수 이름은 도구의 대응표에 있는 것만 받는다(`strcpy` → `strcpy_s` 등). 그 밖의 이름이면 기각한다
- 크기 인자는 `sizeof(그 지역 배열)`이나 `_countof(그 지역 배열)`만 받는다. 숫자 상수, `_TRUNCATE`, 멤버의 `sizeof`는 기각한다

### 6.3 안과 무관하게 고칠 것(코드)

1. **컴파일 검사가 막힌 경우를 통과로 치지 않는다.** 수정 전이나 후의 결과에 치명적 오류가 있으면 그 파일의 L3는 "미수행(헤더 오류로 막힘)"으로 기록하고 검증 수준은 L2로 둔다. 보고서 첫머리에 막힌 파일 수와 필요한 조치(include 경로)를 적는다.
2. **없는 이름을 기각한다.** 환경 호환성 작업은 새 이름 검사를 기각으로 돌린다. 밑줄로 시작하고 `_s`로 끝나는데 알려진 CRT 이름이 아닌 것은 어떤 작업에서든 기각한다.
3. **동작이 달라지는 수정은 "고침"으로 세지 않는다.** 따로 "검토 필요"로 세고, 한 건이라도 있으면 종료 코드 1을 낸다.
4. **불합격을 수정 단위로 뺀다.** 컴파일 오류가 난 줄에 걸친 수정만 빼고 다시 검사한다. 지금은 파일의 sLLM 수정을 모두 뺀다.
5. `sizeof`의 인자가 멤버 접근일 때도 선언을 찾아 검사한다.

### 6.4 요청문 경로의 보호

3.3의 두 번째 경로(요청문이 일반 수정 의도로 나뉜 경우)에도 같은 일이 생길 수 있다. 수정 결과에 보안 CRT 함수 호출이 새로 생기면 6.2의 조건과 6.3의 검사를 작업 종류와 무관하게 적용하는 쪽이 맞다.
