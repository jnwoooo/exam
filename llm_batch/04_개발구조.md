### 0.1 v3에서 바뀐 것(코드 0.2.0)

- 한 번에 보낼 수 없는 구간을 나눠 순서대로 처리하는 분할 순차를 구현했다. 설계는 `05_기능정의.md` 8절에 있다.
- 요청사항(배열 → 구조체)의 변수 인덱스 접근을, 요청에서 켜면 sLLM에 맡길 수 있게 했다. 기본은 수동 검토다.
- 자체 시험이 22항목에서 27항목으로 늘었다.
- sLLM 호출은 아직 설정의 주소로 직접 한다. MCP 서버 경유로 바꾸는 일은 남아 있다(`05_기능정의.md` 10절).

### 0.2 v4에서 바뀐 것(코드 0.3.0)

- **토큰 한도.** 서버가 한도 초과로 거절한 요청을 그대로 다시 보내던 결함을 고쳤다. 서버가 알려 준 한도와 실제 토큰 수를 반영해 더 작게 다시 계획한다. 응답에 담긴 실제 입력 토큰 수로 추정식을 보정한다. 응답이 출력 상한에서 잘린 경우와 과부하 응답도 따로 다룬다(5.3).
- **실행 옵션.** 환경값(`--platform` 등), 처리 범위(`--only`, `--exclude`), 단계 건너뛰기(`--no-llm`, `--no-chunk`), 호출자(`--caller`), PC별 값(`--vs-path`, `--compile-parallel`)을 더했다. sLLM 주소와 Visual Studio 경로는 환경변수로도 받는다(3절).
- **규칙의 버전 구간.** 규칙마다 "문제가 생긴 VS 연도"를 두고, 원본 < 그 연도 ≤ 대상일 때만 켠다. `vupdate rules --from-vs 2015 --to-vs 2022`로 켜지는 규칙과 꺼진 이유를 볼 수 있다(10절, 13절).
- **컴파일 검사 병렬화.** 0.2.0까지는 한 파일씩 순서대로 돌았다. 설정값 `compile_parallel`은 있었지만 쓰이지 않았다. 0.3.0에서 실제로 병렬로 돌린다.
- 토크나이저 주소를 직접 부르던 경로(`llm.tokenize_endpoint`)를 없앴다. `05_기능정의.md`의 결정대로다.
- 자체 시험이 27항목에서 36항목으로 늘었다. 개발용 시험 2개(`test_limits.py`, `test_compile.py`)를 더했다.
- sLLM 호출은 아직 설정의 주소로 직접 한다(`05_기능정의.md` 10절).

## 1. 단일 파일로 가능한가

**가능하다.** 최초 개발본을 실제로 파일 하나로 만들었다.

| 항목 | 값 |
|---|---|
| 파일 | `vupdate.py` 1개, 약 4,040줄 |
| 외부 패키지 | 0개(표준 라이브러리만) |
| 구획 | 21개. 가장 큰 구획(S6)이 약 800줄 |
| exe 묶기 | PyInstaller `--onefile`로 묶어 자체 시험 통과(리눅스에서 확인) |

**얻는 것**
- 배포 파일이 하나다. 폐쇄망 PC에 Python이나 패키지를 설치하지 않아도 된다.
- 구획마다 목적·산출·한계를 머리 주석으로 적어, AI에 구획 단위로 수정을 맡길 수 있다.

**치르는 값**
- 구문 분석을 자체 구현(괄호 짝)으로 대체했다. 매크로가 문법을 바꾸는 파일에서는 함수 경계를 못 잡는다. 이런 파일은 표시해 두고 줄 단위로 처리한다.
- ripgrep 대신 파이썬 정규식을 쓴다. 162만 자 파일도 1초 안에 처리했지만, 파일 수가 매우 많은 패키지에서는 느릴 수 있다.
- 파일이 길어 통째로는 24k 한도의 모델에 넣을 수 없다. 수정은 구획 단위로 한다(15절).

**나눠야 할 때.** 전체가 3,500줄을 넘거나 한 구획이 500줄을 넘으면 그 구획을 별도 파일로 떼는 것을 검토한다. PyInstaller는 여러 파일도 exe 하나로 묶으므로 배포 형태는 달라지지 않는다.

0.3.0에서 전체가 약 4,040줄, S6이 약 800줄, M11이 약 670줄(그중 자체 시험이 약 380줄)이 되어 이 기준을 모두 넘었다. 이번 판에서는 나누지 않고, S6의 머리 주석에 함수를 읽는 순서(조각 만들기, 분할, 호출과 판정)를 적어 두었다. 다음 판에서 자체 시험을 별도 파일로 떼는 것부터 검토한다.

## 2. 배포 구성(폐쇄망)

```
vupdate.exe                  필수. 이것만 있어도 실행된다
Invoke-VersionUpdate.ps1     선택. PowerShell에서 한 명령으로 부를 때
config/                      선택. 없으면 내장 기본값을 쓴다
  server.json                sLLM 주소(환경변수로도 줄 수 있다), 토큰 한도, 허용 동시 수
  profiles/*.json            환경값 프로필
  requests/*.json            패키지별 요청사항
  rules.json                 추가 규칙
  prompts/system.txt         프롬프트 교체용
  prompts/user.txt
runs/                        실행하면 생긴다
```

**exe 만들기**
1. 인터넷이 되는 Windows PC에 Python 3.8 이상을 설치한다.
2. `pip install pyinstaller`
3. `pyinstaller --onefile --name vupdate vupdate.py`
4. `dist\vupdate.exe`를 폐쇄망으로 옮긴다.
5. 옮긴 PC에서 `vupdate.exe selftest`로 동작을 확인한다.

주의할 점:
- exe는 만든 운영체제용이다. Windows용 exe는 Windows에서 만들어야 한다.
- PyInstaller로 만든 exe를 백신이 오탐하는 경우가 있다. 반입 전에 보안 정책을 확인한다.
- Python을 설치할 수 있는 PC라면 exe 없이 `python vupdate.py ...`로도 똑같이 실행된다.

## 3. 실행 방법

```
vupdate run --package D:\src\PKG_A --from-vs 2008 --to-vs 2022
vupdate run --package D:\src\PKG_A --profile vs2008_to_vs2022 --request PKG_A
vupdate run --package D:\src\PKG_A --from-vs 2008 --to-vs 2022 --dry-run
vupdate run --package D:\src\PKG_A --from-vs 2015 --to-vs 2022 --platform x64 --only Src/Net/* --no-llm
vupdate run --resume D:\work\runs\PKG_A\20261124_101500
vupdate preflight --package D:\src\PKG_A
vupdate status --run D:\work\runs\PKG_A\20261124_101500
vupdate rules
vupdate rules --from-vs 2015 --to-vs 2022
vupdate selftest
```

PowerShell에서는 다음과 같다.

```powershell
.\Invoke-VersionUpdate.ps1 -Package D:\src\PKG_A -FromVs 2008 -ToVs 2022
```

| 명령 | 하는 일 |
|---|---|
| `run` | 패키지 하나를 S0~S9까지 처리 |
| `preflight` | 환경 점검만 수행(S0, S1). `03_확인사항.md`의 점검을 자동으로 한다 |
| `status` | 실행 폴더의 진행 상태 조회 |
| `rules` | 규칙 목록과 켜지는 조건 출력. `--from-vs`, `--to-vs`(또는 `--profile`)를 주면 그 환경값에서 켜지는지와 꺼진 이유도 보여 준다 |
| `selftest` | 샘플 패키지와 모의 sLLM으로 전 단계를 돌려 설치를 확인 |

| `run`의 인자 | 뜻 |
|---|---|
| `--package` | 대상 패키지 폴더 |
| `--from-vs`, `--to-vs` | 원본과 대상의 VS 제품 연도. 프로필 없이 쓸 때 |
| `--profile` | 환경값 프로필. 파일 경로 또는 `config/profiles`의 이름 |
| `--cpp-standard` | C++ 언어 표준. 생략하면 c++14 |
| `--platform` | 대상 플랫폼(keep, x86, x64). x64면 64비트 규칙이 켜지고 컴파일 검사도 x64용으로 한다 |
| `--conformance` | 준수 모드 `/permissive-`(off, on) |
| `--charset` | 문자셋(keep, mbcs, unicode) |
| `--deprecated` | 사용 중단 경고 처리. suppress(설정으로 끈다) 또는 fix(코드를 고친다) |
| `--request` | 요청사항. 파일 경로 또는 `config/requests`의 이름 |
| `--only`, `--exclude` | 처리할 파일 범위. 패키지 기준 경로에 대는 와일드카드. 여러 번 주거나 쉼표로 잇는다. 폴더나 파일 이름만 줘도 된다 |
| `--llm-endpoint` | sLLM 주소. 없으면 환경변수 `VUPDATE_LLM_ENDPOINT`, 그다음 서버 설정의 값 |
| `--max-parallel` | sLLM 동시 요청 수. 서버 설정의 허용 동시 수(`llm.max_parallel`) 이하로만 적용된다 |
| `--caller` | 호출자 표시. 기본은 PC 이름\\계정. 요청 머리말(`X-Vupdate-Caller`)과 보고서에 실린다 |
| `--out` | 실행 폴더를 만들 위치. 생략하면 `.\runs` |
| `--dry-run` | 탐지까지만(S0~S2) 수행하고 보고 |
| `--until` | 지정한 단계까지만 수행(예: `S4`) |
| `--resume` | 중단된 실행 폴더를 이어서 수행 |
| `--no-compile` | 컴파일 검사를 하지 않음 |
| `--no-llm` | sLLM 단계를 건너뛴다. 규칙 수정만 하고 sLLM 대상 이슈는 수동 검토로 보낸다 |
| `--no-chunk` | 분할 순차를 끈다. 토큰 한도를 넘는 구간은 수동 검토로 보낸다 |
| `--compile-parallel` | 컴파일 검사 동시 수. 0이면 CPU 수에 맞춘다(기본) |
| `--vs-path` | Visual Studio 설치 폴더(또는 그 안의 VsDevCmd.bat)를 직접 지정. 자동 탐지가 틀릴 때 쓴다 |

값이 여러 곳에 있을 때의 우선순위는 명령줄 > 환경변수 > (이어서 실행할 때) 처음 실행의 값 > 설정 파일 > 내장 기본값이다. `--platform` 같은 환경값은 프로필보다 명령줄이 우선한다.

| 환경변수 | 뜻 |
|---|---|
| `VUPDATE_LLM_ENDPOINT` | sLLM(또는 중계 서버) 주소. exe나 .ps1에 주소를 적어 배포하지 않기 위한 것이다 |
| `VUPDATE_VS_PATH` | Visual Studio 설치 폴더 |

이어서 실행할 때(`--resume`)는 처음 실행의 옵션(`run.json`의 `opts`)을 그대로 쓴다. 처리 범위와 호출자는 중간에 바꿀 수 없다.

`--only`, `--exclude`로 범위를 좁히면 범위 밖 파일은 탐지와 수정을 하지 않는다(매니페스트의 상태는 범위제외). 스냅샷과 include 조사는 그대로 한다. 헤더만 고치고 그 헤더를 쓰는 범위 밖 파일은 그대로 두는 식의 어긋남은 확인하지 않는다.

| 종료 코드 | 뜻 |
|---|---|
| 0 | 완료. 수동 검토 항목 없음 |
| 1 | 완료. 수동 검토 항목 있음 |
| 2 | 단계 실패로 중단. `--resume`으로 이어서 실행 가능 |
| 3 | 입력 오류(경로, 프로필, 버전 값) |

버전 값은 축별로 형식을 검사한다. `--to-vs 13`이나 `--cpp-standard 14`처럼 어느 체계인지 알 수 없는 값은 종료 코드 3으로 거부하고, 사용할 수 있는 값을 알려 준다.

**구획 사이의 약속**
- 단계 함수는 `ctx` 하나만 받는다. 자료는 저장소(`ctx.store`)의 테이블로 주고받는다.
- 파일 본문의 위치 값은 모두 "작업 본문" 기준이다. 줄끝이 전부 CRLF인 파일은 LF로 바꿔 작업하고, 쓸 때 되돌린다.
- 규칙·요청사항 수정은 스냅샷 본문 기준, sLLM 수정은 규칙 수정을 반영한 본문 기준의 위치를 쓴다.

### 5.3 S6의 내부 흐름

```
T3 이슈(sLLM 대상)
  → [한도]  서버의 모델 목록에서 토큰 한도를 받는다(주면). 설정값보다 작으면 서버 값을 쓴다
  → [계획]  파일별로 모으고, 30줄 안의 이슈는 한 작업으로 묶는다
  → [조각]  이슈 앞뒤 25줄. 큰 초기화 목록은 /*@@ELIDED ... @@*/ 표식으로 바꾼다
            토큰이 한도를 넘으면 앞뒤 줄 수를 줄인다(25 → 12 → 5 → 0)
            그래도 넘거나 예상 응답이 출력 상한을 넘으면 문장 경계에서 나눈다(분할 순차)
  → [확인]  첫 차례에는 가장 큰 조각 1건만 보내 실제 토큰 수를 확인한다
            보내기 직전마다 크기를 다시 본다(보정값이 바뀌었거나 정의 보강으로 커졌을 수 있다)
  → [호출]  동시 요청 수만큼 병렬. 같은 입력은 저장된 응답을 재사용
            분할 조각은 한 구간 안에서 한 번에 하나씩, 앞 조각에서 바꾼 내용을 붙여서
  → [보정]  응답에 담긴 실제 입력 토큰 수로 추정식을 맞춘다(실제 = 비율 × 추정 + 고정분)
  → [응답]  수정 블록(SEARCH/REPLACE) | NO_CHANGE | NEED_CONTEXT: 심볼
  → [검사]  형식 / 원문에 한 번만 일치 / 대상 줄 근처 / 표식 미포함 / 인코딩 / 괄호 짝
            통과 → 수정 레코드
            기각 → 사유를 붙여 재요청(기본 2회) → 넘으면 수동 검토
```

토큰 한도에 걸린 작업은 같은 요청을 다시 보내지 않고 더 작게 다시 계획한다(`_replan`).

| 걸리는 경우 | 다시 계획하는 방법 |
|---|---|
| 보내기 직전 확인에서 한도 초과 | 주변 줄을 줄인다. 안 되면 문장 경계에서 나눈다 |
| 서버가 한도 초과로 거절 | 서버가 알려 준 한도와 실제 토큰 수를 반영한 뒤 위와 같이 |
| 응답이 출력 상한에서 잘림 | 수정 지점을 절반씩 나눈다. 수정 지점이 하나뿐이면 수동 검토 |
| 분할 순차 도중에 걸림 | 끝난 앞 조각은 그대로 두고, 걸린 조각부터 남은 부분만 다시 나눈다 |

- 작업 하나에 다시 계획은 2회까지다. 그래도 안 되면 수동 검토로 보낸다. 분할 구간이면 그 구간의 수정을 모두 취소한다.
- 다시 계획된 옛 작업은 tasks 표에 `replanned` 상태로 남는다.
- 과부하 응답(429, 503)은 그 요청만 기다렸다 다시 보낸다(기본 5회).
- 한도와 무관한 요청 거절(400, 401, 403)은 다시 보내지 않고 수동 검토로 보낸다.
- `NEED_CONTEXT`가 오면 함수 목록과 소스에서 정의를 찾아 붙이고 다시 요청한다(기본 2회까지). 실패 횟수로 세지 않는다.
- `NO_CHANGE`는 그대로 받아들이지 않고 수동 검토로 보낸다. 규칙이 탐지한 것을 sLLM이 고칠 필요 없다고 한 경우이므로 사람이 봐야 한다.
- 서버 호출이 한 번도 성공하지 못한 채 3회 실패하면 남은 작업을 수동 검토로 보내고 단계를 끝낸다. 전체 실행은 계속된다.

토큰 한도를 다루는 방식의 배경과 확인 결과는 `06_충족점검.md` 6절에 있다.

### 5.4 S8의 되돌림 순서

불합격이면 다음 순서로 수정을 빼고 다시 병합해 재검증한다.

1. sLLM 수정을 뺀다.
2. 요청사항 수정을 뺀다.
3. 그 파일의 수정을 모두 뺀다(파일은 원본 그대로 남고 상태는 수동검토).

뺀 수정에 연결된 이슈는 수동 검토 목록으로 간다. 규칙 수정은 가능한 한 남긴다.

환경 등급 나에서는 변경된 .cpp의 컴파일 검사를 S8 맨 앞에서 한꺼번에 병렬로 돌려 둔다(`--compile-parallel`). 수정을 빼고 다시 병합한 파일만 그 자리에서 새로 검사한다.

**형식**


- 함수명은 로그를 남긴 함수의 이름이 자동으로 들어간다. 직접 적지 않는다.
- 모듈은 구획 이름이다(`M07.컴파일`, `S6.sLLM수정` 등).

**위치**

| 파일 | 내용 |
|---|---|
| `logs/run.log` | 전체 로그. 콘솔에 안 나오는 상세(DEBUG) 줄도 여기에 남는다 |
| `logs/llm/taskNNNN_aN_prompt.txt`, `..._response.txt` | sLLM 요청과 응답 원문 |
| `logs/compile/snapshot/`, `logs/compile/merged/` | 컴파일 검사 출력 원문(환경 등급 나) |
| `logs/smoke_test.log` | S0의 컴파일러 동작 확인 출력 |

**오류를 찾는 순서**
1. 콘솔의 마지막 `ERROR` 줄에서 `[모듈][함수명]`을 본다.
2. 단계가 실패했으면 `[M10.실행기][run_pipeline] 단계 Sn(...) 실패` 줄 아래에 호출 경로 전체가 남는다. 마지막 줄이 원인이고, 경로에 파일의 줄 번호가 나온다.

4. 원인을 고친 뒤 `--resume <실행 폴더>`로 이어서 실행한다.

## 8. 파일 처리

### 8.1 파일이 거치는 위치

```
원본 패키지(읽기 전용, 손대지 않음)
   → snapshot/      S0에서 복사. 이후 모든 단계가 이것만 읽는다
   → 수정 레코드    S4, S5, S6에서 생성. DB에만 있고 파일은 아직 없다
   → work/merged/   S7에서 스냅샷 + 수정 레코드로 생성
   → out/changed/   S7에서 변경된 파일만. 최종 산출물
   → out/diff/      S9에서 스냅샷 본문과 결과 본문을 비교해 생성
```

### 8.2 파일 상태(매니페스트에 기록되는 값)

| 상태 | 뜻 |
|---|---|
| 제외 | 바이너리 등 수정 대상이 아닌 종류, 읽기 실패, 인코딩 판별 불가 |
| 탐지제외 | .rc, .idl, .def, 프로젝트 파일. 규칙 탐지를 하지 않음 |
| 범위제외 | `--only`, `--exclude`로 정한 처리 범위 밖의 소스. 탐지와 수정을 하지 않음 |
| 변경없음 | 이슈가 없거나 설정으로 흡수됨 |
| 변경없음(읽기전용) | 같은 바이트로 다시 쓸 수 없는 파일. 탐지만 하고 수정하지 않음 |
| 변경됨 | 수정이 적용되고 검증 통과. 남은 수동 검토 없음 |
| 부분수정 | 수정이 적용되고 검증 통과. 수동 검토 항목이 남음 |
| 수동검토 | 자동 수정이 없거나 모두 취소됨. 수동 검토 항목만 있음 |

### 8.3 수정 레코드 상태

| 상태 | 뜻 |
|---|---|
| accepted | 규칙·요청사항이 만들었거나, sLLM 수정이 수용 검사를 통과 |
| applied | 결과 파일에 반영됨 |
| verified | 반영 후 검증 통과 |
| rejected | 범위 겹침, 원문 불일치, 검증 불합격 등으로 제외. 사유가 기록됨 |

### 8.4 처리 원칙

- 원본 패키지와 `snapshot/`은 어떤 단계도 수정하지 않는다.
- 파일을 쓰는 단계는 S7과, 되돌림 때의 S8뿐이다. 병렬로 도는 sLLM 호출은 결과만 돌려준다.
- 결과 파일은 원본의 인코딩, BOM, 줄끝을 그대로 따른다. S1에서 "읽은 그대로 다시 쓰면 같은 바이트가 되는지"를 미리 확인하고, 안 되는 파일은 수정하지 않는다.
- 큰 초기화 목록(기본 2,000자 이상)은 sLLM에 보내지 않고, 병합 후 원문이 그대로 있는지 확인한다.
- 되돌림의 단위는 파일이 아니라 수정 레코드다.
- 규칙은 다시 실행해도 같은 결과가 나온다. 이미 고친 곳은 다시 잡지 않는다.

### 8.5 경우별 처리

| 상황 | 처리 |
|---|---|
| 이슈가 없는 파일 | `out/changed/`에 넣지 않는다 |
| 규칙 수정만 있는 파일 | sLLM을 거치지 않고 병합 |
| 규칙 수정과 sLLM 수정이 함께 있는 파일 | 규칙 수정을 먼저 반영한 본문을 기준으로 sLLM 조각을 만든다 |
| sLLM 수정이 기각됨 | 그 이슈만 수동 검토로. 같은 파일의 다른 수정은 유지 |
| 괄호 짝 분석이 실패한 파일 | 함수 경계를 쓰지 않고 줄 단위로 처리. 매니페스트 비고에 표시 |
| 큰 상수 배열이 있는 파일 | 배열 본문은 규칙으로만 점검. 주변 코드만 sLLM 대상 |
| 줄끝이 섞인 파일 | 규칙 수정은 하고 sLLM 수정은 하지 않는다 |
| 인코딩 판별 불가 | 수정하지 않는다. 매니페스트에 제외로 기록 |
| 요청사항의 배열 → 구조체 | 상수 인덱스 접근만 치환하고 "사람이 확인할 수정"으로 표시. 선언부와 변수 인덱스는 수동 검토 |
| 프로젝트 파일 | 수정하지 않는다. 설정을 읽어 보고서에 쓰고, 변경할 설정을 `project_settings.md`로 낸다 |
| 바이너리(.lib, .dll) | 복사하지 않고 목록만 기록. `project_settings.md`에 재빌드·교체 확인 대상으로 낸다 |

배열 → 구조체 요청은 선언부가 수동 검토로 남으므로, 선언을 고치기 전에는 치환된 코드가 컴파일되지 않는다. 환경 등급 나에서는 컴파일 검사가 이를 잡아 요청사항 수정을 자동으로 뺀다. 환경 등급 가에서는 치환된 채로 나가므로 `manual_review.md`의 선언부 항목을 반드시 처리해야 한다.

## 10. 설정 파일

모두 JSON이다. 없으면 내장 기본값을 쓴다.

환경값 프로필(`config/profiles/vs2008_to_vs2022.json`):

```json
{
  "from": { "vs": 2008 },
  "to": {
    "vs": 2022,
    "cpp_standard": "c++14",
    "conformance": "off",
    "platform": "keep",
    "charset": "keep"
  },
  "policy": { "deprecated_warnings": "suppress" }
}
```

| 값 | 선택지 | 기본 |
|---|---|---|
| `vs` | 2005, 2008, 2010, 2012, 2013, 2015, 2017, 2019, 2022 | 필수 |
| `cpp_standard` | c++14, c++17, c++20, c++latest | c++14 |
| `conformance` | off, on | off |
| `platform` | keep, x86, x64 | keep |
| `charset` | keep, mbcs, unicode | keep |
| `deprecated_warnings` | suppress(설정으로 억제), fix(코드 수정) | suppress |

요청사항(`config/requests/EXAMPLE.json`):

```json
{
  "features": [
    {
      "id": "REQ-001",
      "type": "array_to_struct",
      "target": "g_data",
      "mapping": { "IDX_TEMP": "temp", "IDX_COUNT": "count" }
    }
  ]
}
```

`mapping`에는 CSV 파일 경로(인덱스,필드명)를 줄 수도 있다. 이 판이 처리하는 요청 유형은 `array_to_struct`뿐이다.

요청 항목에 `"llm_variable_index": true`를 넣으면 변수 인덱스 접근(`g_data[i]`)을 sLLM에 맡긴다. 넣지 않으면 수동 검토로 보낸다. sLLM에 맡긴 결과는 모두 검토 대상이다.

서버 설정(`config/server.json`)의 주요 값:

| 값 | 뜻 | 기본 |
|---|---|---|
| `llm.endpoint` | sLLM 주소(OpenAI 호환). `--llm-endpoint`나 환경변수가 있으면 그쪽이 우선. 어디에도 없으면 sLLM 대상 이슈를 수동 검토로 보낸다 | 빈 값 |
| `llm.max_total_tokens` | 요청 1건의 입력+출력 한도. 서버가 더 작은 값을 알려 주면 서버 값을 쓴다 | 24000 |
| `llm.max_output_tokens` | 출력 상한 | 3000 |
| `llm.max_parallel` | 서버가 허용하는 동시 요청 수. `--max-parallel`은 이 값 이하로만 적용된다 | 4 |
| `llm.retries` | 수정 블록 기각이나 호출 실패 시 재요청 횟수 | 2 |
| `llm.server_prompt_reserve_tokens` | 서버가 공통 프롬프트를 덧붙일 때 그 몫으로 비워 둘 토큰 수. 서버 프롬프트의 상한을 적는다 | 0 |
| `llm.busy_retries` | 과부하 응답(429, 503)일 때 기다렸다 다시 보내는 횟수 | 5 |
| `llm.calibrate_first` | 첫 요청 1건으로 실제 토큰 수를 확인한 뒤 나머지를 보낸다 | true |
| `limits.big_init_chars` | 이 길이 이상의 초기화 목록은 sLLM에 보내지 않는다 | 2000 |
| `limits.slice_context_lines` | 수정 지점 앞뒤로 같이 보낼 줄 수 | 25 |
| `limits.chunk_enabled` | 한도를 넘는 구간을 나눠 순서대로 처리(분할 순차). false면 수동 검토로 보냄 | true |
| `limits.chunk_ledger_chars` | 뒤 조각에 넘기는 "앞 조각에서 바꾼 내용"의 최대 글자 수 | 1500 |
| `limits.chunk_head_lines` | 뒤 조각에 참고로 붙이는 함수 앞부분 줄 수 | 25 |
| `limits.compile_parallel` | 컴파일 검사 동시 수. 0이면 CPU 수에 맞춘다(한 개는 남기고 최대 8) | 0 |
| `compile.mode` | off 또는 changed(변경 파일만 검사) | changed |

추가 규칙(`config/rules.json`)은 내장 규칙과 같은 형식의 배열이다. 같은 ID가 있으면 내장 규칙을 대신한다.

규칙의 발동 조건(`when`)에 쓸 수 있는 값:

| 값 | 뜻 |
|---|---|
| `since` | 이 문제가 생긴 VS 제품 연도. 원본 < since ≤ 대상일 때만 켠다. 원본 버전에서 이미 겪은 문제는 다시 잡지 않고, 대상 버전에 아직 없는 문제도 잡지 않는다 |
| `standing` | true면 원본이 since 이후여도 켠다. 오류가 아니라 경고여서 고치지 않은 채 남아 있을 수 있는 것에 쓴다(C4996 사용 중단 경고) |
| `min_std` | 대상 언어 표준이 이 값 이상일 때 |
| `platform`, `conformance`, `deprecated` | 환경값이 이 값일 때 |

조건을 여러 개 적으면 모두 만족해야 켜진다. `when`이 없으면 항상 켜진다. 새 규칙을 넣을 때는 "어느 VS 버전에서 바뀌었는가"를 `since`로 적는다.

```json
[
  {
    "id": "R-T1-EXAMPLE",
    "tier": "T1",
    "title": "예시: 이름이 바뀐 함수",
    "when": { "since": 2015 },
    "pattern": "\\bold_name\\s*\\(",
    "action": { "type": "replace", "text": "new_name(" }
  }
]
```

## 11. 실행 폴더

```
runs/<패키지>/<실행ID>/
├─ run.json                  실행 인자, 실제 적용된 환경값, 실행 옵션(opts)
├─ state.db                  상태 저장소
├─ snapshot/                 원본 복사본(소스, 프로젝트, 텍스트 파일)
├─ work/merged/              병합 결과(환경 등급 나에서는 전체 트리)
├─ logs/
│  ├─ run.log
│  ├─ llm/
│  └─ compile/
└─ out/
   ├─ changed/               변경된 파일(원본과 같은 폴더 구조)
   ├─ diff/                  파일별 diff, all.patch
   ├─ report.md              보고서
   ├─ manifest.csv           전체 파일의 처리 상태
   ├─ manual_review.md       수동 검토 목록
   ├─ project_settings.md    프로젝트 설정 변경 목록, 재빌드 확인 대상 바이너리
   ├─ build_guide.md         빌드 환경용 절차서
   └─ preflight.md           환경 점검 결과
```

diff는 검토용으로 UTF-8로 쓴다. 원본이 CP949면 `patch` 명령으로 바로 적용하는 용도가 아니다. 적용은 `out/changed/`의 파일을 덮어쓰는 방식으로 한다.

## 12. MCP 서버에 추가할 내용

> 이 절은 `05_기능정의.md`로 대체됐다. 05에서는 sLLM 주소를 MCP 서버가 갖고, py가 서버의 모델 호출 도구를 부른다. 아래는 0.1.0 기준의 초기 구상으로만 남긴다.

MCP 도구는 exe를 호출하는 얇은 래퍼로 만든다. 처리 로직은 MCP 서버에 두지 않는다.

| 도구 | 하는 일 | 호출 |
|---|---|---|
| `preflight` | 환경 점검 | `vupdate preflight --package ...` 실행 후 `out/preflight.md` 반환 |
| `start_update` | 실행 시작 | `vupdate run ...`을 백그라운드로 띄우고 실행 폴더 경로 반환 |
| `get_status` | 진행 상태 | `vupdate status --run <실행 폴더>` |
| `get_report` | 보고서 | `out/report.md` 읽기 |
| `list_manual` | 수동 검토 목록 | `out/manual_review.md` 읽기(응답 크기 제한) |
| `resume` | 이어서 실행 | `vupdate run --resume <실행 폴더>` |

- `start_update`는 끝날 때까지 기다리지 않는다. 실행 폴더를 돌려주고, 진행은 `get_status`로 본다.
- 실행 폴더 경로를 실행 ID로 쓴다. `--out`으로 위치를 고정해 두면 찾기 쉽다.
- sLLM은 vupdate가 직접 HTTP로 호출한다. 주소는 `config/server.json`에 적는다. MCP 서버가 sLLM 앞단 역할을 해야 한다면 그 주소를 `llm.endpoint`에 적으면 된다.
- v1에서 적었던 조회용 도구(`search`, `read_range` 등)는 이 도구에 없다. 탐색은 프로그램이 하므로 sLLM에 필요하지 않다.

| R-T3-STDINT-TYPEDEF | T3 sLLM | VS2010부터 | stdint 타입 이름의 자체 typedef |
| R-T3-FILE-INTERNALS | T3 수동 | VS2015부터 | FILE 내부 필드, `_iob` 사용 |
| R-T3-HASH-MAP | T3 수동 | VS2015부터 | `hash_map`, `hash_set` 사용 |
| R-T3-PTR-TRUNC | T3 수동 | x64 | 포인터를 32비트 정수로 캐스팅 |
| R-T3-WINDOWLONG | T3 sLLM | x64 | `SetWindowLong` 계열 |
| R-T3-INLINE-ASM | T3 수동 | x64 | 인라인 어셈블리 |

"VS2015부터"는 원본이 2015보다 앞이고 대상이 2015 이상일 때만 켜진다는 뜻이다. 예를 들어 2015 → 2022에서는 VS2015부터인 규칙 6개와 그 앞의 규칙이 꺼진다(원본에서 이미 겪은 문제다).

버전 값의 근거:

| 연도 | 규칙 | 근거 |
|---|---|---|
| 2015 | 리터럴 접합, snprintf 매크로, FILE 내부, hash_map | MS 문서 "Visual C++ change history 2003 - 2015"의 2015 항목에서 확인 |
| 2012 | make_pair | MS 문서 "Breaking Changes in Visual C++"(Visual Studio 2012)에서 확인. 처음에 2010으로 적었다가 문서를 보고 고쳤다 |
| 2015 | 좁히기 변환(C2397, C4838) | MS의 경고 문서와 다른 프로젝트의 VS2015 전환 기록 |
| 2013 | Winsock 사용 중단 경고 | Windows SDK 8.1(VS2013)의 빌드 경고 사례 |
| 2010 | stdint.h | VS2010에서 헤더가 추가됐다는 여러 프로젝트의 기록 |
| 2005 | CRT 경고(C4996) | 널리 알려진 내용. 이번에 문서로 다시 확인하지는 않았다 |

규칙 수는 출발점일 뿐이다. 실제 패키지를 `--dry-run`으로 돌려 보고, MS 변경 이력 문서와 대조해 늘려야 한다.

## 15. AI로 수정할 때

- **구획 단위로 맡긴다.** 고칠 구획의 머리 주석과 코드, 그리고 4절의 "구획 사이의 약속"만 주면 된다. 파일 전체를 줄 필요가 없다.
- **고친 뒤에는 반드시 `vupdate selftest`를 돌린다.** 36항목이 모두 통과해야 한다. Python이 있는 PC라면 `tests/`의 시험 4개도 돌린다. 동작을 바꿨다면 자체 시험의 기대값도 함께 고친다.
- **로그 규칙을 지킨다.** 새 함수는 그 구획의 로거(`LOG6` 등)를 쓴다. 접두어는 자동으로 붙는다.
- **구획 사이에 새 전역 변수를 만들지 않는다.** 단계 사이의 자료는 저장소 테이블로 넘긴다.

| 하려는 일 | 고칠 곳 |
|---|---|
| 규칙 추가·수정 | `config/rules.json`(코드 수정 없음) 또는 M05의 `RULES` |
| 특수한 탐지 로직 | M05의 `_DETECTORS`에 함수 추가 |
| 프롬프트 문구 | `config/prompts/system.txt`, `user.txt`(코드 수정 없음) 또는 S6의 `SYSTEM_PROMPT` |
| sLLM 호출 규격 | M06의 `llm_chat` |
| 서버의 오류 응답 구분(한도 초과 문구 등) | M06의 `classify_llm_error` |
| 토큰 추정식과 보정 | M06의 `est_tokens`, `learn_tokens` |
| 한도에 걸렸을 때 줄이는 방법 | S6의 `_replan`, `plan_chunks` |
| 실행 옵션 추가 | M02의 `collect_opts`, M11의 `build_parser`, `Invoke-VersionUpdate.ps1` |
| 수정 블록 수용 조건 | S6의 `check_block` |
| 컴파일 옵션 구성 | M07의 `cl_flags_for` |
| Visual Studio 탐지 경로 | M07의 `find_tools` |

| 새 요청 유형 | S5의 `s5_impact`, M02의 `load_request` |
| 새 VS 버전 | M02의 `VERSION_MAP` |
