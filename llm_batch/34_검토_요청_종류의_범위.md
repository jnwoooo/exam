# 검토: 요청문의 종류가 다루는 범위와 한계

| 항목 | 내용 |
|---|---|
| 읽는 순서 | 34 |
| 작성일 | 2026-11-26 |
| 대상 코드 | `vupdate.py` 0.10.7 (**이 문서로 코드를 바꾸지 않았다**) |
| 배경 | 지금의 종류(type)가 어떤 요청을 다루는지, 버전 전환 때 흔한 요청이 얼마나 처리되는지, 배열 → 구조체 같은 예외 주제가 더 있는지, 구조상의 한계가 어디인지 확인 요청 |
| 확인 범위 | Linux, 공개 코드(Notepad++의 소스 804개, 함수 10,058개), 모의 sLLM. 의미 분석의 답은 "모델이 이렇게 분류했다"고 정해 두고 도구가 대상을 얼마나 찾는지만 쟀다. 실제 gemma4의 분류와 수정 품질은 확인하지 못했다 |

## 1. 결론

- 지금의 종류는 **"이름이나 구문으로 짚을 수 있는 줄을, 그 줄 주변 안에서 고치는 요청"**을 다룬다. 여기에 전용 분석이 붙은 주제가 하나 있다(배열·오프셋 → 구조체).
- 흔한 요청 12개를 걸어 보니 **되는 것 3, 일부만 되는 것 6, 안 되는 것 3**이었다(3절).
- 안 되는 것의 공통점은 셋이다. 코드 전체를 봐야 대상을 알 수 있다 / 선언과 사용처를 여러 파일에서 함께 바꿔야 한다 / 새 함수나 새 파일이 필요하다. "많이 쓰는 로직의 공통화"는 셋 모두에 걸린다.
- 종류를 늘릴 수 있는 방향은 분명하다. **도구가 기계적으로 할 수 있는 것**(이름 바꾸기, 기계적 치환, 시그니처의 단순 변경)과 **탐지해서 보고만 하는 것**(중복 로직, 64비트에서 크기가 바뀌는 구조체)은 지금 구조에 얹을 수 있다. 타입의 전파, 소유권, 흐름을 알아야 하는 것은 지금 구조로는 안 된다(5절).

## 2. 지금의 종류가 다루는 질문

| 종류 | 다루는 질문의 꼴 | 조건 |
|---|---|---|
| `modify` | "이 이름이 쓰인 줄을 이렇게 고친다" / "이런 낱말이 든 함수의 호출을 고친다" / "if·for 안의 것을 고친다" | 고칠 내용이 한 조각(대상 8곳, 150줄까지) 안에서 끝나야 한다 |
| `find` | 위와 같은 방식으로 찾아 목록만 낸다 | - |
| `array_to_struct` | 전문 버퍼의 위치 접근 → 기존 구조체의 필드 / 지역 병렬 배열 → 구조체의 배열 / 상수 인덱스로 쓰는 표 → 구조체 | 코드에서 그 꼴이 탐지돼야 한다 |
| `constraint` | 모든 수정에 붙는 조건 | 물음에 글로 붙을 뿐이다. 모델이 지켰는지 도구가 검사하지 않는다 |
| `compat` | 요청문으로 처리하지 않는다 | 규칙(68개)과 `--compat-llm`이 한다 |

## 3. 흔한 요청 12개

대상 수는 공개 코드에서 잰 값이다.

| # | 요청 | 가는 길 | 찾은 대상 | 판정 | 까닭 |
|---|---|---|---|---|---|
| 1 | 사용 중단 함수를 보안 함수로 | 규칙, 3단계 | 경고 줄 72곳 가운데 규칙 5곳, 나머지 67곳은 sLLM | 일부 | 대상이 선언이 보이는 배열일 때만 바꾼다. 나머지는 설정으로 경고만 끈다 |
| 2 | API의 1:1 교체(`sprintf` → `snprintf`) | `modify`, 이름 | 14곳(파일 7) | 됨 | 줄 안에서 끝난다 |
| 3 | 특정 호출 뒤에 검사 추가(`malloc` 뒤 NULL 검사) | `modify`, 이름 | 6곳(파일 5) | 됨 | 줄 주변에 넣으면 된다 |
| 4 | 조건에 맞는 곳 찾기(if 안의 `memcpy`) | `find` | 45곳(파일 23) | 됨 | 목록만 낸다 |
| 5 | 기계적 치환(`NULL` → `nullptr`) | `modify`, 이름 | 980곳(파일 120) | 일부 | 대상은 찾는다. 글자만 바꾸면 되는 일을 조각마다 sLLM에 묻게 되어 호출이 수백 회다. 요청문에는 기계적 치환의 길이 없다(규칙 파일 `--rules`로는 된다) |
| 6 | 상수 교체(`MAX_PATH` → 새 상수) | `modify`, 이름 | 302곳(파일 43) | 일부 | 쓰인 줄은 고친다. 새 상수의 정의를 어느 헤더에 둘지, include를 어디에 더할지는 정하지 못한다 |
| 7 | 함수 호출에 인자 추가(로그 함수에 줄 번호) | `modify`, 낱말 | 후보 7개, 47곳(파일 15) | 일부 | 호출은 고친다. 선언과 정의가 함께 바뀌어야 하는데 조각마다 따로 묻고, 어긋나면 되돌리는 장치가 없다 |
| 8 | 타입 바꾸기(`TCHAR` → `wchar_t`, 유니코드 전환) | `modify`, 이름 | 6곳(파일 3) | 일부 | 그 이름이 쓰인 줄만 본다. 바뀐 타입이 다른 변수, 인자, 호출로 번지는 것을 따라가지 않는다. `--charset`은 컴파일 옵션에만 쓰인다 |
| 9 | 배열·오프셋 → 구조체 | `array_to_struct` | 75곳(파일 16) | 일부 | 위치와 길이를 확정한 것만 규칙이 바꾼다. 나머지는 sLLM에 가거나 사유와 함께 남는다 |
| 10 | 되풀이되는 로직을 공통 함수로 | `modify` | 0 | 안 됨 | 이름도 낱말도 없어 대상을 찾지 못한다. 4절 |
| 11 | 메모리 누수 수정 | `modify`, 낱말 | 후보 98개 | 안 됨 | 낱말(free, delete)로 잡히는 것은 그 낱말이 든 함수 이름이지 누수가 난 자리가 아니다. 할당과 해제의 흐름을 보지 않는다 |
| 12 | 포인터를 int로 받는 곳(64비트) | `modify` | 0 | 안 됨 | 요청문으로는 대상이 없다. `--platform x64`를 주면 규칙이 탐지해 수동 검토 목록에 올리기만 한다 |

구문만 준 요청("for 문을 고친다")은 for 문의 머리 2,659곳(파일 323)이 모두 대상이 됐다. 이름 없이 구문만으로는 범위가 너무 넓다.

판정은 "도구가 대상을 찾고 물음을 만들 수 있는가"까지다. sLLM이 그 줄을 옳게 고치는지는 재지 않았다.

## 4. 배열 → 구조체처럼 전용 처리가 필요한 주제

줄 단위 수정으로는 안 되고, 주제마다 탐지와 일관된 변경을 따로 만들어야 하는 것들이다.

| 주제 | 줄 단위로 안 되는 까닭 | 지금 구조에 얹을 수 있는가 |
|---|---|---|
| 이름 일괄 변경 | 수백 곳을 똑같이 바꾼다 | 된다. 규칙형이고 sLLM이 필요 없다. 같은 이름의 다른 변수, 매크로가 만드는 이름은 가리지 못한다 |
| 기계적 치환(`NULL` → `nullptr`, 옛 캐스트 등) | 위와 같다 | 된다. 지금도 규칙 파일로 된다. 요청문에서 그 길로 잇는 것을 만들면 된다 |
| 함수 시그니처 변경 | 선언, 정의, 모든 호출이 함께 바뀐다 | 일부. 인자의 추가(고정값), 삭제, 순서 바꾸기는 기계적이다. 호출마다 새 인자를 계산해야 하면 sLLM에 맡기고 어긋날 때 되돌리는 계약이 필요하다(배열 요청에 있는 방식) |
| 옛 컴파일러 분기 걷어내기(`#if _MSC_VER < …`) | 전처리 블록 단위다 | 일부. 조건이 단순한 것만 |
| 매직 넘버, 되풀이되는 문자열 → 상수 | 탐지와 정의의 위치 | 탐지와 보고까지. 정의를 둘 곳을 정하지 못한다 |
| 구조체의 크기·정렬이 64비트에서 바뀌는 곳 | 배치 계산 | 탐지와 보고는 된다. 구조 분석이 배치를 이미 계산한다 |
| 전문 버퍼 접근이 구조체의 범위를 넘는 곳 | 위와 같다 | 탐지와 보고는 된다 |
| **되풀이되는 로직의 공통화** | 중복 탐지, 새 함수, 여러 곳의 교체 | 탐지와 보고까지. 글자 수준으로 같은 문장 묶음을 찾을 수는 있다. 공통 함수로 빼는 것은 안 된다(아래) |
| 타입의 전파(`char` → `TCHAR`, `int` → `INT_PTR`) | 선언에서 사용처로 번진다 | 안 된다. 타입 정보가 없다 |
| 전역 변수 묶기, 클래스 추출, 파일 나누기 | 여러 파일의 구조가 바뀐다 | 안 된다 |
| 원시 포인터 → 스마트 포인터, 예외 안전, 스레드 안전, 누수 | 소유권과 실행 흐름 | 안 된다 |
| 문자열 클래스 통일(`CString` ↔ `std::string`) | 타입의 전파 | 안 된다 |

공통화가 안 되는 까닭을 구체적으로 적는다.

1. **찾는 길이 없다.** 중복은 이름으로 짚을 수 없다. 코드 전체에서 비슷한 문장 묶음을 찾아야 한다.
2. **빼낼 함수의 인자를 정하지 못한다.** 어떤 변수가 밖에서 들어오고 어떤 값이 나가는지는 자료의 흐름을 봐야 안다. 지금은 글자 수준의 분석이다.
3. **새 함수를 둘 곳이 없다.** 도구는 기존 파일의 바뀐 사본만 낸다. 새 파일, 헤더의 새 선언, include 추가, 프로젝트 파일 수정을 하지 않는다.
4. **한 번의 물음에 다 들어가지 않는다.** 송신 20k, 수신 3k 토큰이라 함수 하나쯤이 한계다. 중복된 여러 곳과 새 함수를 함께 보고 함께 고칠 수 없다.
5. **확인할 방법이 없다.** 동작이 같은지는 실행해 봐야 안다. 개발 PC에서 빌드가 안 되고, 되는 환경에서도 파일 단위의 문법 검사까지다.

## 5. 한계가 나오는 곳

| 제약 | 그래서 못 하는 것 |
|---|---|
| sLLM이 보는 것은 코드 조각 하나(24k 토큰, 수신 3k) | 여러 함수나 파일을 함께 봐야 하는 판단, 큰 함수의 통째 재작성 |
| 조각마다 따로 묻는다 | 선언과 사용처의 일관된 변경(배열 요청만 되돌림이 있다) |
| 대상을 이름, 낱말, 구문으로 찾는다 | 뜻으로만 정해지는 대상(누수, 중복, 위험한 캐스팅) |
| 글자 수준의 분석(타입, 호출 관계, 자료의 흐름이 없다) | 타입의 전파, 영향 범위의 정확한 계산 |
| 기존 파일의 바뀐 사본만 낸다 | 새 파일, 프로젝트 파일, 조각 밖의 include 추가 |
| 검증이 정적 검사와 파일 단위 컴파일 검사까지 | 동작이 같은지의 확인, 링크 |
| 조건(`constraint`)은 글로만 붙는다 | "전문 길이를 유지한다" 같은 조건의 위반 탐지(구조 분석이 규칙으로 바꾼 것은 지킨다. sLLM의 수정은 검사하지 않는다) |

이 가운데 토큰 한도와 빌드 불가는 환경에서 오고, 나머지는 도구의 구조에서 온다.

## 6. 종류의 확장 가능성

| 갈래 | 내용 | 가능성 |
|---|---|---|
| 기계형 | 이름 변경, 기계적 치환, 시그니처의 단순 변경, 단순한 전처리 분기 제거 | 높다. sLLM 없이 규칙으로 하고 요청문에서는 그 규칙을 고르기만 한다 |
| 탐지·보고형 | 중복 로직, 매직 넘버, 64비트에서 바뀌는 구조체, 범위를 넘는 버퍼 접근 | 높다. 고치지는 않고 위치와 근거를 낸다 |
| 계약형 | 시그니처 변경처럼 선언과 사용처가 묶인 것 | 중간. 주제마다 탐지, 기계적인 부분, 되돌림을 따로 만들어야 한다. 배열 → 구조체를 여러 판에 걸쳐 다듬어 온 것과 같은 종류의 일이다 |
| 분석형 | 타입의 전파, 소유권, 흐름, 공통 함수 추출 | 낮다. 글자 수준의 분석과 조각 단위의 물음으로는 근거를 만들 수 없다 |

지금의 다섯 종류에 새 종류를 더하는 것 자체는 어렵지 않다. 의미 분석의 프롬프트에 종류를 더하고 그 종류의 처리기를 붙이면 된다. 어려운 것은 처리기다. 종류가 늘수록 모델이 종류를 잘못 고를 가능성도 는다(실제 모델로 확인하지 못했다).
