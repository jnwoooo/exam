# 오류 대응: 실행 중 오류, 수동 검토 목록, 빌드 오류

| 항목 | 내용 |
|---|---|
| 읽는 순서 | 7 / 8 |
| 문서 버전 | v1 |
| 작성일 | 2026-11-24 |
| 대상 코드 | `vupdate.py` 0.4.0 |
| 관련 문서 | `03_확인사항.md`(빌드 환경), `04_개발구조.md`(실행 방법), `06_충족점검.md`(토큰 한도) |
| 성격 | 절차서. 3.9의 오류 코드별 대응표는 MS 문서와 널리 알려진 전환 사례를 정리한 것이며, 실제 패키지의 빌드에서 확인한 것이 아니다 |

## 0. 오류는 세 군데에서 나온다

| 구분 | 어디서 | 무엇을 보나 | 이 문서 |
|---|---|---|---|
| 가 | `vupdate`를 돌리는 도중 | 화면과 `logs/run.log`, 종료 코드 | 1절 |
| 나 | `vupdate`가 끝난 뒤 남긴 목록 | `out/manual_review.md`, `out/project_settings.md` | 2절 |
| 다 | 결과물을 빌드 환경에 가져가 빌드했을 때 | 컴파일러와 링커의 오류 목록(`msbuild.log`) | 3절 |

가와 나는 이 PC에서 끝난다. 다는 빌드 환경에서 로그를 받아 와야 한다. 이 도구는 다의 오류를 **분류하고 대응을 안내**한다. 자동으로 고치지는 않는다.

```
[이 PC]  vupdate run  ──▶  out/changed, report.md, manual_review.md, project_settings.md, build_guide.md
                               │
[빌드 환경]  결과 파일 반영 → 프로젝트 변환 → 설정 적용 → 빌드(/fl) ──▶ msbuild.log
                               │
[이 PC]  vupdate buildlog --log msbuild.log --run <실행 폴더>  ──▶  out/build_errors.md, build_errors.csv
                               │
          분류에 따라 처리(설정 추가 / 수정 되돌림 / 규칙 추가 후 다시 실행 / 직접 수정 / .lib 재빌드 요청)
                               │
[빌드 환경]  다시 빌드 ──▶ 오류가 없어질 때까지 반복
```

## 1. 도구를 돌리는 도중의 오류

### 1.1 종료 코드로 먼저 가른다

| 종료 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 | 끝났고 수동 검토 항목이 없다 | 결과물을 빌드 환경으로 가져간다 |
| 1 | 끝났고 수동 검토 항목이 있다 | 2절 |
| 2 | 단계가 실패해 멈췄다 | 1.2 |
| 3 | 입력이 잘못됐다(경로, 버전 값, 프로필, 옵션) | 화면의 안내 문구대로 고쳐 다시 실행한다. 만들어진 것은 없다 |

### 1.2 단계 실패(종료 코드 2)

1. 화면 마지막의 `[M10.실행기][run_pipeline] 단계 S6(...) 실패` 줄에서 멈춘 단계를 본다.
2. `logs/run.log`에서 그 줄 바로 아래의 호출 경로를 본다. 맨 마지막 줄이 원인이고, 줄 머리의 `[구획][함수명]`이 고칠 곳이다.
3. 원인을 고친 뒤 `vupdate run --resume <실행 폴더>`로 이어서 실행한다. 끝난 단계는 건너뛴다.

| 로그에 보이는 것 | 원인 | 할 일 |
|---|---|---|
| `PermissionError`, `OSError`가 `snapshot`이나 `out` 경로에서 | 파일이 열려 있거나 쓸 수 없는 위치 | 파일을 닫거나 `--out`으로 다른 위치를 준다 |
| `sqlite3.OperationalError: database is locked` | 같은 실행 폴더를 두 번 동시에 돌렸다 | 하나만 돌린다 |
| `MemoryError` | 매우 큰 파일 | `--exclude`로 그 파일을 빼고 돌린 뒤 따로 본다 |
| 그 밖의 예외 | 도구의 결함 | `run.log`의 호출 경로 전체를 보관한다. `04_개발구조.md` 15절의 방법으로 해당 구획을 고친다 |

### 1.3 멈추지는 않지만 로그에 경고가 남는 경우

실행은 끝까지 가고, 해당 항목만 수동 검토로 넘어간다. `run.log`에서 `WARN`, `ERROR`로 찾는다.

| 로그 문구 | 뜻 | 할 일 |
|---|---|---|
| `sLLM 주소 미설정. 대상 이슈 n건을 수동 검토로 보냅니다` | 주소가 없어 sLLM 단계를 건너뛰었다 | 환경변수 `VUPDATE_LLM_ENDPOINT`나 `--llm-endpoint`를 주고 새로 실행한다(`--resume`은 끝난 단계를 다시 돌지 않는다) |
| `sLLM 서버 호출이 연속으로 실패했습니다` | 서버에 닿지 않거나 서버가 거절한다 | `vupdate llmcheck`로 서버를 점검한다(1.4) |
| `서버가 토큰 한도 초과로 거절` 뒤 `다시 계획합니다` | 조각이 한도를 넘어 더 작게 나눴다 | 정상 동작이다. 반복되면 `llmcheck`가 제안하는 설정을 적용한다 |
| `더 작게 나눌 수 없음`, `다시 계획 2회 뒤에도 한도에 걸림` | 문장 하나가 한도보다 크거나 추정이 크게 어긋난다 | 그 지점은 수동 검토로 갔다. 서버 한도 설정을 확인한다 |
| `분할 조각 n/m 실패 ... 모두 취소` | 나눠 처리하던 구간에서 한 조각이 실패했다 | 그 구간 전체가 수동 검토로 갔다. 일부만 바뀐 상태는 남지 않는다 |
| `검증 불합격 ... 수정 n건을 빼고 다시 병합합니다` | 수정 결과의 괄호 짝이나 컴파일 검사가 원본보다 나빠졌다 | 문제의 수정은 빠졌다. 빠진 항목은 수동 검토 목록에 있다 |
| `인코딩을 판별하지 못해 제외합니다` | CP949, UTF-8, UTF-16이 아닌 파일 | 매니페스트에서 그 파일을 확인하고 직접 본다 |
| `규칙 ... 가 ... 에서 실패. 이 규칙은 이 파일에서 건너뜁니다` | 규칙의 정규식이 그 파일에서 오류를 냈다 | 그 규칙만 그 파일에서 빠졌다. 규칙을 고친다 |

### 1.4 서버 쪽이 의심될 때

```
vupdate llmcheck
```

실제 서버에 작은 요청 몇 건과 일부러 한도를 넘긴 요청 한 건을 보내 다음을 확인한다. 결과는 화면과 `runs/_llmcheck/<시각>/llm_check.md`에 나온다.

| 항목 | 정상이 아니면 생기는 일 |
|---|---|
| 기본 호출 | sLLM 단계를 쓸 수 없다. 주소, 모델 이름, 인증을 확인한다 |
| 토큰 수 반환 | 추정 보정을 하지 못한다. 한도 초과는 거절당한 뒤에야 안다 |
| 한도 초과 거절 | 문구를 알아보지 못하면 줄여서 다시 보내지 않고 수동 검토로 보낸다. 서버가 넘는 요청을 받아들이면 본문이 잘려 들어갈 수 있으므로 반드시 확인한다 |
| 출력 형식 | 모델이 수정 블록 형식을 지키지 않으면 대부분의 조각이 기각된다 |
| 같은 입력에 같은 응답 | 다시 실행할 때 결과가 달라진다 |
| 동시 요청 | 실패가 섞이면 허용 동시 수를 낮춘다 |

## 2. 도구가 남긴 목록의 처리

### 2.1 처리 순서

1. **`project_settings.md`부터.** 2절의 전처리기 정의와 옵션은 코드 수정 없이 오류를 없애는 항목이다. 4절의 프로젝트 파일 점검은 빌드 전에 알아야 하는 설정이다(경고를 오류로 처리하는 프로젝트라면 2절이 필수가 된다).
2. **`manual_review.md`.** 자동으로 고치지 못한 지점이다. 아래 2.2의 사유별로 처리한다.
3. **`report.md` 7절의 "적용했지만 사람이 확인해야 하는 수정".** 자동으로 고쳤지만 뜻이 바뀔 수 있는 것이다(T2 규칙, 요청사항, sLLM 수정). `out/diff/`에서 본다.

### 2.2 수동 검토 목록의 사유별 처리

| 사유(목록에 적힌 문구) | 뜻 | 할 일 |
|---|---|---|
| 자동 수정 대상이 아닌 유형 | 탐지만 하는 규칙이다. 고치는 방법이 타입이나 설계에 달려 있다 | 규칙의 지침대로 직접 고친다. `vupdate rules`에 규칙별 설명이 있다 |
| sLLM 응답에 이 지점의 수정이 없음 | 같은 조각의 다른 지점은 고쳤는데 이 줄은 건드리지 않았다 | 직접 고친다. 같은 규칙에서 반복되면 그 규칙의 지침 문구를 더 구체적으로 고친다 |
| sLLM 이 수정 불필요로 판단함 | 규칙은 잡았는데 모델이 고칠 필요가 없다고 했다 | 사람이 판단한다. 오탐이면 그대로 둔다 |
| sLLM 수정 실패: 수정 블록 기각 ..., 형식 오류 | 모델의 답이 원문과 맞지 않거나, 범위를 벗어났거나, 정해진 형식이 아니다(다시 물은 2회까지) | 직접 고친다. `logs/llm/`에 요청과 응답이 있다 |
| sLLM 수정 실패: 추가 정의 요청 횟수 초과, 요청한 정의를 찾지 못함 | 모델이 다른 정의를 더 보여 달라고 했는데 줄 수 없었다 | 직접 고친다 |
| sLLM 수정 실패: 호출 실패 ... | 서버에 닿지 않았거나 서버 쪽 오류다(다시 보낸 2회까지) | 1.4의 서버 점검 뒤 다시 실행한다 |
| sLLM 수정 실패: 서버가 요청을 거절함 | 서버가 요청 자체를 받지 않았다 | 1.4의 서버 점검 |
| 토큰 한도: ... | 한도 안으로 줄이지 못했다 | 직접 고친다 |
| 분할 순차 취소: 같은 구간의 조각 n/m 이(가) 실패함 | 나눠 처리하던 구간이 통째로 취소됐다 | 그 구간을 직접 고친다. 취소된 수정 내용은 `manual_review.md` 아래쪽의 "기각된 수정"에 있어 참고할 수 있다 |
| 검증 불합격: ... | 수정을 적용했더니 구조가 깨지거나 새 컴파일 오류가 났다 | 기각된 수정을 참고해 직접 고친다 |
| 다른 규칙 수정과 범위가 겹침 | 두 규칙이 같은 자리를 고치려 했다 | 뒤의 것을 직접 적용한다 |
| 파일을 같은 바이트로 다시 쓸 수 없어 자동 수정하지 않음 | 인코딩이나 줄끝이 섞인 파일이다 | 파일을 정리한 뒤 다시 실행하거나 직접 고친다 |
| 배열 선언. 구조체 정의로 교체 필요 | 요청사항(배열 → 구조체)의 선언부다 | 구조체 정의와 선언을 직접 바꾼다. 사용처의 상수 인덱스는 이미 바뀌어 있다 |
| 변수 인덱스 접근. 매핑표로 결정할 수 없음 | `arr[i]`처럼 어느 필드인지 정해지지 않는다 | 직접 고치거나, 요청 파일에서 `llm_variable_index`를 켜고 다시 실행한다 |
| sLLM 주소 미설정, sLLM 단계를 건너뜀(--no-llm), sLLM 서버 호출 실패 | sLLM 단계를 돌지 않았다 | 서버를 준비해 다시 실행한다 |

## 3. 빌드 환경에서 난 빌드 오류

### 3.1 로그를 만든다

빌드 환경의 개발자 PowerShell에서:

```
msbuild 솔루션이름.sln /p:Configuration=Release /p:Platform=Win32 /fl /flp:Encoding=UTF-8
```

- 같은 폴더에 `msbuild.log`가 생긴다. `/flp:Encoding=UTF-8`을 빼면 msbuild의 판에 따라 시스템 코드 페이지(한국어 Windows는 CP949)로 쓰일 수 있다. UTF-8, UTF-16, CP949 모두 읽는다.
- Visual Studio 화면에서 빌드했다면 출력 창의 내용을 텍스트 파일로 저장해도 된다.
- 컴파일러는 파일 하나에서 오류가 100개가 되면 멈춘다. 첫 로그의 오류 수가 전부가 아니다.

### 3.2 분류한다

로그를 이 도구가 있는 PC로 가져와서:

```
vupdate buildlog --log msbuild.log --run <그 결과물을 만든 실행 폴더>
```

`--run`을 주면 오류가 난 줄을 그 실행의 수정 내용과 대조한다. 결과는 실행 폴더의 `out/build_errors.md`와 `build_errors.csv`다. `--run` 없이도 분류는 된다.

| `build_errors.md`의 절 | 내용 | 쓰임 |
|---|---|---|
| 1. 처리 순서 | 아래 3.3의 원칙 | |
| 2. 단계별 건수 | 프로젝트, 옵션, 컴파일, 리소스, 링크 | 어느 단계에서 막혔는지 |
| 3. 오류 코드별 대응 | 코드마다 건수, 흔한 원인, 대응. 메시지 문구로 원인이 좁혀지면 그 대응 | 같은 원인의 오류를 묶어서 한 번에 처리 |
| 4. 파일별 첫 오류 | 파일마다 가장 먼저 난 오류와 이 도구의 수정과의 관계 | 여기부터 고친다 |
| 5. 이 도구가 고친 줄에서 난 오류 | 수정이 원인일 수 있는 것 | 3.4 |
| 6. 대응표에 없는 코드 | | 반복되면 대응표에 더한다 |
| 7. 경고 요약 | | 경고를 오류로 처리하는 프로젝트가 아니면 뒤로 미룬다 |

`--run`을 주지 않으면 5절이 없고 뒤의 번호가 하나씩 당겨진다.

### 3.3 처리 순서의 원칙

1. **프로젝트·옵션 단계의 오류를 먼저 푼다.** 툴셋이나 SDK를 못 찾는 상태에서 나온 컴파일 오류는 의미가 없다.
2. **컴파일 오류는 C1083(파일을 열 수 없음)부터.** 헤더 하나를 못 찾으면 그 뒤로 수십 개의 오류가 따라 나온다.
3. **파일마다 첫 오류만 본다.** 같은 파일의 뒤 오류(C2143, C2059 같은 구문 오류)는 앞 오류의 여파인 경우가 많다.
4. **같은 코드의 오류는 묶어서 한 번에 처리한다.** 대부분 전처리기 정의 하나나 규칙 하나로 수십 건이 없어진다.
5. **한 묶음을 고치면 다시 빌드한다.** 오류 수가 줄지 않는 수정은 되돌린다.
6. **링크 오류는 컴파일 오류가 모두 없어진 뒤에 본다.**

### 3.4 "이 도구의 수정과의 관계"에 따라 갈린다

| 관계 | 뜻 | 대응 |
|---|---|---|
| 이 도구가 고친 줄 | 자동 수정이 오류를 만들었을 수 있다 | `out/diff/`에서 그 줄의 변경을 본다. 틀렸으면 그 줄을 원본으로 되돌린다. 같은 규칙에서 반복되면 규칙을 고치거나 끈다(3.6) |
| 수동 검토로 남긴 곳 | 도구가 미리 알려 준 지점이다 | 2.2대로 직접 고친다. 예상된 오류다 |
| 이 도구가 고친 파일의 다른 줄, 고치지 않은 파일 | 규칙에 없는 유형이다 | 3.9의 대응표를 따른다. 설정으로 풀리면 설정을, 반복되는 코드 수정이면 규칙을 더한다(3.5) |
| (관계 없음) | 링크 오류나 프로젝트 오류처럼 소스 줄이 없는 것 | 3.7, 3.9 |

### 3.5 같은 오류가 여러 곳에서 나면 규칙으로 만든다

고치는 방법이 하나로 정해지는 오류가 여러 파일에서 반복되면 `config/rules.json`에 규칙을 더하고 그 파일들만 다시 돌린다. 코드를 고칠 필요가 없다.

```json
[
  {
    "id": "R-T1-MY-RENAME",
    "tier": "T1",
    "title": "이름이 바뀐 함수",
    "pattern": "(?<![\\w.>:])OldName\\s*\\(",
    "action": { "type": "replace", "text": "NewName(" }
  }
]
```

```
vupdate run --package <패키지> --from-vs 2008 --to-vs 2022 --rules config/rules.json --only "Src/Net/*"
```

- 한 번에 고칠 자신이 없으면 `"tier": "T3", "llm": false`로 두어 탐지만 한다. 어디에 몇 건인지 먼저 볼 수 있다.
- 문맥을 보고 고쳐야 하면 `"tier": "T3", "llm": true`와 `"guidance"`(고치는 방법을 적은 문장)로 sLLM에 맡긴다.
- 규칙의 형식은 `04_개발구조.md` 10절에 있다.

### 3.6 자동 수정이 틀렸을 때

| 범위 | 방법 |
|---|---|
| 그 줄만 | 빌드 환경에서 원본 줄로 되돌린다. 이 PC의 원본 패키지는 바뀌지 않았으므로 원본을 그대로 참고할 수 있다 |
| 그 파일 전체 | `out/changed/`의 그 파일을 쓰지 않고 원본 파일을 쓴다 |
| 그 규칙 전체 | `config/rules.json`에 같은 ID로 규칙을 다시 적으면 내장 규칙을 대신한다. 조건(`when`)을 좁히거나 `"tier": "T3", "llm": false`로 바꿔 탐지만 하게 한 뒤 다시 실행한다 |
| 특정 폴더 | `--exclude`로 빼고 다시 실행한다 |

### 3.7 링크 오류의 갈래

링크 오류는 대부분 소스가 아니라 **함께 링크하는 것들이 서로 맞지 않아서** 난다. `project_settings.md` 3절의 바이너리 목록과 4절의 프로젝트 설정을 같이 본다.

| 증상 | 원인 | 대응 |
|---|---|---|
| LNK2038 `_MSC_VER` 불일치 | 구 버전으로 만든 .lib가 섞였다 | 그 .lib를 대상 툴셋으로 다시 빌드한다. 소스가 없으면 제공처에 요청한다. VS2015 이후끼리는 호환된다 |
| LNK2019에 `_sprintf`, `_vsnprintf`, `__imp__fprintf` 같은 이름 | VS2015 이전에 만든 .lib가 구 CRT의 stdio 함수를 참조한다 | 그 .lib를 다시 빌드하는 것이 원칙이다. 다시 빌드할 수 없으면 `legacy_stdio_definitions.lib`를 추가로 링크한다 |
| LNK2019에 `__iob_func`, `_iob` | 같은 원인인데 없어진 CRT 내부를 참조한다 | `legacy_stdio_definitions.lib`로는 풀리지 않는다. 그 .lib를 다시 빌드한다. 소스가 없으면 제공처에 새 바이너리를 요청하거나, 그 라이브러리를 구 컴파일러로 만든 별도 DLL 뒤로 감싼다 |
| LNK2019에 `unsigned short const *` | wchar_t 설정(/Zc:wchar_t)이 .lib와 다르다 | 양쪽 설정을 맞춘다 |
| LNK1104 `mfc90.lib`, `LIBC.lib` 같은 구 이름 | 구 버전 개체가 남아 있거나 없어진 라이브러리를 요구한다 | 중간 산출물 폴더를 지우고 전부 다시 빌드한다. 구 .lib는 다시 빌드한다 |
| LNK1112 | x86과 x64가 섞였다 | 플랫폼에 맞는 .lib를 쓴다 |
| LNK2005, LNK4098 | 런타임 라이브러리(/MT, /MD)가 섞였다 | 모든 프로젝트와 .lib를 하나로 통일한다 |

### 3.8 빌드가 된 뒤에 볼 것

빌드 성공은 이 작업의 목표이지만 끝은 아니다. 아래는 컴파일러가 알려 주지 않는 동작 변화다.

| 항목 | 확인할 것 |
|---|---|
| `manual_review.md`의 남은 항목 | 빌드와 무관하게 남은 것(GetVersionEx 등 동작이 달라지는 것) |
| T2 규칙과 sLLM의 수정 | `report.md` 7절의 확인 대상. 특히 가드로 감싼 매크로(round 등)는 새 CRT의 함수로 바뀌므로 음수 반올림 같은 경계 동작 |
| 경고 | C4244, C4267(자료 손실), C4477(형식 문자열)은 x64에서 실제 오류가 될 수 있다 |
| 구조체 크기 | `time_t`를 담은 구조체, WINVER에 따라 크기가 달라지는 Windows 구조체. 파일이나 통신으로 주고받는 것이면 반드시 확인한다 |
| 실행 환경 | 대상 PC에 새 런타임(재배포 패키지)이 있는지 |

### 3.10 한계

- **자동으로 고치지 않는다.** 빌드 오류를 이슈로 넣어 sLLM에 다시 맡기는 일은 만들지 않았다. 실제 로그에서 어떤 오류가 많이 나오는지 본 뒤에 만드는 것이 맞다.
- **대응표는 출발점이다.** 실제 패키지의 빌드로 확인한 것이 아니다. 로그를 한 번 돌려 보면 표에 없는 코드와 맞지 않는 대응이 드러난다. 그때 `ERROR_GUIDE`를 고친다.
- **줄 대조는 근사다.** "이 도구가 고친 줄"은 오류 줄이 바뀐 줄의 앞뒤 2줄 안에 있다는 뜻이다. 수정이 원인이라는 증명은 아니다.
- **빌드 환경에서 직접 고친 내용은 이 PC의 원본에 반영되지 않는다.** 다시 실행하면 그 수정은 결과물에 없다. 반복되는 수정은 규칙으로 옮겨 둔다(3.5).
