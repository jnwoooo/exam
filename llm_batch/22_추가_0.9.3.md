0.9.2는 `--compat-llm`에 값 1, 2, 3을 처음 넣은 판이고, 0.9.3은 그 단계의 뜻을 "처리의 깊이"로 다시 정한 판이다. 0.9.2의 단계 정의는 쓰지 않는다. 이 문서는 0.9.3 기준이다.

## 1. 한눈에

| 무엇 | 0.9.1 | 0.9.3 |
|---|---|---|
| `--compat-llm` | 값 없는 켬/끔 | **값 1, 2, 3**. 주지 않으면 1 |
| 보안 CRT 함수의 변환 | 켜면 규칙에 걸린 줄을 모두 sLLM에 보냄 | 2단계부터, **조건에 맞는 줄만 규칙이 바꾼다**. sLLM에 보내지 않는다 |
| Winsock 사용 중단 함수 | 켜면 모두 sLLM에 보냄 | 어느 단계에서도 바꾸지 않는다(설정으로만 해결) |
| 규칙이 못 고치는 필수 항목(`gets` 등) | 켜면 sLLM에 보냄 | 3단계에서 sLLM에 보낸다 |
| 없는 `_s` 함수 이름 | 메모만 남기고 받음 | 기각 |
| 헤더 오류로 막힌 컴파일 검사 | "새 오류 없음"으로 통과 | **미수행**으로 기록, 검증 수준 L2 |
| 사용 예 | 머리말의 몇 줄 | `vupdate examples`, 문서 23 |

값 없이 `--compat-llm`만 주면 입력 오류다(단계의 뜻을 알려 준다). PowerShell 스크립트는 `-CompatLlm 3`처럼 준다.

## 2. `--compat-llm`의 세 단계

단계가 올라갈수록 처리가 깊어진다. 위 단계는 아래 단계의 일을 모두 한다.

| 단계 | 하는 일 | sLLM 호출 | 남는 것 |
|---|---|---|---|
| **1** (기본) | **기계적 변경만.** 글자 꼴만 보고 정하는 규칙의 수정(10개 규칙)과 설정 처리 | 없음 | 규칙이 못 고친 것은 수동 검토 |
| **2** | 1 + **선언을 읽어 판정하는 기계적 변환.** 같은 함수의 `char` 지역 배열에 쓰는 `strcpy`, `strcat`, `sprintf`를 보안 CRT 함수로 바꾼다(규칙 `R-T2-CRT-SECURE-LOCAL`) | 없음 | 규칙이 못 고친 것은 수동 검토 |
| **3** | 2 + **기계적 변경 뒤에 남은 것을 sLLM에 맡긴다.** 고치지 않으면 컴파일되지 않는 것(규칙 5개: 없어진 `gets`, x64의 `SetWindowLong` 계열, `stdint` 타입·`timespec`·`char16_t`의 자체 정의) | 있음 | sLLM이 못 고친 것은 수동 검토 |

- 3단계에서 sLLM이 받는 조각에는 1, 2단계의 수정이 이미 반영돼 있다.
- 2단계의 변환만 빼고 3단계를 쓰려면 `--compat-llm 3 --disable-rule R-T2-CRT-SECURE-LOCAL`을 준다.
- `vupdate rules --from-vs … --to-vs … --compat-llm 2`로 그 단계에서 켜지는 규칙을 볼 수 있다.
- 3은 호출이 늘 수 있다. `--max-calls`와 함께 쓴다.

### 2.1 단계를 이렇게 나눈 근거

| 판단 | 근거 |
|---|---|
| 단계의 축을 "누가 고치는가"로 잡았다 | 1 → 2 → 3으로 갈수록 판정에 필요한 정보가 늘고(글자 꼴 → 선언 → 문맥), 결과의 예측 가능성은 준다. 1과 2는 같은 입력에 늘 같은 결과가 나오고 호출이 없다. 3만 모델의 답에 달려 있다 |
| 보안 CRT 변환을 sLLM이 아니라 규칙(2단계)에 뒀다 | 바꿔도 되는 조건을 도구가 판정할 수 있으면 수정도 한 가지 꼴로 정해진다(3.3). 모델에 맡기면 호출이 들고, 같은 답을 얻기 위해 수용 검사를 따로 둬야 한다. 0.9.2가 그렇게 했고 이 판에서 걷어냈다 |
| 조건에 맞지 않는 보안 CRT 줄은 3단계에서도 sLLM에 보내지 않는다 | `strncpy`, 구조체 멤버, 버퍼의 위치에 쓰는 줄에는 동작이 같은 보안 함수 꼴이 없다. 누가 바꿔도 실제 코드에서 나온 결함(공간 부족, 다음 필드에 NUL, 잘림)이 된다 |
| Winsock은 어느 단계에도 넣지 않았다 | 새 함수는 인자와 반환값의 꼴이 다르다. 도구가 "바꿔도 같다"를 판정할 조건을 정하지 못했고, 설정으로 빌드가 된다 |
| 3단계에서 sLLM이 받는 것을 "고치지 않으면 컴파일되지 않는 것"으로 한정했다 | 맞는 답이 있고, 규칙으로는 못 정하고, 안 고치면 빌드가 안 되는 것만 모델에 맡길 값이 있다 |
| 필수 항목(`gets`)이 선택 항목(보안 CRT)보다 뒤 단계에 있다 | 축을 필요성이 아니라 깊이로 잡은 결과다. 필수만 sLLM에 맡기고 싶으면 위의 `--disable-rule` 조합을 쓴다 |
| `gets`를 2단계의 규칙으로 옮기지 않았다 | 지역 배열이면 `gets_s(배열, sizeof(배열))`로 기계적으로 바꿀 수 있다. 이번에는 단계 정의만 바꿨다. 옮기면 3단계의 호출이 준다(하지 않음) |

## 3. 2단계: 보안 CRT의 기계적 변환

### 3.1 바꾸는 줄

다음을 모두 만족하는 줄만 바꾼다.

1. 호출이 `strcpy`, `strcat`, `sprintf` 가운데 하나다.
2. 호출이 문장 하나로 쓰였다. 반환값을 쓰지 않는다(`if (..)`, `else`, `for (..)` 뒤의 문장은 된다).
3. 첫 인자가 단순한 이름이고, 그 이름은 **같은 함수에서 선언된 1차원 `char` 지역 배열**이다.
4. 배열 크기를 숫자로 알 수 있다. 숫자, 패키지의 `#define`·`enum` 값, `MAX_PATH` 같은 널리 쓰이는 상수와 사칙연산을 읽는다.
5. 그 배열이 같은 함수에서 바이트 단위 함수(`memcpy`, `memmove`, `memcmp`, `fwrite`, `WriteFile`, `send`, `sendto`, `write` 등)의 인자로 쓰이지 않는다.
6. `sprintf`는 형식이 문자열 리터럴이고, 형식에서 계산한 최소 출력 길이 + 1이 배열 크기 이하다. `strcpy`·`strcat`에 문자열 리터럴을 주면 그 길이 + 1이 배열 크기 이하다.

### 3.2 바꾸지 않는 줄과 사유

사유별 줄 수와 예는 보고서의 "보안 CRT 함수의 기계적 변환" 절에 표로 나온다. 이 줄들은 sLLM에도 보내지 않는다.

| 사유 | 예 |
|---|---|
| 대상 함수가 아님 | `strncpy(...)`, `strncat(...)`, `fopen(...)`, `_itoa(...)`, `strtok(...)` |
| 구조체 멤버에 쓰는 줄 | `sprintf(m->seq, "%06d", n);`, `strcpy(msg.code, s);` |
| 버퍼의 위치에 쓰는 줄 | `strcpy(buf + 5, s);`, `sprintf(&hex[i * 2], "%02x", b);` |
| 반환값을 쓰거나 다른 식 안에 있는 호출 | `p = strcpy(a, s);`, `n = sprintf(a, "%d", v);` |
| 첫 인자가 이 함수의 지역 배열이 아님 | 함수 인자, 전역, 포인터 |
| `char` 1차원 배열이 아님 | `unsigned char`, 2차원 배열 |
| 배열 크기를 숫자로 확인하지 못함 | `char un[SOME_EXPR];` |
| 바이트 단위 함수에도 쓰이는 버퍼 | `strcpy(raw, s); memcpy(out, raw, 16);` |
| `sprintf`의 형식이 리터럴이 아니거나 읽지 못함 | `sprintf(a, fmt, n);`, `"%" PRIuPTR` |
| 최소 길이와 NUL이 배열에 들어가지 않음 | `char seq[6]; sprintf(seq, "%06d", n);`, `char one[1]; sprintf(one, "%d", n);` |
| 같은 줄의 다른 호출이 조건에 맞지 않음 | `strcpy(a, s); strcpy(out, s);` |
| 함수 밖의 코드 | 매크로 정의 안의 호출 |

형식의 최소 출력 길이는 폭을 준 변환(`%06d`)은 그 폭, 정수와 문자는 1, `%s`는 0, 글자는 바이트 수(CP949의 한글은 2)로 센다.

### 3.3 바꾼 꼴은 하나

```c
strcpy(buf, src);              →  strcpy_s(buf, sizeof(buf), src);
strcat(buf, ".dat");           →  strcat_s(buf, sizeof(buf), ".dat");
sprintf(buf, "%s:%d", s, n);   →  sprintf_s(buf, sizeof(buf), "%s:%d", s, n);
```

함수 이름 뒤에 `_s`를 붙이고 첫 인자 바로 뒤에 `sizeof(첫 인자)`를 넣는다. 나머지 인자, 공백, 줄바꿈, 주석은 건드리지 않는다.

### 3.4 그래도 달라지는 것(검토 대상)

- 버퍼가 모자랄 때의 동작이 달라진다. 옛 함수는 넘쳐 썼고, 보안 함수는 잘못된 매개변수 처리기를 불러 프로그램을 끝낸다.
- Debug 빌드에서는 문자열 뒤의 남는 자리가 0xFE로 채워진다. 버퍼 전체를 길이와 함께 넘겨 쓰는 **자체 함수**가 있으면 도구가 알 수 없다. 그 함수의 이름을 서버 설정의 `limits.scrt_raw_calls`에 적으면 그 함수에 넘기는 버퍼는 변환에서 빠진다.

```json
{ "limits": { "scrt_raw_calls": ["SendPacket", "WriteRecord"] } }
```

- 바꾼 곳은 모두 보고서의 "적용했지만 사람이 확인해야 하는 수정" 목록에 나온다.
- 줄 단위로 빼려면 예외 파일에 적는다: `{"skip": [{"path": "Src/Msg.c", "rules": ["R-T2-CRT-SECURE-LOCAL"], "lines": "120-140"}]}`

## 4. 검증과 수용 검사의 보강

### 4.1 컴파일 검사가 막힌 경우

컴파일 검사(L3)는 수정 전과 후의 오류 목록을 비교해 새 오류가 있는지 본다. 원본이 치명적 오류(열 수 없는 헤더 C1083, 오류 수 초과 C1003 등)로 중단되면 컴파일러가 그 뒤의 줄을 보지 않아 두 목록이 같아진다. 0.9.1은 이것을 통과로 기록했다.

| 경우 | 처리 |
|---|---|
| 원본에 치명적 오류가 있다 | L3 **미수행**. 사유에 오류 코드와 메시지를 적는다. 파일의 검증 수준은 L2다 |
| 원본에는 없고 수정 뒤에 치명적 오류가 생겼다 | 불합격. 수정을 취소한다 |
| 원본에도 있던 보통 오류 | 전과 같다. 새 오류로 치지 않는다 |

검사하지 못한 변경 파일이 있으면 로그에 경고가 나오고 보고서 첫머리에 파일 수와 해야 할 일(include 경로를 맞춘 뒤 다시 실행)이 적힌다. 파일별 컴파일 출력은 `logs/compile/`에 있다.

### 4.2 없는 `_s` 함수 이름

sLLM의 수정에 새로 생긴 `_s`로 끝나는 함수 호출이 조각, 패키지, C 런타임의 이름 목록 어디에도 없으면 기각한다(`_strncat_s`, `_gets_s`). 어떤 작업의 수정이든 본다. 실제로 있는데 목록에 없는 이름이 기각되면 서버 설정의 `limits.known_names`에 적는다. `limits.new_name_check`가 `off`면 이 검사도 하지 않는다.

## 5. [수정 대상 줄]의 표식은 무엇인가

수정 요청문에는 같은 표식이 두 곳에 나온다.

```
[수정 지침]
- [R-T3-GETS-REMOVED] 없어진 함수 gets 사용(C3861): VS2015 부터 gets 가 없다. ...
- [ASK-1-1] 사용자 요청: WriteLog 호출에 줄 번호 인자를 추가한다: ...

[수정 대상 줄] (코드 조각 안의 줄 번호와 내용)
- 7번째 줄 [R-T3-GETS-REMOVED]: gets(buf);
- 9번째 줄 [ASK-1-1]: WriteLog("start");
```

- 표식은 **그 줄에 어느 지침을 적용할지 잇는 이름표**다. 조각 하나에 종류가 다른 대상이 섞일 수 있어서 줄마다 붙인다.
- 지침은 종류마다 한 번만 적고, 대상 줄은 표식으로 그 지침을 가리킨다. 지침 문장을 줄마다 되풀이하지 않기 위한 것이다.
- 모델의 응답에는 쓰이지 않는다. 응답은 수정 블록뿐이고 도구는 표식을 읽지 않는다.
- 조각에 지침이 하나뿐이면 줄마다 같은 표식이 되풀이되어 정보가 없다. 줄당 몇 토큰이 더 들 뿐 해는 없다. 이 경우 표식을 빼는 것은 하지 않았다.
- 0.9.1에서 보이던 `[L-CRT-SECURE]`는 보안 CRT 줄을 sLLM에 보낼 때의 표식이다. 0.9.3은 그 줄을 sLLM에 보내지 않으므로 이 표식은 더 나오지 않는다.

## 6. 확인한 것

| 무엇 | 조건 | 결과 |
|---|---|---|
| 실제 코드의 결함과 같은 꼴(전문 조립 예제 8줄) | 3단계, 모의 모델이 결함과 같은 수정으로 답하게 함 | sLLM 호출 0회. 지역 배열의 `strcpy` 1줄만 규칙으로 바뀌고 나머지 7줄은 원본과 같다. 0.9.1은 결함 수정 8건을 모두 받았다 |
| 대상 선정 | 사유별 합성 예제 34줄 | 바꿀 9줄만 바꿨고, 나머지 25줄은 한 글자도 바뀌지 않았으며 사유가 기대와 같았다 |
| 변환의 꼴 | 공백이 다른 호출, 여러 줄에 걸친 호출, `if`/`else` 뒤의 호출 | 이름과 크기 인자만 바뀌고 나머지는 그대로다 |
| 공개 코드(Notepad++ 610만 자) | 2단계, 전 단계 실행 | 보안 CRT 줄 72곳 가운데 5곳을 규칙으로 바꿨다. sLLM 호출 0회, 전체 9초 |
| 막힌 컴파일 검사 | 모의 컴파일러(C1083) | 미수행, L2, 보고서에 경고 |
| 사용 예 | 표의 명령 61개 | 모두 명령줄 형식에 맞고, 실행할 수 있는 59개를 돌려 입력 오류가 없었다 |
| 시험 | Linux, 모의 모델 | 자체 시험 50, 규칙 시험 33, `tests/` 9종 전 항목 통과(`test_v092.py` 24항목) |

공개 코드에서 바꾼 5곳은 `char intBuffer[32]; sprintf(intBuffer, "%d", ...)` 같은 임시 문자열 버퍼였고, 바꾸지 않은 것에는 `sprintf(hashStr + i * 2, "%02x", hash[i])` 같은 위치 쓰기가 있었다.

## 7. 하지 않은 것

| 항목 | 상태 |
|---|---|
| `gets`를 2단계의 규칙으로 옮기기(2.1) | 하지 않았다 |
