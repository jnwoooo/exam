## 2. 책임 구간

요청 하나가 지나가는 구간과, 구간마다 누가 무엇을 책임지는지다.

| 구간 | 책임 | 하는 일 | 보장하는 것 | 실패하면 |
|---|---|---|---|---|
| G1 요청 접수·분류 | 사용자, 도구(모델은 선택) | 요청을 유형과 세 칸(무엇을, 어디에서, 동작)으로 정한다 | 유형이 정해진 요청만 뒤로 간다 | 분류 못 한 요청은 실행 전에 거절하고 이유를 말한다 |
| G2 대상 추출 | 도구 | 유형별 추출기로 대상 지점을 찾는다 | 추출 기준에 맞는 곳은 빠짐없이 찾는다(글자 기준) | 범위를 못 정한 곳은 "미확정"으로 분리한다(E6) |
| G3 계약 확정 | 도구, 사람 확인 | 파일 사이에 걸친 변경의 새 정의를 먼저 정한다(E3) | 모든 사용처가 같은 정의를 본다 | 계약을 못 정하면 그 요청 전체를 수동으로 |
| G4 조각 구성·예산 | 도구 | 편집 영역과 참고 영역을 만들고 토큰 예산에 맞춘다 | 한도 안에 든다. 생략한 곳은 모델이 건드릴 수 없다 | 줄여도 안 되면 분할, 그래도 안 되면 수동 |
| G5 호출·한도 | 도구, 서버 | 순서, 동시 수, 재요청, 예산 | 넘치는 요청은 잘리지 않고 거절된다(서버). 받은 응답은 다시 보내지 않는다 | 남은 작업은 대기로 두고 이어서 |
| G6 수정 생성 | sLLM | 조각을 읽고 수정 블록을 낸다 | **없음**. 틀릴 수 있다고 본다 | G7이 걸러 낸다 |
| G7 건별 수용 검사 | 도구 | 형식, 위치, 범위, 불변식 | 통과한 수정은 원문의 정해진 범위만 바꾼다 | 기각 사유를 붙여 재요청(2회), 그 뒤 수동 |
| G8 병합·영향 확인 | 도구 | 수정을 합치고, 바뀐 선언의 사용처와 남은 옛 참조를 다시 찾는다(E2, E4) | 계약과 어긋나는 잔여 참조를 보고한다 | 어긋나면 그 요청의 수정을 되돌린다 |
| G9 파일 검증 | 도구, 컴파일러 | 원본과 비교한 차등 검증(F6) | 새 구문 오류가 없다. 컴파일러가 있으면 새 컴파일 오류가 없다 | sLLM 수정만 빼고 다시, 그래도 안 되면 파일 전체 제외 |
| G10 빌드·시험·검토 | 사람 | 실제 빌드와 동작 확인 | 링크와 실행 동작은 여기서만 확인된다(F11) | 오류 로그를 `--build-log`로 다시 넣는다 |

원칙은 하나다. **모델은 G6 한 구간만 맡고, 그 앞뒤는 전부 도구가 결정적으로 처리한다.** 모델이 틀려도 G7~G9에서 걸리거나, 걸리지 않으면 "검토 필요"로 사람에게 간다.

## 4. 분류와 추출 (G1, G2)

### 4.1 세 칸과 유형 사전

요청은 세 칸으로 옮긴다. 도구가 가진 추출기는 "어디에서"의 정해진 목록에 대응한다.

| 칸 | 값의 종류 | 누가 정하나 |
|---|---|---|
| 무엇을 | 이름 집합, 글자 패턴, 오류 줄 | 문장 속 이름(도구), 뜻 → 이름(모델 1회 + 사람 확인) |
| 어디에서 | 파일 범위, 영역(코드·문자열·주석), 구문 범위(함수, if, for, switch, 초기화 목록) | 유형 사전의 값 |
| 동작 | 찾기, 교체, 호출 수정, 문장 묶음 수정, 계약 변경, 추가 | 유형 사전의 값 |

유형 하나는 다음을 묶는다: 추출기, 조각 단위, 수정 지침, 수용 검사(불변식), 부작용 점검 항목. 설정 파일에 두고 관리자가 추가한다. 사용자는 문장만 쓴다.

### 4.2 추출기와 구현 수단 (표준 라이브러리만)

| 추출기 | 방법 | 상태 |
|---|---|---|
| 이름 일치 | 주석·문자열을 가린 본문에서 단어 경계 일치 | 있음 |
| 문장 속 이름 | 요청문의 영문 이름 중 코드에 있는 것. "~로"가 붙은 이름은 결과로 본다 | 시험 코드로 확인(5문장 중 이름이 있는 4문장) |
| 호출 이름 목록 | `이름(` 꼴을 세어 빈도표를 만든다 | 시험 코드로 확인 |
| 구문 범위(if, for, switch) | 조건 괄호의 짝 → 본문의 `{}` 짝 또는 `;` → `else` 연쇄 | 시험 코드로 확인(중첩, 중괄호 없는 if, `#if` 제외) |
| 선언 찾기 | 함수 본문 시작부터 대상 줄까지 거꾸로 훑어 가장 가까운 선언. 없으면 인자, 그다음 전역·타입 | 시험 코드로 확인 |
| 초기화 목록 | 2,000자를 넘는 `= { ... }`의 범위와 해시 | 있음 |
| 초기화 목록의 모양 | 행 수, 행마다의 요소 수 | 시험 코드로 확인(152만 자, 0.12초) |
| 문자열·주석 영역 | 가리기의 반대(가린 구간이 곧 영역) | 구간 정보는 있음. 추출기는 없음 |
| 오류 줄 | 빌드 로그의 파일·줄·코드 | 있음 |

### 4.3 추출이 틀리는 곳

- 괄호를 숨긴 매크로, `#if`로 갈라진 문장: 범위가 틀릴 수 있다. 괄호 깊이가 함수 끝에서 0이 아니면 그 함수는 "범위를 못 정함"으로 분리한다.
- 별칭, 함수 포인터, 매크로를 거친 접근: 글자 일치로는 못 찾는다. E6대로 근사임을 표기한다.
- 뜻 → 이름을 모델이 틀리게 고르는 경우: 고른 이름 목록을 실행 전에 보여 준다. 시험은 `--only`로 파일을 한정해 먼저 돌린다.

## 5. 조각 구성: 함수 일부를 뽑고 줄이는 방법 (G4)

### 5.1 지금 구현의 원리

1. 규칙 수정을 반영한 본문에서 줄 범위를 고른다.
2. 그 범위의 "보기"를 만든다. 큰 초기화 목록은 표식 한 줄로 바꾸고, 보기의 각 구간이 원문의 어디인지 대응표를 남긴다(`build_view`, `segs`).
3. 모델은 보기 안의 글자를 SEARCH로 가리킨다. 도구는 대응표로 원문 좌표를 구해 그 범위만 바꾼다(`view_to_text`).
4. 표식에 걸친 SEARCH는 기각한다. 병합 뒤 큰 초기화 목록의 해시를 다시 확인한다.

그래서 **생략한 부분은 모델이 다시 쓰지 않는다.** 줄였기 때문에 내용이 깨지는 일은 구조상 없다. 깨질 수 있는 것은 "줄여서 모델이 못 본 정보" 때문에 생기는 틀린 수정이다(6절).

### 5.2 편집 영역과 참고 영역

| 영역 | 내용 | 규칙 |
|---|---|---|
| 편집 영역 | 대상 줄이 든 문장과 그 주변 | 원문 그대로 보낸다(D12). SEARCH는 여기서만 일치한다 |
| 참고 영역 | 함수 머리, 감싼 블록의 머리 줄, 선언, 타입 정의, 계약 발췌 | 읽기 전용이다. SEARCH의 일치 대상이 아니라서 고칠 수 없다. 주석을 지우고 줄여도 된다(D12) |

### 5.3 예산을 채우는 순서

지금은 "앞뒤 25줄 고정, 넘칠 때만 12, 5, 0줄로 줄임"이다. 이 축소는 PC 안의 글자 수 계산이고 모델 호출이 아니다(400줄 조각의 추정에 0.03ms). 다만 남는 예산을 쓰지 않는다.

바꿀 방식은 쓸모 있는 순서로 넣다가 목표 예산에서 멈추는 것이다.

1. 대상 줄이 든 문장 전체(편집)
2. 대상을 감싼 블록의 머리 줄: 함수, if, for, switch(참고)
3. 대상 줄에 쓰인 이름의 선언: 지역 → 인자 → 전역·타입·매크로(참고)
4. 계약 가운데 이 조각에 나온 이름에 해당하는 항목만(참고)
5. 앞뒤 줄(편집). 문장 경계에 맞춘다
6. 대상이 없는 형제 블록은 표식으로 접는다

입력 상한은 (24,000 − 출력 3,000 − 서버 몫) ÷ 1.1 = 약 19,000 추정 토큰이다. 목표 예산은 그보다 훨씬 작게 둔다(예: 4,000). 입력이 길면 느리고, 작은 모델은 긴 입력에서 정확도가 떨어진다.

## 6. 조각 때문에 생기는 수정 오류와 대처

"사전"은 틀린 수정이 덜 나오게 하는 것이고 "사후"는 나온 것을 잡는 것이다. 사전은 확률을 올릴 뿐이고 보장은 사후 검사에서만 나온다.

| # | 오류 | 예 | 사전 | 사후 | 0.7.1 |
|---|---|---|---|---|---|
| X1 | 선언을 몰라 틀리게 고침 | `gets(ptr)` → `fgets(ptr, sizeof(ptr), stdin)`. `ptr`이 포인터면 크기가 4나 8이 된다. 문법은 맞아서 컴파일도 된다 | 선언 주입(5.3의 3) | 유형별 검사: `sizeof` 대상의 선언이 포인터면 기각 | **없음**. 실행 확인: 6줄의 `char line[64];`가 69줄 대상의 요청문에 없다 |
| X2 | 조각 밖에서도 쓰는 이름을 바꿈 | 지역 변수의 이름이나 타입을 바꿨는데 조각 아래에서 계속 쓴다 | 지침 | 수정 전후의 선언·이름 집합을 비교하고, 달라진 이름을 함수 전체에서 다시 찾는다 | 없음 |
| X3 | 조각에 없는 이름을 지어냄 | 없는 변수 `bufSize`를 쓴다 | 선언 주입 | 새 이름 검사: 조각, 참고, 지침, 패키지 어디에도 없는 이름이면 기각 | 없음 |
| X4 | 잘린 경계의 괄호를 "고침" | 조각 끝에 `}`를 더한다 | 문장 경계에 맞춰 자른다 | 괄호 짝이 원문과 같은지 | 검사 있음. 경계 맞춤은 분할 순차에만 |

| X7 | 생략 표식 훼손 | | | 표식 검사, 해시 | 있음 |
| X8 | 같은 함수의 다른 작업과 충돌 | 두 작업이 같은 보조 변수를 각각 선언한다 | 같은 함수의 작업은 차례로 보내고 앞 작업의 변경 내역을 붙인다 | 병합 뒤 같은 범위의 중복 선언 검사 | 분할 묶음만 내역을 공유 |
| X9 | 응답이 잘림 | | 예상 출력이 상한의 80%를 넘으면 나눈다 | 잘림 표시면 나눠서 다시 계획 | 있음 |

X1, X2, X3, X8의 대처는 전부 도구가 하는 결정적 처리이고 모델 없이 시험할 수 있다. X11은 정적 검사로 다 막지 못한다. 남는 위험이다.

시험 코드로 확인한 선언 주입 결과:

| 대상 | 찾은 선언 |
|---|---|
| 69줄 `gets(line);` | 6줄 `char line[64];` |
| 140줄 `gets(ptr);` | 7줄 `char* ptr = user->name;` → `user`는 인자 `USER_T*` → `typedef struct { char name[32]; int id; } USER_T;` |

참고로 지금의 정의 보강(`NEED_CONTEXT`)은 함수, `#define`, typedef, struct만 찾는다. 지역 변수는 찾지 못해 수동 검토로 간다.

## 7. 토큰 한도 우회

### 7.1 원칙

**모델의 출력은 바뀌는 부분만이다. 데이터는 다시 쓰게 하지 않는다.**
입력은 약 19,000 추정 토큰까지 들어가지만 출력은 3,000이다. 14,000자 표는 추정 5,008토큰이라 입력에는 들어가도 출력으로는 한 번에 못 받는다. 그래서 크기 문제는 "어떻게 나눠 보낼까"보다 "보내지 않고 처리할 수 있는가"를 먼저 본다.

### 7.2 전략

| 전략 | 쓰는 경우 | 모델 토큰 | 검증 | 상태 |
|---|---|---|---|---|
| T-A 데이터 불변 | 선언(타입)만 바뀌고 초기값의 순서는 그대로인 경우. 1차원 배열 → 구조체, 2차원 표 → 행 구조체의 배열, 평면 배열 → 구조체 배열 | 데이터에 0 | 초기화 목록의 해시가 같다 | 1차원은 됨. 2차원은 시험 코드로 확인 |
| T-B 명세로 변환 | 데이터 배치가 바뀌는 경우. 열 순서 변경, 병렬 배열 합치기, 값 → 이름 치환 | 명세만(수백) | 리터럴의 개수와 순서(또는 정한 순열)가 보존된다 | 없음 |
| T-C 행 단위 재출력(D11) | 행마다 판단이 필요한 경우만 | 데이터 전체 | 조각마다 행 수와 요소 수가 같다 | 없음(D11 미충족) |
| T-D 지점 조각 + 계약 발췌 | 사용처 | 곳당 수천 이하 | 6절 | 조각은 됨. 발췌는 없음 |

T-C의 호출 수는 추정 토큰 ÷ 2,400이다. 14,000자면 3회 이상, 152만 자면 227회다. 큰 데이터에는 쓰지 않는다. 쓰려면 호출 수를 보여 주고 승인을 받는다.

### 7.3 14,000자 상수 배열 → 구조체의 처리 절차 (송신 20k, 수신 3k)

| 단계 | 책임 | 내용 | 송신 | 수신 |
|---|---|---|---|---|
| 1 | 도구 | 선언, 요소 타입, 행·열 수 확인. 행마다 요소 수가 같은지 | 0 | 0 |
| 2a | 도구 | 매핑표(열 → 필드)가 있으면 구조체 정의를 만든다 | 0 | 0 |
| 2b | 모델, 사람 | 매핑표가 없으면 선언, 앞 5행, 사용처 표본을 주고 필드 이름을 제안받는다. 사람이 확인한다 | 1~2천 | 수백 |
| 3 | 도구 | 선언만 바꾼다. 초기화 목록은 그대로 두고 해시로 확인한다 | 0 | 0 |
| 4a | 도구 | 열이 상수인 사용처: `X[r][COL_MAX]` → `X[r].max` | 0 | 0 |
| 4b | 모델 | 열이 변수인 사용처, 통째로 넘기는 곳 | 곳당 1~3천 | 곳당 수백 |
| 5 | 도구 | 병합 뒤 옛 접근이 남았는지 재탐지(E4), 파일 검증 | 0 | 0 |

데이터는 어느 단계에서도 모델에 가지 않는다. 180만 자여도 같다(P5, D7).

실행 결과(0.7.1, 약 12,500자의 1차원 배열, 요소 1,000개):
- 선언 2곳을 구조체로 바꿨다. 초기화 목록의 해시는 원본과 같았다.
- 상수 인덱스 2곳은 필드로 바꿨다. `memcpy`의 인자에는 `&`를 붙였다.
- `for`에서 `PARAM_TBL[i]`로 도는 곳은 수동 검토가 됐다.

시험 코드 결과(약 16,500자의 2차원 표, 500행 × 6열):
- 선언 `const int LIMIT_TBL[500][6] =` → `const LIMIT_ROW_T LIMIT_TBL[500] =`. 초기화 목록의 해시는 같았다.
- 사용처 `LIMIT_TBL[row][COL_MIN]` → `LIMIT_TBL[row].min`.

### 7.4 0.7.1에서 고쳐야 하는 것

| 항목 | 문제 | 방향 |
|---|---|---|
| 계약 발췌 | 구조체 정의 전체가 요청문마다 들어간다(요소 1,000개에서 추정 1만 토큰) | 조각에 나온 이름의 필드만 넣고, 나머지는 "필드 N개, 순서는 인덱스와 같음" 한 줄로 |
| 2차원 표·구조체 배열 | 선언을 못 찾는다 | 선언과 사용처의 둘째 인덱스를 처리하는 규칙 추가 |
| 변수 인덱스·순회 | 구조체로 바꾸면 `X[i]`로 돌 수 없다. 지금은 수동 | 변환 전에 변수 인덱스 사용 건수를 보여 주고 결정받는다. 선택지로 "배열 보기 유지"(공용체로 필드와 배열을 함께 둠. `X[i]` → `X.raw[i]`로 규칙 치환)를 둔다. 표준 밖의 쓰임이라 기본값으로 하지 않는다 |
| 요소 1,024개 제한 | 1차원 배열이 그보다 크면 변환하지 않는다 | 유지. 필드가 그만큼 많은 구조체는 표(2차원)로 보는 것이 맞다 |

## 8. 호출 진행 (G5, G6)

### 8.1 호출 종류와 횟수

| 종류 | 언제 | 횟수 |
|---|---|---|
| 해석 | 뜻 → 이름, 필드 이름 제안 | 요청당 1~2 |
| 수정 | 작업마다 | 1 + 검사 기각 재요청 2까지 + 다시 계획 2까지 |
| 정의 보강 | `NEED_CONTEXT` | 2까지. 선언 주입이 들어가면 줄어든다 |
| 검토(선택) | 유형이 문장 묶음 수정일 때 | 수용 건당 1 |

횟수 제한은 되풀이가 생기는 곳에만 둔다. 위 표의 제한과, 연쇄 수정의 깊이(9.2)다.

### 8.2 순서

- 계약 → 헤더·타입 → 정의 → 사용처(E3). 지금은 이 순서를 보장하지 않는다.
- 같은 함수의 작업은 차례로 보내고 앞 작업의 변경 내역을 붙인다. 다른 함수는 병렬이다.
- 요청이 여럿이면 차례로 처리한다. 뒤 요청은 앞 요청의 결과 위에서 대상을 다시 찾는다.

### 8.3 양의 제어

- 한 번 실행에 보낼 호출 수를 예산으로 받는다. 남은 작업은 수동이 아니라 "대기"로 저장한다.
- 다음 실행이 대기부터 이어 간다. 받은 응답은 캐시에 있어 다시 보내지 않는다.
- 서버의 일일 한도에 걸렸을 때도 같은 경로로 이어 간다.
- 요청문 하나의 300곳 상한은 없앤다. 대신 실행 전에 대상 수와 예상 호출 수를 보여 준다.

### 8.4 서버가 책임지는 것

- 한도를 넘는 요청은 자르지 않고 거절한다. 실제 입력 토큰 수를 응답마다 돌려준다.
- Ollama 뒤라면 서버가 직접 판정해야 한다(앞선 답변의 내용 그대로).

## 9. 수정이 만드는 부작용 (E절)

### 9.1 분류 (E2)

도구가 수정 전후의 선언을 비교해 나눈다.

| 등급 | 뜻 | 처리 |
|---|---|---|
| ① 함수 안 | 본문의 문장만 바뀜. 선언과 이름 집합이 그대로 | 6절의 검사 |
| ② 파일·클래스 | 파일 안의 정적 함수, 지역 타입, 파일 범위 변수가 바뀜 | 같은 파일에서 사용처를 다시 찾아 대조 |
| ③ 파일 사이 | 헤더의 선언, 구조체, 전역, 매크로가 바뀜 | 계약이 있는 요청만 허용. 계약 없이 나온 ③은 기각 |

### 9.2 ③의 처리 (E3, E4)

1. 계약을 먼저 정한다. 사용처 요청문에는 계약의 발췌를 고정 사실로 넣는다.
2. 병합 뒤 패키지 전체에서 옛 이름과 옛 접근 형태를 다시 찾는다. 남은 것은 건수와 위치를 보고한다.
3. 남은 곳을 연쇄 수정으로 다시 보낼 때는 깊이를 2로 제한한다. 그 뒤는 수동이다.

### 9.3 배치와 크기 (E5)

- 구조체 정의를 건드리는 수정은 `sizeof`, 메모리 복사·송수신 함수, `offsetof`, 패킹 지정의 사용처를 점검 목록으로 낸다(지금 있음).
- 배열 → 구조체는 요소 타입과 순서를 유지해 크기와 배치가 같게 만든다. 정렬 때문에 달라질 수 있는 경우(요소 타입이 섞인 구조체)는 자동으로 바꾸지 않는다.
- 32비트와 64비트에서 크기가 다른 타입은 보지 않는다. 남는 일이다.

### 9.4 보장 범위

| 항목 | 보장 | 근거 |
|---|---|---|
| 생략한 데이터가 그대로다 | 예 | 해시 |
| 수정이 정한 범위 밖을 건드리지 않았다 | 예 | 좌표 대응, 범위 검사 |
| 새 구문 오류가 없다 | 예 | 차등 검증 |
| 계약과 어긋난 옛 참조가 글자 기준으로 없다 | 9.2를 구현하면 예 | 재탐지 |
| 컴파일된다 | 컴파일러가 있을 때만 | `cl /Zs` |
| 동작이 같다 | **아니오** | 빌드와 시험으로만 확인 |

## 11. 확인하지 못한 것

- 실제 sLLM이 선언을 보고 옳게 고치는지, 필드 이름을 쓸 만하게 제안하는지, 뜻 → 이름을 맞게 고르는지.
- 숫자 데이터의 실제 토큰 수. 추정은 2.8자당 1토큰인데 숫자와 쉼표는 더 잘게 쪼개질 수 있다. 실행 중 서버가 준 값으로 보정된다.
- 시험 코드의 선언 찾기와 구문 범위 찾기는 예제 몇 개로만 돌렸다. 매크로가 많은 실제 코드에서의 적중률은 모른다.
- "배열 보기 유지"(공용체) 방식이 대상 코드베이스의 규칙에 맞는지.
