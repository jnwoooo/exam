# 점검: 0.10.5의 실행 오류 가능성(vupdate.py)과 0.10.6의 보강

| 항목 | 내용 |
|---|---|
| 읽는 순서 | 31 |
| 작성일 | 2026-11-26 |
| 대상 코드 | `vupdate.py` 0.10.5를 점검하고 0.10.6에서 보강 |
| 배경 | 0.10.3이 실제 코드에서 IndexError로 멈춤(`30_추가_0.10.4.md`). 같은 종류의 오류가 더 있는지 점검 요청 |
| 확인 범위 | Linux, 공개 코드(Notepad++)와 합성 패키지, 모의 sLLM, 모의 컴파일러, g++. 실제 코드, 실제 gemma4, Windows의 cl에서는 확인하지 못했다 |

## 1. 결론

- 점검에서 **새로 드러난 실행 오류는 없었다.** 예외로 끝난 실행, 로그의 오류 표시, 구조 분석이 읽지 못한 함수 모두 0건이다.
- 다만 "오류가 없다"를 보장하는 점검은 아니다. 실제 코드의 꼴은 합성 패키지와 다를 수 있다.
- 그래서 0.10.6은 **오류가 나더라도 실행 전체가 멈추지 않게** 했다. 0.10.3의 사고는 함수 하나를 처리하다 난 오류가 실행 전체를 멈춘 것이었다.

## 3. 까다로운 합성 패키지에 넣은 꼴

- 구조체: 이름 없는 것, 포인터 별명만 있는 것, 비트 필드, 길이 0 배열과 크기 없는 배열, 정의되지 않은 크기, 함수 포인터 멤버, 안쪽의 이름 없는 구조체와 공용체, `#if`가 든 것, 템플릿, 빈 구조체, 선언만 있는 것, 두 파일에 다르게 정의된 것, `pack(1)`
- 클래스: 상속받은 멤버, 구조체 배열 멤버, 안쪽 구조체, static 멤버, 헤더 안에 본문이 있는 메서드
- 버퍼 접근: 조건식이 든 위치, `i++` 첨자, `sizeof x`, `sizeof(*p)`, `sizeof(((T*)0)->m)`, `_countof`, 인자가 모자란 `memcpy_s`, 괄호와 따옴표가 든 문자열, switch의 이어지는 case, do-while, try/catch, 람다, goto, 옛 방식 함수 정의, 빈 함수
- 묶음: `'\0'`, `'\''`, `0x20`, 음수로 채우기, 길이를 식으로 준 것, 중괄호 없는 if 안의 memset, 쉼표로 이은 문장, 매크로로 채우기, static·const 배열, 3차원 배열, 크기 1, 크기 없는 배열, 안쪽 블록의 배열, 도구가 쓰는 이름(`iRec`, `stRec`)과 같은 변수
- 사용 중단 함수: 여러 줄에 걸친 호출, 매크로 안, 문자열과 주석 안, 조건식 안, 인자 수가 다른 호출, 반환값을 쓰는 호출
- 파일: 빈 파일, CR만 있는 파일, 줄끝이 섞인 파일, BOM, 잘못된 바이트와 NUL, 한 줄이 4만 자인 파일, 한글과 공백과 괄호가 든 이름, 깊은 경로, 괄호 짝이 맞지 않는 파일
- 백업: 백업 폴더, `_old` 사본, 서로를 include하는 백업 헤더
- 프로젝트: 깨진 XML, 옛 형식(.vcproj), 없는 파일과 프로젝트를 가리키는 것, 매크로·절대 경로·패키지 밖을 가리키는 include 경로

## 4. 0.10.6의 보강

오류를 가두는 범위를 좁은 것부터 적는다.

| 범위 | 0.10.5 | 0.10.6 |
|---|---|---|
| 버퍼 하나의 처리 계획 | 오류가 나면 실행이 멈춤 | 그 버퍼만 바꾸지 않는다. 사유 "분석 중 오류로 바꾸지 않음"을 남기고 sLLM에도 보내지 않는다 |
| 묶음 하나를 이름을 정해 다시 계획 | 멈춤 | 그 묶음만 바꾸지 않는다 |
| 요청 하나(`buffer_fields`, `record_group`, 배열 요청) | 멈춤 | 그 요청이 넣은 수정과 이슈를 **모두 되돌리고** 사유를 남긴 뒤 다음 요청으로 간다. 일부만 바뀐 결과를 내지 않는다 |
| 요청문의 대상 찾기 | 멈춤 | 남은 요청문을 수동 검토로 올리고 계속한다 |
| 결과 문서(`struct_scan.md`, `ask_plan.json`) 쓰기 | 멈춤 | 경고만 남기고 계속한다 |
| 집계의 호출 수 세기 | 작업 번호를 한 문장에 모두 넣음 | 500개씩 나눠 센다 |

오류가 난 자리는 `run.log`에 오류의 종류와 호출 경로가 남고, 수동 검토 목록과 보고서에 "도구의 오류"로 나온다. 조용히 넘어가지 않는다.

이미 보호되던 곳: 규칙 하나가 파일 하나에서 실패하는 것(S2), 함수 하나의 구조 분석(S5의 탐지), sLLM 수정의 추가 검사(S6), 추적 파일과 집계(0.10.4).

## 5. 남는 위험

- **Windows에서만 도는 부분**은 이 점검으로 확인되지 않는다. 컴파일러 찾기, 환경 설정, 실제 `cl` 실행, 콘솔 인코딩이다. 0.10.3에서 고친 include 경로 조합도 실제 `cl`로는 돌려 보지 못했다.
- **실제 모델의 응답**은 모의 응답 9가지와 다를 수 있다. 응답 처리는 예전부터 있던 코드이고 실제 시험을 거쳤지만, 3단계에서 호출이 크게 늘면 처음 보는 꼴이 나올 수 있다.
- 요청 하나를 되돌린 경우 `out/struct_scan.md`에는 되돌리기 전의 계획이 적혀 있을 수 있다. 보고서와 수동 검토 목록의 "적용하지 않음"이 맞다.
- 그 밖의 단계(S0, S1, S4, S7, S8, S9의 본문)에서 난 오류는 지금처럼 실행을 멈추고 종료 코드 2로 끝난다. 로그의 마지막에 `--resume`으로 이어서 돌리는 방법이 나온다.
- 실행 오류와 별개로, 컴파일 검사를 하지 못하는 환경(등급 가)에서는 sLLM이 없는 이름을 쓴 수정이 표시만 붙고 들어갈 수 있다(`limits.new_name_check`의 기본값 mark). 등급 나에서는 컴파일 검사가 걸러 낸다.
