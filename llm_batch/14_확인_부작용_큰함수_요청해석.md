## 1. 배열 → 구조체의 부작용은 감당할 수 있는가

**결론: 0.7.1 그대로는 감당하지 못한다. 아래 네 가지를 넣으면 조건을 걸고 감당할 수 있다.**

### 1.1 0.7.1을 부작용 예제에 돌린 결과

전역 배열 `g_data`를 구조체로 바꾸는 요청을, 사용 형태 26가지를 넣은 예제에 돌렸다.

| 결과 | 건수 | 내용 |
|---|---|---|
| 선언은 못 바꾸고 사용처만 바꿈 | 5곳 | 배열 선언은 "크기를 정할 수 없음(4, 8, IDX_MAX)"으로 수동이 됐는데 `g_data[IDX_TEMP]` → `g_data.temp`는 적용됐다. **결과물이 컴파일되지 않는다** |
| 다른 것을 잘못 바꿈 | 3곳 | `obj.g_data[IDX_TEMP]`, `po->g_data[IDX_COUNT]`(다른 구조체의 같은 이름 멤버), 같은 이름의 지역 배열 |
| 보고 없이 빠뜨림 | 9곳 | 인덱스 계산식 `g_data[IDX_TEMP + 1]`, `memset`·`memcpy`·`fwrite`의 인자, `Send(g_data, 8)`, `int* p = g_data;`, `*(g_data + 1)`, `_countof(g_data)`, 처리 범위에서 뺀 파일의 사용처 |
| 잘못 분류 | 1곳 | `#define CUR_TEMP g_data[IDX_TEMP]`를 "배열 선언"으로 봤다(수동 검토로는 감) |

원인은 셋이다.
- 같은 이름이면 전부 같은 배열로 본다. 구조체 멤버 `int g_data[4]`와 지역 배열까지 선언으로 세어 크기가 충돌했다.
- 선언 계획이 실패해도 사용처 치환은 그대로 진행한다.
- 통째로 쓰는 곳은 선언 계획이 성공했을 때만 찾는다. 인덱스는 이름 하나나 숫자 하나일 때만 잡는다.

### 1.2 부작용의 성격

| 성격 | 예 | 누가 드러내나 |
|---|---|---|
| 시끄러움 | 남은 `X[i]`, 통째 사용, `_countof(X)`, 범위 밖 파일의 사용처, C++ 파일의 `extern` 불일치 | 컴파일러나 링커. 다만 빌드 전에는 모른다 |
| 조용함 | C 파일의 `extern int X[];`(이름에 타입이 실리지 않아 링크가 된다), 필드 타입을 바꿔 크기·배치가 달라진 뒤의 복사·파일·통신 | 실행해야 드러난다 |
| 보이지 않음 | `##`로 이름을 만드는 매크로, 패키지 밖에서 이 배열을 쓰는 모듈, 다른 언어의 코드 | 글자 검색으로는 못 찾는다 |

### 1.3 감당하게 만드는 네 가지

| # | 항목 | 내용 | 막는 것 |
|---|---|---|---|
| 1 | 기호 구분 | `.`, `->` 뒤의 이름, 구조체 본문 안의 멤버 선언, 같은 이름의 지역 변수가 선언된 함수 안의 사용은 대상에서 뺀다 | 다른 것을 잘못 바꿈 |
| 2 | 전수 분류 | 이름이 나오는 곳을 처리 범위 밖 파일까지 전부 세고, 하나도 남기지 않고 분류한다. 센 수와 분류한 수가 다르면 중단한다 | 보고 없이 빠뜨림 |
| 3 | 원자성 | 선언 계획이 실패했거나, 범위 밖 파일에 사용처가 있거나, 정책이 정해지지 않은 사용처가 있으면 **아무것도 적용하지 않고 보고만 한다** | 선언과 사용처의 어긋남 |
| 4 | 배치 동일 | 필드의 타입과 순서를 배열 그대로 둔다. 그러면 크기와 배치가 같아서 복사, 파일, 통신, 포인터 별칭은 그대로 맞는다. 통째로 넘기는 경계에서만 `&이름`이나 `(int*)&이름`으로 바꾼다 | 조용한 부작용 |

시험 코드로 2번을 같은 예제에 돌린 결과: 이름이 나온 곳 30개, 분류한 곳 30개, 빠진 것 0개.

| 분류 | 곳 | 처리 |
|---|---|---|
| 선언(헤더 `extern`, 정의, 다른 파일의 `extern` 둘) | 4 | 구조체 선언으로 교체 |
| 상수 인덱스(이름, 숫자, `IDX_TEMP + 1` 같은 계산식, 매크로 본문) | 7 | 규칙으로 필드 접근 |
| 변수 인덱스 | 2 | 정책(`stop`, `llm`, `cast`, `raw_view`) |
| 메모리·입출력 함수의 인자 | 3 | 규칙: `&이름` |
| `sizeof(이름)` | 3 | 그대로 |
| `sizeof` 안의 요소 접근 | 1 | 수동 |
| 이름을 통째로 사용 | 4 | 정책(`cast`면 `(int*)&이름`) |
| 다른 기호(멤버 접근 2, 멤버 선언 1, 지역 변수 2) | 5 | 건드리지 않음 |
| 범위 밖 파일의 사용처 | 1 | 요청 중단 또는 경고 |

`#define G(name) g_##name[IDX_TEMP]`는 사용처를 찾지 못한다. 대신 "대상 이름의 앞부분이 `##`에 붙어 있는 매크로"로 경고를 냈다.

### 1.4 그래도 남는 것

- `##` 매크로, 패키지 밖의 사용처는 경고만 할 수 있다.
- 배열을 순회하는 코드가 많으면 구조체로 바꾸는 것 자체가 맞지 않는다. 변수 인덱스 건수를 먼저 보고 사람이 판단해야 한다.
- 동작이 같은지는 빌드와 시험으로만 확인된다.

## 2. 2,000줄 함수

### 2.1 0.7.1 실행 결과

함수 하나가 2,000줄인 예제 네 가지를, 대상 줄(`gets(이름);`)을 실제로 고쳐 주는 모의 모델로 돌렸다.

| 예제 | 대상 | 작업 | 호출 | 최대 입력 | 최대 출력 | 결과 |
|---|---|---|---|---|---|---|
| A. 대상 3곳이 멀리 떨어짐 | 3 | 3건(각각 따로) | 3 | 817 | 32 | 3건 수용 |
| B. 20줄마다 대상 | 100 | 분할 조각 2건 | 2 | 11,472 | 1,880 | 2건 수용 |
| D. 본문이 switch 하나, case마다 대상 | 200 | 분할 조각 4건 | 4 | 7,162 | 1,925 | 4건 수용 |
| A에서 1곳 실패 | 3 | 3건 | 4 | | | 2건 수용, 1건 수동 |
| **B에서 1곳 실패** | 100 | 분할 조각 2건 | 2 | | | **0건 수용, 100건 전부 수동** |

토큰 수는 모의 서버가 글자 수로 센 값이다.

### 2.2 드러난 문제

- **독립인 수정이 한 묶음이 된다.** 대상끼리 30줄 안이면 잇는 규칙 때문에 100곳이 사슬처럼 이어져 한 구간이 됐다. 구간이 한도를 넘어 분할 순차로 갔다.
- **조각 하나가 너무 크다.** B의 첫 조각은 1,086줄에 대상 57곳이었다. 모델이 수정 블록 57개를 한 번에 정확히 내야 한다.
- **하나가 틀리면 전부 버린다.** 분할 순차는 "한 조각이 실패하면 구간 전체 취소"다. 서로 무관한 100곳이 한 번의 형식 오류로 전부 수동이 됐다.
- **선언은 함수 앞 25줄만 붙는다.** 지역 변수 100개 중 앞쪽 20여 개만 들어갔다.
- switch 하나로 된 본문은 안쪽에서 나눠졌다. 큰 문장 하나 때문에 못 나누는 일은 이 예제에서는 없었다.

### 2.3 개선

수정을 두 종류로 나눈다. 유형(규칙, 요청)이 어느 쪽인지 정한다.

| | 독립 수정 | 결합 수정 |
|---|---|---|
| 뜻 | 대상마다 자기 줄만 고친다. 함수 호출 교체, 인자 추가 | 함수 전체에서 일관돼야 한다. 지역 변수의 타입 변경 |
| 묶는 기준 | 작업당 대상 수와 조각 크기에 상한(예: 8곳, 150줄) | 지금의 분할 순차 |
| 보내는 순서 | 병렬 | 차례로, 앞 조각의 변경 내역을 붙임 |
| 실패 | 그 작업의 대상만 수동 | 구간 전체 취소 |
| 선언 | 그 작업의 대상 줄에 쓰인 이름의 선언만 주입 | 같음 |
| 병합 뒤 | 같은 범위의 중복 선언 검사 | 같음 |

같은 예제에 상한(8곳)을 적용하면 호출 수는 늘고 한 번의 크기는 줄어든다.

| 예제 | 지금 | 개선 뒤 |
|---|---|---|
| B. 대상 100곳 | 2회, 조각당 대상 50여 곳 | 13회, 작업당 8곳 |
| D. 대상 200곳 | 4회, 조각당 50곳 | 25회, 작업당 8곳 |

호출은 6배쯤 늘지만 병렬로 나가고 출력이 짧다. 한 번 틀렸을 때 잃는 것은 100곳이 아니라 8곳이다.

### 2.4 큰 함수에서의 선언 찾기

대상 줄에서 거꾸로 가며 찾는다. 이미 닫힌 형제 블록 안의 선언은 보지 않는다(범위 규칙). 함수 머리에 닿으면 인자 목록에서 찾고, 없으면 그 함수가 속한 클래스의 본문에서 찾는다.

실제 코드에서 잰 결과(버퍼를 첫 인자로 받는 호출 201곳의 첫 인자):

| 결과 | 곳 | 비율 |
|---|---|---|
| 지역 선언을 찾음 | 150 | 75% |
| 함수 인자에서 찾음 | 19 | 9% |
| 클래스 본문에서 멤버로 찾음 | 13 | 6% |
| 후보가 여럿이라 확정 못 함 | 11 | 5% |
| 패키지에 하나 있으나 범위를 확인 못 함 | 4 | 2% |
| 못 찾음 | 4 | 2% |

90%는 선언을 확정했다. 나머지 10%는 "선언을 확정하지 못함"으로 표시하고 후보를 후보라고 적어 보내거나 수동으로 돌린다. 선언 주입으로 이 유형의 오류를 전부 막는다고 말할 수는 없다.

## 3. 요청 → 의미 → 이름 → 코드 → 수정

### 3.1 앞선 설명에서 틀린 것

"호출 이름 목록을 모델에 보여 주고 고르게 한다(1회)"고 했다. 실제 코드에서 재 보니 맞지 않는다.

| 항목 | 값 |
|---|---|
| `이름(` 꼴의 서로 다른 이름 | 6,893개 |
| 이름만 보낼 때 | 추정 41,835토큰. 입력 상한 약 19,000을 넘는다 |
| 2회 이상 나온 이름만 | 4,463개, 추정 24,999토큰. 여전히 넘는다 |

18만 줄 규모에서 이미 한 번에 못 보낸다. 사슬을 아래처럼 고친다.

### 3.2 고친 사슬

예: "if문에 들어간 로그 호출을 찾아줘(또는 바꿔줘)"

| 단계 | 책임 | 하는 일 | 송신 / 수신 | 실제 코드에서 |
|---|---|---|---|---|
| 1 요청 해석 | 모델 1회 | 문장을 세 칸으로: 동작(찾기), 위치(if문 안), 찾을 것의 낱말(log, trace, print, debug, dump, output) | 수백 / 100 안팎 | |
| 2 패턴 확장 | 도구 | 이름을 낱말로 쪼개(`writeCertVerifLog` → write, Cert, Verif, Log) 낱말이 일치하는 이름만 고른다 | 0 | 글자 포함으로 맞추면 101개(`doDialog`, `EndDialog`가 섞임), 낱말 단위면 47개 |
| 3 후보 추리기 | 모델 1회 | 후보 이름과 사용 예 한 줄씩을 주고 "로그 출력인 것"만 고르게 한다 | 추정 1,449 / 수백 | 47개 가운데 `dump_integer`, `JSON_HEDLEY_PRINTF_FORMAT` 같은 것이 여기서 빠져야 한다 |
| 4 검증 | 도구 | 모델이 낸 이름 중 목록에 없는 것은 버린다. 답이 형식에 안 맞으면 다시 묻는다 | 0 | |
| 5 확인과 저장 | 사람 | 고른 이름을 요청 파일에 명시형으로 저장한다. 다음 실행부터는 1~4를 다시 하지 않는다. 시험은 `--only`로 파일을 한정해 돌린다 | 0 | |
| 6 구조 필터 | 도구 | if문 범위를 찾고 그 안의 호출만 남긴다 | 0 | if문 11,223개의 범위를 전부 정함(0.1초). 고른 이름 9개의 호출 41곳 중 if 안은 23곳 |
| 7 작업 만들기 | 도구 | 감싼 if문 하나를 작업 하나로 묶는다 | 0 | 작업 21건. 감싼 if문의 크기는 중간값 92토큰, 최대 894토큰 |
| 8 수정 | 모델, 작업당 1회 | "찾아줘"면 이 단계 없이 목록을 보고서로 낸다. "바꿔줘"면 조각(13번 F2)으로 보낸다 | 작업당 수천 이하 / 수백 | |
| 9 검사와 병합 | 도구 | 수용 검사, 병합, 잔여 재탐지 | 0 | |

모델 호출은 해석에 2회, 수정에 작업 수만큼이다. 코드 전체를 모델에 보여 주는 단계는 없다.

### 3.3 이 사슬의 한계

- **낱말로 못 잡는 이름**: 사내 약어(`WR_EVT` 같은)로 된 로그 함수는 2단계에서 빠진다. 3단계 뒤에 사람이 이름을 더할 수 있어야 한다. 보조 경로로 "2회 이상 나온 이름 목록을 나눠 보내 고르게 하기"가 있지만 이 코드에서 2회가 든다.
- **이름이 아니라 쓰임으로 정해지는 것**: 같은 `printf`가 로그일 때도 있고 화면 출력일 때도 있다. 이 구분은 8단계의 모델이 조각을 보고 하며 `NO_CHANGE`로 답할 수 있다.
- **위치 조건의 목록은 정해져 있다**: 함수, if, for, while, switch, 초기화 목록, 문자열, 주석. 목록에 없는 조건("오류 처리 경로 안")은 못 받는다.
- **1단계와 3단계의 품질**은 실제 모델에서만 확인할 수 있다. 5단계에서 사람이 확인하는 이유다.

1~6은 모델 없이 시험할 수 있다. 7은 1, 3단계의 품질을 실제 모델에서 확인해야 한다.

## 5. 확인하지 못한 것

- 사용자 코드에서의 수치. 실제 코드 측정은 공개 코드 하나에서 한 것이다. C 양식이 강하고 전역 변수와 매크로가 많은 코드에서는 선언 찾기의 비율이 달라진다.
- 실제 모델이 3.2의 1, 3단계를 쓸 만하게 답하는지, 대상 8곳짜리 작업의 수정 블록을 얼마나 정확히 내는지.
- `cast`, `raw_view` 정책이 대상 코드의 작성 규칙에 맞는지.
- 2.3의 상한 값(8곳, 150줄)은 예로 든 값이다. 실제 모델의 실패율을 보고 정해야 한다.
