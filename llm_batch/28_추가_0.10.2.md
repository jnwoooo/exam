# 0.10.2에서 달라진 것: 요청문의 의미 분석 답과 처리 건수를 로그에 남긴다

| 항목 | 내용 |
|---|---|
| 읽는 순서 | 28 |
| 작성일 | 2026-11-26 |
| 대상 코드 | `vupdate.py` 0.10.2 |
| 배경 | 실제 시험에서 의미 분석이 제대로 됐는지 판단할 로그가 없었다. 요청문은 1건인데 수정 요청은 여러 건일 수 있어, 어떻게 나뉘었는지와 건수를 볼 수 있어야 한다 |
| 확인 범위 | Linux, 합성 예제, 모의 sLLM. 실제 gemma4와 실제 코드에서는 확인하지 못했다 |

**이 판은 기록만 더했다. 무엇을 고치고 무엇을 sLLM에 보내는지는 0.10.1과 같다.** `27_검토_0.10.1_실시험.md`의 문제 8가지는 그대로 남아 있다.

## 1. 한눈에

| 무엇 | 0.10.1 | 0.10.2 |
|---|---|---|
| 의미 분석의 답 원문 | `logs/llm/ask_*.txt`에만. 캐시에서 답하면 남지 않음 | `run.log`의 `답\|` 줄, `out/ask_trace.md`, `out/ask_plan.json`. 캐시에서 답한 것도 남음 |
| 의도별로 받은 내용 | `run.log`에는 종류만(`의도 2개로 나눔(...)`) | 의도마다 지시, 이름, 낱말, 구문, 파일 |
| 답을 그대로 쓰지 않은 곳 | 기록 없음 | 모르는 종류를 modify로 본 것, 식별자 꼴이 아니어서 버린 이름 등을 적음 |
| 의도별 건수 | 보고서의 여러 절에 흩어져 있음 | 대상 / 규칙 수정 / sLLM 수정 요청 / sLLM 수정 / 미수정과 비고를 한 줄로 |
| 처리 단계(`--compat-llm`)별 건수 | 규칙별 표만 | 단계별 표와 미수정 비고 |

새 옵션은 없다. 설정값 두 개가 늘었다(4절).

## 2. 요청문의 흐름과 기록되는 곳

```
요청문 1건(--ask 하나, 또는 --ask-file 파일 전체)
  → 의미 분석 호출 1회(답을 쓸 수 없으면 한 번 더)
  → 의도 n개(modify, find, array_to_struct, compat, constraint)
  → 의도마다 대상 m곳
  → 규칙 수정 / sLLM 수정 요청(작업, 호출) / 미수정
```

`--ask-file`은 파일 전체가 요청 1건이다. 문장이 여러 개여도 분석 호출은 1회이고, 모델이 의도로 나눈다. 따로 분석하게 하려면 `--ask`를 여러 번 준다.

| 단계 | `run.log`의 줄 | 뜻 |
|---|---|---|
| 물음 | `요청 ASK-1 의미 분석 물음: 요청문 94자, 모델에 알려 준 이름 3개 (...)` | 요청문에 적힌 영문 이름 가운데 코드에 있는 것을 모델에 알려 준다 |
| 답 | `요청 ASK-1 의미 분석 답(1차, 호출, 1820ms, 329자). 원문 파일: ...` | 호출인지 캐시인지, 걸린 시간, 글자 수 |
| 답 원문 | `요청 ASK-1 답\| {"intents": [...` | 모델이 쓴 글 그대로. 줄마다 한 줄 |
| 바꾼 것 | `의미 분석 답을 해석하면서 바꾼 것: 2번째 의도: 이름 'm_st.szLot' 은(는) ...` | 도구가 답을 그대로 쓰지 않은 곳 |
| 쓸 수 없음 | `의미 분석 답(1차)을 쓸 수 없음: ... 한 번 다시 묻는다` | JSON이 아니거나 의도가 없을 때 |
| 의도 | `요청 ASK-1-1 [array_to_struct] 지시: ...` / `이름: Data, TC / 낱말: - / 구문: any / 파일: -` | 의도 하나에 두 줄 |
| 버린 이름 | `모델이 낸 이름 ... 은(는) 코드에 없어 버립니다` | 0.10.1에도 있던 줄 |
| 후보 확인 | `요청 ASK-1-2 후보 확인(묶음 1/1): 후보 12개 가운데 3개를 남김 (...)` | 낱말로 고른 후보를 모델이 추린 결과 |
| 집계(S9) | `요청 ASK-1-1 [modify] 집계: 대상 3 / 규칙 수정 0 / sLLM 수정 요청 3(보낸 것 3, 작업 2, 호출 2) / sLLM 수정 2 / 미수정 0` | 실행이 끝난 뒤의 건수 |
| 비고(S9) | `요청 ASK-1-1 미수정 비고(2건): 수정 기각: ... (처음 Src/A.cpp:120)` | 같은 비고끼리 묶어 건수가 많은 것부터 |

건수의 뜻은 다음과 같다.

| 이름 | 뜻 |
|---|---|
| 대상 | 의도가 가리킨 코드의 자리 수 |
| 규칙 수정 | sLLM 없이 고친 자리 |
| sLLM 수정 요청 | sLLM에 맡기기로 한 자리. 괄호 안은 실제로 보낸 자리, 작업 수, 호출 수 |
| sLLM 수정 | sLLM의 수정을 받아들인 자리 |
| sLLM이 고칠 필요가 없다고 본 곳 | 모델이 그대로 두라고 답한 자리(예: 호출을 고치는 요청에 걸린 선언) |
| 미수정 | 수동 검토로 남은 자리 |
| 대상을 찾지 못한 이름·요청 | 코드에서 자리를 정하지 못한 것. 비고에 이름과 사유가 있다 |

## 3. `out/ask_trace.md`

요청문마다 한 절이다. 사람이 읽고 "모델이 제대로 이해했는가"를 판단하는 파일이다.

1. 요청 원문
2. 의미 분석: 모델에 알려 준 이름, 차수별 답 원문(전체), 쓸 수 있었는지, 해석하면서 바꾼 것
3. 해석된 의도의 표(요청문 1건 → 의도 n개): 종류, 지시, 이름, 버린 이름, 낱말, 구문, 파일
4. 의도별: 처리 경로와 결과, 집계, 미수정과 오류의 비고(건수, 처음 위치), sLLM 작업 목록(파일, 줄, 상태, 시도, 비고)

S5가 끝나면 분석까지 적고, S9에서 최종 건수로 다시 쓴다. `--until S5`로 멈추면 분석 결과만 먼저 볼 수 있다.

보고서에는 같은 내용의 요약이 "요청문 처리 추적" 절로 들어간다.

## 4. 처리 단계별 집계

보고서 4절 끝과 `run.log`(S9)에 나온다.

| 처리 단계 | 들어가는 것 |
|---|---|
| 설정 처리 | T0 규칙. 코드는 두고 프로젝트 설정으로 경고를 끈다 |
| 1단계 | 글자 꼴만 보고 고치는 규칙 |
| 2단계 | 선언을 읽어 판정하는 규칙(`R-T2-CRT-SECURE-LOCAL`) |
| 3단계 | sLLM에 맡기는 규칙 |
| 수동 검토 전용 | 규칙도 sLLM도 고치지 않는 것 |

단계마다 대상, 규칙 수정, sLLM 수정 요청(보낸 것, 작업, 호출), sLLM 수정, 설정으로 처리, 미수정을 적고, 미수정의 비고를 규칙별로 묶어 적는다. 보안 CRT 경고 줄 가운데 코드가 그대로 남은 줄 수도 함께 적는다. `--compat-llm`이 3보다 낮으면 3단계의 대상은 "보낸 것 0, 미수정 n"으로 나온다.

설정값(`config/server.json`의 `limits`):

| 키 | 기본 | 뜻 |
|---|---|---|
| `ask_log_chars` | 6000 | 답 원문을 `run.log`에 적는 글자 수 상한. 넘으면 자르고 원문 파일을 알려 준다. 0이면 적지 않는다 |
| `tally_log_notes` | 8 | `run.log`에 적는 미수정 비고의 수(단계마다, 의도마다) |
