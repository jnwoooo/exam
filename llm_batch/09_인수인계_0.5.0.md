## 0. 요약

- 0.5.0은 "지금 요구사항에서 밖의 결정 없이 코드로 옮길 수 있는 것"을 모두 옮긴 판이다. 요구사항 100개 기준으로 충족 71, 부분 21, 미충족 5, 해당 없음 3이다(0.4.0은 61, 24, 12, 3).
- **확인은 전부 리눅스의 합성 예제와 모의 서버에서 했다.** Windows, 실제 sLLM, 실제 MCP 서버, 실제 패키지, 실제 빌드 로그에서는 한 번도 돌리지 못했다. 별도 환경에서 처음 할 일은 3절의 확인이다.
- 서버 쪽은 세 가지 방법 어느 것으로도 붙는다: sLLM 직접, OpenAI 호환 중계, MCP 도구 호출(2.4). 중계 서버는 참고 구현을 넣었다(2.5).

## 2. 쓰는 방법

### 2.1 빌드 오류를 다시 넣어 고치기

```
1. vupdate run --package D:\src\PKG_A --from-vs 2008 --to-vs 2022          (처음 실행)
2. out\changed 의 파일을 빌드용 소스 트리에 덮어쓰고 빌드한다(/fl 로 msbuild.log 를 만든다)
3. vupdate run --package D:\build\PKG_A --from-vs 2008 --to-vs 2022 --build-log D:\build\msbuild.log
4. 3번의 out\changed 를 다시 빌드용 소스 트리에 덮어쓰고 빌드한다. 오류가 줄지 않으면 07_오류대응.md 3절로 간다
```

- **3번의 `--package`는 로그를 낸 소스 트리(2번의 트리)여야 한다.** 줄 번호를 그 트리에 맞추기 때문이다. 원본 패키지를 주면 줄이 어긋난다.
- 이미 고친 트리를 다시 돌려도 규칙 수정은 더 생기지 않는다(같은 결과물을 다시 처리하면 수정 0건임을 확인했다). 새로 생기는 것은 로그에서 온 이슈(`B-오류코드`)뿐이다.

| 로그의 오류 | 처리 |
|---|---|
| 컴파일 오류이고 패키지 파일의 줄을 가리킨다 | sLLM에 맡긴다. 지침은 컴파일러 메시지와 오류 코드별 대응(`07_오류대응.md` 3.9)으로 만든다. 결과는 검토 대상이다 |
| 헤더를 못 찾음(C1083), `#error`(C1189), 미리 컴파일된 헤더 등 | 수동 검토. 코드가 아니라 설정이나 환경으로 푼다 |
| 메시지에 나온 이름이 그 줄에 없다 | 수동 검토. 로그와 소스가 다른 판이다 |
| 한 파일에서 5건을 넘는 오류 | 수동 검토. 앞의 오류를 고치면 없어지는 경우가 많다(`limits.buildlog_max_per_file`) |
| 프로젝트, 옵션, 링크 단계의 오류 | 수동 검토 목록에 대응과 함께 올린다 |
| 경고 | 넣지 않는다 |

### 2.2 구조체 변경 요청(struct_change)

```json
{
  "features": [
    { "id": "REQ-002", "type": "struct_change", "target": "MSG_HEADER",
      "rename": { "nLen": "nLength", "nSeq": "nSequence" },
      "definition_after_file": "MSG_HEADER_new.txt",
      "pack": 1, "check_layout": true, "llm_unresolved": false }
  ]
}
```

| 값 | 뜻 |
|---|---|
| `target` | 구조체 이름(태그 이름이나 typedef 이름) |
| `rename` | 바뀌는 필드 이름. `{옛 이름: 새 이름}` |
| `definition_after`, `definition_after_file` | 새 정의(`struct ... { ... }`까지). 주면 정의 전체를 이것으로 바꾼다. 안 주면 정의 안의 필드 이름만 바꾼다 |
| `pack` | 요청의 패킹 값. 정의 앞에 `#pragma pack`이 없으면 수동 검토로 알린다 |
| `check_layout` | 참이면 `sizeof`, `memcpy`·송수신 함수, `offsetof` 사용처를 수동 검토 목록에 올린다. 새 정의를 주면 기본이 참 |
| `llm_unresolved` | 참이면 타입을 확정할 수 없는 접근을 sLLM에 맡긴다. 기본은 수동 검토 |

| 대상 | 처리 |
|---|---|
| 구조체 정의 | 새 정의로 교체하거나 필드 이름만 치환(검토 표시) |
| 그 타입(typedef 별칭 포함)으로 선언된 변수의 `v.옛이름`, `p->옛이름`, `arr[i].옛이름` | 새 이름으로 치환(검토 표시). 변수는 그 파일과 그 파일이 포함하는 패키지 헤더의 선언에서 찾는다 |
| 그 밖의 `.옛이름`, `->옛이름`(함수 반환값, 중첩 멤버, `this`, 한 줄에 여러 변수를 선언한 경우의 둘째 이후) | 수동 검토("미확정 접근") 또는 sLLM |
| `sizeof`, 메모리 복사·송수신, `offsetof` | 수동 검토("배치 점검"). 상대 프로세스와 크기·패킹·타입 크기를 맞춘다 |

이름이 같은 필드를 가진 다른 구조체의 변수가 같은 이름으로 선언돼 있으면 잘못 바꿀 수 있다. 그래서 이 요청의 수정은 모두 검토 대상으로 표시한다.

### 2.3 예외 파일과 소스의 표식

`config/EXAMPLE_exceptions.json`을 복사해 고쳐 쓰고 `--exceptions`로 준다.

```json
{
  "rules_off": ["R-T3-GETVERSIONEX"],
  "skip": [
    { "path": "ThirdParty/*" },
    { "path": "Src/Legacy/*", "rules": ["R-T1-CRT-NONSTDC"] },
    { "path": "Src/Main.cpp", "rules": ["R-T2-MAKE-PAIR"], "lines": "120-140" }
  ],
  "brace_macros": { "open": ["TRY_BEGIN"], "close": [], "ignore": ["DECLARE_MY_TABLE"] }
}
```

| 값 | 뜻 |
|---|---|
| `rules_off` | 끌 규칙. `--disable-rule`과 같다 |
| `skip` | 탐지에서 뺄 곳. `rules`를 생략하면 모든 규칙, `lines`를 생략하면 파일 전체 |
| `brace_macros.open`, `close` | 여는 괄호나 닫는 괄호를 **한쪽만** 숨긴 매크로. 양쪽을 모두 숨긴 짝(예: 네임스페이스를 여닫는 매크로 한 쌍)은 적지 않는다. 괄호 수가 이미 맞는다 |
| `brace_macros.ignore` | 세미콜론 없이 쓰는 선언 매크로처럼 함수 경계 분석을 헷갈리게 하는 것 |

소스에 직접 적는 표식(주석 안에 쓴다):

```cpp
x = old_call(a);            // vupdate:skip                     이 줄은 어떤 규칙도 건드리지 않는다
// vupdate:skip-next R-T2-MAKE-PAIR                             다음 줄에서 이 규칙만 뺀다
y = std::make_pair<int, int>(a, b);
```

### 2.4 서버 붙이기: 세 가지

| 방법 | PC의 설정 | 서버에 필요한 것 |
|---|---|---|
| 가. sLLM 직접 | `VUPDATE_LLM_ENDPOINT=http://<sLLM>/v1` | 없음. 주소가 바뀌면 PC마다 고쳐야 한다 |
| 나. OpenAI 호환 중계 | `VUPDATE_LLM_ENDPOINT=http://<서버>:8765/v1` | `POST /v1/chat/completions`(와 `GET /v1/models`). `08_MCP역할목록.md` 8.1 |
| 다. MCP 도구 호출 | `config/server.json`에 `"transport": "mcp"`, `"endpoint": "http://<서버>/mcp"` (`config/EXAMPLE_server_mcp.json`) | 아래 도구 |

MCP 도구의 약속(이름은 설정 `llm.mcp_tool`, `llm.mcp_info_tool`로 바꿀 수 있다):

| 도구 | 입력 | 출력 |
|---|---|---|
| `llm_complete` | `system`, `user`, `max_tokens`, `temperature`(0), `caller`, `run_id`, `job_id` | `content`, `finish_reason`, `prompt_tokens`, `completion_tokens`. `structuredContent`에 담거나 JSON 문자열로 준다. JSON이 아닌 글이면 그 글 전체를 응답 본문으로 본다(토큰 수는 모름) |
| `llm_info` (선택) | `caller`, `run_id` | `max_total_tokens`, `max_output_tokens`, `max_parallel`, `reserve_tokens`, `model` |
| `job_open`, `job_progress`, `job_close` (선택) | 호출자, 실행 ID, 패키지, 단계, 건수 | `job_open`은 `job_id` |

오류는 `isError: true`와 함께 아래 값을 준다.

| `code` | 함께 주는 값 | py의 동작 |
|---|---|---|
| `over_limit` | `limit`, `input_tokens` | 줄여서 새로 보낸다 |
| `busy` | `retry_after`(초) | 기다렸다 다시 보낸다 |
| `denied`, `bad_request` | | 다시 보내지 않고 수동 검토로 |
| 그 밖 | | 2회 다시 보낸다 |

전송은 Streamable HTTP다. py는 `initialize` → `notifications/initialized` → `tools/call` 순서로 부르고, 응답이 JSON 한 건이든 SSE든 읽는다. 서버가 세션 ID를 주면 이후 요청에 싣고, 세션이 끝났다는 응답(404)을 받으면 한 번 다시 연다. 서버의 입력·출력 이름이 위와 다르면 M06의 `_llm_chat_mcp`에서 `args`를 만드는 줄과 `payload`를 읽는 줄만 고친다.

### 2.5 중계 서버 참고 구현

```
python tools/relay_reference.py --config config/EXAMPLE_relay.json
vupdate llmcheck --llm-endpoint http://<서버>:8765/v1
```

- `08_MCP역할목록.md` 3절의 약속 10가지를 그대로 옮긴 것이다. 파일 머리에 약속 번호와 구현 위치의 대응이 있다.
- 2.4의 "나"와 "다"를 한 서버에서 함께 연다(`/v1/...`과 `/mcp`).
- 쓰임은 둘이다. 조직의 MCP 서버에 같은 기능을 넣을 때의 본보기, 그리고 MCP 서버가 준비되기 전에 sLLM 앞에 임시로 세워 쓰는 것.
- 표준 라이브러리만 쓴다. `vupdate.py`와는 따로 돌고, 로컬 PC에는 배포하지 않는다.


외부 규칙에는 규칙 안에 시험 예를 적는다. 규칙을 고친 뒤 이 명령으로 확인한다.

## 3. 별도 환경에서의 진행 순서

각 단계의 결과가 기대와 다르면 4절에서 고칠 곳을 찾는다.

| 순서 | 할 일 | 기대하는 결과 |
|---|---|---|
| 1 | 인터넷이 되는 Windows PC에서 `tools\make_exe.bat` | `dist\vupdate.exe` |
| 2 | 대상 PC에서 `vupdate selftest` | `합계: 50개 중 50개 통과` |
| 3 | `vupdate rules --test` | `시험 예 20건 중 20건 통과` |
| 4 | `vupdate preflight --package <패키지>` | `out\preflight.md`에 컴파일러, SDK, 프로젝트 파일이 맞게 나온다 |
| 5 | `vupdate rules --from-vs <원본> --to-vs <대상>` | 켜지는 규칙과 꺼진 이유 |
| 6 | `vupdate run --package <패키지> --from-vs <원본> --to-vs <대상> --dry-run` | `report.md` 4절의 규칙별 건수. 말이 안 되게 많은 규칙이 있으면 오탐이다 |
| 7 | 서버를 붙이고(2.4) `vupdate llmcheck` | 전 항목 "정상". "주의"는 설명을 읽고 설정에 반영 |
| 8 | 작은 범위로 실행: `vupdate run ... --only "Src/한폴더/*"` | `out\changed`, `out\diff`. `report.md` 6절의 기각률과 토큰 한도 대응 |
| 9 | 전체 실행 뒤 결과물을 빌드하고 `vupdate buildlog` | `build_errors.md` |
| 10 | 컴파일 오류가 남으면 2.1의 `--build-log` | 오류 수가 줄어든다 |
| 11 | 반복되는 수정은 `report.md`의 "규칙 후보"를 보고 `config/rules.json`으로 옮긴다 | 다음 실행에서 sLLM 호출이 준다 |

## 4. 증상별로 고칠 곳

| 증상 | 볼 곳 |
|---|---|
| exe가 뜨지 않거나 한글이 깨진다 | `--console-encoding utf-8`을 준다. 그래도 안 되면 M01의 `Log`, M11의 `main` |
| `preflight`가 Visual Studio를 못 찾는다 | `--vs-path`로 직접 준다. 근본 수정은 M07의 `find_tools` |
| 컴파일 검사가 전부 실패한다 | `logs\compile\`의 출력. M07의 `run_cl_syntax`, `cl_flags_for` |
| `.vcxproj`의 설정이 비어 있다 | 설정이 `.props`에 있는 프로젝트다. M07의 `parse_vcxproj` |
| 함수 경계를 못 잡는 파일이 많다(보고서의 파일 처리 결과) | 예외 파일의 `brace_macros`. 근본 수정은 M04의 `analyze_structure` |
| 규칙이 엉뚱한 곳을 잡는다 | 그 줄에 `// vupdate:skip`, 또는 `config/rules.json`에서 같은 ID로 규칙을 다시 적고 `rules --test`로 확인 |
| `llmcheck`의 "한도 초과 거절"이 주의 | 서버가 낸 문구를 M06의 `classify_llm_error`(`_LIMIT_MSG_RE`, `_LIMIT_NUM_RES`, `_ASKED_IN_RES`)에 더한다 |
| `llmcheck`의 "토큰 수 반환"이 주의 | 서버가 `usage.prompt_tokens`를 주게 한다. 못 하면 그대로 써도 되지만 거절이 늘어난다 |
| `llmcheck`의 "출력 형식"이 실패 | 모델이 수정 블록 형식을 지키지 않는다. `config/prompts/system.txt`로 프롬프트를 바꿔 본다(S6의 `SYSTEM_PROMPT`가 원본) |
| 응답이 자주 잘린다 | 추론 모드가 켜져 있다. `llm.extra_body`나 서버에서 끈다 |
| MCP 경유에서 `initialize` 실패 | `llm.mcp_protocol`을 서버의 판으로. M06의 `_mcp_rpc`, `_mcp_ready` |
| MCP 도구의 입력·출력 이름이 다르다 | M06의 `_llm_chat_mcp` |
| sLLM 수정이 대부분 기각된다 | `logs\llm\`의 요청과 응답을 본다. 기각 사유는 S6의 `check_block` |
| 빌드 로그의 오류 수가 로그 끝의 합계와 다르다 | M12의 `parse_build_log`(`_BUILD_DIAG_RE`) |
| `--build-log`의 오류가 전부 "줄이 맞지 않음" | `--package`가 그 로그를 낸 트리가 아니다 |
| 구조체 요청이 엉뚱한 변수를 바꾼다 | 요청에서 그 파일을 `--exclude`로 빼고 수동으로. 근본 수정은 S5의 `_struct_change`(`decl_rx`) |

## 6. 이 코드를 sLLM(24k)으로 고칠 때

`vupdate.py`는 6,142줄이다. 통째로는 넣을 수 없으므로 함수나 구획 단위로 준다.

| 구획 | 줄 수 | 구획 | 줄 수 |
|---|---|---|---|
| M01 공통 | 126 | S2 탐지 | 162 |
| M02 설정 | 451 | S5 영향분석 | 222 |
| M04 어휘분석 | 293 | S6 sLLM수정 | 839 |
| M05 규칙 | 675 | S8 검증 | 216 |
| M06 sLLM연결 | 441 | S9 산출 | 235 |
| M07 컴파일 | 295 | M12 부가명령 | 562 |
| 그 밖(M03, S0, S1, S3, S4, S7, M10) | 각 200 이하 | M11 명령줄(자체 시험 포함) | 903 |

- 500줄을 넘는 구획(M05, S6, M12, M11)은 **함수 하나와 그 구획의 머리 주석**만 준다. 가장 긴 함수는 `s6_llm`(227줄), `s9_report`(161줄)다.
- 규칙, 오류 대응표, 프롬프트, 예외는 코드가 아니라 자료다. 가능하면 `config/`의 파일로 고친다.
- 고친 뒤에는 `vupdate selftest`와 `vupdate rules --test`를 돌린다. Python이 있으면 `tests/`의 6개도 돌린다.
- 각 구획 머리 주석의 "수정:" 줄에 고칠 곳이 적혀 있다. 하려는 일과 고칠 곳의 대응은 `04_개발구조.md` 15절과 이 문서 4절에 있다.
