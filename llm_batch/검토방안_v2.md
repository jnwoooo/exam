## 0. 이 문서의 성격과 근거 수준

### 0.1 성격

이 문서는 **설계 제안**이다. 대상 프로젝트의 코드, 실제 sLLM 서버, 실제 개발환경에서 실행하거나 측정한 것은 없다. v1이 "가능하다"는 어조로 쓰인 것은 설계 문서의 서술 방식 때문이며, 검증을 마쳤다는 뜻이 아니었다. v2는 각 내용이 무엇에 근거하는지 구분해 적는다.

## 1. 결론 요약

**이번 판에서 새로 내린 판단**

1. **v1은 검증된 내용이 아니라 설계 제안이다.** 근거 수준을 등급으로 표시했다(0절).
2. **버전 체계는 명시해야 한다.** "2008 → 2022"만으로는 툴셋만 정해지고, 언어 표준·준수 모드·플랫폼·문자셋이 정해지지 않아 수정 범위가 달라진다(8절).
3. **ripgrep은 만능이 아니다.** 패턴이 있는 줄을 찾을 뿐이고 주석·문자열·함수 경계·타입을 모른다. 구문 분석 도구는 사실상 필요하다. clang은 Windows·MSVC 헤더가 있어야 쓸 수 있고, 있으면 품질이 크게 오른다(9절).
4. **빌드 불가 대처는 "왜 불가한가"에 따라 갈린다.** 컴파일러 자체가 없는지, 의존성이 없어 전체 빌드만 안 되는지, 다른 곳에서는 빌드가 되는지를 먼저 확인해야 한다(10절).
5. **"정적분석으로 빌드 가능성 보장"은 컴파일러 없이는 문자 그대로 달성할 수 없다.** "빌드 실패 위험을 줄이고 남은 위험을 목록으로 넘긴다"로 정의를 바꿔야 한다(10.4).

**v1에서 유지하는 방향**

6. 기계적 수정은 LLM 없이 처리하고(T0~T2), sLLM은 탐지만 가능한 건(T3)에 쓴다(3절).
7. 24k 한도는 수정 지점 단위 호출로 대응한다. 함수 전체 변경의 실용 범위는 약 5,000줄로 추정한다(4절).
8. 140만~180만 자 상수 배열은 sLLM에 보내지 않는다(4.6).
9. 출력은 수정 블록을 기본으로 한다(5절).
10. 병렬 처리는 스냅샷 읽기, 수정 레코드 기록, 단독 병합 구조로 한다(6절).
11. MCP는 파이프라인 단계를 도구로 노출하고, 탐색의 주도권은 프로그램이 가진다(7절).

6~11은 방향으로서 타당하다고 판단한다. 다만 수치와 성공률은 파일럿 전에는 알 수 없다.

## 2. 전체 구조

> 근거 수준: B. 구조 자체는 통용되는 방식이다. 단계별 성능은 미검증이다.

```
[0 인벤토리] → [1 탐지 스캔] → [2 설정 흡수 T0] → [3 규칙 적용 T1/T2]
   → [4 영향 분석·계약 확정] → [5 sLLM 수정 T3] → [6 병합·적용]
   → [7 정적 검증] → [8 diff·보고서]

7단계 불합격 → 5단계 재시도(횟수 제한) → 초과 시 수동 검토 큐
```

| 단계 | 내용 | sLLM | 병렬 단위 |
|---|---|---|---|
| 0 인벤토리 | 전 파일 목록, 인코딩, 함수 경계, 크기·토큰 측정 | 미사용 | 파일 |
| 1 탐지 스캔 | 규칙 카탈로그로 전수 스캔, 이슈 목록 생성 | 미사용 | 파일 |
| 2 설정 흡수 | 프로젝트 설정과 전역 매크로로 해결 | 미사용 | 없음 |
| 3 규칙 적용 | T1/T2 수정 레코드 생성 | 미사용 | 파일 |
| 4 영향 분석 | 심볼 인덱스, 변경 계약 확정 | 일부 | 직렬 |
| 5 sLLM 수정 | 슬라이스 단위 수정 블록 생성 | 사용 | 슬라이스 |
| 6 병합·적용 | 수정 레코드를 적용해 출력 트리 생성 | 미사용 | 파일 |
| 7 정적 검증 | L0~L3 | 미사용 | 파일 |
| 8 보고서 | diff, 통계, 수동 검토 목록 | 미사용 | 없음 |

## 3. 기계적 수정의 LLM 비의존 처리

> 근거 수준: 컴파일러 옵션과 규칙 예시는 A, 4단계 분업은 B, 규칙으로 해결되는 비율은 D.

### 3.1 규칙 4단계

| 단계 | 방식 | 예 | 적용 |
|---|---|---|---|
| T0 설정 흡수 | 코드 무변경. 컴파일 옵션·전역 매크로 | `_CRT_SECURE_NO_WARNINGS`, `_CRT_NONSTDC_NO_DEPRECATE`, `/permissive`, `/Zc:strictStrings-`, `legacy_stdio_definitions.lib`, `NOMINMAX`. C++17 이상 선택 시 `_HAS_AUTO_PTR_ETC=1`, `_HAS_STD_BYTE=0` | 방침 파라미터에 따름 |
| T1 문맥 무관 치환 | 주석·문자열 마스킹 후 정규식 | `"…"MACRO` 공백 삽입, `#define snprintf _snprintf` 제거, `std::tr1::` → `std::`, `itoa` → `_itoa` | 자동 |
| T2 구문 인식 치환 | 토큰/구문 구조 확인 후 치환 | `make_pair<T,U>(…)`의 명시 인자 제거, `SetWindowLong` → `SetWindowLongPtr` | 검토 표시 후 적용 |
| T3 탐지만 | 탐지와 수정 지침을 sLLM/수동으로 전달 | 초기화 목록의 좁히기 변환(C2397/C4838), `auto_ptr` → `unique_ptr`, 포인터 절단(x64), 반복자 오용, 스트림의 bool 변환 | sLLM |

T2와 T3를 가르는 기준은 타입 정보가 필요한지다. `auto_ptr`는 이름만 바꾸면 소유권을 넘기는 지점에서 컴파일 오류가 나므로 T3에 둔다(9.3). 컴파일러 기반 도구(clang-tidy)를 쓸 수 있는 환경에서만 자동 수정 대상이 된다.

T0에 대한 판단:
- "최소 빌드 가능성"만 보면 T0가 가장 싸다. deprecated 경고(C4996)는 기본 설정에서 오류가 아닌 경고이므로 빌드를 막지 않는다. 단, `/sdl`이나 `/WX`를 켠 프로젝트에서는 오류가 된다.
- 다만 T0는 deprecated 코드를 그대로 남긴다. "deprecated 대응"을 코드 수정까지로 볼지는 방침으로 정해야 한다(요구사항 B8).
- 권고는 항목별 선택이다. 호환 옵션이 없으면 빌드가 깨지는 항목은 코드를 고치고, 경고 수준 항목은 프로젝트 방침에 따른다.

### 3.2 규칙 엔진 구조

1. **후보 선별**: ripgrep으로 규칙 패턴 전체를 한 번에 스캔한다(패턴 파일, JSON 출력). 규칙별·파일별 적중 목록이 나온다.
2. **정밀 판정**: 적중 파일만 읽고, 주석·문자열·대용량 초기화 목록을 마스킹한 뒤 다시 판정해 오탐을 걸러낸다.
3. **수정 레코드 생성**: 파일에 직접 쓰지 않고 레코드로 남긴다. sLLM 수정과 같은 형식이라 병합, diff, 보고서 경로가 하나로 통일된다.
4. **수렴 확인**: 적용 결과를 다시 스캔해 잔여 탐지가 없는지, 재적용 시 변화가 없는지 본다.

ripgrep은 탐지만 맡는다. 치환 옵션은 출력만 바꾸고 파일은 수정하지 않으므로, 실제 치환은 파이프라인 자체 엔진이 수행한다.

### 3.3 sLLM 비중을 줄이는 방법

**기능변경 요청의 기계화.** 배열 → 구조체 변경은 접근 형태에 따라 나눈다.

| 접근 형태 | 처리 |
|---|---|
| 상수 인덱스: `a[IDX_TEMP]`, `a[3]` | 규칙(매핑표로 필드명 치환) |
| 변수 인덱스·루프: `a[i]` | sLLM + 변경 계약 |
| `memcpy`, `sizeof`, 포인터 연산, 별칭 | 수동 검토 |

IPC 구조체도 같다. 구조체 정의는 명세에서 생성하고, 필드명 변경은 규칙으로, 크기·오프셋에 의존하는 코드는 탐지 후 검토로 보낸다.

**T3 수정 지침 부착.** 탐지 규칙이 "무슨 문제이고 어떻게 고치는지"를 프롬프트에 넣어 주면, sLLM은 좁은 변환만 수행한다. 정확도가 오르고 토큰이 줄어든다.

**규칙 승격.** sLLM 수정 중 같은 전/후 패턴이 반복되면 규칙 후보로 보고한다. 프로젝트를 거듭할수록 T1/T2가 늘고 T3가 줄어든다.

규칙으로 해결되는 비율은 1단계 탐지 스캔 결과로 산정한다. 사전에 숫자로 단정할 근거는 없다.

## 4. 24k 한도에서의 큰 함수 처리

> 근거 수준: 수치는 모두 C(추정). 대용량 배열을 구문 분석으로 식별하는 것은 A'(9.3). sLLM이 분할 처리를 일관되게 해내는지는 D.

### 4.1 토큰 예산 (가정)

| 구성 | 토큰 |
|---|---|
| 고정 지시, 출력 형식 | 1.5k |
| 환경값·요청사항(선별분) | 1.0k |
| 컨텍스트 헤더(시그니처, 변수표, 타입, 계약) | 2.5k |
| 여유(토크나이저 오차, 채팅 템플릿) | 1.0k |
| **소계** | **6.0k** |
| **코드 입력 + 출력에 쓸 수 있는 양** | **18.0k** |

토큰 밀도 가정:
- 영문 위주 코드: 1줄 약 35자, 약 11토큰
- 한글 주석이 많은 코드: 1줄 약 15토큰
- 숫자 상수 데이터: 1토큰당 약 1.2~2.5자

모델의 추론(thinking) 모드를 켜면 추론 토큰이 출력에 포함되어 이 예산을 잠식한다. 슬라이스 작업은 끄거나 상한을 두는 것을 기본으로 본다.

### 4.2 예상 처리 가능 규모 (추정)

| 방식 | 1회 호출 코드량 | 감당 가능한 함수 크기 |
|---|---|---|
| 조각 재출력 | 입력 9k + 출력 9k. 약 600~800줄 (2.5만~3만 자) | 단일 호출로 약 700줄 |
| 수정 블록 출력 | 입력 15k + 출력 3k. 약 1,000~1,350줄 (4만~5만 자) | 단일 호출로 약 1,200줄 |
| 지점 슬라이스 | 창 60~150줄. 호출당 약 6k~8k | 함수 크기 무관. 호출 수가 수정 지점 수에 비례 |
| 분할 순차 + 변경 원장 | 조각당 600~1,000줄 | 실용 약 5,000줄. 10,000줄까지는 위험 증가 |
| 상수 데이터 | 전송하지 않음 | 140만~180만 자는 약 56만~150만 토큰. 규칙 전용 |

함수 전체에 걸친 변경을 기준으로 한 구간별 판단:

| 함수 크기 | 처리 | 판단 |
|---|---|---|
| 약 1,000줄 이하 | 단일 호출 | 가능 |
| 1,000~5,000줄 | 분할 순차 2~8조각 | 실용 범위 |
| 5,000~10,000줄 | 분할 순차 약 8~16조각 | 권장 조각 수(10)를 넘을 수 있음. 가능하나 조각 간 불일치 위험. 결과 전수 검토 |
| 10,000줄 초과 | 계약 기반 기계 치환 + 수동 검토 | 함수 전체 변경을 sLLM에 맡기는 것은 비권장 |

국소 수정(API 치환, 캐스팅, 시그니처 맞춤)은 이 표와 무관하게 지점 슬라이스로 처리한다. 버전 대응의 대부분이 여기에 해당한다.

### 4.3 처리 경로 결정 순서

1. 함수 본문에서 대용량 상수 데이터를 자리표시자로 바꾼 뒤 토큰을 측정한다.
2. 이슈가 국소적이면 지점 슬라이스로 보낸다.
3. 함수 전체 변경이 필요하고 단일 호출 한도 안이면 단일 호출로 보낸다.
4. 한도를 넘으면 분할 순차로 보낸다(10조각 이내 권장).
5. 그 이상이면 계약 기반 기계 치환과 수동 검토로 보낸다.

### 4.4 지점 슬라이스

- 창 구성: 수정 지점 앞뒤 줄, 소속 함수 시그니처, 창 안에서 쓰는 변수의 선언, 관련 타입 정의, 해당 규칙의 수정 지침.
- 컨텍스트 헤더는 심볼 인덱스에서 프로그램이 추출한다. sLLM을 쓰지 않는다. 타입 정보가 없는 색인은 동명 심볼과 오버로드를 구분하지 못하므로, 후보가 여럿이면 모두 싣거나 `NEED_CONTEXT` 응답에 맡긴다.
- 참고용 컨텍스트는 주석을 제거·축약해 토큰을 줄이고, 편집 대상 구간은 원문 그대로 둔다.
- 가까운 지점(예: 30줄 이내)은 한 창으로 묶어 호출 수를 줄인다.
- 호출당 6k~8k로 한도에 여유가 있으므로, 필요하면 창이나 컨텍스트를 더 넓힐 수 있다.

### 4.5 분할 순차

- 분할 지점: 함수 본문의 최상위 문장 경계(case 절, if/else 묶음, 반복문). 문장 중간에서는 자르지 않는다.
- 경계 판정: 구문 분석 도구(tree-sitter)를 쓰고, 매크로 때문에 실패하면 마스킹한 본문의 괄호 깊이로 대체한다.
- 각 조각의 헤더: 시그니처, 지역변수 타입표, 변경 계약, 변경 원장.
- 변경 원장은 뒤 조각에 영향을 주는 내용(타입·이름 변경)만 담고 약 1k 토큰으로 제한한다.
- 재조립 후 괄호·전처리기 균형과 잔여 탐지를 검사한다.

10조각 이내를 권장하는 이유는 조각이 늘수록 앞쪽에서 선언된 변수, goto 레이블, 매크로 같은 조각 간 의존이 누적되고, 컴파일로 확인할 수 없기 때문이다. 경험적 추정이므로 파일럿에서 조정한다.

### 4.6 대용량 상수 배열 (140만~180만 자)

**규모.** 1토큰당 1.2~2.5자로 보면 약 56만~150만 토큰이다. 24k 한도의 약 23~63배이고, 모델 고유 컨텍스트(256K, 즉 262,144토큰)도 넘는다.

**보낼 필요가 없는 이유.**
- 버전 대응에서 데이터 값 자체는 바뀌지 않는다.
- LLM이 긴 숫자열을 다시 출력하면 요소 누락이나 변형이 생길 수 있다.

**처리 방법.**
1. 초기화 목록을 감지한다(임계값 예: 2,000자 초과).
2. 자리표시자로 치환한다. 요소 수, 요소 형태, 길이, 해시, 앞뒤 요소 몇 개를 표기한다.
3. 선언부와 주변 코드만 규칙·sLLM 대상으로 삼는다.
4. 처리 후 원문을 복원하고 해시 일치를 확인한다. 자리표시자를 건드린 수정 블록은 기각한다.

**데이터에 대한 버전 대응 점검(규칙 전용).**
- 좁히기 변환: `char` 배열에 0x80 이상 값이 있는 경우처럼 요소 타입 범위를 벗어난 값. VS2015 이후 오류(C2397) 또는 경고(C4838)가 된다. 스크립트가 값 범위를 계산해 탐지한다.
- 선언 크기와 요소 수의 일치.
- `char*` 문자열 테이블의 const 적합성(표준 준수 모드를 쓸 때).

좁히기 변환의 수정(요소 타입을 `unsigned char`로 변경 등)은 선언부에서 이뤄지며 사용처에 영향을 준다. 영향 분석(요구사항 E절) 대상으로 넘긴다.

### 4.7 한도 자체의 완화

모델은 256K를 지원하므로 24k는 서빙 설정값이다. 상향 가능 여부를 먼저 확인할 가치가 있다. 한도와 동시 처리 수는 메모리를 나눠 쓰는 관계이므로, 가능하다면 다음 구성을 검토한다.
- 일반 작업: 24k, 높은 동시 수
- 대형 함수 전용: 더 큰 한도, 낮은 동시 수

## 5. 출력 형식 검토

> 근거 수준: 형식 비교는 B. 이 모델의 형식 준수율은 D.

### 5.1 비교

| 방식 | 출력량 | 장점 | 단점 | 판단 |
|---|---|---|---|---|
| 파일 전체 재출력 | 파일 크기만큼 | 형식이 단순 | 큰 파일은 한도 초과, 무관한 코드 변형 위험, 상수 데이터 훼손 위험 | 불채택 |
| 조각 재출력 | 조각 크기만큼 | 형식 오류가 적음 | 입력의 2배 예산, 범위 밖 변경 가능 | 보조 |
| SEARCH/REPLACE 블록 | 변경 줄의 약 2배 | 줄 번호 불필요, 원문 일치로 검증 | 원문을 조금만 다르게 써도 실패, 중복 구문은 모호 | 기본 |
| 줄 번호 지정 치환 | 변경 줄만 | 출력 최소 | 줄 번호 오류 위험, 입력에 줄 번호를 붙이는 비용 | 대안 |
| unified diff | 변경 줄 + 헤더 | 표준 형식 | 헝크 헤더와 문맥 줄을 정확히 맞추기 어려움 | 불채택 |

### 5.2 수정 블록이 나은 이유

- **토큰**: 출력이 변경분에 비례한다. 파일 전체 출력은 약 9k 토큰을 넘는 파일에서 아예 불가능하다.
- **안전**: 바뀌지 않은 코드는 원문 바이트 그대로 유지된다(인코딩, 공백, 상수 데이터).
- **추적**: 블록 하나가 이슈 하나에 대응해 보고서 작성이 쉽다.
- **병렬**: 독립 작업의 블록을 한 파일에 병합할 수 있다.
- **속도**: 생성은 토큰 단위 순차 처리라 출력이 줄면 시간이 준다.

### 5.3 권고 형식

```
<<<<<<< SEARCH
    char* p = strdup(name);
=======
    char* p = _strdup(name);
>>>>>>> REPLACE
```

- 응답 유형: 수정 블록 / `NO_CHANGE` / `NEED_CONTEXT: 심볼명`
- 코드 본문은 JSON에 담지 않는다. 이스케이프 오류가 생기고 토큰이 낭비된다. 판정 결과 같은 메타 정보만 구조화한다.
- SEARCH 실패가 2회 반복되면 해당 창을 조각 재출력으로 전환하고, 프로그램이 diff를 계산해 허용 범위의 변경만 채택한다.
- 구간의 약 40~50% 이상이 바뀌면 수정 블록의 출력이 재출력보다 많아지므로 처음부터 조각 재출력을 쓴다.
- 줄 번호 지정 방식은 파일럿에서 형식 준수율을 비교해 채택 여부를 정한다.

### 5.4 수용 검사

1. 형식 파싱 성공
2. SEARCH가 창 안에서 정확히 1회 일치(공백만 다르면 정규화 비교 후 원문 공백 유지)
3. 수정 범위가 허용 범위 안
4. 자리표시자 미훼손
5. 수정문이 원본 인코딩으로 표현 가능
6. 적용 후 구문 검사 통과, 대상 이슈의 잔여 탐지 없음, 새 탐지 없음

최종 diff는 원본과 결과 파일을 도구로 비교해 만든다. sLLM이 쓴 diff는 사용하지 않는다.

## 6. 병렬 처리 구조

> 근거 수준: 구조는 B. 서빙 엔진별 동작과 처리량은 D.

### 6.1 원칙

읽기는 스냅샷에서, 쓰기는 수정 레코드로, 병합은 단독으로 한다. 작업끼리 파일을 직접 고치지 않으므로 경쟁 상태가 생기지 않는다.

### 6.2 작업 단위와 의존성

| 단계 | 단위 | 병렬성 | 제약 |
|---|---|---|---|
| 인벤토리, 탐지, 규칙, 검증 | 파일 | 완전 병렬 | 없음 |
| 변경 계약 확정 | 계약 | 직렬 | 사용처 처리의 선행 조건 |
| sLLM 슬라이스 | 슬라이스 | 병렬 | 같은 파일에서 범위가 겹치면 사전에 묶음 |
| 분할 순차 | 함수 | 함수 내 순차, 함수 간 병렬 | 변경 원장 전달 |
| 병합 | 파일 | 파일 간 병렬, 파일 내 단독 | 뒤쪽 위치부터 적용 |

### 6.3 상태 관리

- 작업 테이블(대기/실행/완료/기각/수동)과 응답 캐시를 SQLite 파일 하나로 관리한다. 오프라인 Windows에서 별도 서버 없이 동작한다.
- 작업 ID는 파일 해시, 범위, 이슈 ID, 템플릿·파라미터 버전의 해시다. 같은 입력이면 캐시를 재사용하므로 중단 후 재개와 재실행이 안전하다.
- temperature 0이어도 동시 처리 조건에 따라 응답이 미세하게 달라질 수 있다. 재현성은 응답 캐시로 확보한다.
- 작업별 타임아웃과 재시도 횟수를 둔다. 실패한 작업은 기각 상태로 남기고 나머지 작업은 계속 진행한다.
- 병합은 작업 완료 순서가 아니라 고정된 순서(파일 경로, 위치)로 수행해, 병렬 여부와 관계없이 결과가 같게 한다.

### 6.4 서빙 엔진 고려

- 연속 배칭을 지원하는 엔진(vLLM 등)은 동시 요청을 보내면 전체 처리량이 늘어난다.
- 슬롯 분할 방식(llama.cpp 계열)은 전체 컨텍스트를 슬롯 수로 나눈다. 24k가 이 분할의 결과인지 확인이 필요하다.
- 동시 수는 4~8에서 시작해 처리량을 측정하며 조정한다.
- 프롬프트 고정부를 앞에 두면 프리픽스 캐시로 입력 처리 시간이 줄어든다.

### 6.5 소요 시간 가늠

```
총 시간 ≈ Σ(입력 토큰 ÷ 입력 처리 속도 + 출력 토큰 ÷ 생성 속도) ÷ 유효 동시 수
```

지점 슬라이스는 출력이 수백 토큰이라 입력 처리 시간의 비중이 크다. 프리픽스 캐시와 동시 수의 효과가 크게 나타나는 구조다. 실제 속도는 파일럿에서 측정한다.

## 7. MCP·도구 구성

> 근거 수준: 구조 비교는 B, 토큰 계산은 C, ripgrep 동작은 A'(9.3).

### 7.1 구조 대안

| 안 | 구조 | 장점 | 단점 |
|---|---|---|---|
| A 파이프라인 주도 | 프로그램이 대상과 순서를 정하고, sLLM은 조각별 수정에만 호출. MCP는 단계 실행 도구를 노출 | 전수 처리 보장, 재현성, 토큰 최소, 병렬 용이 | 파이프라인 구현 필요 |
| B sLLM 에이전트 주도 | sLLM이 MCP 도구(검색, 읽기, 편집)를 스스로 호출하며 탐색 | 구현이 단순하고 유연 | 도구 정의와 누적 결과가 24k를 잠식, 탐색 누락 가능, 재현성 낮음 |
| C 혼합 | A를 기본으로, 컨텍스트 부족 시 제한된 조회만 허용 | 통제와 유연성의 절충 | 조회 규약 설계 필요 |

**권고는 A를 기본으로 하고 C로 보완하는 것이다.**

B안의 토큰 계산(추정): 도구 정의 5개 1~1.5k, 지시문 1.5k, 검색 1회 1~2k, 읽기 1회 2~3k. 턴마다 이력이 다시 전송되므로 도구 호출 5~6회면 누적 15k 안팎이 되고, 수정 출력에 쓸 여유가 부족해진다. Gemma 4 31B는 함수 호출을 자체 지원하므로 B안이 기술적으로 불가능한 것은 아니다. 제약은 모델 능력이 아니라 24k 예산과 전수 처리 보장이다.

C안의 조회는 `NEED_CONTEXT: 심볼명` 응답으로 구현한다. 프로그램이 인덱스에서 정의를 찾아 붙여 재요청하며 최대 2회로 제한한다. 도구 호출 루프 없이 같은 효과를 낸다.

그래도 sLLM에 도구를 직접 줘야 한다면 읽기 전용 조회 도구만 5개 이하로 제공하고, 작업당 호출 횟수에 상한을 둔다.

### 7.2 MCP 도구 구성 (A안 기준)

| 도구 | 역할 | 응답 |
|---|---|---|
| `inventory` | 전수 목록, 인코딩, 함수 크기 분포 | 요약 통계. 상세는 파일 |
| `scan` | 규칙 탐지 | 규칙별 건수 |
| `apply_rules` | T1/T2 적용 | 적용 건수 |
| `plan` | 슬라이스와 작업 생성 | 작업 수, 경로별 분포 |
| `run_llm` | 작업 큐 실행(동시 수 지정) | 진행 상태 |
| `verify` | 정적 검증 | 수준별 건수 |
| `report` | diff와 보고서 생성 | 파일 경로 |

조회용 도구(상한 적용):

| 도구 | 상한 |
|---|---|
| `search` | 20건 이하, 줄당 200자 이하, 총건수와 다음 페이지 표시 |
| `read_range` | 200줄 이하, 대용량 초기화 목록 자동 생략 |
| `get_symbol` | 정의와 시그니처 |
| `find_refs` | 건수와 상위 N건 |
| `outline` | 함수 골격(시그니처, 지역 선언, 블록 구조와 줄 범위) |

원칙은 "결과 본문은 디스크에, 응답은 요약과 경로"다.

**sLLM 연결 모듈.**
- 엔드포인트 주소, 모델명, 토큰 한도, 출력 상한, 동시 수, 타임아웃을 설정으로 둔다.
- 전송 전에 토큰을 계산해 한도 초과를 차단한다.
- 모든 요청과 응답을 기록한다.
- 호출 규격(OpenAI 호환 여부)은 서빙 엔진 확인 후 확정한다.

### 7.3 ripgrep 검토

**효용.**
- 단일 실행 파일(rg.exe)이라 설치 없이 오프라인 반입이 쉽다.
- 멀티스레드로 대규모 소스 트리를 빠르게 스캔한다.
- 패턴 파일로 규칙 전체를 한 번에 스캔하고, JSON 출력으로 파일·줄·일치 위치를 구조화해 받는다.
- 용도: 규칙 탐지 스캔, 영향범위 참조 조회, 수정 후 잔여 탐지 재스캔, 최소 컨텍스트 추출.

A안에서는 프로그램이 ripgrep을 쓰므로 검색 결과가 sLLM 토큰을 전혀 소모하지 않는다. 컨텍스트 제약 아래에서 가장 효율적인 사용 방식이다.

**한계.**
- 텍스트 검색이므로 주석·문자열 안의 적중, 매크로, 스코프, 오버로드를 구분하지 못한다. 함수 경계와 정의 조회는 tree-sitter나 ctags를 병행한다.
- 파일을 수정하지 않는다. 치환은 파이프라인 엔진이 한다.

**옵션과 주의점.**

| 항목 | 내용 |
|---|---|
| 전수 검사 | 기본값은 ignore 파일 대상, 숨김 파일, 바이너리 판정 파일을 건너뛴다. `-uuu` 또는 `--no-ignore --hidden --text`를 쓴다 |
| 인코딩 | CP949 파일은 `-E euc-kr`. 혼재 시 인벤토리의 인코딩 판별 결과로 그룹을 나눠 실행. BOM 있는 UTF-16은 자동 처리 |
| 초장문 줄 | `--max-columns 300 --max-columns-preview`로 줄 길이를 제한 |
| 건수 제한 | 먼저 `-c`로 건수만 확인하고, `-m N`으로 파일당 건수를 제한 |
| 구조화 출력 | `--json` |
| 개행 | CRLF 파일에서 `$` 앵커를 쓰려면 `--crlf` |
| 순서 고정 | `--sort path`. 병렬 탐색이 꺼지므로 속도는 떨어짐 |
| 고급 정규식 | 전후방 탐색은 `-P`. 지원 여부는 `rg --pcre2-version`으로 확인 |
| 위치 정보 | 인코딩 변환 시 바이트 위치가 원본과 다를 수 있다. 줄 번호로 받고 적용 위치는 원문에서 다시 확인 |

위 항목 중 전수 검사, 인코딩, 초장문 줄, 개행은 합성 예제로 동작을 확인했다(9.3).

**PowerShell 경유 시.**

권고는 MCP 서버가 rg.exe를 인자 배열로 직접 실행하는 것이다. 셸 문자열을 조립하지 않으면 인용부호와 인코딩 문제를 피할 수 있다.

PowerShell을 반드시 거쳐야 한다면 다음을 지킨다.
- 패턴은 `-f patterns.txt`로 넘긴다. 정규식의 `"`, `$`, `|`, 백틱 인용 문제를 피한다.
- 출력을 받기 전에 `[Console]::OutputEncoding`을 UTF-8로 설정한다. 설정하지 않으면 한글이 깨진다.
- Windows PowerShell 5.1의 `>`와 `Out-File`은 기본이 UTF-16이다. 결과 저장 시 인코딩을 명시한다.
- 호출마다 powershell.exe를 새로 띄우면 기동 시간이 누적된다. `-NoProfile`을 쓰고 호출을 묶거나 상주 프로세스를 쓴다.
- 소스 파일 읽기/쓰기에 `Get-Content`/`Set-Content`의 기본 인코딩을 쓰지 않는다. 바이트 단위로 입출력한다.

**대체 수단.** `Select-String`은 상대적으로 느리고, `findstr`은 정규식 기능이 제한적이다. ripgrep을 반입할 수 없을 때의 비상 경로로만 둔다.

## 8. 버전 체계: 명시가 필요한가

> 근거 수준: A. 버전 대응과 옵션은 공식 문서로 확인했다.

**판단: 필요하다.** 요구사항에 규칙으로 넣어야 한다(요구사항 v3의 B1, B9, B10, 부록 A).

### 8.1 이유

**수정 규칙이 발동하는 축이 여러 개다.**

| 축 | 값의 예 | 이 축이 좌우하는 수정 |
|---|---|---|
| 툴셋(컴파일러·라이브러리) | v90 → v143 | CRT·표준 라이브러리·MFC 변경, 컴파일러가 더 엄격해진 부분. 반드시 대응 |
| C++ 언어 표준 | (선택 없음) → C++14/17/20 | C++17 이상에서 제거된 기능(`auto_ptr` 등)의 대응 여부 |
| 준수 모드 | `/permissive-` 사용 여부 | 비표준 코드가 오류가 되는지 여부 |
| 플랫폼 | x86 → x64 | 포인터 크기에 의존하는 코드 |
| Windows SDK·대상 OS | `WINVER` | 제거·대체된 API |
| 문자셋 | MBCS → Unicode | 문자열 API 전반 |
| CRT 링크 방식 | `/MT`, `/MD` | 서드파티 라이브러리와의 호환 |

**"2008 → 2022"가 정하는 것은 툴셋 하나뿐이다.** 나머지 축이 정해지지 않으면 같은 코드라도 수정 범위가 달라진다.
- `auto_ptr`: C++14면 그대로 컴파일된다. C++17 이상이면 수정해야 한다.
- 문자열 리터럴을 `char*`로 넘기는 코드: 준수 모드를 끄면 통과하고, 켜면 오류다.
- 포인터를 `int`로 캐스팅하는 코드: x86을 유지하면 문제가 없고, x64로 가면 수정해야 한다.

**MS의 공식 업그레이드 절차도 첫 단계가 이 값들의 설정이다.** 플랫폼 툴셋, C++ 언어 표준, Windows SDK 버전을 먼저 정하도록 안내한다.

**입력하는 사람이 버전 체계를 몰라도 되어야 한다.** 숫자 체계가 세 가지(제품 9.0/17.x, 툴셋 v90/v143, 언어 표준 C++14)라 혼동하기 쉽다. 명시 규칙이 없으면 파라미터를 잘못 넣을 가능성이 높다.

### 8.2 명시 방법

- 입력은 VS 제품 연도만으로 가능하게 하고, 툴셋은 대응표(요구사항 부록 A)로 자동 파생한다.
- 나머지 축은 기본값을 두고, 바꿀 때만 명시한다.
- 실제 적용된 값 전체를 보고서 첫머리에 기록한다.

최소 변경이 목적일 때의 기본값:

| 축 | 기본값 | 이유 |
|---|---|---|
| 툴셋 | 대상 VS의 기본(2022면 v143) | 제품 연도에서 파생 |
| C++ 언어 표준 | C++14 | VS2022의 기본값이자 선택 가능한 최저값. 수정 범위가 가장 작다 |
| 준수 모드 | 1차에서는 끔 | MS 권장 절차도 오류가 많으면 일시적으로 끄고 나중에 켠다 |
| 플랫폼 | 기존 유지 | x64 전환은 별도 요청사항으로 다룬다 |
| 문자셋 | 기존 유지 | 변경하면 문자열 API 전반에 영향 |
| Windows SDK | 대상 환경에 설치된 버전 | 대상 환경에서 확인 |

### 8.3 규칙 카탈로그와의 연결

각 규칙은 "어느 축의 어떤 변화에서 발동하는지"를 속성으로 가져야 한다. 예를 들어 `auto_ptr` 규칙은 "언어 표준 C++17 이상", 포인터 캐스팅 규칙은 "플랫폼 x64"에서만 켜진다. 이렇게 해야 임의의 환경 조합에서 필요한 규칙만 선택된다.

## 9. 분석 도구 판단: ripgrep은 만능인가, 구문 분석과 clang이 필요한가

> 근거 수준: 도구의 성격은 A, 아래 예제 결과는 A', 대상 코드에서의 성공률은 D.

**판단**
- ripgrep만으로는 부족하다. 후보를 빠르게 찾는 용도로는 필수지만, 그 이상은 못 한다.
- 구문 분석(tree-sitter 수준)은 사실상 필요하다. 함수 경계, 슬라이스, 분할 지점, 상수 배열 식별이 여기에 달려 있다.
- clang 같은 컴파일러 프런트엔드는 헤더가 있어야만 의미가 있다. 헤더를 확보할 수 있으면 강력히 권장한다.

### 9.1 도구 계층

| 계층 | 도구 | 알 수 있는 것 | 모르는 것 | 필요 조건 | 판단 |
|---|---|---|---|---|---|
| 텍스트 검색 | ripgrep | 패턴이 있는 줄 | 주석·문자열 구분, 함수 경계, 타입, 매크로 | 실행 파일 1개 | 필수(후보 선별) |
| 어휘 분석 | 자체 구현(마스킹, 괄호 깊이) | 코드와 주석·문자열의 구분, 대략의 블록 경계 | 구문 구조 | 자체 개발 | 필수 |
| 구문 분석 | tree-sitter | 함수·문장·호출·초기화 목록의 범위 | 타입, 매크로 전개, include 내용 | 라이브러리 설치 | 사실상 필수 |
| 심볼 색인 | ctags | 정의 위치 | 참조의 정확한 대상(오버로드, 스코프) | 실행 파일 1개 | 권장 |
| 범용 정적분석 | cppcheck | 일부 버그와 문법 오류. 헤더 없이도 동작 | 버전 이행에 특화된 진단 | 설치 | 선택 |
| 컴파일러 프런트엔드 | `cl /Zs`, clang-cl, clang-tidy | 타입, 오버로드, 실제 컴파일 오류 | 링크 오류 | 전체 헤더와 파일별 컴파일 옵션 | 헤더 확보 시 강력 권장 |

### 9.2 기능별로 필요한 계층

| 기능 | 최소 계층 | 비고 |
|---|---|---|
| T1 규칙 탐지 | 텍스트 검색 + 어휘 분석 | 어휘 분석 없이는 주석·문자열 오탐이 섞인다 |
| 함수 경계, 슬라이스, 분할 지점, 상수 배열 생략 | 구문 분석 | 매크로가 많은 파일은 어휘 분석으로 대체 |
| T2 치환(호출 인자 구조 등) | 구문 분석 | 타입에 의존하는 치환은 불가 |
| 타입 의존 판단(좁히기 변환, 포인터 절단, 오버로드) | 컴파일러 프런트엔드 | 없으면 휴리스틱 탐지 후 sLLM·수동 검토 |
| 영향범위(참조 추적) | 심볼 색인(근사) 또는 컴파일러(정확) | 색인만으로는 텍스트 근사 |
| 컴파일 오류 확인 | 컴파일러 프런트엔드 | 없으면 불가 |

### 9.3 합성 예제로 확인한 결과

**ripgrep**

| 확인 항목 | 결과 |
|---|---|
| 전수 검사 | 기본 설정은 4개 파일 중 2개만 검색했다(숨김 폴더와 ignore 대상 제외). `-uuu`를 주면 4개 모두 검색했다 |
| 코드·주석·문자열 구분 | 같은 패턴이 코드, 주석, 문자열에 하나씩 있을 때 3건 모두 적중했다. 실제 호출은 1건이다 |
| CP949 파일 | 인코딩을 지정하지 않아도 영문 패턴은 적중했으나 한글이 깨져 출력됐다. `-E euc-kr`을 주면 정상 출력됐다 |
| 150만 자 한 줄 | 제한이 없으면 적중 한 건이 약 150만 바이트를 출력했다. `--max-columns`를 주면 264바이트였다 |
| CRLF 줄끝 | `;$` 패턴이 기본 설정에서는 0건, `--crlf`에서는 2건이었다 |

**tree-sitter**

| 예제 | 결과 |
|---|---|
| 일반 함수 | 오류 0개. 함수 2개를 모두 식별 |
| MFC 매크로(메시지 맵 등)가 섞인 코드 | 오류 노드 12개. 함수 2개의 위치는 찾았으나, 하나는 반환 타입이 빠졌고 다른 하나는 함수 이름이 클래스 이름으로 잘못 추출됨 |
| `#if`가 여는 괄호를 나누는 코드 | 오류 1개. 두 분기 중 한쪽 정의만 인식 |
| 사용자 매크로가 함수 틀을 만드는 코드 | 해당 함수를 인식하지 못함. 뒤따르는 함수는 정상 인식 |
| 150만 자 상수 배열을 가진 함수 | 약 0.4초에 파싱. 오류 0개. 초기화 목록의 범위를 정확히 식별 |

**clang**

| 확인 항목 | 결과 |
|---|---|
| Windows 헤더 없이 `#include <windows.h>`가 있는 파일 검사 | 첫 줄에서 "파일을 찾을 수 없음"으로 중단 |
| 2008식 코드 5줄을 C++14로 구문 검사 | 리터럴 접합, 좁히기 변환(128과 255를 `char`에 넣음), for 변수 범위 오류를 위치와 함께 보고 |
| `auto_ptr`를 이름만 `unique_ptr`로 치환 | 컴파일 오류 2건(대입, 인자 전달) |
| 같은 코드를 clang-tidy로 자동 수정 | 소유권 이전 지점에 `std::move`가 삽입됐고 오류 0건 |

**해석**
- 대용량 상수 배열의 식별과 생략은 구문 분석으로 충분히 된다.
- 매크로가 문법을 바꾸는 코드에서는 구문 분석이 함수를 놓치거나(사용자 매크로 예제), 이름과 반환 타입을 잘못 추출한다(MFC 예제). 어휘 분석 기반의 대체 경로와, 구문 분석 실패 파일의 목록화가 반드시 있어야 한다.
- 타입이 걸린 판단과 수정은 컴파일러 프런트엔드가 있어야 정확하다. 없으면 sLLM과 수동 검토에 의존하게 되고 결과를 확인할 수단도 없다.

### 9.4 clang에 대한 판단

**전제 조건.** clang-cl은 Visual Studio 설치를 찾지 못하면 표준 헤더조차 찾지 못한다. 최소한 Windows SDK가 필요하고, MFC·ATL 헤더는 Visual Studio에 들어 있다. 서드파티(DB, HMI SDK) 헤더도 필요하다.

**한계.** clang의 진단은 MSVC의 진단과 일치하지 않는다.
- clang의 MSVC 호환 기능은 아직 진행 중인 작업으로 문서화되어 있다.
- MSVC로만 빌드해 온 코드는 먼저 clang으로 빌드되도록 손을 봐야 한다고 MS 스스로 안내한다.
- 따라서 clang이 낸 오류가 곧 VS2022의 오류는 아니다. 근사 검증으로 취급해야 한다.

**쓸모.** clang-tidy의 자동 수정은 타입 정보를 쓰므로 정규식보다 안전하다. 다만 인스턴스화되지 않은 템플릿은 고치지 못하는 등 문서화된 한계가 있다.

**우선순위.** 헤더를 확보했다면 clang보다 `cl /Zs`가 먼저다. 대상 컴파일러 자신이 내는 진단이기 때문이다. clang은 자동 수정(clang-tidy)과 정밀한 영향 분석이 필요할 때 추가한다.

### 9.5 환경별 권장 구성

| 환경 | 구성 | 도달 가능한 검증 |
|---|---|---|
| 가. 컴파일러와 헤더가 전혀 없음 | ripgrep + 어휘 분석 + tree-sitter + ctags (+ cppcheck) | L0~L2 |
| 나. 헤더와 컴파일러 프런트엔드를 쓸 수 있음 | 가 + `cl /Zs` (+ clang-tidy) | L3(파일 단위 컴파일 검사) |
| 다. 외부에 빌드 환경이 있음 | 가 또는 나 + 빌드 오류 로그 반입 | 실제 빌드 결과 |

어느 환경인지가 설계 전체를 좌우한다. 파일럿 전에 가장 먼저 확인해야 한다.

## 10. 빌드 불가 상황의 대처방안

> 근거 수준: 문제 범주와 도구 동작은 A, 대처방안의 효과는 B~D.

### 10.1 먼저 "왜 불가한가"를 구분한다

| 원인 | 가능한 대처 |
|---|---|
| ① 컴파일러(VS2022)가 없고 반입도 불가 | 환경 가. 헤더만이라도 반입할 수 있는지 확인(라이선스, 보안 정책) |
| ② 컴파일러는 있으나 의존성(서드파티 lib, DB·HMI SDK)이 없어 전체 빌드가 실패 | 환경 나. 링크 없이 파일 단위로 컴파일 검사. 없는 SDK 헤더는 스텁으로 대체 |
| ③ 개발환경에서는 불가하지만 다른 곳(빌드 서버, 현장)에서는 가능 | 환경 다. 빌드 오류 로그를 받아 다시 처리 |

"전체 빌드가 안 된다"와 "컴파일 검사를 전혀 못 한다"는 다르다. ②에 해당하면 검증 수준이 크게 올라간다.

### 10.2 MS 분류로 본 "빌드 없이 할 수 있는 것"

MS는 업그레이드 문제를 범주별로 정리해 두었다. 범주마다 문제가 드러나는 단계가 다르다.

| 문제 범주 | 드러나는 단계 | 빌드 없이 할 수 있는 것 |
|---|---|---|
| 라이브러리·툴셋 의존성(구 버전 .lib/.dll, CRT 혼용) | 링크, 실행 | 소스 분석으로는 확정 불가. 바이너리와 링크 설정을 목록화 |
| 프로젝트 설정(경로, 기본 라이브러리 제외 옵션, 미해결 외부 참조) | 링크 | 프로젝트 파일에서 설정을 추출해 점검 목록 작성 |
| `wchar_t` 처리 방식 | 컴파일 | 설정 추출과 패턴 탐지(부분) |
| 언어 준수성 강화 | 컴파일 | 변경 이력 기반 규칙(부분). 완전한 확인은 컴파일 검사 필요 |
| `<stdint.h>` 타입 재정의 | 컴파일 | 규칙(typedef 탐지) |
| CRT 함수 변경·제거 | 컴파일, 링크 | 규칙(함수명 목록) |
| C++ 표준 변경(구 헤더, 좁히기 변환) | 컴파일 | 규칙과 값 범위 계산 |
| 보안 CRT 경고 | 컴파일(경고) | 규칙 또는 설정 흡수 |
| Windows API·SDK 변경 | 컴파일 | 규칙(API 목록), 설정 추출 |
| ATL·MFC | 컴파일, 링크 | 일부 규칙. 대부분은 실제 빌드 필요 |
| 32/64비트 | 컴파일, 실행 | 패턴 탐지(부분). 실행 시 문제는 검출 불가 |
| Unicode/MBCS | 컴파일(경고) | 설정 흡수 |

**링크와 실행 단계의 문제는 어떤 정적 도구로도 소스만 보고 확정할 수 없다.** 이 부분의 대처는 목록화와 실제 빌드 시 확인뿐이다.

### 10.3 대처방안

**1. 공식 변경 이력에 대한 규칙 커버리지 측정**
- MS는 VS2003부터 VS2015까지의 호환성 깨짐 변경을 한 문서에 정리해 두었고, 이후 버전은 준수성 개선 문서로 이어진다.
- 규칙 카탈로그의 각 규칙을 이 문서의 항목에 대응시키고, "문서화된 변경 중 몇 건을 탐지 규칙으로 덮었는지"를 보고한다.
- 빌드 없이 제시할 수 있는 가장 객관적인 지표다. 덮지 못한 항목은 목록으로 남긴다.

**2. 차등 검증(원본과 비교)**
- 원본은 VS2008에서 빌드되던 코드다. 원본과 수정본에 같은 도구(구문 분석, cppcheck, 가능하면 컴파일 검사)를 돌려 "새로 생긴 문제"만 본다.
- 도구의 오탐과 한계가 양쪽에 똑같이 걸리므로 상쇄된다.

**3. 기계적 수정의 동등성 검사**
- 이름 치환류는 수정 전후의 토큰열을 비교해 "의도한 토큰만 바뀌었는지" 확인한다.

**4. 파일 단위 컴파일 검사(환경 나)**
- `cl /Zs`는 출력 파일을 만들지 않고 오류만 보고한다. 링크가 필요 없다.
- 프로젝트 파일에서 include 경로와 전처리기 정의를 추출해 파일별 옵션을 구성한다.
- 이 검사가 가능하면 컴파일러 오류 자체를 탐지 수단으로 쓸 수 있어 규칙 카탈로그의 빈틈을 메운다.

**5. 스텁 헤더**
- 없는 서드파티·SDK 헤더를 선언만 담은 스텁으로 대체해 나머지 코드의 컴파일 검사를 가능하게 한다.
- 작성 비용이 크다. 사용하는 API가 적은 SDK에 한정한다.

**6. 빌드 오류 로그 반입(환경 다)**
- 외부에서 빌드한 오류 로그(파일, 줄, 오류 코드)를 파이프라인 입력으로 받는다.
- 오류 코드를 규칙·수정 지침에 대응시키고, 해당 지점을 슬라이스로 만들어 sLLM에 보낸다.
- 최종적으로는 누군가 VS2022에서 빌드해야 한다. 그 첫 빌드의 로그를 회수하는 절차를 산출물에 넣어 두면, 2차 처리를 자동화할 수 있다.
- 로그 한 번의 정보량이 정적 추정 전체보다 많다. 가능하다면 가장 효과가 큰 대처다.

**7. 프로젝트 파일 처리**
- .vcproj → .vcxproj 변환은 Visual Studio가 수행한다(프로젝트 열기 또는 `devenv /Upgrade`). 변환 보고서도 함께 만들어진다.
- Visual Studio가 없는 개발환경에서는 변환과 그 검증이 불가능하다.
- 파이프라인이 할 일은 두 가지다. 프로젝트 파일에서 설정을 추출해 분석과 보고에 쓰는 것, 그리고 변환 후 적용할 설정 변경 목록을 만드는 것이다.
- MS는 VS2008 이하 프로젝트에 별도의 2단계 업그레이드 절차를 안내한다. 세부 절차는 변환을 수행할 환경에서 공식 문서로 확인해야 한다.

**8. 서드파티 바이너리**
- MS는 서로 다른 컴파일러 버전으로 만든 바이너리를 정적 링크하지 말 것을 권고한다. VS2015 이후 툴셋끼리는 이진 호환이지만 VS2008과는 아니다.
- 선택지는 재빌드, 호환 버전 입수, DLL로 감싸 경계를 분리하는 것이다.

**9. 단계적 엄격화**
- 1차 목표는 준수 모드를 끄고 C++14로 컴파일 가능한 상태다. 이후 단계에서 준수 모드와 표준을 올린다. MS 권장 절차와 같은 순서다.

**10. 검증 수준의 표기**
- 보고서에 파일별 도달 수준(L0~L3)과 미검증 사유를 적는다.

### 10.4 무엇을 "보장"이라 부를 수 있는가

| 환경 | 말할 수 있는 것 | 말할 수 없는 것 |
|---|---|---|
| 가 | 알려진 변경 패턴을 처리했다. 새 구문 오류를 만들지 않았다 | 컴파일된다, 링크된다 |
| 나 | 파일 단위로 컴파일 검사를 통과했다 | 링크된다, 실행 시 동작이 같다 |
| 다 | 실제로 빌드됐다 | 실행 시 동작이 같다 |

요구사항의 "정적분석으로 최소한의 빌드 가능성 보장"은 환경 가에서는 문자 그대로 달성할 수 없다. 환경 가에서의 목표는 다음으로 정의하는 것이 정확하다.

> 문서화된 변경 패턴을 가능한 한 덮고, 수정으로 새 문제를 만들지 않으며, 확인하지 못한 위험을 범주별 목록으로 넘긴다.

## 11. 요구사항별 실현 가능성

> 근거 수준: 판단. 근거는 각 절 참조.

| 요구사항 | 판단 | 조건과 근거 |
|---|---|---|
| A 전수 검사, 원본·인코딩 보존 | 가능 | 일반적인 구현. ripgrep의 기본 제외 동작만 해제하면 된다 |
| B 파라미터화, 프롬프트 템플릿 | 가능 | 버전 축을 분리해 정의해야 한다(8절) |

| C 규칙 T2 | 조건부 | 구문 분석 도구 필요. 타입 의존 치환은 제외 |
| C13 기능변경의 기계화 | 조건부 | 상수 인덱스 접근만 가능. 별칭·포인터 접근은 수동 |

| F 검증 L0~L2 | 가능 | 단, "빌드 보장"은 아니다 |
| F 검증 L3 | 환경 의존 | 헤더와 컴파일러 프런트엔드 필요 |
| "정적분석으로 빌드 가능성 보장" | 문자 그대로는 불가 | 10.4의 정의로 바꿔야 한다 |

| I MCP, ripgrep | 가능 | PowerShell 인코딩과 인용부호 관리 필요 |
| J 분석 도구 계층 | 조건부 | 도구 반입 가능 범위에 달려 있다 |

## 13. 진행 단계와 파일럿 측정 항목

**0. 환경 확인(가장 먼저)**
- 빌드가 불가능한 이유가 10.1의 ①, ②, ③ 중 무엇인지
- 외부에 빌드 가능한 환경이 있는지, 오류 로그를 받아 올 수 있는지
- VS2022·Windows SDK 헤더와 분석 도구의 반입 가능 범위
- 24k 한도의 상향 가능 여부와 서빙 엔진
- MCP 호스트가 무엇인지

**1. 인벤토리와 탐지 스캔(LLM 없음)**: 파일 수, 함수 크기 분포, 규칙별 건수, 구문 분석 실패 파일 수를 얻는다.

**2. 규칙 엔진 T0~T2**: 수정 레코드, 병합, diff까지 LLM 없이 한 바퀴 돌린다. 규칙 커버리지를 산출한다.

**3. sLLM 지점 슬라이스**: 프로젝트 하나로 파일럿을 수행한다.

**4. 분할 순차와 계약 기반 처리**: 기능변경 요청을 포함한다.

**5. 보고서, MCP 도구, 빌드 환경용 절차서 정리.**

| 측정 항목 | 보정 대상 |
|---|---|
| 줄당 토큰 수(영문 코드, 한글 주석, 숫자 데이터) | 4.1 예산, 4.2 규모표 |
| 함수 크기 분포 | 4.3 경로 임계값 |
| 구문 분석 실패 파일 비율 | 9절 대체 경로의 비중 |
| 수정 블록 형식 준수율, 기각률 | 5.3 기본 형식 선택 |
| 호출당 시간, 동시 수별 처리량 | 6.4 동시 수 |
| 규칙 대 sLLM 건수 비율, 규칙 커버리지 | 3절 규칙 확충 우선순위 |
