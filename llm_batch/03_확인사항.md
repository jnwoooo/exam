| 항목 | 내용 |
|---|---|

## 1. 왜 확인하는가

지금 가장 큰 변수는 "이 PC에서 어디까지 컴파일해 볼 수 있는가"다. 결과에 따라 검증 수준이 달라진다.

| 환경 | 상태 | 도달 가능한 검증 |
|---|---|---|
| 가 | 컴파일러와 헤더가 없음 | 텍스트·구문 수준 분석까지 |
| 나 | 컴파일러와 헤더는 있으나 전체 빌드는 안 됨 | 파일 단위 컴파일 검사까지 |
| 다 | 전체 빌드가 됨 | 실제 빌드 결과와 오류 로그 |

현재 알려진 사실은 두 가지다.
- 소스는 압축 형태로 받았고, Visual Studio(또는 Visual C++ 2008~2022)를 설치했다.
- clang으로 분석했을 때 math.h를 찾지 못했다.

math.h를 못 찾았다는 것은 컴파일러·헤더가 실제로는 없거나, 있는데 clang이 위치를 모른다는 신호다. 아래 절차로 어느 쪽인지 가린다.

이 문서의 명령은 표준 설치 경로를 기준으로 작성했으며, 대상 PC에서 실행해 검증한 것은 아니다. 경로가 다르면 실제 위치에 맞게 바꾼다.

## 2. 빌드에 필요한 네 가지

| 항목 | 무엇인가 | 어디서 오는가 | 없으면 |
|---|---|---|---|
| 컴파일러 | 소스를 기계어로 바꾸는 프로그램(cl.exe)과 링커 | Visual Studio 설치 때 "C++를 사용한 데스크톱 개발"을 선택해야 들어온다 | 컴파일 검사 전부 불가 |
| 표준 헤더·라이브러리 | math.h, stdio.h, windows.h 등 | VS2015 이후에는 Windows SDK 폴더에 있다 | 거의 모든 파일이 첫 줄에서 실패 |
| 프로젝트 파일 | .sln, .vcproj. 어떤 소스를 어떤 옵션과 경로로 컴파일할지 적힌 설정 파일 | 받은 압축 안에 있어야 한다 | 옵션을 추정해야 해 정확도가 떨어진다 |
| 외부 의존성 | 소스가 가져다 쓰는 남의 헤더와 .lib (DB 클라이언트, HMI SDK 등) | 압축에 들어 있거나 별도로 받아야 한다 | 그것을 쓰는 파일은 컴파일 불가, 링크 불가 |

MFC를 쓰는 소스라면 MFC 헤더·라이브러리도 필요하다. Visual Studio의 선택 구성요소다.

## 3. 주의: "Visual C++ 20xx Redistributable"은 컴파일러가 아니다

프로그램 목록에 "Microsoft Visual C++ 2008 Redistributable", "2015-2022 Redistributable" 같은 항목이 여러 개 보이는 것은 흔한 일이다. 이것은 이미 만들어진 프로그램을 실행할 때 쓰는 런타임 라이브러리이고, 컴파일러와 헤더는 들어 있지 않다.

"Visual C++ 2008~2022를 설치했다"가 이 항목들을 가리킨다면 빌드 도구는 없는 상태다. 4.1로 확인한다.

## 4. 확인 절차

PowerShell에서 실행한다. `D:\src`는 압축을 푼 실제 경로로 바꾼다.

### 4.1 컴파일러가 있는가

```powershell
Get-ChildItem "C:\Program Files*\Microsoft Visual Studio*" -Recurse -Filter cl.exe -ErrorAction SilentlyContinue | Select-Object FullName
```

| 결과 | 뜻 |
|---|---|
| 아무것도 안 나옴 | 컴파일러 없음. 환경 가 |
| `...\2022\...\VC\Tools\MSVC\14.xx...\cl.exe` | VS2022 컴파일러 있음 |
| `...\Microsoft Visual Studio 9.0\VC\bin\cl.exe` | VS2008 컴파일러 있음 |

### 4.2 표준 헤더(Windows SDK)가 있는가

```powershell
Get-ChildItem "C:\Program Files (x86)\Windows Kits" -Recurse -Filter math.h -ErrorAction SilentlyContinue | Select-Object FullName
```

| 결과 | 뜻 |
|---|---|
| `...\Windows Kits\10\Include\10.0.xxxxx.0\ucrt\math.h` | Windows SDK 있음 |
| 아무것도 안 나옴 | Windows SDK 없음. clang이 math.h를 못 찾은 원인일 가능성이 높다 |

### 4.3 MFC 헤더가 있는가

소스가 MFC를 쓰는 경우에만 해당한다(소스에 `afxwin.h`, `stdafx.h`의 `afx...` include가 있으면 MFC를 쓰는 것이다).

```powershell
Get-ChildItem "C:\Program Files*\Microsoft Visual Studio*" -Recurse -Filter afxwin.h -ErrorAction SilentlyContinue | Select-Object FullName
```

결과가 없으면 MFC 구성요소가 설치되지 않은 것이다.

### 4.4 컴파일러가 실제로 동작하는가

시작 메뉴에서 **Developer PowerShell for VS 2022**를 열고 실행한다. 일반 PowerShell에서는 헤더 경로가 잡히지 않아 실패할 수 있다.

```powershell
@'
#include <math.h>
int main() { return (int)sqrt(4.0); }
'@ | Set-Content -Encoding ascii t.cpp
cl /Zs t.cpp
```

| 결과 | 뜻 |
|---|---|
| 오류 없이 끝남 | 컴파일러와 표준 헤더가 정상. 환경 나 이상 |
| `cl`을 찾을 수 없음 | 컴파일러 미설치, 또는 Developer PowerShell이 아닌 창에서 실행 |
| `math.h`를 열 수 없음 | Windows SDK 미설치 |

`/Zs`는 출력 파일을 만들지 않고 오류만 확인하는 옵션이다.

### 4.5 받은 소스에 프로젝트 파일이 있는가

```powershell
Get-ChildItem "D:\src" -Recurse -Include *.sln,*.vcproj,*.vcxproj,*.dsw,*.dsp | Select-Object FullName
```

| 결과 | 뜻 |
|---|---|
| .sln과 .vcproj가 있음 | VS2008 형식의 프로젝트. 정상 |
| .dsw, .dsp만 있음 | VC6 형식. VS2022는 이 형식의 변환을 더 이상 지원하지 않으므로 중간 버전을 거쳐야 한다 |
| 아무것도 없음 | 소스만 받은 것. 제공처에 프로젝트 파일을 요청한다 |

### 4.6 프로젝트 설정 값

프로젝트 파일에 적힌 주요 설정을 뽑는다.

```powershell
Get-ChildItem "D:\src" -Recurse -Filter *.vcproj |
  Select-String -Pattern 'RuntimeLibrary=|CharacterSet=|UseOfMFC=|AdditionalIncludeDirectories=|AdditionalDependencies=|PreprocessorDefinitions=' |
  Select-Object Filename, Line
```

| 설정 | 값의 뜻 | 왜 보는가 |
|---|---|---|
| `RuntimeLibrary` | 0, 1은 정적 링크(/MT, /MTd). 2, 3은 DLL(/MD, /MDd) | "정적빌드" 제약이 정적 링크를 뜻하는지 확인 |
| `CharacterSet` | 1은 Unicode, 2는 MBCS | 문자셋 유지 여부 판단 |
| `UseOfMFC` | 0은 미사용, 1은 정적, 2는 공유 DLL | MFC 구성요소 필요 여부 |
| `AdditionalIncludeDirectories` | 헤더를 찾는 추가 경로 | 경로가 소스 폴더 밖을 가리키면 외부 의존성 |
| `AdditionalDependencies` | 링크할 .lib 목록 | 받은 압축에 그 .lib가 있는지 대조 |
| `PreprocessorDefinitions` | 전처리기 정의 | 파일 단위 컴파일 검사 때 그대로 넘겨야 한다 |

### 4.7 외부 의존성이 빠져 있는가

소스가 include하는 헤더 중 받은 소스 폴더 안에 없는 것을 뽑는다.

```powershell
$src = "D:\src"
$have = Get-ChildItem $src -Recurse -File | ForEach-Object { $_.Name.ToLower() } | Sort-Object -Unique
Get-ChildItem $src -Recurse -Include *.cpp,*.c,*.h,*.hpp |
  Select-String -Pattern '^\s*#\s*include\s*[<"]([^>"]+)[>"]' |
  ForEach-Object { $_.Matches[0].Groups[1].Value } |
  Sort-Object -Unique |
  Where-Object { $have -notcontains (Split-Path $_ -Leaf).ToLower() }
```

나온 목록을 다음 기준으로 나눈다.

| 헤더 | 출처 | 조치 |
|---|---|---|
| stdio.h, math.h, string.h 등 | Windows SDK | 4.2로 확인 |
| windows.h, winsock2.h 등 | Windows SDK | 4.2로 확인 |
| vector, string, map처럼 확장자 없는 이름 | Visual Studio의 C++ 표준 라이브러리 | 4.1로 확인 |
| afx로 시작하는 헤더 | MFC | 4.3으로 확인 |
| atl로 시작하는 헤더 | ATL | Visual Studio 구성요소 추가 |
| 그 외(DB 제품이나 HMI 제품 이름이 들어간 헤더 등) | 외부 의존성 | 제공처에 헤더와 .lib를 요청 |

마지막 줄에 해당하는 헤더가 이 PC에서 컴파일할 수 없는 부분의 범위를 정한다.

### 4.8 자동 점검

4.1~4.7은 `vupdate`가 자동으로 수행한다. 명령 하나로 끝난다.

```
vupdate preflight --package D:\src
```

결과는 화면과 `runs\<패키지>\<실행ID>\out\preflight.md`에 나온다. `vupdate run`을 실행해도 같은 점검이 맨 앞(S0, S1)에서 수행된다.

| 수동 점검 | 자동 점검이 하는 일 |
|---|---|
| 4.1 컴파일러 | 표준 설치 경로에서 cl.exe를 찾는다. VS2008 컴파일러도 따로 찾는다 |
| 4.2 Windows SDK | Windows Kits 폴더에서 math.h를 찾는다 |
| 4.3 MFC | afxwin.h를 찾는다 |
| 4.4 동작 확인 | math.h를 쓰는 두 줄짜리 소스를 `cl /Zs`로 실제 검사한다 |
| 4.5 프로젝트 파일 | 패키지 안의 프로젝트 파일을 나열한다 |
| 4.6 프로젝트 설정 | .vcproj에서 문자셋, 런타임(정적/DLL), MFC 사용, 추가 include 경로, 링크 .lib를 뽑는다 |
| 4.7 외부 의존성 | include된 헤더를 내부, 표준/Windows, MFC, ATL, 외부 후보로 나눈다 |
| 5.1 판정 | 환경 등급(가 또는 나)을 정한다 |
| 5.3 대체 수단 | 없는 항목별로 영향과 조치를 표로 낸다 |

주의할 점:
- 자동 점검의 Visual Studio 탐지와 컴파일러 호출은 Windows에서 아직 검증하지 못했다. 자동 점검과 수동 점검(4.1~4.4)의 결과가 다르면 수동 점검이 기준이다. 차이가 나면 `logs\run.log`의 `[M07.컴파일]` 줄에 찾은 경로가 남아 있으니 그것을 보고 코드를 고친다.
- Visual Studio가 표준 경로가 아닌 곳에 설치돼 있으면 자동 점검이 못 찾을 수 있다. 이때는 "Developer PowerShell for VS 2022"에서 `vupdate`를 실행하면 그 창에 잡힌 컴파일러를 그대로 쓴다.
- 환경 등급 다(전체 빌드 가능)는 자동으로 판정하지 않는다.

## 5. 결과 판정

### 5.1 확인 결과의 조합별 판정

| 4.1 컴파일러 | 4.2 SDK | 4.5 프로젝트 파일 | 4.7 외부 의존성 | 환경 | 가능 | 불가능 |
|---|---|---|---|---|---|---|
| 없음 | - | - | - | 가 | 텍스트·구문 분석, 규칙 기반 수정 | 컴파일 검사 전부 |
| 있음 | 없음 | - | - | 가 | 위와 같음 | 표준 헤더를 못 찾아 컴파일 검사 불가 |
| 있음 | 있음 | 없음 | - | 나(제한적) | 옵션을 추정한 파일 단위 검사 | 원래 설정대로의 빌드 |
| 있음 | 있음 | 있음 | 빠진 것 있음 | 나 | VS2022로 프로젝트 변환, 외부 헤더를 안 쓰는 파일의 컴파일 검사 | 외부 헤더를 쓰는 파일의 검사, 링크 |
| 있음 | 있음 | 있음 | 모두 있음 | 다 | 실제 빌드, 오류 로그로 수정 반복 | 실행 동작 확인 |

실행 동작 확인은 DB와 HMI 장비가 연결돼야 하므로 어느 경우든 이 PC에서는 불가능하다.

### 5.2 하려는 일별로 반드시 필요한 것

| 하려는 일 | 반드시 필요한 것 | 없어도 되는 것 |
|---|---|---|
| 규칙 탐지, 기계적 수정, sLLM 수정, 구문 수준 검증 | 소스 | 컴파일러, SDK, 프로젝트 파일, 외부 의존성 |
| 파일 단위 컴파일 검사 | 컴파일러, Windows SDK, 그 파일이 include하는 모든 헤더(MFC와 외부 헤더 포함) | 외부 .lib. 프로젝트 파일은 없으면 옵션을 추정 |
| 프로젝트 파일 변환 | Visual Studio 2022 본체(IDE), 프로젝트 파일 | 외부 의존성 |
| 전체 컴파일(링크 직전까지) | 위 두 줄의 것 전부와 모든 외부 헤더 | 외부 .lib |
| 링크(실행 파일 생성) | 위에 더해 모든 외부 .lib의 VS2022 호환본 | 없음 |
| 실행 동작 확인 | 위에 더해 DB, HMI 장비 등 실행 환경 | 없음 |

아래로 갈수록 필요한 것이 늘어난다. 소스 수정 작업 자체는 첫 줄만으로 시작할 수 있다. 나머지 줄은 "수정 결과를 어디까지 확인할 수 있는가"를 정한다.

### 5.3 항목별: 없을 때의 영향과 대체 수단

| 항목 | 없으면 못 하는 것 | 대체 수단 | 판정 |
|---|---|---|---|
| VS2022 컴파일러 | 컴파일 검사, 빌드, 오류 로그 확보 | ① 설치(Visual Studio Installer, 또는 컴파일러만 설치하는 Build Tools) ② 다른 PC에서 빌드하고 오류 로그만 받아 오기 ③ 둘 다 안 되면 규칙 탐지와 구문 수준 검증으로 진행 | 부분 대체. "컴파일된다"는 확인은 컴파일러 없이는 불가 |
| Windows SDK | 표준 헤더를 못 찾아 모든 컴파일 검사가 첫 줄에서 실패한다. clang을 써도 같다 | 설치뿐이다(Visual Studio Installer의 구성요소, 또는 SDK 단독 설치 프로그램) | 컴파일 검사에는 대체 불가. 텍스트·구문 분석에는 필요 없음 |
| MFC·ATL | MFC·ATL을 쓰는 파일의 컴파일 검사. 공통 헤더(stdafx.h)가 MFC를 include하면 전 파일이 해당한다 | 설치뿐이다(Visual Studio Installer의 구성요소). 규모가 커서 스텁으로 흉내 낼 수 없다 | MFC 프로젝트면 대체 불가 |
| VS2022 본체(IDE) | 프로젝트 파일 변환 | 변환만 다른 PC에서 하고 결과를 받아 오기. 또는 새 프로젝트 파일을 직접 작성 | 부분 대체 |
| 프로젝트 파일 | 원래 설정대로의 빌드. 빌드 대상 소스 목록, include 경로, 전처리기 정의를 알 수 없다 | ① 제공처에 요청 ② 빌드 스크립트(.bat, makefile)에서 옵션 복원 ③ 옵션을 추정해 파일 단위 검사만 수행 | 부분 대체. 추정으로는 전체 빌드를 재현하기 어렵다 |
| 외부 헤더(DB, HMI SDK 등) | 그 헤더를 include하는 파일의 컴파일 검사. 공통 헤더가 include하면 전 파일이 해당한다 | ① 제공처에 요청 ② 공개 배포되는 SDK면 같은 버전을 입수 ③ 쓰는 선언만 담은 스텁 헤더 작성 ④ 해당 파일을 검사에서 제외 | 대체 가능. 스텁은 비용이 들고 정확도가 떨어진다 |
| 외부 .lib | 링크. 실행 파일이 만들어지지 않는다 | 없다. 있더라도 VS2008로 만든 정적 .lib은 VS2022와 호환이 보장되지 않아 재빌드본이 필요하다 | 링크에는 대체 불가. 소스 수정과 컴파일 검사에는 필요 없음 |
| VS2008 컴파일러 | 받은 원본이 온전한지의 사전 확인 | 제공처에 "2008에서 빌드되던 상태 그대로인지" 확인. 압축에 빌드 로그나 산출물이 있는지 확인 | 없어도 됨 |
| ripgrep | 없다. 속도만 느려진다 | PowerShell의 Select-String, 자체 검색 | 대체 가능 |
| 구문 분석 도구 | 정확한 함수 경계 파악 | 괄호 깊이를 세는 어휘 분석 | 대체 가능. 정확도는 떨어진다 |
| clang | 타입 정보를 쓰는 자동 수정(clang-tidy) | VS2022 컴파일러의 검사로 대부분 대체. 자동 수정은 sLLM과 수동 검토로 | 없어도 됨 |
| 실행 환경(DB, HMI 장비) | 실행 동작 확인 | 없다. 확인 목록으로 넘긴다 | 대체 불가. 이 작업의 범위 밖 |
| 인터넷 연결 | Visual Studio 구성요소의 온라인 추가 | 연결된 PC에서 오프라인 설치 파일을 만들어 옮긴다 | 대체 가능 |
| Python | 없다. `vupdate`를 exe로 배포하면 대상 PC에 Python이 필요 없다 | exe를 다른 Windows PC에서 만들어 옮긴다(`04_개발구조.md` 2절) | 없어도 됨 |

Build Tools와 SDK 단독 설치 프로그램은 사용 전에 라이선스 조건을 확인한다.

### 5.4 정리와 확보 우선순위

**대체할 수 없는 것**
- 컴파일 검사를 하려면: Windows SDK. MFC 프로젝트면 MFC도.
- 링크하려면: 외부 .lib의 VS2022 호환본.
- 실행 동작을 확인하려면: 실행 환경.

**없어도 진행되는 것**
- 소스 수정 작업 자체(규칙, sLLM). 다만 결과를 컴파일로 확인하지 못한다.
- ripgrep, 구문 분석 도구, clang, VS2008 컴파일러. 속도나 정확도가 떨어질 뿐이다.

**확보 우선순위**

| 순위 | 확보할 것 | 이유 |
|---|---|---|
| 1 | VS2022 컴파일러, Windows SDK, (MFC 프로젝트면) MFC | 설치만 하면 되고 효과가 가장 크다. 컴파일 검사가 가능해진다 |
| 2 | 프로젝트 파일 | 없으면 컴파일 옵션이 추정이 된다. 제공처에 요청하면 되는 일이다 |
| 3 | 외부 헤더 | 공통 헤더가 include하고 있으면 1순위와 같은 급으로 올린다. 없으면 검사가 통째로 막힌다 |
| 4 | 외부 .lib | 링크까지 확인하려 할 때만 필요하다 |

부족한 항목의 설치·요청 방법은 6절에 있다.

## 6. 부족한 것이 있을 때의 조치

**컴파일러나 SDK가 없을 때**
1. Visual Studio Installer를 실행하고 설치된 Visual Studio 2022의 "수정"을 누른다.
2. 워크로드에서 "C++를 사용한 데스크톱 개발"을 선택한다.
3. 개별 구성 요소에서 다음이 선택됐는지 확인한다(이름은 버전에 따라 조금 다를 수 있다).
   - MSVC v143 빌드 도구
   - Windows 10 또는 11 SDK
   - v143 빌드 도구용 C++ MFC (소스가 MFC를 쓰는 경우)
   - v143 빌드 도구용 C++ ATL (소스가 ATL을 쓰는 경우)
4. PC가 인터넷에 연결돼 있지 않으면 구성요소 추가가 되지 않는다. 이 경우 연결된 PC에서 오프라인 설치 파일을 만들어 옮겨야 한다.

Visual Studio Installer 자체가 없다면 Visual Studio가 설치되지 않은 것이다(3절).

**프로젝트 파일이 없을 때**
- 소스 제공처에 .sln과 .vcproj를 요청한다. 빌드 스크립트(.bat, makefile)가 따로 있는지도 묻는다.

**외부 의존성이 빠졌을 때**
- 4.7에서 나온 헤더 목록과 4.6의 .lib 목록을 제공처에 전달해 요청한다.
- 받을 수 없으면 그 부분은 컴파일 검사 대상에서 빠진다. 보고서에 미검증으로 남긴다.

## 7. clang이 math.h를 못 찾는 문제

| 경우 | 원인 | 조치 |
|---|---|---|
| 4.2 결과가 없음 | Windows SDK 미설치 | 6절의 조치 |
| 4.2 결과가 있음 | clang에 헤더 경로가 전달되지 않음 | Developer PowerShell for VS 2022에서 clang을 실행 |

Developer PowerShell에서는 헤더 경로가 환경변수로 잡힌다. 다음으로 확인할 수 있다.

```powershell
$env:INCLUDE -split ';'
```

`...\ucrt`로 끝나는 경로가 목록에 있으면 정상이다. 파이썬 등에서 clang 라이브러리를 직접 부르는 방식이라면 이 경로들을 include 경로 인자로 넘겨야 한다.

컴파일러가 확인되면 clang보다 Visual Studio 자체 컴파일러의 검사(`cl /Zs`)를 먼저 쓴다. 대상 컴파일러가 직접 내는 진단이라 더 정확하다.

## 8. 확인 후 다음 단계

**VS2008 컴파일러가 있는 경우: 원본을 먼저 빌드해 본다**
- 수정 전 원본을 VS2008에서 그대로 빌드한다.
- 성공하면 받은 소스가 온전하다는 뜻이다. 실패하면 오류 메시지가 빠진 의존성을 알려 준다.
- 수정 작업과 무관하게 "받은 소스 자체의 문제"를 먼저 걸러낼 수 있다.

**VS2022 컴파일러가 있는 경우: 변환과 빌드를 시도해 로그를 확보한다**
1. 소스를 복사한다. 변환은 되돌릴 수 없으므로 반드시 복사본에서 한다.
2. 복사본의 .sln을 VS2022로 연다. 변환이 진행되고 변환 보고서(UpgradeLog.htm)가 프로젝트 폴더에 생긴다.
3. 빌드를 실행하고 오류 목록을 파일로 저장한다. Developer PowerShell에서는 다음과 같이 한다(구성과 플랫폼 이름은 프로젝트에 맞춘다).

```powershell
msbuild 솔루션이름.sln /p:Configuration=Release /p:Platform=Win32 /fl
```

`/fl`을 주면 같은 폴더에 msbuild.log가 생긴다. 이 로그가 수정 대상을 가장 정확하게 알려 주는 자료다.

VS2008 이하 프로젝트는 변환에 별도 절차가 필요할 수 있다. 직접 열어서 변환이 되지 않으면 MS의 업그레이드 안내 문서를 확인한다.

**문서 갱신**
- 컴파일러가 확인되면 요구사항 v3의 전제 P2("개발환경에서 컴파일·빌드 불가")가 바뀐다. 환경 나 또는 다를 기준으로 요구사항과 검토방안을 고친다.
- 실행 흐름은 `04_개발구조.md` 6절의 환경 분기로 이미 대응해 두었으므로 구조를 다시 짤 필요는 없다.
