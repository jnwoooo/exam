## 1. 이름을 넓혀 찾기: `--ask-match 1|2|3|4`

요청문의 이름(의미 분석의 `names`)이 코드에 없을 때 어디까지 넓혀 찾을지 정한다. 위 단계는 아래 단계의 것을 모두 찾는다.

| 단계 | 찾는 것 | 예(`tc`) | 낱말 검색(`words`) |
|---|---|---|---|
| 1 (기본) | 정확히 같은 이름만 | 못 찾음 | 함수 이름만 본다 |
| 2 | 대소문자만 다른 이름 | `TC` | 함수 이름만 본다 |
| 3 | 그 낱말이 든 모든 이름 | `TC`, `szTc`, `ParseTc`, `MES_TC`, `g_nTcTable` | 변수, 필드, 타입, 매크로까지 본다(`lot` → `szLot`) |
| 4 | 그 글자가 들어 있는 모든 이름(3글자 이상일 때) | 2글자라 3단계와 같음. `bat` → `nBatch` | 3단계에 글자 포함을 더한다 |

- 기본은 1이라 주지 않으면 0.10.6과 같다. PowerShell 스크립트는 `-AskMatch 3`.
- 옵션이 없으면 설정 `limits.ask_match_level`을 쓴다.
- 코드에 정확히 있는 이름은 넓히지 않는다. 넓히는 것은 코드에 없어 버려지던 이름뿐이다.
- 이름은 낱말로 쪼개 비교한다. `szTc` → sz, tc / `MES_TC` → mes, tc / `m_nLotCount` → n, lot, count. 2글자 이상의 낱말만 본다.
- 좁은 단계에서 찾은 이름이 앞에 오고, 같은 단계에서는 많이 쓰인 이름이 앞에 온다. 이름 하나에서 찾은 것이 `limits.ask_widen_max`(기본 30)를 넘으면 앞의 것만 대상으로 하고 전체 수를 적는다.
- 넓혀 찾은 이름은 일반 수정 요청의 대상과, 구조 분석의 대상을 좁히는 데 쓴다. **배열을 구조체로 바꾸는 표 변환의 대상으로는 삼지 않는다**(우연히 낱말이 같은 배열을 바꾸지 않게).

### 1.1 얼마나 잡히는지 보는 방법

`--until S5`로 대상 찾기까지만 돌리면 sLLM의 수정 호출 없이 범위를 볼 수 있다.

```
vupdate run ... --ask-file asks.txt --ask-match 3 --until S5
```

| 어디 | 무엇 |
|---|---|
| `logs/run.log` | `요청 ASK-1-1: 이름 tc 은(는) 코드에 없어 넓혀 찾음(--ask-match 3): TC(대소문자만 다름, 12곳), szTc(낱말이 같음, 40곳) …` |
| `out/ask_trace.md` | 의도마다 "넓혀 찾은 이름", 찾은 방식, 쓰인 횟수, 대상 줄 수. 머리에 지금 단계 |
| 보고서 | "요청문 처리 추적" 표의 이름 칸에 "(넓혀 찾음: tc)" |

단계를 올려 가며 같은 요청문으로 돌려, 대상 줄 수가 감당할 만한 단계를 고른다. 이어서 실행(`--resume`)할 때 `--ask-match`를 다시 줄 수 있지만 S5가 이미 끝난 실행에는 적용되지 않는다.

### 1.2 메모: 오탐 제외(시험 뒤에 진행)

넓힐수록 관계없는 이름이 섞인다. 이번 판에는 걸러 내는 장치를 넣지 않았다. 지금 있는 것은 둘뿐이다: 이름 하나당 상한(30개), 낱말 후보가 8개를 넘을 때 sLLM에 번호 목록을 보내 고르게 하는 것.

시험에서 볼 것:

- 단계마다 넓혀 찾은 이름의 수와 대상 줄 수(`ask_trace.md`)
- 잡힌 이름 가운데 요청과 관계없는 것의 비율과 그 꼴(어떤 낱말에서, 어떤 종류의 이름이)
- 관계있는데 잡히지 않은 이름(한글 용어, 약어, 다른 표기)

후보로 생각한 방법(정하지 않았다):

| 방법 | 내용 | 걸리는 점 |
|---|---|---|
| 후보 확인을 기본으로 | 넓혀 찾은 이름이 2개 이상이면 종류·횟수·쓰인 줄의 예를 붙여 sLLM에 고르게 한다 | 의도마다 호출 1회 이상. 모델이 코드 한 줄만 보고 고른다 |
| 이름의 종류로 거르기 | 요청이 "구조체", "배열", "함수"를 말하면 그 종류만 남긴다 | 종류를 요청문에서 읽어야 한다(의미 분석의 답에 칸을 더한다) |
| 흔한 낱말 빼기 | `data`, `buf`, `len`, `idx`, `tmp` 같은 낱말은 낱말 단위로 넓히지 않는다 | 이번 요청이 바로 `data`를 말한다. 목록을 사람이 정해야 한다 |
| 같이 나오는 낱말 | 요청문의 다른 낱말과 같은 함수·파일에 나오는 이름을 앞에 둔다 | 점수의 기준을 정해야 한다 |
| 쓰인 횟수의 상·하한 | 너무 많이 쓰인 이름(수백 곳)은 빼거나 따로 묻는다 | 정말 고쳐야 할 이름일 수 있다 |
| 범위 한정 | 의미 분석의 `files`나 `--only`로 파일을 좁힌다 | 지금도 된다. 요청문에 경로를 적어야 한다 |
| 사람이 고르기 | `--until S5` 뒤에 `ask_plan.json`에서 뺄 이름을 지우고 이어서 실행 | 지금은 이어서 실행할 때 그 파일을 다시 읽지 않는다(만들어야 한다) |
| 요청 파일의 제외 목록 | `exclude_names`로 빼는 이름을 적는다 | 만들어야 한다 |

## 2. sLLM 단계의 진행 로그

### 2.1 "2차 요청: 작업 451건" 뒤로 멈춘 것처럼 보인 까닭

- sLLM 단계는 차수로 돈다. 1차에 모든 작업을 보내고, 답이 걸러진 작업(수정 블록 기각 등)은 사유를 붙여 2차에 다시 보낸다. 재요청은 작업마다 2번까지다(`llm.retries`).
- 0.10.6까지는 **한 차수의 응답이 모두 돌아온 뒤에** 작업별 결과를 적었다. 그 사이에는 로그도, 응답 파일도, 결과 파일도 나오지 않는다. 451건이면 "451 ÷ 동시 요청 수 × 건당 응답 시간"만큼 조용하다. 건당 1분, 동시 4건이면 2시간쯤이다.
- 멈춘 것이 아니라 2차 응답을 기다리는 중이었다. 결과 파일(변경 파일, 보고서)은 sLLM 단계가 끝난 뒤 병합·검증·산출 단계에서 나온다.
- 왜 451건이 다시 갔는지는 1차의 작업별 줄(`작업 N … 1차: 재요청 - 사유`)에 있다.

### 2.2 0.10.7에서 바꾼 것

| 무엇 | 내용 |
|---|---|
| 진행 로그 | 응답을 받는 대로 센다. 10건마다, 그리고 적어도 1분에 한 번 `2차 요청 진행: 120/451건 응답(실패 3건), 경과 31분 20초, 남은 예상 약 86분`을 적는다(`limits.progress_every`, `limits.progress_sec`) |
| 받은 답의 보관 | 받은 답을 바로 캐시에 넣는다. 도중에 끊어도 `--resume`으로 이어서 돌리면 받은 답은 다시 부르지 않는다. 0.10.6까지는 차수가 끝나기 전에 끊으면 그 차수의 답을 모두 잃었다 |
| 호출 중 예외 | 한 작업의 호출이 예외로 끝나도 그 작업만 실패로 친다 |
| 다시 묻지 않는 작업 | 3단계의 남은 사용 중단 경고 줄만 든 작업은 답이 모두 걸러지면 다시 묻지 않고 사유와 함께 남긴다. 고치지 않아도 설정으로 경고가 꺼지는 줄에 호출을 한 번 더 쓰지 않는다(`limits.soft_retry`를 1로 주면 예전처럼 다시 묻는다) |

마지막 항목은 2차의 작업 수를 줄인다. 고치지 않으면 컴파일되지 않는 대상(`gets` 등)이나 요청문의 대상이 섞인 작업은 예전처럼 다시 묻는다.
