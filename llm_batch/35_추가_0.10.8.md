# 0.10.8에서 달라진 것: 매크로로 채우는 묶음, 같은 이름·중첩 구조체의 타입 연결

| 항목 | 내용 |
|---|---|
| 읽는 순서 | 35 |
| 작성일 | 2026-11-27 |
| 대상 코드 | `vupdate.py` 0.10.8 |
| 배경 | 0.10.5 실제 코드 시험에서 나온 두 가지 누락. (1) 병렬 배열 묶음이 공백(0x20)으로 채우는 매크로 초기화 때문에 바뀌지 않음. (2) 같은 이름의 구조체가 다른 헤더에도 정의돼 있고 안에 구조체를 품은 타입이 배치 후보가 되지 못하고, 물음에 다른 쪽 정의가 참고로 붙음 |
| 확인 범위 | Linux, 합성 예제, 공개 코드(Notepad++), 모의 sLLM, g++. 실제 코드, 실제 gemma4, Windows의 cl로는 확인하지 못했다 |

## 1. 결론

- 두 누락 모두 0.10.7에도 그대로 있었다(0.10.6과 0.10.7은 이 부분을 건드리지 않았다). 합성 예제로 재현했고 0.10.8에서 고쳤다.
- 묶음: 채우는 값이 상수 매크로여도, 채우는 호출을 함수 꼴 매크로로 감싸도 읽는다.
- 타입 연결: 같은 이름의 정의가 여러 헤더에 있으면 이름을 버리지 않고, 파일마다 그 파일이 include 하는 정의를 고른다. 구조체 안에서 정의한 구조체의 배치도 계산한다. 물음에 붙는 참고 정보도 같은 기준으로 고른다.
- 고르지 못하면 어느 쪽도 쓰지 않고 까닭을 남긴다. 다른 쪽 정의를 붙이지 않는다.
- 옵션은 바뀌지 않았다.

## 2. 묶음의 채우는 문장

### 2.1 원인

0.10.3은 채우는 값이 글자·숫자 상수(`' '`, `0x20`, `32`)일 때만 "값으로 채우는 문장"으로 읽었다. 값이 매크로 이름이거나 호출이 매크로면 "이름을 통째로 사용"으로 분류했고, 그런 곳이 하나라도 있으면 묶음 전체를 바꾸지 않았다.

재현(0.10.7, 합성 예제): `memset(szLot, SPACE, sizeof(szLot));` 5문장이 든 묶음, `INIT_SPACE(szLot);` 3문장이 든 묶음, `SET_SPACE(szLot, sizeof(szLot));`가 든 묶음 3개가 모두 "바꾸지 않음"이었다.

### 2.2 읽는 꼴

| 꼴 | 0.10.7 | 0.10.8 |
|---|---|---|
| `memset(a, SPACE, sizeof(a))` — `#define SPACE 0x20` | 묶음을 막음 | 바꿈 |
| 값이 `' '`, `(char)0x20`, `_T(' ')`, 다른 매크로를 가리키는 매크로, enum 항목 | 묶음을 막음 | 바꿈 |
| `INIT_SPACE(a)` — `#define INIT_SPACE(x) memset((x), 0x20, sizeof(x))` | 묶음을 막음 | 바꿈 |
| `SET_SPACE(a, sizeof(a))`, `SET_SPACE(a, 44)` — 길이를 인자로 받는 매크로 | 묶음을 막음 | 바꿈 |
| 본문이 `do { } while (0)`, `{ }`, 괄호로 감싸였거나 `;`로 끝나는 매크로 | 묶음을 막음 | 바꿈 |
| 세미콜론 없이 줄마다 쓴 매크로 호출(본문이 `;`나 `}`로 끝남) | 묶음을 막음 | 바꿈 |
| 길이가 `sizeof(a[0]) * 개수` | 묶음을 막음 | 바꿈 |
| `ZeroMemory`, `RtlZeroMemory`, `SecureZeroMemory`, `FillMemory`, `RtlFillMemory` | `ZeroMemory`만 | 모두 읽음 |

- 매크로는 본문에 인자를 넣어 펼친 글로 판단한다. 펼친 글이 다시 매크로 호출이면 세 번까지 더 펼친다.
- 값은 글이 아니라 값으로 견준다. `' '`, `0x20`, `SPACE`는 같은 값이다.
- 값의 이름이 그 함수의 지역 변수나 인자면 상수로 보지 않는다. 같은 이름의 enum 항목이 패키지에 있어도 그렇다.

### 2.3 바꿔 쓰는 방법

| 경우 | 결과 |
|---|---|
| 묶음의 모든 배열을 같은 값으로 채움 | 문장 하나: `memset(stRec, SPACE, sizeof(stRec));` 또는 `INIT_SPACE(stRec);` |
| 일부만 채우거나 값이 다름(문자열은 공백, 숫자는 0) | 레코드마다 도는 반복문 안에서 필드마다 채움 |

- 값의 글은 원본의 것을 그대로 쓴다(`SPACE`는 `SPACE`로 남는다).
- 매크로 호출은 이름만 바꿔도 뜻이 같을 때 그대로 둔다. 도구가 바꾼 호출을 다시 펼쳐 "대상 전체를 채우는 호출"인지 확인한다.
- 이름만 바꾸면 틀리는 경우는 펼친 `memset`으로 쓴다. 길이를 숫자로 준 호출(`SET_SPACE(a, 44)`)과, 값 하나인 필드라 `&`가 필요한 경우다.

### 2.4 바꾸지 않는 꼴과 사유

묶음을 그대로 두고 `out/struct_scan.md`와 수동 검토 목록에 아래 사유를 적는다.

| 사유의 글 | 해당하는 것 |
|---|---|
| 채우는 값(…)이 상수인지 확인하지 못함 | 변수, 함수 호출, 식, `const` 변수, 헤더마다 값이 다른 매크로 |
| 길이(…)가 배열 전체의 크기인지 확인하지 못함 | 배열의 일부만 채우는 길이, 실행 중에 정해지는 길이 |
| 매크로 …를 문장 하나로 펼치지 못함 | 본문이 문장 둘 이상, `#`·`##` 사용, 정의가 여러 곳에서 다름, 인자 수가 다름 |
| 매크로 …의 본문이 이 배열 전체를 채우는 호출 하나가 아님 | 채우기가 아닌 일을 하는 매크로 |

## 3. 타입 연결

### 3.1 원인 세 가지

| 원인 | 0.10.7의 동작 |
|---|---|
| 같은 이름의 정의가 두 곳 이상 | 그 이름을 양쪽 모두 쓰지 않았다. 배치 후보에서도, 겹쳐 보는 포인터의 인식에서도 빠졌다 |
| 구조체 안에서 구조체를 정의(`struct { … } stItem;`) | 본문에 `{ }` 블록이 있으면 그 구조체를 읽지 않았다 |
| 물음에 붙는 참고 정보(`[참고: 선언]`, 모델이 요청한 정의) | 같은 이름의 정의 가운데 경로 순서로 처음인 것을 붙였다. 그 파일이 include 하는지 보지 않았다 |

재현(합성 예제. `mes/MesDef.h`와 `plc/PlcDef.h`가 `TC_HEAD`, `TC_BODY`를 서로 다르게 정의하고, mes 쪽 `TC_BODY`는 안에 구조체와 공용체를 품음):

| 항목 | 0.10.7 | 0.10.8 |
|---|---|---|
| 필드 접근으로 바꾼 문장 | 0 | 14 |
| "맞는 구조체가 없음"으로 남은 문장 | 14 | 2(어느 헤더도 include 하지 않는 파일) |
| 이미 있는 겹쳐 보기 포인터의 인식 | 0 | 2 |
| plc 파일의 물음에 붙은 `TC_BODY` 정의 | mes 쪽 정의 | plc 쪽 정의 |

### 3.2 파일마다 보이는 정의를 고르는 순서

1. 같은 파일에 있는 정의.
2. 그 파일이 직접 또는 다른 헤더를 거쳐 include 하는 헤더의 정의.
3. 같은 폴더에 있는 정의(추정).
4. 폴더가 가장 가까운 정의(추정).
5. 그래도 여럿이면, 남은 정의의 배치가 모두 같을 때만 그 가운데 하나를 쓴다. 아니면 그 이름을 쓰지 않고 까닭을 남긴다.

- 3과 4는 include로 확인하지 못한 추정이다. 결과 문서에 "include 로는 확인하지 못함"이라고 적는다.
- 구조체의 멤버가 다른 구조체 타입이면, 그 정의가 든 헤더를 기준으로 같은 순서로 고른다.
- include는 경로까지 맞춰 따라간다. 순서는 적은 파일의 폴더, 그 파일을 실은 프로젝트의 추가 include 폴더, 패키지 루트, 경로의 끝이 같은 파일 가운데 가장 가까운 폴더다. 0.10.7까지는 파일 이름만 봐서 이름이 같은 헤더를 구분하지 못했다.

### 3.3 구조체 안의 정의

| 꼴 | 처리 |
|---|---|
| `struct { … } 이름;`, `struct 태그 { … } 이름;` | 안쪽 멤버를 `이름.필드`로 넣는다 |
| `struct { … };` (이름 없음, 선언자 없음) | 안쪽 멤버가 바깥의 멤버로 들어간다 |
| `union { … } 이름;`, 공용체 타입의 멤버 | 크기만 구해 통째로 한 자리로 둔다. 안은 필드로 내지 않는다 |
| `enum { … } 이름;` | 4바이트로 본다(`#pragma pack(1)` 안에서만 확정) |
| 안에서 정의한 이름 있는 타입을 뒤에서 이름으로 씀 | 그 타입의 배치로 계산한다 |

확정의 조건은 그대로다. 모든 멤버가 1바이트 타입이거나 `#pragma pack(1)` 안에서 정의됐을 때만 확정한다.

### 3.4 참고 정보

- `[참고: 선언]`의 타입 정의와 모델이 요청한 정의(NEED_CONTEXT)를 3.2의 순서로 고른다. 붙일 때 정의가 든 파일과 고른 근거를 함께 적는다.
- sLLM에 주는 필드 표도 그 파일에서 보이는 정의의 것만 붙인다. 이름이 여러 곳에 있는 구조체는 표에 정의 파일을 적는다.
- 고르지 못하면 정의를 붙이지 않고 "같은 이름의 정의가 N곳에 있어 붙이지 않는다"고 적는다.

### 3.5 결과에서 볼 곳

| 볼 곳 | 내용 |
|---|---|
| `run.log`의 `구조체 표: 같은 이름의 정의가 여러 곳에 있는 이름 N개(…)` | 어떤 이름이 여러 곳에 있는지 |
| `out/struct_scan.md` 3절 | 구조체마다 정의 파일, 크기, 필드의 위치, 고른 근거와 쓰는 파일 |
| `out/struct_scan.md` 버퍼의 "사유" 줄 | "맞는 구조체가 없음"일 때, 그 파일이 include 하거나 이름을 쓰는 구조체 가운데 배치를 확정하지 못해 빠진 것과 그 까닭 |

## 4. 함께 고친 것

고치면서 찾은 결함이다.

| 결함 | 0.10.7 | 0.10.8 |
|---|---|---|
| 상속이 있는 구조체(`struct D : public B`) | 기반 클래스의 멤버를 빼고 배치를 계산했다(합성 예제에서 크기 5인 구조체를 3으로 계산) | 확정하지 않는다 |
| 컴파일 검사에 쓸 프로젝트 고르기 | 프로젝트 파일이 소스를 `..\Src\A.cpp`로 적으면 그 파일의 프로젝트를 찾지 못하고 첫 프로젝트의 설정을 썼다 | 그 파일을 실은 프로젝트의 설정을 쓴다 |
| `--backups keep`일 때 백업 사본의 같은 이름 구조체 | 그 구조체를 쓰지 못했다 | 그 파일이 include 하는 정의를 고른다 |

두 번째는 프로젝트가 여럿이고 소스가 프로젝트 폴더 밖에 있을 때만 차이가 난다. 실제 cl로는 확인하지 못했다.

## 5. 남은 한계

**묶음**

- `const` 변수(`const char SPACE = ' ';`)는 상수로 보지 않는다.
- 매크로가 아닌 보조 함수(`FillSpace(szLot, sizeof(szLot))`)로 채우는 문장은 읽지 않는다.
- 채우는 문장 말고 다른 사유(이름을 함수 인자로 통째로 넘김, 초기화 목록이 있는 선언)로 막힌 묶음은 그대로다.

**타입 연결**

- 공용체의 안쪽 필드에는 대응시키지 않는다.
- 함수 본문, 상속, 비트 필드, 포인터 멤버, `#if`가 든 구조체는 확정하지 않는다.
- 구조체 배열 멤버의 요소 하나하나에는 대응시키지 않는다.
- 같은 헤더 안에서 `#if`로 갈린 같은 이름의 정의는 가리지 못한다.
- include 폴더에 매크로(`$(…)`)가 들었거나 헤더가 패키지 밖에 있으면 include로 확인하지 못한다.
- 프로젝트의 구성(Debug, Release)마다 include 폴더가 달라도 합쳐서 본다.
