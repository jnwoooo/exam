## 0. v1에서 바뀐 것

| 항목 | v1 | v2 |
|---|---|---|
| 배치 형태 | 미정(같은 PC, 다른 PC 모두 기술) | 확정. MCP 서버는 서버에서, py는 로컬 PC에서 실행 |
| 작업 시작 | 서버가 py를 실행하는 경우 포함 | 사람이 로컬 PC에서 py를 실행하고, py가 서버에 작업을 등록 |
| 토큰 계산 | 서버의 `count_tokens`를 매번 사용 | py는 추정, 서버가 실제 값으로 검사. `count_tokens`는 선택(4.2) |
| 동시 호출 | 언급만 | 원칙과 확인 결과 추가(6.1) |
| 분할 순차 | 기능 단위 정의 | 0.1.0에서 구현하지 않은 이유와 구현 조건 추가 |

v3에서는 코드 0.2.0에 분할 순차를 구현한 것을 반영했다(6.1, 7절, 8절, 10절). 결과가 원본이 아니라 별도 파일과 diff로 나오고 사람이 검토하는 구조이므로, 먼저 넣어 두고 실제 sLLM으로 맞춰 가기로 했다.

v4에서는 코드 0.3.0을 반영했다. py 쪽에서 먼저 만들 수 있는 부분(토큰 한도 초과 대응, 추정 보정, 과부하 대기, 호출자 표시)을 직접 호출 구조 위에 구현했다. 서버 경유로 바꾸는 일(10절의 1, 4, 7번)은 그대로 남아 있다. 바뀐 곳은 4.2, 4.5, 6.1, 7절, 10절이다.

v5에서는 코드 0.4.0을 반영하고, 서버 쪽 할 일을 `08_MCP역할목록.md`로 따로 정리했다. 달라진 판단은 하나다. **접점을 여는 방법이 두 가지이고, 그중 OpenAI 호환 중계(08의 8.1)를 택하면 py를 고치지 않는다.** 이 문서의 4절은 접점을 MCP 도구(`llm_complete` 등)의 이름으로 적었지만, 4절 첫머리에 적은 대로 전송 규격은 서버 구현에서 정한다. py가 지금 보내는 요청(OpenAI 호환 HTTP)과 받는 응답은 4.2의 입력·출력과 내용이 같다. 그래서 서버가 같은 내용을 HTTP 경로 하나로 열면 10절의 1번은 할 일이 없어진다. MCP 도구 호출로만 열 수 있다면 10절대로 py를 고친다.

## 1. 결정 사항

1. **sLLM의 주소, 모델, 한도, 동시 수, 공용 원칙 프롬프트는 MCP 서버가 가진다.**
2. **py는 sLLM 주소를 모른다.** MCP 서버의 "모델 호출 도구"만 부른다. sLLM의 토크나이저 주소도 직접 부르지 않는다.
3. **MCP 서버는 서버에서, py는 로컬 PC에서 실행한다.** 서버는 py를 띄우지 않고, 패키지 파일에도 접근하지 않는다.
4. **파일을 다루는 일과 처리 중간 상태는 전부 py가 맡는다.** 대용량 함수의 분할, 조각 순서, 재조립도 py다.
5. **MCP 서버는 응답 내용을 해석하지 않는다.** 수정이 옳은지, 다시 물을지는 py가 판단한다.
6. **출력 형식은 py가 정한다.** 형식을 읽고 검사하는 코드가 py에 있기 때문이다.

현재의 `vupdate.py` 0.4.0은 설정 파일이나 환경변수(`VUPDATE_LLM_ENDPOINT`)의 주소로 OpenAI 호환 요청을 보낸다. 그 주소가 sLLM이면 결정 1, 2와 다르고, 서버의 중계 주소이면 결정 1, 2를 만족한다(py는 중계 주소만 알고, sLLM 주소와 모델은 서버가 갖는다). 중계 주소가 지켜야 할 약속은 `08_MCP역할목록.md` 3절에 있다.

## 2. 책임 분담

| 항목 | py (로컬 PC) | MCP 서버 | sLLM |
|---|---|---|---|
| 호출자 식별, 권한 | 자기 신원과 작업 ID를 호출에 싣는다 | 담당 | - |
| 작업 등록, 진행 기록, 조회 창구 | 등록하고 진행을 보고한다 | 담당 | - |
| sLLM 주소, 모델, 호출 파라미터 | 모른다 | 담당 | - |
| 토큰 한도, 동시 수 | 서버에 물어서 따른다 | 담당 | - |
| 토큰 수 | 추정해서 조각 크기를 정한다 | 실제 값으로 한도를 검사한다 | - |
| 공용 원칙 프롬프트 | 받지 않는다. 서버가 붙인다 | 담당 | - |
| 작업 프롬프트(출력 형식, 수정 지침, 코드 조각) | 담당 | 손대지 않고 전달 | - |
| 패키지 파일 읽기, 쓰기 | 담당 | 접근하지 않는다 | - |
| 환경 점검, 파일 조사, 규칙 탐지·수정 | 담당 | - | - |
| 조각 만들기, 대용량 함수 분할 | 담당 | - | - |
| 조각 수정안 작성 | - | - | 담당 |
| 응답 해석, 수용 검사, 재요청 판단 | 담당 | 하지 않는다 | - |
| 중간 상태(조각 순서, 변경 원장, 수정 레코드) | 담당(실행 폴더의 상태 DB) | 보관하지 않는다 | - |
| 전송 수준의 재시도(연결 실패, 과부하) | 서버의 오류 코드를 따른다 | 담당 | - |
| 호출 기록(누가, 어느 작업, 토큰, 시간) | 자기 실행 폴더에 기록 | 담당(전체 호출자 통합) | - |
| 병합, 검증, 되돌림, 보고서 | 담당 | - | - |

**파일 처리를 py에 두는 이유**
- 패키지와 Visual Studio가 로컬 PC에 있다. 서버가 파일에 접근할 필요가 없다.
- 처리 결과가 서버 상태와 무관하게 재현된다.
- 서버는 가볍게 유지된다. 호출자가 늘어도 서버의 일은 "받아서 넘기고 기록하는 것"뿐이다.

## 3. sLLM 주소가 바뀌면

py와 .ps1을 여러 PC에 배포해도 sLLM 주소는 어디에도 들어 있지 않다. 서버 설정만 고치면 된다.

| 바뀌는 것 | 고치는 곳 | py 재배포 |
|---|---|---|
| sLLM 주소, 포트 | MCP 서버 설정 | 불필요 |
| 모델 교체, 토큰 한도, 동시 수 | MCP 서버 설정 | 불필요. py가 실행할 때마다 서버에 묻는다 |
| 공용 원칙 프롬프트 | MCP 서버 | 불필요 |
| MCP 서버 주소 | 각 PC의 환경변수 또는 설정 파일 | 불필요. exe 안에 주소를 넣지 않는다 |
| 출력 형식, 수용 검사 | py | 필요(exe 교체) |
| 규칙 | py 또는 `config/rules.json` | 규칙 파일이면 불필요 |

py가 아는 주소는 MCP 서버 주소 하나다. 다음 순서로 찾는다.
1. 실행 인자
2. 환경변수
3. 설정 파일(`config/server.json`)

주소는 IP가 아니라 이름으로 적어 두는 것을 권한다. 서버를 옮겨도 이름이 가리키는 곳만 바꾸면 각 PC는 손댈 것이 없다.

## 4. 접점 정의

접점은 세 가지다. 여기서는 입력, 출력, 책임만 정한다. 전송 규격(MCP 도구 호출의 구체 형식, 인증 방식)은 서버 구현에서 정한다.

### 4.1 작업 보고 접점 (py → MCP 서버)

서버가 py를 띄우지 않으므로, 작업은 py가 시작하면서 서버에 등록한다.

| 도구 | 시점 | 입력 | 서버가 하는 일 | 출력 |
|---|---|---|---|---|
| `job_open` | 실행 시작 | 호출자 신원, PC 이름, 패키지 이름, 환경값, py 버전 | 호출자 확인, 허용 여부 판단, 작업 ID 발급 | 작업 ID, 허용 여부 |
| `job_progress` | 단계가 끝날 때마다 | 작업 ID, 단계, 이슈·수정·수동 검토 건수 | 기록 | 없음 |
| `job_close` | 종료 | 작업 ID, 종료 코드, 요약 | 기록 | 없음 |

- 서버에 연결할 수 없어도 py는 멈추지 않는다. sLLM이 필요 없는 단계는 끝까지 수행한다(4.5).
- 보고서와 변경 파일은 로컬 PC의 실행 폴더에 남는다. 서버에는 요약만 간다. 보고서 본문을 서버에 올릴지는 정해야 한다(12절).

### 4.2 모델 호출 접점 (py → MCP 서버)

| 도구 | 입력 | 서버가 하는 일 | 출력 |
|---|---|---|---|
| `llm_info` | 작업 ID | 이 호출자에게 적용되는 값을 알려 준다 | 요청 1건의 토큰 한도, 서버가 미리 쓰는 토큰 수(공용 원칙), 출력 상한, 허용 동시 수, 공용 원칙의 판 번호 |
| `llm_complete` | 작업 ID, 조각 ID, 작업 유형, 작업 프롬프트(규칙 부분과 본문), 출력 상한 | 아래 순서 | 응답 본문, 입력·출력 토큰 수, 모델 이름, 공용 원칙의 판 번호, 요청 번호 |
| `count_tokens` (선택) | 텍스트(여러 건 가능) | 실제 토크나이저로 센다 | 건별 토큰 수 |

`llm_complete`에서 서버가 하는 일의 순서:
1. 호출자와 작업 ID 확인
2. 실제 토큰 수로 한도 검사. 넘으면 호출하지 않고, 실제 토큰 수를 담아 오류로 돌려준다
3. 공용 원칙 프롬프트를 앞에 붙인다
4. 동시 수를 넘으면 대기시키거나 "잠시 후 다시"로 돌려준다
5. sLLM 호출. 연결 실패 같은 전송 오류는 서버가 정한 횟수만큼 다시 시도한다
6. 기록을 남기고 응답을 그대로 돌려준다

서버가 하지 않는 일:
- py가 보낸 본문을 고치거나 줄이거나 요약하지 않는다.
- 응답 내용을 해석하거나 고치지 않는다.

작업 유형은 `slice_fix`(지점 조각 수정)와 `chunk_fix`(분할 조각 수정) 두 가지로 시작한다. 서버는 유형별로 호출 파라미터(추론 모드 사용 여부 등)를 다르게 줄 수 있다. py는 "같은 입력에 같은 응답"을 요구한다.

**토큰 수를 다루는 방식**

py는 토크나이저를 직접 부르지 않는다. 조각마다 서버에 토큰 수를 물으면 호출이 두 배가 되므로, 다음 세 단계로 한다.

1. py가 로컬 추정으로 조각 크기를 정한다. 여유를 10% 둔다.
2. 서버가 실제 토큰 수로 한도를 검사한다. 넘으면 거절하고, py는 조각을 줄여 다시 만든다.
3. 서버 응답에 담긴 실제 입력 토큰 수로 py가 추정 비율을 실행 중에 보정한다.

`count_tokens`는 분할 순차처럼 분할 지점을 미리 정확히 정해야 할 때만 쓴다.

0.3.0의 상태: 위 세 단계를 직접 호출 구조에서 구현했다. 토크나이저 주소를 직접 부르던 경로는 없앴다.

| 단계 | 0.3.0의 구현 | 서버 경유로 바뀌면 |
|---|---|---|
| 1. 로컬 추정 | 글자 수 추정 × 보정 비율. 여유 10%. 서버 몫(예약량)을 뺀다 | 예약량을 `llm_info`로 받는다 |
| 2. 한도 초과 거절 | HTTP 400과 문구로 알아본다(vLLM 문구, `over_limit`). 서버가 알려 준 한도와 토큰 수를 반영해 조각을 줄이거나 나눈다. 같은 요청은 다시 보내지 않는다. 작업당 2회까지 | 오류 코드와 수치를 정해진 필드로 받는다 |
| 3. 실제 값으로 보정 | 응답의 `usage.prompt_tokens`로 "실제 = 비율 × 추정 + 고정분"을 맞춘다. 고정분이 서버가 덧붙인 프롬프트에 해당한다 | 같다 |

py가 서버 프롬프트의 크기를 미리 알 필요는 없다. 응답 몇 건이면 고정분으로 드러난다. 다만 처음 한두 건이 거절될 수 있으므로, 서버가 예약량을 알려 주는 편이 낫다.

### 4.3 조회 접점 (호출자 → MCP 서버)

| 도구 | 입력 | 출력 |
|---|---|---|
| `get_status` | 작업 ID 또는 호출자 | py가 보고한 단계와 건수 |
| `list_jobs` | 기간, 호출자 | 작업 목록과 종료 코드 |

서버가 가진 것은 py가 보고한 내용뿐이다. 실행 중단, 이어서 실행, 환경 점검은 로컬 PC에서 py 명령으로 한다(`run --resume`, `preflight`).

### 4.4 프롬프트의 소유와 조립

| 부분 | 소유 | 내용 |
|---|---|---|
| 공용 원칙 | MCP 서버 | 역할, 최소 수정, 추측 금지, 주석과 공백 보존 등 모든 호출자·모든 작업에 공통인 원칙 |
| 작업 규칙 | py | 출력 형식(수정 블록, 변경 없음, 정의 요청), 생략 표식을 건드리지 말라는 규칙 |
| 작업 본문 | py | 환경값, 수정 지침, 수정 대상 줄, 코드 조각, 이전 응답의 기각 사유 |

조립 순서는 공용 원칙 → 작업 규칙 → 작업 본문이다.

지켜야 할 약속:
- 공용 원칙에는 출력 형식을 넣지 않는다. 형식 지시가 두 군데서 나오면 응답이 깨지고, py의 해석기가 읽지 못한다.
- 공용 원칙이 바뀌면 판 번호가 바뀐다. py는 판 번호를 기록하고 응답 캐시의 구분에 넣는다.
- 공용 원칙이 차지하는 토큰은 `llm_info`로 알려 준다. py는 그만큼을 빼고 조각 크기를 정한다.

### 4.5 오류와 재시도의 분담

| 상황 | 처리 주체 | 동작 |
|---|---|---|
| sLLM 연결 실패, 일시 과부하 | 서버 | 정한 횟수만큼 다시 시도한 뒤 오류 코드로 돌려준다 |
| 동시 수 초과 | 서버 → py | 서버가 대기시키거나 "잠시 후 다시"를 돌려주고, py는 기다렸다 다시 요청한다(0.3.0: HTTP 429, 503에 구현. 기본 5회) |
| 토큰 한도 초과 | 서버 → py | 서버가 거절하고, py는 조각을 줄여 다시 만들거나 수동 검토로 보낸다(0.3.0에 구현) |
| 응답이 출력 상한에서 잘림 | py | 같은 요청을 다시 보내지 않고 수정 지점을 나눠 다시 보낸다(0.3.0에 구현) |
| 요청 자체의 거절(형식 오류 등) | 서버 → py | 다시 보내도 같으므로 재요청하지 않고 수동 검토로 보낸다(0.3.0에 구현) |
| 권한 없음 | 서버 → py | 서버가 거절하고, py는 작업을 중단한다(종료 코드 2) |
| 응답의 형식 오류, 원문 불일치, 블록 겹침 | py | 사유를 붙여 다시 요청한다. 횟수를 넘으면 수동 검토 |
| 정의가 필요하다는 응답 | py | 정의를 찾아 붙여 다시 요청한다 |
| 서버에 연결할 수 없음 | py | sLLM 대상 이슈를 수동 검토로 보내고 나머지 단계는 끝까지 수행한다. 나중에 `--resume`으로 sLLM 단계만 다시 돌릴 수 있다 |

오류 코드는 최소한 `over_limit`, `busy`, `timeout`, `unavailable`, `denied`, `bad_request`를 구분한다.

## 5. 전체 흐름

| 순서 | 누가 | 하는 일 |
|---|---|---|
| 1 | 사용자 | 로컬 PC에서 `vupdate run ...` 또는 .ps1을 실행한다 |
| 2 | py → MCP 서버 | `job_open`으로 작업을 등록하고 작업 ID를 받는다 |
| 3 | py | 환경 점검, 원본 스냅샷(S0) |
| 4 | py | 파일 조사, 규칙 탐지(S1, S2) |
| 5 | py | 설정 흡수 목록, 규칙 수정, 요청사항 처리(S3~S5). 수정 레코드만 쌓는다 |
| 6 | py → MCP 서버 | `llm_info`로 한도와 허용 동시 수를 받는다 |
| 7 | py | 남은 이슈를 조각으로 자르고 작업 프롬프트를 만든다 |
| 8 | py → MCP 서버 → sLLM | `llm_complete`를 허용 동시 수만큼 한꺼번에 요청한다. 서버가 공용 원칙을 붙여 sLLM을 호출하고 응답을 돌려준다 |
| 9 | py | 응답을 해석하고 수용 검사를 한다. 통과하면 수정 레코드로, 실패하면 사유를 붙여 8번으로 |
| 10 | py | 병합. 스냅샷에 수정 레코드를 적용해 결과 파일을 만든다(S7) |
| 11 | py | 검증. 불합격한 수정은 되돌린다(S8) |
| 12 | py | diff, 보고서, 수동 검토 목록을 로컬 실행 폴더에 만든다(S9) |
| 13 | py → MCP 서버 | 단계마다 `job_progress`, 끝나면 `job_close` |
| 14 | 관리자 → MCP 서버 | `get_status`, `list_jobs`로 누가 무엇을 돌렸는지 본다 |

## 6. sLLM 호출로 코드를 고치는 흐름

조각 하나가 거치는 과정이다. 괄호 안은 맡는 쪽이다.

```
1. 이슈 위치를 모은다. 가까운 것끼리 한 조각으로 묶는다              (py)
2. 조각을 만든다. 이슈 주변 줄 + 속한 함수의 머리 + 큰 배열은 생략 표식  (py)
3. 작업 프롬프트를 만든다. 작업 규칙 + 환경값 + 수정 지침 + 대상 줄 + 코드 (py)
4. 토큰을 추정한다. 한도를 넘으면 주변 줄 수를 줄여 2번부터 다시       (py)
5. 모델 호출을 요청한다                                            (py → 서버)
6. 한도 검사, 공용 원칙 부착, 대기, sLLM 호출, 기록                  (서버)
7. 조각의 수정안을 쓴다                                            (sLLM)
8. 응답을 해석한다. 수정 블록 / 변경 없음 / 정의 요청 / 형식 오류      (py)
9. 수용 검사를 한다                                                (py)
   ├ 통과        → 수정 레코드로 저장
   ├ 기각        → 사유를 붙여 5번으로 (횟수 제한)
   ├ 정의 요청   → 정의를 찾아 붙여 5번으로 (횟수 제한)
   └ 횟수 초과   → 수동 검토 목록
10. 모든 조각이 끝나면 병합하고 검증한다                             (py)
```

수용 검사의 항목:
- 수정 블록의 형식이 맞는가
- 찾을 문자열이 조각 안에서 정확히 한 번 나오는가
- 수정 위치가 대상 줄의 앞뒤 10줄 안인가
- 생략 표식을 건드리지 않았는가
- 바꾼 내용이 원본 파일의 인코딩으로 표현되는가
- 괄호 짝이 수정 전과 같은가

### 6.1 동시 호출과 함수 보존 원칙

**동시 호출은 가능하다.** 0.1.0부터 구현돼 있고 동시 수는 설정값이다. 아래 원칙으로 함수가 깨지지 않게 한다.

| 번호 | 원칙 | 내용 | 상태 |
|---|---|---|---|
| 1 | 같은 기준 본문 | 모든 조각을 같은 본문(스냅샷에 규칙 수정을 반영한 것)에서 잘라 낸다. 다른 조각의 응답을 기다리거나 반영하지 않는다 | 구현 |
| 2 | 수정 범위의 분리 | 조각이 고칠 수 있는 범위는 대상 줄의 앞뒤 10줄이다. 이슈가 30줄 넘게 떨어져야 다른 조각이 되므로 조각끼리 수정 범위가 겹치지 않는다. 가까운 이슈는 한 조각으로 묶는다 | 구현 |
| 3 | 응답은 기록으로만 | 동시에 도착한 응답을 파일에 바로 쓰지 않는다. 수정 레코드로 저장하고, 파일은 병합 단계에서 한 번에 만든다 | 구현 |
| 4 | 처리 순서 고정 | 응답이 도착한 순서가 아니라 조각 순서대로 처리한다. 동시 수가 달라도 결과가 같다 | 구현 |
| 5 | 블록 단위 검사 | 수정 블록마다 원문 일치와 괄호 짝을 검사한다 | 구현 |
| 6 | 겹침 거부 | 병합 때 범위가 겹치는 수정은 적용하지 않고 수동 검토로 보낸다 | 구현 |
| 7 | 파일 단위 검증과 되돌림 | 병합 결과의 괄호·전처리기 균형이 원본과 다르면 sLLM 수정을 빼고 다시 병합한다 | 구현 |
| 8 | 서로 의존하는 수정은 동시에 보내지 않는다 | 한 지점의 수정이 같은 함수의 다른 지점에 영향을 주는 경우(선언의 타입 변경 등)는 함수 단위로 한 조각에 담거나 순서대로 처리한다. 규칙마다 수정 범위(국소/함수/파일 간)를 속성으로 둔다 | 미구현 |
| 9 | 분할 순차는 구간 안에서 순서대로 | 분할 조각은 앞 조각의 결과가 필요하므로 한 구간 안에서는 한 번에 하나만 보낸다. 다른 구간의 조각과 일반 조각은 동시에 간다. 한 조각이 실패하면 그 구간의 수정을 모두 취소한다 | 구현(0.2.0) |
| 10 | 서버가 허용한 동시 수 이하 | py 설정값과 `llm_info`의 허용값 중 작은 쪽을 쓴다. `busy`를 받으면 기다린다 | 부분(0.3.0: 설정 파일의 허용 동시 수를 넘지 않고, 과부하 응답이면 기다린다. 서버에 허용값을 묻지는 않는다) |
| 11 | 다시 계획한 조각은 겹치지 않게 | 토큰 한도에 걸려 분할 구간의 남은 부분을 다시 나눌 때, 이미 끝난 앞 조각의 줄과 겹치지 않게 한다. 겹치면 같은 줄을 두 번 고치게 된다 | 구현(0.3.0) |

8번이 버전 대응에서 문제가 되지 않는 이유는 sLLM에 보내는 규칙 2개가 모두 국소 수정이기 때문이다. 다만 0.2.0에서 요청사항의 변수 인덱스 접근을 sLLM에 맡기는 선택 기능이 생겼고, 이것은 함수 전체에 걸칠 수 있다. 가까운 지점은 한 조각이나 분할 묶음으로 순서대로 처리되지만, 30줄 넘게 떨어진 지점은 별개의 조각으로 동시에 간다. 이 기능을 본격적으로 쓰기 전에 8번을 넣어야 한다.

**확인 결과(리눅스, 모의 서버, 응답 지연 0.25초)**

파일 3개, 조각 36개(수정 지점 39곳)를 동시 수만 바꿔 처리했다. 한 함수 안의 떨어진 지점 3곳과 가까운 지점 2곳을 포함한다.

| 동시 수 | 소요 | 서버에 동시에 걸린 최대 요청 | 결과 |
|---|---|---|---|
| 1 | 9.4초 | 1 | 39곳 수정, 괄호 짝 유지 |
| 4 | 2.6초 | 4 | 동시 수 1의 결과와 바이트 단위로 같음 |
| 8 | 1.5초 | 8 | 동시 수 1의 결과와 바이트 단위로 같음 |

확인하지 못한 것:
- 실제 sLLM이 동시 요청을 받을 때의 처리량과 응답 품질.
- 여러 PC가 동시에 실행할 때의 합계 부하. 서버가 호출자별 허용 동시 수를 정해 `llm_info`로 알려 줘야 한다.
- 24k 한도는 요청 1건 기준이라 동시 수와 무관하다. 다만 sLLM 서빙 엔진이 전체 컨텍스트를 동시 처리 칸 수로 나누는 방식이면 동시 수를 늘릴 때 요청당 한도가 줄어든다. 서버 쪽에서 확인해야 한다.

## 8. 대용량 함수의 처리 흐름

### 8.1 판단 순서

```
함수 안의 이슈를 확인한다
 │
 ├ 큰 상수 배열이 있는가
 │    → 배열 본문을 생략 표식으로 바꾼다. 항상 적용한다
 │
 ├ 이슈가 국소적인가 (버전 대응의 대부분)
 │    → 이슈 주변만 조각으로 만든다. 함수 크기와 무관하다
 │    → 한도를 넘으면 주변 줄 수를 줄인다 (25 → 12 → 5 → 0줄)
 │    → 그래도 넘으면 분할 순차로 보낸다
 │    → 입력은 들어가도 예상 응답이 출력 상한을 넘으면 분할 순차로 보낸다
 │
 └ 함수 전체에 걸친 변경인가 (요청사항 등)
      → 매핑표로 결정되는 부분은 규칙으로 처리한다
      → 남은 부분이 한도 안이면 한 조각, 넘으면 분할 순차
```

### 8.2 경우별 처리

| 경우 | 예 | 처리 | 상태 |
|---|---|---|---|
| A. 큰 상수 배열이 있는 함수 | 140만~180만 자 배열 | 배열 본문은 보내지 않는다. 선언부와 주변 코드만 조각으로. 배열 데이터는 규칙으로만 점검. 결과에서 배열이 바이트 단위로 같은지 확인 | 구현. 162만 자 예제로 확인 |
| B. 줄 수가 많은 함수의 국소 이슈 | 5천 줄 함수 안의 API 한 줄 | 이슈 주변만 조각으로. 함수 머리(시그니처)를 참고로 붙인다 | 구현 |
| C. 한 번에 보낼 수 없는 구간 | 가까운 수정 지점이 수백 줄에 걸쳐 이어짐. 배열 → 구조체에서 변수 인덱스 접근이 함수 전체에 퍼져 있음 | 분할 순차(8.3) | 구현(0.2.0). 모의 서버로만 확인 |
| D. 나눌 수 없는 구간이 한도를 넘음 | 문장 경계 사이가 한도보다 김(한 문장이 수천 줄) | 수동 검토 | 구현(수동 검토로 보냄) |

### 8.3 분할 순차 처리의 기능 단위

| 번호 | 기능 | 정의 | 0.2.0의 구현 |
|---|---|---|---|
| 1 | 분할 지점 선정 | 문장 중간에서 자르지 않는다. 조각 크기는 한도에서 역산한다 | 줄 앞의 마지막 코드 문자가 `;`, `{`, `}`이고 소괄호가 닫혀 있는 줄에서만 나눈다. 입력 추정 토큰과 예상 응답 토큰이 모두 한도 안에 들도록 채운다. 최상위 문장만 고르지는 않는다(중첩된 블록 안에서도 나눈다) |
| 2 | 조각 머리 정보 | 함수 시그니처, 지역 변수 선언표, 관련 타입, 요청사항의 변경 내용 | 함수 시그니처, "몇 조각 중 몇 번째", 함수 앞부분 25줄(지역 변수 선언표 대신), 수정 지침. 지역 변수 선언표와 관련 타입의 자동 추출은 없다 |
| 3 | 순차 호출 | 첫 조각부터 차례로 요청한다 | 구간마다 차례가 된 조각 하나만 보낸다. 다른 구간과 일반 조각은 같은 회차에 동시에 보낸다 |
| 4 | 변경 원장 | 앞 조각에서 바뀐 이름과 타입을 요약해 넘긴다. 크기에 상한을 둔다 | 앞 조각에서 수용된 수정을 "원문 => 바뀐 내용" 목록으로 넘긴다. 기본 1,500자. 이름·타입만 추린 요약은 아니다 |
| 5 | 조각별 수용 검사 | 지점 조각과 같은 검사 | 같은 검사 |
| 6 | 재조립 검사 | 합친 뒤 괄호·전처리기 균형과 잔여 탐지 확인 | 분할 전용 검사는 없다. 병합 후의 파일 단위 검증(S8)이 맡는다 |
| 7 | 실패 처리 | 실패한 조각만 다시 요청. 횟수를 넘으면 구간의 수정 전체를 취소 | 구현. "수정 불필요" 응답은 실패로 보지 않고 그 조각의 이슈만 수동 검토로 보낸 뒤 계속 간다 |
| 8 | 상태 보관 | 조각 순서, 변경 원장, 조각별 상태를 상태 DB에 둔다 | 작업 표에 묶음 번호와 순번을 기록한다. 중단 후 이어서 실행하면 S6을 처음부터 다시 계획하되, 저장된 응답을 재사용해 호출은 반복하지 않는다 |

분할 수정은 구간 단위로 전부 적용하거나 전부 취소한다. 일부 조각만 적용하면 함수 안에서 이름과 타입이 어긋날 수 있기 때문이다.

분할 순차로 만든 수정은 수정 레코드에 "분할 순차 n/m"으로 표시되고, 보고서의 sLLM 항목에 구간 수, 조각 수, 취소된 구간 수가 나온다. 설정 `limits.chunk_enabled`를 false로 두면 이 경로를 끄고 수동 검토로 보낸다.

### 8.4 MCP 서버에서 보이는 모습

- 분할 조각 하나가 `llm_complete` 한 번이다. 작업 유형은 `chunk_fix`이고, 조각 ID에 "몇 번째 중 몇 번째"가 들어간다.
- 서버는 조각의 순서, 변경 원장, 재조립을 모른다. 기록에 남은 작업 ID와 조각 ID로 추적만 한다.
- 분할 호출은 순서대로 가므로 한 함수가 동시 수를 한 자리만 쓴다.

### 8.5 규모의 가늠

`02_검토방안_v2.md` 4절의 추정을 그대로 쓴다. 모두 추정이며 서버의 실제 토큰 수로 보정해야 한다.

| 경우 | 추정 |
|---|---|
| 조각 하나에 담기는 코드 | 약 1,000~1,350줄 |
| 분할 순차의 실용 범위 | 약 5,000줄(조각 10개 이내 권장) |
| 그 이상 | 규칙 처리와 수동 검토 |

### 8.6 분할 순차를 0.2.0에 넣은 판단과 남은 위험

0.1.0에서는 구현하지 않았다. 결과를 확인할 수단(실제 sLLM, 컴파일 검사)이 없어서, 틀린 채 통과시키는 것보다 수동 검토로 보내는 쪽을 기본값으로 뒀다.

0.2.0에서 넣은 이유는 다음과 같다.
- 결과가 원본이 아니라 별도 파일과 diff로 나온다. 틀려도 원본은 그대로이고, 사람이 diff를 보고 고르면 된다.
- 넣어 두어야 실제 sLLM으로 돌려 보며 조각 크기와 넘겨주는 정보를 맞출 수 있다.

대신 다음 장치를 붙였다.
- 한 조각이라도 실패하면 그 구간의 수정을 모두 취소한다.
- 이 경로로 만든 수정은 모두 검토 대상으로 표시한다.
- 설정으로 끌 수 있다.

**확인한 것(리눅스, 모의 서버, 토큰 한도를 4,000으로 낮춘 합성 예제)**

| 항목 | 결과 |
|---|---|
| 분할 | 수정 지점 40곳인 구간이 4조각, 20곳인 구간이 3조각으로 나뉨 |
| 순서 | 구간마다 한 회차에 한 조각씩 진행. 두 구간은 같은 회차에 함께 진행 |
| 앞 조각의 변경 내용 | 2번째 조각부터 프롬프트에 포함됨 |
| 결과 | 40곳 모두 수정, 괄호 짝과 CRLF 유지 |
| 실패 처리 | 3조각 중 2번째가 실패한 구간은 앞서 수용한 수정 10건까지 모두 취소되고 20곳이 수동 검토로 감 |

**남은 위험**

| 위험 | 설명 | 대응 |
|---|---|---|
| 조각 사이의 뜻이 어긋남 | 괄호 짝과 형식은 검사하지만, 뒤 조각이 앞 조각의 이름과 타입을 따랐는지는 검사하지 못한다 | 컴파일 검사가 되는 PC에서 돌린다. 안 되면 diff를 사람이 전부 본다 |
| 실제 sLLM의 동작을 모름 | 모의 서버는 줄 단위 치환만 한다. 앞 조각의 변경 내용을 실제 모델이 어떻게 쓰는지 확인하지 못했다 | 패키지 하나로 파일럿. `logs/llm/`의 요청과 응답 확인 |
| 조각 크기가 추정에 의존 | 토큰 수가 추정치다 | 서버가 실제 토큰 수를 돌려주면 보정(4.2) |
| 함수 앞부분이 원본 기준 | 뒤 조각에 붙이는 함수 앞부분은 수정 전 원본이다. 앞부분이 이미 바뀌었다면 변경 내용 목록과 함께 읽어야 한다 | 실제 응답을 보고 형식을 조정 |
| 떨어진 지점은 별개로 감 | 30줄 넘게 떨어진 지점은 다른 조각으로 동시에 간다. 서로 의존하는 수정이면 어긋날 수 있다(6.1의 8번) | 규칙의 수정 범위 속성을 넣는다(10절의 8번) |

## 9. MCP 서버 기능 정의

구현은 범위 밖이다. py가 기대하는 기능만 적는다.

| 번호 | 기능 | 설명 | 접점 |
|---|---|---|---|
| M-01 | 호출자 식별과 권한 | 누가 요청했는지 확인하고 허용 여부를 정한다 | 전체 |
| M-02 | 작업 등록 | 작업 ID를 발급한다. py를 실행하지는 않는다 | `job_open` |
| M-03 | 작업 기록과 조회 | 진행과 종료를 기록하고 조회에 답한다 | `job_progress`, `job_close`, `get_status`, `list_jobs` |
| M-04 | 모델 연결 정보 관리 | sLLM 주소, 모델, 호출 파라미터를 가진다 | 내부 |
| M-05 | 한도와 동시 수 관리 | 호출자별 한도와 허용 동시 수를 정하고 알려 준다 | `llm_info` |
| M-06 | 공용 원칙 프롬프트 관리 | 내용과 판 번호를 관리한다. 출력 형식은 넣지 않는다 | 내부, `llm_info` |
| M-07 | 모델 호출 중계 | 실제 토큰 수로 한도 검사, 공용 원칙 부착, 대기, 전송 재시도, 응답 전달 | `llm_complete` |
| M-08 | 호출 기록 | 호출자, 작업 ID, 조각 ID, 토큰, 시간, 결과 코드 | 내부 |
| M-09 | 토큰 계산(선택) | 실제 토크나이저로 센다 | `count_tokens` |

서버가 하지 않는 일:
- py를 실행하거나 패키지 파일에 접근하지 않는다.
- py가 보낸 작업 프롬프트를 고치지 않는다.
- 응답을 해석하거나 수정의 옳고 그름을 판단하지 않는다.
- 조각 순서나 변경 원장 같은 중간 상태를 보관하지 않는다.

## 10. vupdate.py에서 바꿔야 할 것

상태는 0.4.0 기준이다. **0.5.0에서 1번(MCP 도구 호출), 2번(서버가 알려 준 한도와 동시 수), 6번(오류 코드 대응), 7번(작업 보고)을 구현했다(`09_인수인계_0.5.0.md` 2.4). 남은 것은 4, 8, 9번이다.** 이 목록은 서버가 MCP 도구 호출로만 접점을 열 때(08의 8.2)의 것이다. 서버가 OpenAI 호환 중계 주소를 열면(08의 8.1) 1번과 6번의 남은 부분은 할 일이 없고, 2, 5, 7번은 선택 사항이 된다(08의 4절).

| 번호 | 바꿀 내용 | 고칠 곳 | 상태 |
|---|---|---|---|
| 1 | sLLM 직접 호출을 서버의 `llm_complete` 호출로 바꾼다. 설정에서 sLLM 주소, 모델, 키를 없애고 MCP 서버 주소만 받는다 | M06 | 미착수. 주소를 환경변수로 받을 수 있게만 함 |
| 2 | 토큰 한도, 출력 상한, 허용 동시 수를 `llm_info`로 받는다. 동시 수는 py 설정값과 허용값 중 작은 쪽을 쓴다 | M06, S6 | 부분. 모델 목록으로 한도를 받고, 동시 수는 설정의 허용값 이하로 제한 |
| 3 | 토크나이저 주소를 직접 부르는 경로를 없앤다. 로컬 추정을 쓰고, 서버가 돌려준 실제 토큰 수로 추정 비율을 보정한다 | M06 | 완료(0.3.0) |
| 4 | 내장 프롬프트에서 공용 원칙을 떼어 내고 작업 규칙(출력 형식, 생략 표식 규칙)만 남긴다 | S6 | 미착수 |
| 5 | 호출에 작업 ID, 조각 ID, 작업 유형을 싣는다. 응답의 판 번호와 토큰 수를 기록하고 캐시 구분에 판 번호를 넣는다 | S6, 저장소 | 부분. 호출자와 실행 ID를 싣고 토큰 수를 기록 |
| 6 | 서버 오류 코드에 대응한다. `busy`는 기다렸다 재요청, `over_limit`은 조각 축소, `denied`는 중단 | S6 | 부분. HTTP 응답 기준으로 구현. `denied`는 중단이 아니라 수동 검토로 보냄 |
| 7 | 작업 등록, 진행, 종료를 서버에 알린다 | 실행기 | 미착수 |
| 8 | 규칙에 수정 범위(국소/함수/파일 간) 속성을 두고, 서로 의존하는 수정은 동시에 보내지 않는다 | M05, S6 | 미착수 |
| 9 | 분할 순차를 실제 sLLM으로 확인하고 조정한다(조각 크기, 앞 조각 변경 내용의 형식, 함수 앞부분) | S6 | 미착수(실제 sLLM 필요) |
| 10 | 자체 시험의 모의 서버를 새 접점에 맞춘다 | 명령줄 | 부분. 한도 초과, 과부하, 잘린 응답, 토큰 수 반환을 흉내 냄 |
| 11 | 실제 서버가 접점의 약속을 지키는지 점검하는 명령 | 부가명령 | 완료(0.4.0). `vupdate llmcheck` |

서버 경유로 바꿀 때 py에서 고칠 곳은 M06의 `llm_chat`(보내는 방식), `classify_llm_error`(오류 구분), `llm_probe`(한도 조회) 세 함수다. S6의 재계획과 보정은 그대로 쓴다.

바꾼 뒤에도 유지할 동작:
- 서버에 연결할 수 없으면 sLLM 대상 이슈만 수동 검토로 보내고, 규칙 수정과 검증과 보고서는 끝까지 만든다.
- 탐지만 하는 실행(`--dry-run`)과 환경 점검(`preflight`)은 서버 없이 동작한다.

## 12. 확인 필요

1. 서버가 호출자를 무엇으로 식별하는지(계정, 키, PC 이름).
2. 서버가 동시 수를 넘는 요청을 대기시키는지, 거절하는지. 호출자별 허용 동시 수를 얼마로 둘지.
3. sLLM 서빙 엔진이 동시 요청을 어떻게 처리하는지. 동시 수를 늘릴 때 요청당 한도가 줄어드는 방식인지.
4. 보고서 본문을 서버에 올릴지. 보고서에는 코드 조각이 들어 있다.
5. 서버가 실제 토큰 수를 돌려줄 수 있는지. 못 하면 py의 추정 보정이 불가능하다. 0.3.0은 이 경우에도 한도 초과 거절에는 대응하지만(줄여서 다시 계획), 거절이 더 자주 난다.
6. 한도 초과를 어떤 형식으로 거절하는지(상태 코드, 문구, 수치). py의 `classify_llm_error`가 알아볼 수 있어야 한다. 알아보지 못하면 수동 검토로 보낸다.
7. 서버가 덧붙이는 공통 프롬프트의 상한(예약량)을 얼마로 둘지.
8. 공용 원칙 프롬프트의 초안을 누가 쓰는지. 지금 py에 있는 문구 중 원칙에 해당하는 부분을 출발점으로 쓸 수 있다.

5~7번은 서버가 준비되면 `vupdate llmcheck`가 확인해 준다. 정해야 할 것만 추린 목록은 `08_MCP역할목록.md` 10절에 있다.
