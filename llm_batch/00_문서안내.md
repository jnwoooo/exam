## 실제 작업 순서

읽는 순서와 작업 순서는 다르다.

1. Windows PC에서 `vupdate.py`를 exe로 만든다(`04_개발구조.md` 2절).
2. 대상 PC에서 `vupdate selftest`로 동작을 확인한다.
3. `vupdate preflight --package <패키지>`로 환경을 점검한다(`03_확인사항.md` 4.8). 결과가 이상하면 4.1~4.7을 수동으로 확인한다.
4. `vupdate rules --from-vs <원본> --to-vs <대상>`으로 이 조합에서 켜지는 규칙을 확인한다.
5. `vupdate run ... --dry-run`으로 탐지 건수를 본다.
6. 서버에 중계 주소를 만든다(`08_MCP역할목록.md` 3절, 8절). 주소를 환경변수 `VUPDATE_LLM_ENDPOINT`에 넣고 `vupdate llmcheck`로 확인한다. 결과의 "설정에 반영할 것"을 `config/server.json`에 적는다.
7. 패키지 하나로 `vupdate run`을 돌려 sLLM 수정까지 확인한다. 보고서 6절에서 토큰 한도 대응이 실제 서버에서 동작했는지 본다.
8. 결과물을 빌드 환경으로 가져가 빌드한다(실행 폴더의 `out/build_guide.md`). 오류가 나면 로그를 가져와 `vupdate buildlog`로 분류하고 `07_오류대응.md` 3절대로 처리한다.
9. `06_충족점검.md` 7절의 순서로 기능을 넓힌다.

## 문서와 코드의 성격

- 01, 02는 설계 단계의 문서다. 대상 코드, 실제 sLLM 서버, 실제 개발 PC에서 검증한 내용이 아니다. 근거 수준은 `02_검토방안_v2.md` 0절에 등급으로 표시했다.
- 05는 책임 분담의 배경과 흐름이고, 08은 그것을 서버 쪽 할 일의 목록으로 줄인 것이다. 서버가 08의 8.1(OpenAI 호환 중계)로 만들면 py를 고치지 않는다. 05의 10절은 MCP 도구 호출 방식(08의 8.2)을 택할 때의 변경 목록이다.
- 07의 오류 코드별 대응표는 MS 문서와 널리 알려진 전환 사례를 정리한 것이다. 실제 패키지의 빌드에서 확인한 것이 아니다.
- 코드는 리눅스에서 합성 예제와 모의 서버로 실행을 확인했다. Windows, 실제 sLLM, 실제 패키지, 실제 빌드 로그에서는 확인하지 못했다. 확인한 것과 못 한 것은 `04_개발구조.md` 14절에 있다.
