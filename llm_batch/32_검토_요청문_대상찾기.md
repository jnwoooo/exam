# 검토: 요청문의 의도가 코드의 대상과 sLLM 호출로 이어지는 방식

| 항목 | 내용 |
|---|---|
| 읽는 순서 | 32 |
| 작성일 | 2026-11-26 |
| 대상 코드 | `vupdate.py` 0.10.6 (**이 문서로 코드를 바꾸지 않았다**) |
| 배경 | 의도가 종류마다 하나만 생기는지, 의도마다 따로 호출하는지, 코드를 모르는 sLLM이 낸 이름으로 대상을 찾는 것이 맞는지에 대한 확인 요청 |
| 확인 범위 | Linux, 합성 예제, 모의 sLLM(의미 분석의 답을 정해 두고 도구의 동작만 봄). 실제 gemma4가 어떤 이름과 낱말을 내는지는 확인하지 못했다 |

## 1. 결론

| 물음 | 답 |
|---|---|
| 의도는 종류마다 하나인가 | 아니다. 같은 종류가 여러 개 올 수 있다. 요청문 1건에 12개까지 받는다 |
| 의도마다 따로 코드를 뽑고 따로 호출하는가 | 대상 찾기는 의도마다 따로 한다. **호출은 의도가 아니라 코드 조각 단위다.** 한 조각에 여러 의도의 대상이 있으면 한 번의 호출에 함께 들어간다 |
| `names`에 든 이름만 찾는가 | 아니다. 길이 넷이다(3절). 다만 이름으로 찾는 길은 **글자가 정확히 같아야** 한다 |
| 이대로 대상을 잘 찾는가 | 요청문에 코드의 이름이 그대로 적혀 있으면 찾는다. 업무 용어로만 적으면 **구조 변환 요청은 진행되고, 일반 수정 요청은 대부분 대상을 찾지 못한다** |

우려하신 대로다. 모델은 코드를 보지 못하므로 이름을 맞힐 수 없다. 지금 설계는 모델이 이름을 지어내지 못하게 막는 쪽으로 돼 있고, 요청문에 코드의 이름이 없을 때 코드에서 후보를 찾아 주는 쪽이 약하다.

## 2. 의도의 수와 호출의 단위

- 의미 분석의 프롬프트는 "요청 하나에 여러 가지 일이 섞여 있으면 의도를 여러 개로 나눈다"고만 한다. 종류마다 하나라는 제한은 없다.
- 의도마다 번호가 붙는다(`ASK-1-1`, `ASK-1-2`, …). 대상 줄은 의도마다 따로 찾고 그 번호로 기록한다.
- sLLM 호출은 "작업" 단위다. 작업은 한 파일의 가까운 대상 줄들을 묶은 코드 조각이다(대상 8곳, 150줄까지). 의도가 달라도 같은 조각에 있으면 같은 작업에 들어간다.
- 한 작업의 물음에는 의도마다 지침이 한 번씩 들어가고, 대상 줄마다 어느 의도의 것인지 표시가 붙는다.

```
- [ASK-1-1] 사용자 요청: …: 대상은 ParseInsp 이다. 이 조각의 [수정 대상 줄]을 이 요청대로 고친다. …
- [ASK-1-7] 사용자 요청: …: 대상은 m_stInsp 이다. …
- 13번째 줄 [ASK-1-1]: n = p.ParseInsp(in); …
- 13번째 줄 [ASK-1-7]: n = p.ParseInsp(in); …
```

확인: 의도 12개(그 가운데 `modify` 10개)를 준 실행에서 12개가 모두 따로 처리됐고, 작업은 7개, 호출은 7회였다. 한 작업에 의도가 6개까지 함께 들어갔다.

작은 모델에는 한 물음에 지침이 여럿 섞이는 것이 부담일 수 있다. 실제 모델로 확인하지 못한 부분이다.

## 3. 대상을 찾는 네 가지 길

| 길 | 근거 | 찾는 것 | 맞추는 방식 |
|---|---|---|---|
| 이름(`names`) | 모델이 낸 이름 | 그 이름이 쓰인 줄 전부(함수, 변수, 필드, 타입, 매크로) | 글자가 정확히 같아야 한다(대소문자 포함). 코드에 없는 이름은 버린다 |
| 낱말(`words`) | 모델이 낸 영어 낱말(3글자 이상) | 그 낱말이 든 **함수 이름**이 쓰인 줄 | 이름을 낱말로 쪼개 비교한다(`ParseInsp` → parse, insp). 대소문자 무시. 후보가 8개를 넘으면 번호 목록을 모델에 보내 고르게 한다 |
| 구문(`construct`) | 모델이 고른 구문 | 이름이 없으면 그 구문의 머리 줄 전부(if, for 등) | - |
| 구조 분석 | 코드 자체 | 전문 버퍼의 위치 접근, 지역 병렬 배열 | `array_to_struct` 의도에서만. 이름과 무관하게 코드에서 탐지한다 |

이름을 돕는 장치가 하나 있다. 의미 분석을 부르기 전에 **요청문의 영문 낱말 가운데 코드에 실제로 있는 것**을 골라 모델에 알려 준다("ParseInsp (함수 호출 3곳)"). 모델에는 "요청 원문에 적힌 이름만 넣고 지어내지 않는다"고 지시한다.

## 4. 확인한 결과

요청문 "data의 배열 및 숫자 오프셋 기반 처리를 기존 tc구조체와 필드 접근 기반으로 개선한다. ParseInsp 도 본다", 코드에는 `Data`, `TC`, `ParseInsp`, `m_stInsp`, `szLot`, `MES_INSP`가 있다.

모델에 알려 준 이름은 `ParseInsp` 하나였다. `data`와 `tc`는 코드의 `Data`, `TC`와 대소문자가 달라 알려 주지 않았다.

| 모델의 답(모의) | 대상 | 결과 |
|---|---|---|
| 이름 `ParseInsp` | 3곳 | 찾음. 선언, 정의, 호출 줄 |
| 이름 `parseinsp` | 0 | 버림(대소문자가 다름) |
| 이름 `data`, `tc` | 0 | 버림(코드는 `Data`, `TC`) |
| 낱말 `parse` | 9곳 | 찾음. `ParseInsp`, `ParseTc`, `ParseVar`가 쓰인 줄 |
| 낱말 `insp` | 3곳 | 찾음 |
| 낱말 `검사` | 0 | 버림(영문만 받는다) |
| 이름 `m_stInsp`, `szLot`, `MES_INSP` | 8, 11, 2곳 | 찾음 |
| 낱말 `lot` | 0 | 못 찾음. `szLot`은 변수여서 낱말 검색의 대상이 아니다 |
| 구조 변환, 이름 `data`, `tc` | 34곳 | 이름은 버리고 구조 분석이 탐지한 전체로 진행 |
| 구문 for(이름 없음) | 6곳 | for 문의 머리 전부 |

## 5. 약한 곳

1. **대소문자와 표기.** `tc`와 `TC`, `data`와 `Data`를 다른 이름으로 본다. 요청문을 사람이 자연스럽게 쓰면 여기서 대부분 빠진다.
2. **낱말 검색이 함수 이름만 본다.** 변수, 필드, 타입, 매크로는 낱말로 찾지 못한다(`lot` → `szLot`).
3. **한글 용어를 코드에 잇는 길이 없다.** 주석이나 문자열에 그 말이 있어도 찾지 않는다.
4. **대상이 "이름이 쓰인 줄"이다.** "ParseInsp 함수 안의 처리를 고쳐 줘"라고 하면 대상은 그 함수의 본문이 아니라 선언, 정의의 머리, 호출 줄이다. 물음의 조각에 본문이 함께 들어가기는 하지만 고치라고 짚는 줄은 머리 줄이다.
5. **모델은 코드의 이름을 고를 기회가 없다.** 낱말 후보가 8개를 넘을 때만 코드에서 뽑은 목록을 보고 고른다. 그 밖에는 요청문의 낱말을 되풀이할 뿐이다.
6. 한 물음에 여러 의도의 지침이 섞인다(2절).

구조 변환 요청은 이름에 기대지 않으므로 1~5의 영향을 덜 받는다. 대신 대상을 좁히지 못해 패키지 전체에서 탐지된 것이 대상이 된다.

## 6. 개선 방향

핵심은 **모델이 이름을 내게 하지 말고, 도구가 코드에서 후보를 뽑아 모델이 고르게 하는 것**이다. 후보는 실제로 있는 이름이므로 틀린 이름이 나올 수 없다.

| 순서 | 내용 | 메우는 약점 |
|---|---|---|
| 1 | 이름이 정확히 맞지 않으면 대소문자를 무시하고, 접두를 뗀 꼴로도 찾는다(`tc` → `TC`, `szTc`, `m_nTc`). 하나로 정해지면 그대로 쓰고 여럿이면 3번으로 넘긴다 | 1 |
| 2 | 낱말 검색을 함수 이름에서 모든 이름으로 넓힌다. 후보에 종류와 쓰인 횟수, 쓰인 줄의 예를 붙인다 | 2 |
| 3 | 후보 확인을 기본 경로로 한다. 후보가 2개 이상이면 번호 목록을 모델에 보내 의도에 맞는 것을 고르게 한다(지금은 8개를 넘을 때만) | 5 |
| 4 | 한글 용어는 주석과 문자열에서 찾아, 그 주석이 붙은 함수와 근처의 이름을 후보로 올린다 | 3 |
| 5 | 고른 이름이 함수이고 요청이 "그 함수 안의 처리"이면 대상을 함수의 본문으로 한다 | 4 |
| 6 | 의도별로 호출을 나누는 설정을 둔다(호출은 늘어난다) | 6 |

1~3은 지금 있는 장치(낱말 쪼개기, 후보 확인 호출)를 넓히는 것이고 4~5는 새로 만드는 것이다. 호출은 의도마다 후보 확인 1회쯤 늘어난다.

먼저 볼 것은 실제 모델의 답이다. 0.10.2부터 `out/ask_trace.md`에 답 원문, 버린 이름, 의도별 대상 수가 남는다. 버린 이름이 많고 "대상을 찾지 못함"이 많으면 1~3이 바로 효과가 있다.
